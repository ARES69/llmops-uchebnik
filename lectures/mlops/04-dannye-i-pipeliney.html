RAG-система не начинается с модели. Она начинается с папки, из которой эта модель вообще что-то узнает. И в 9 случаях из 10, когда ассистент отвечает «откуда это?!», виноват не эмбеддинг и не промпт — виновата та стадия, которая на 12 шагов раньше: как ты собрал и почистил корпус. Эта лекция про пайплайн данных и про один артефакт, без которого никакая оценка качества невозможна, — золотой набор вопросов. Здесь ты закрываешь половину DevOps-навыка: расписание, инкрементальность, идемпотентность, метрики, откат. Ровно то, что ты уже делал с CI/CD-пайплайнами, только вместо сборки образа здесь собирается индекс знаний.

Откуда берутся данные корпоративного ассистента

Типовой набор источников для внутреннего ассистента выглядит так. Обрати внимание на последнюю колонку: она важнее остальных.

Источник Коннектор Объём Что ломает качество
Файловая система / SMB-шары os.walk + smbclient 1–50 тыс. файлов битая кодировка, PDF-сканы, дубли файл (1).docx
Confluence / SharePoint REST API + пагинация, delta-токен 5–100 тыс. страниц макросы, html-мусор, страницы-шаблоны без пользы
База знаний тикетов (Jira / ServiceNow) SQL SELECT или REST 50 тыс.+ тикетов комментарии-флуд, вложения, персональные данные
CMDB / ServiceNow SQL 1–5 тыс. записей устаревшие записи, несколько источников правды
Почтовые архивы IMAP / Graph API очень много личные данные, вложения, цепочки ответов
Репозитории (README, ADR, runbook) git clone / GitHub API сотни файлов история без контекста, шаблоны CI

Практическое правило: начинай с двух источников, а не с шести. Два источника, полная очистка и работающая выдача с цитатами полезнее, чем шесть источников, из которых три дают мусор. Расширение корпуса — это операционная работа, а не разовая задача, и каждое следующее подключение источника стоит дороже предыдущего.

⚠Важно

Порядок работы с любым новым источником: сначала 50–100 документов глазами. Открой их в исходном виде, потом после очистки. Если после очистки текст читается как мусор — этот источник нельзя подключать до тех пор, пока не написан нормализатор. Никакая модель эмбеддингов не спасёт систему, в которой половина векторов соответствует тексту «jjhkjh kjhg» из-за неверной кодировки.

Сбор: коннектор, состояние, инкрементальность

Сборщик должен быть инкрементальным и идемпотентным. Инкрементальность — тянуть только новое и изменённое. Идемпотентность — повторный запуск с тем же состоянием даёт тот же индекс.

Простейший и самый надёжный критерий «изменилось» — хеш содержимого. Не дата модификации: при переносе файлов между дисками mtime меняется у всего, а при копировании PDF внутрь себя он не меняется.

python
1# /opt/rag-pipeline/collectors/files.py
2import hashlib
3import json
4import os
5from pathlib import Path
6
7SKIP_DIRS = {".git", "node_modules", "__pycache__", "$RECYCLE.BIN", ".snapshot"}
8SKIP_EXT = {".exe", ".dll", ".iso", ".zip", ".7z", ".png", ".jpg", ".mp4"}
9
10
11def sha256(path: Path) -> str:
12    h = hashlib.sha256()
13    with open(path, "rb") as f:
14        for block in iter(lambda: f.read(1 << 20), b""):
15            h.update(block)
16    return h.hexdigest()
17
18
19def scan(root: str, state_path: str) -> list[dict]:
20    """Возвращает список документов: только новые и изменившиеся."""
21    state = {}
22    if os.path.exists(state_path):
23        with open(state_path, encoding="utf-8") as f:
24            state = json.load(f)
25
26    out, seen, deleted = [], {}, []
27    for dirpath, dirnames, filenames in os.walk(root):
28        dirnames[:] = [d for d in dirnames if d not in SKIP_DIRS]
29        for fn in filenames:
30            p = Path(dirpath) / fn
31            if p.suffix.lower() in SKIP_EXT or fn.startswith("~$"):
32                continue
33            rel = str(p.relative_to(root)).replace("\\", "/")
34            digest = sha256(p)
35            seen[rel] = digest
36            if state.get(rel) != digest:
37                out.append({"path": rel, "sha256": digest, "mtime": p.stat().st_mtime})
38
39    deleted = [k for k in state if k not in seen]
40    new_state = {**{k: v for k, v in state.items() if k in seen}, **seen}
41
42    os.makedirs(os.path.dirname(state_path), exist_ok=True)
43    tmp = state_path + ".tmp"
44    with open(tmp, "w", encoding="utf-8") as f:
45        json.dump(new_state, f, ensure_ascii=False)
46    os.replace(tmp, state_path)          # атомарно: состояние не побивается при падении
47
48    print(f"scanned={len(seen)} new_or_changed={len(out)} deleted={len(deleted)}")
49    return out

Обрати внимание на os.replace — запись состояния через временный файл. Если пайплайн упадёт посередине, состояние останется целым, иначе на следующем запуске ты «забудешь» половину файлов и индексируешь их повторно (или, что хуже, потеряешь).

Расписание — отдельное решение. Полный обход папки на 30 тысяч файлов занимает минуты и почти не требует ресурсов; на Confluence с rate limit полный обход может идти два часа и упрётся в лимиты. Практика: локальные источники — раз в сутки, недельная дельта; внешние API — раз в час по инкрементальному токену.

bash
1# /etc/cron.d/rag-collect
2# Детальная выгрузка ночью, когда API-провайдеры не режут лимиты
315 2 * * * rag-collector /var/lib/rag/state_files.json >> /var/log/rag/collect.log 2>&1
4# Проверка свежести корпуса каждые 15 минут — лёгкая, только чтение состояния
5*/15 * * * * rag-checker --max-age 2h >> /var/log/rag/freshness.log 2>&1

Очистка: что реально ломает текст

Очистка — это не «убрать теги». У каждого формата свой набор граблей.

Проблема Симптом в ответе Лечение
HTML-мусор из Confluence чанки из 30 слов, полные span style=... и div class=... selectolax или BeautifulSoup, отбросить script/style/nav
Склеенные слова (PDF) «системаапревышает» — эмбеддинг ломается словарь биграмм или pdftotext -layout + хелперы
Колонтитулы и номера страниц весь документ выглядит похожим на соседний вырезать повторяющиеся строки в начале/конце страниц
Дубли Договор (1).pdf один вопрос даёт три одинаковых цитаты дедуп по sha256 + по simhash близких текстов
Оглавление как отдельный текст модель цитирует «Введение … 1 … 2» отбросить блоки, где > 60% символов — цифры и точки
Разная кодировка (cp1251, UTF-16) векторы мусора charset-normalizer с fallback-цепочкой
python
1# /opt/rag-pipeline/clean.py
2import re
3import unicodedata
4from selectolax.parser import HTMLParser
5
6DROP_TAGS = ("script", "style", "nav", "footer", "aside")
7BOILERPLATE = re.compile(r"^\s*(страница|page)?\s*\d+\s*(из|/)\s*\d+\s*$", re.I)
8
9
10def clean_html(raw: str) -> str:
11    tree = HTMLParser(raw)
12    for sel in (" ".join(DROP_TAGS), "meta", "link"):
13        for node in tree.css(sel):
14            node.decompose()
15    # убрать скрытые блоки Confluence: они не видны человеку, но индексируются
16    for node in tree.css("[style*=display:none], .page-metadata"):
17        node.decompose()
18    text = tree.body.text(separator=" ", strip=True) if tree.body else ""
19    return normalize(text)
20
21
22def normalize(text: str) -> str:
23    text = unicodedata.normalize("NFKC", text)
24    text = text.replace("\u00a0", " ").replace("\u00ad", "")   # nbsp и мягкий перенос
25    text = re.sub(r"[ \t]+", " ", text)
26    text = re.sub(r"\n{3,}", "\n\n", text)
27    lines = [ln for ln in text.splitlines() if not BOILERPLATE.match(ln.strip())]
28    return "\n".join(lines).strip()
29
30
31def looks_like_garbage(text: str) -> bool:
32    """Страховка от мусорных чанков: слишком много «слов» без гласных."""
33    words = re.findall(r"[а-яa-z]{4,}", text.lower())
34    if len(words) < 12:
35        return True
36    no_vowel = sum(1 for w in words if not set(w) & set("аеёиоуыэюяaeiou"))
37    return no_vowel / len(words) > 0.5

Последняя функция — дешёвый и неожиданно полезный фильтр. Кусок текста, где больше половины длинных слов не содержат ни одной гласной, почти наверняка пришёл из битой кодировки или из выгрузки разметки.

✨Подсказка

Держи очистку в виде чистой функции bytes -> str без побочных эффектов и без доступа к сети. Тогда её можно прогнать по всему корпусу в офлайн-eval и сравнить: «до очистки recall@5 = 0.61, после = 0.84». Это дешёвый и очень убедительный аргумент в разговоре с руководством о том, что два дня на очистку окупились.

Золотой набор: артефакт, ради которого всё затевается

Золотой набор (golden set, eval set) — это 50–150 вопросов с эталонными ответами и ссылками на источники, на которых дальше меряется вся система. Не тесты, не примеры в документации — измеримый артефакт, который лежит в репозитории рядом с кодом и прогоняется в CI.

Формат: YAML, потому что он читаем и diff-ится человеком; JSON — потому что его ест любая Evaluation-обвязка (Ragas, DeepEval, promptfoo). Держи оба, генерируй одно из другого.

yaml
1# evals/golden_set.yaml — первые два из 120 вопросов
2version: 3
3corpus_snapshot: 2026-09-28T03:00:00Z
4embedding_model: intfloat/multilingual-e5-base
5cases:
6  - id: q001
7    question: Как восстановить пароль от учётной записи в AD?
8    reference_answer: >-
9      Сброс выполняет администратор домена через оснастку «Пользователи и компьютеры»
10      или командой net user <имя> <новый_пароль> на контроллере домена.
11      Пользователь с правами «Сброс пароля» может сделать это самостоятельно.
12    sources:                       # обязательное поле: id документа и чанк
13      - doc_id: "ad/reset-password.md#3"
14        chunk_id: "ad/reset-password.md::chunk_0042"
15    expected_refusal: false
16    tags: [ad, безопасность, частый-вопрос]
17    weight: 3                       # частые вопросы важнее в среднем по корпусу
18
19  - id: q002
20    question: Какой таймаут у клиента к Order Service?
21    reference_answer: ""
22    expected_refusal: true          # ответа в базе знаний нет — ждём отказ
23    sources: []
24    tags: [инцидент, устаревшее]
25    weight: 1                       # такие случаи ловят галлюцинации

Четыре поля здесь обязательны, остальные — по вкусу:

  • sources — список doc_id и chunk_id. Именно по нему считается recall ретривера. Без этого поля у тебя нет объективной метрики поиска, только субъективное «ответ похож на правду».
  • expected_refusal — самый недооценённый элемент. 15–20% вопросов должны быть такими, на которые в базе знаний ответа нет. Без них ты измеряешь только способность галлюцинировать, а не способность отказывать.
  • weight — реальные вопросы приходят неравномерно. Среднее по равным весам завышает оценку: ты можешь «вытянуть» результат на редких вопросах, которые никто не спрашивает.
  • corpus_snapshot — привязка к версии корпуса. Без неё через месяц вопросы перестанут соответствовать данным и оценка станет бессмысленной.

Как собирать, если разметки нет: возьми 200 вопросов из логов реального чата или из тикетов первого уровня, отброси те, где нет ответа в базе знаний, выдели 100–150, для каждого отметь 1–2 источника из фактического документа и попроси двух инженеров согласовать формулировку эталонного ответа. Расхождение — не баг, а сигнал, что вопрос неоднозначен: переформулируй его.

⚡Осторожно

Золотой набор, который собрали «на глаз, чтобы было что показать», хуже отсутствия набора. Он даёт ложную уверенность: цифра 0.82 ничего не значит, если 30 из 150 вопросов сформулированы так, что ответ заведомо содержится в первом же найденном документе. Трать время на источники, а не на красивые формулировки.

Версионирование данных и откат индекса

Индекс — это производный артефакт. Значит, к нему применимы все правила из CI/CD: воспроизводимость, версия, откат.

Полноценный DVC нужен, когда корпус — терабайты и его правят десятки людей. Для 90% корпоративных ассистентов хватает манифеста: JSON со списком документов, их хешами, параметрами пайплайна и результатом индексации.

python
1# /opt/rag-pipeline/manifest.py
2import hashlib
3import json
4import subprocess
5from datetime import datetime, timezone
6
7def git_rev() -> str:
8    return subprocess.run(["git", "rev-parse", "--short", "HEAD"],
9                          capture_output=True, text=True).stdout.strip() or "nogit"
10
11
12def build_manifest(docs: list[dict], params: dict, run_id: str) -> dict:
13    """docs: [{doc_id, sha256, chunks, embed_model, index_collection}]"""
14    payload = {
15        "run_id": run_id,
16        "created_at": datetime.now(timezone.utc).isoformat(),
17        "git_rev": git_rev(),
18        "params": params,          # chunk_size, overlap, embedding_model, qdrant_hnsw_m
19        "counts": {
20            "documents": len(docs),
21            "chunks": sum(d["chunks"] for d in docs),
22            "skipped_garbage": params.get("skipped_garbage", 0),
23        },
24        "corpus_hash": hashlib.sha256(
25            "".join(sorted(d["sha256"] for d in docs)).encode()
26        ).hexdigest()[:16],
27        "docs": docs,
28    }
29    with open(f"manifests/{run_id}.json", "w", encoding="utf-8") as f:
30        json.dump(payload, f, ensure_ascii=False, indent=2)
31    return payload

corpus_hash — ключевое поле. Он меняется при любом изменении корпуса и позволяет одной строкой ответить на вопрос «а что именно было в индексе в момент инцидента 12 октября в 09:14».

Откат индекса — это не «переиндексировать заново», а переключение алиаса. Ветка prod_index в Qdrant всегда указывает на текущую коллекцию; новая индексация идёт в отдельную prod_index_20261012_0315, и переключение — одна операция.

bash
1# Переключение алиаса после успешной индексации и зелёного eval
2curl -X POST http://qdrant:6333/collections/aliases \
3  -H 'Content-Type: application/json' \
4  -d '{"actions":[
5        {"delete_alias":{"collection_name":"prod_index","alias_name":"live"}},
6        {"create_alias":{"collection_name":"prod_index_20261012_0315","alias_name":"live"}}
7      ]}'
8# Откат — тот же вызов с предыдущей коллекцией. Секунды, а не часы переиндексации.
!Внимание

Удаление старой коллекции сразу после переключения алиаса — необратимая операция. Держи минимум 3–5 предыдущих снапшотов. «Нам нужно место» — плохой аргумент: снапшот корпуса на 50k чанков занимает сотни мегабайт, а не гигабайты.

Оркестрация: что выбрать

Инструмент Когда брать Порог перехода Минус
Скрипт + cron + Docker 1–3 источника, одно расписание, до ~100k чанков базовый вариант по умолчанию нет retry-зависимостей, нет UI
Prefect / Dagster появились зависимости: сначала очистка, потом эмбеддинги, потом eval; нужны retries и алерты 2–3 источника, разные расписания ещё один сервис в контуре
Airflow уже есть в компании, нужны общие DAG'и с другими пайплайнами 0 — если Airflow уже стоит тяжёлый, отдельный UI, от operational debt
dbt источники — таблицы, а не файлы: Snowflake, ClickHouse, Postgres когда корпус лежит в БД не умеет ни PDF, ни Confluence
Prefect + dbt комбинация: dbt готовит таблицу чанков, Prefect оркестрирует всё остальное поздняя стадия две системы, две версии
✨Подсказка

Правило выбора, которое экономит месяцы: не поднимай Airflow ради одной ночной задачи. Скрипт в 200 строк, который запускается по cron, в Docker-контейнере, с ненулевым кодом возврата при ошибке, — это уже пайплайн. Оркестратор нужен, когда ты начал рисовать схему с ветвлениями и ретраями, а не раньше. Переезд с cron-скрипта на Prefect занимает полдня — но он возможен, только если скрипт был параметризован CLI-флагами с самого начала.

python
1# Хороший пайплайн начинается с этой формы: вызывается из cron, из CI и руками
2import argparse, json, os, sys, time
3
4def main() -> int:
5    ap = argparse.ArgumentParser()
6    ap.add_argument("--since", default=None, help="инкрементально с даты ISO")
7    ap.add_argument("--full", action="store_true", help="полная переиндексация")
8    ap.add_argument("--run-id", default=None)
9    ap.add_argument("--dry-run", action="store_true")
10    args = ap.parse_args()
11
12    run_id = args.run_id or time.strftime("%Y%m%d_%H%M")
13    t0 = time.time()
14    try:
15        docs = collect(args.since, full=args.full)
16        if args.dry_run:
17            print(json.dumps({"would_index": len(docs)})); return 0
18        chunks = transform(docs)
19        vecs = embed(chunks)
20        upsert(vecs, collection=f"prod_index_{run_id}")
21        eval_golden_set(f"prod_index_{run_id}")     # зелёное? -> переключаем алиас
22        publish_alias(f"prod_index_{run_id}")
23        manifest(docs, run_id=run_id)
24        return 0
25    except Exception:
26        log.exception("pipeline failed run_id=%s", run_id)
27        return 1        # cron увидит не-zero и пришлёт алерт
28
29if __name__ == "__main__":
30    sys.exit(main())

Обрати внимание на строчку eval_golden_set(...) внутри пайплайна. Индексация без проверки качества на золотом наборе — это публикация в прод без тестов, только дороже. Подробно об этом — в оценке RAG.

Инкрементальная переиндексация против полной

Ситуация Что делать Время на 50k чанков
Изменилось 5 файлов из 8000 удалить их чанки по doc_id, добавить новые минуты
Изменился шаблон чанкинга (размер, overlap) полная переиндексация часы
Сменилась модель эмбеддингов полная переиндексация, векторы несопоставимы часы
Сменилась размерность вектора полная, плюс новая коллекция часы
Изменились только метаданные (дата, автор, теги) обновить payload без переэмбеддинга секунды
Плановый полный прогон раз в неделю полная, в отдельную коллекцию, с алиасом ночь
⚠Важно

Правило, которое экономит самые дорогие часы: новая модель эмбеддингов или новый размер чанка = новая коллекция, а не обновление на месте. Старые и новые векторы в одной коллекции не сравнимы: они лежат в разных системах координат, и поиск между ними возвращает мусор. Параллельно держи обе коллекции, сравнивай на золотом наборе, потом переключай алиас.

Мониторинг пайплайна данных

Данные-пайплайн ломается тихо: он не падает, он просто перестаёт обновляться, а пользователи получают вчерашние ответы и не жалуются. Поэтому метрики здесь другие, чем в HTTP-сервисе, и они отвечают на вопрос «жив ли конвейер», а не «были ли ошибки».

Метрика Тип Что означает Порог тревоги
rag_corpus_age_seconds gauge сколько секунд прошло с последнего успешного снапшота > 26 ч для суточного расписания
rag_docs_indexed_total counter документов проиндексировано (сравнивается с ожидаемым) расхождение > 20%
rag_chunks_total gauge чанков в live-коллекции падение более чем на 5% к вчера
rag_index_error_ratio gauge доля документов, не прошедших очистку/эмбеддинг > 2%
rag_pipeline_duration_seconds histogram время полного прогона рост в 2+ раза к медиане
rag_garbage_skipped_total counter сколько документов отброшено фильтром мусора резкий рост = сломался кодировщик
rag_embed_tokens_total counter потраченные токены эмбеддинга квантование бюджета
python
1# /opt/rag-pipeline/metrics.py — экспорт для node_exporter textfile collector
2import os, time, json
3
4SNAP = "/var/lib/rag/last_success.json"     # пишет пайплайн после успеха
5
6def export() -> None:
7    age = int(time.time() - os.path.getmtime(SNAP)) if os.path.exists(SNAP) else 10**9
8    st = json.load(open("/var/lib/rag/state_files.json")) if os.path.exists(SNAP) else {}
9    lines = [
10        "# HELP rag_corpus_age_seconds Сколько секунд с последнего успешного снапшота корпуса",
11        "# TYPE rag_corpus_age_seconds gauge",
12        f"rag_corpus_age_seconds {age}",
13        "# HELP rag_docs_known_total Документов в состоянии коллектора",
14        "# TYPE rag_docs_known_total gauge",
15        f"rag_docs_known_total {len(st)}",
16    ]
17    path = "/var/lib/node_exporter/textfile_collector/rag.prom"
18    tmp = path + ".tmp"
19    open(tmp, "w").write("\n".join(lines) + "\n")
20    os.replace(tmp, path)

Дальше это подхватывает твой существующий Prometheus, а правило тревоги пишется ровно так же, как для любого сервиса — по симптому, а не по причине.

yaml
1# Фрагмент alert-правила Prometheus
2groups:
3  - name: rag-data
4    rules:
5      - alert: RagCorpusStale
6        expr: rag_corpus_age_seconds > 26 * 3600
7        for: 30m
8        labels: {severity: warning}
9        annotations:
10          summary: "Корпус RAG не обновлялся более 26 часов"
11          description: "Ответы ассистента основаны на устаревших данных. Проверь cron, лог пайплайна и статус коннекторов."

Проектировать эти метрики нужно вместе с остальными — по той же схеме SLI/SLO, что и в наблюдаемости. SLI качества данных, в отличие от SLI доступности, меряется офлайн на золотом наборе, а не в реальном времени; об этом — в оценке RAG.

Права доступа и персональные данные

Это самый недооценённый раздел, и он чаще всего становится инцидентом, а не задачей.

Главная опасность: RAG разрушает модель доступа, которой оперировали Confluence и Jira. В исходной системе пользователь видел ровно то, к чему имел права. В индексе лежит всё, что собрал коннектор, а фильтрация по правам обычно не реализована. В результате ответ ассистента цитирует документ из закрытой папки — и юридически это утечка, даже если пользователь и так имел бы доступ завтра.

python
1# Правило, которое проверяется в CI, а не «на память»
2REQUIRED_META = {"acl_groups", "source_system", "doc_id", "retention_class"}
3
4def validate_acl(meta: dict) -> None:
5    missing = REQUIRED_META - set(meta)
6    if missing:
7        raise ValueError(f"документ без ACL-метаданных: {meta.get('doc_id')} — {missing}")

Практические меры:

  • Каждый документ наследует ACL источника и хранит его в метаданных индекса. Поиск всегда идёт с фильтром по группам пользователя. Подробнее про мультиарендность — в RAG-пайплайне.
  • Персональные данные вычищаются на входе, а не на выходе: маскирование ФИО, телефонов, e-mail, паспортов, номеров счёта в тикетах и почте. Если в корпусе лежат данные о здоровье или зарплатах, у документа должен быть retention_class, и он не должен попадать в общий индекс.
  • Индекс — тоже база данных, со своим бэкапом, своими правами и своим журналом доступа. Кто и когда читал какие чанки — вопрос, на который придётся ответить.
!Внимание

Прежде чем подключать к индексации почту или тикеты с персональными данными, получите письменное разрешение. «Мы же не выгружаем наружу» не является защитой: индексирующий коннектор с правами сервисной учётной записи почти всегда читает больше, чем имеет право читать конкретный сотрудник.

Где это ломается

  1. Полная переиндексация каждую ночь без причины. 50k чанков, 6 часов на эмбеддинги, и при этом в 99% суток меняются 30 файлов. Инкрементальность экономит деньги и снижает окно, в которое индекс в несогласованном состоянии.
  2. Дата модификации как критерий «изменилось». rsync, копирование в NAS и восстановление из бэкапа сбивают mtime у всего. После такого индексация либо не срабатывает вообще, либо переиндексирует весь корпус.
  3. Состояние коллектора пишется неатомарно. Пайплайн упал на середине записи — на следующем запуске часть файлов считается «неиндексированной», и индекс расползается. Лечится os.replace на временный файл.
  4. Golden set без поля sources. Нельзя посчитать recall ретривера, и вся оценка превращается в «наши юристы посмотрели и сказали, что примерно правильно».
  5. Golden set без expected_refusal. Половина метрик завышена, галлюцинации не видны, а именно они — то, из-за чего систему закрывают.
  6. Нет удаления из индекса. Документ убрали из Confluence, а его чанки остались в Qdrant и продолжают цитироваться. Дедупликация по doc_id при выгрузке обязана быть двусторонней: не только «новые», но и «удалённые».
  7. Подключили шесть источников за неделю. Половина — мусор, качество упало, откатываться некуда: непонятно, какой источник виноват. Добавляйте по одному, с замером recall на золотом наборе после каждого.
  8. Никаких метрик свежести. Пайплайн молча перестал ходить три недели назад, и об этом узнали от пользователя, который спросил про новый приказ.
  9. Манифест пишется, но не хранится. Нет истории снапшотов — нет возможности сказать «ответ был таким, потому что в тот день в корпусе была версия 2.1 документа, а не 2.3».
