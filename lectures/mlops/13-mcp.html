MCP: протокол контекста

Как один стандартный интерфейс соединяет агента с любой внутренней системой вместо N самописных интеграций, и почему сервер MCP — это новая точка входа, которую надо ограничивать

Агенты из предыдущей лекции умеют вызывать функции, но функции ты пишешь руками — в своём коде, на своём HTTP-клиенте, под свой фреймворк. Добавь пять внутренних систем — получишь пять одинаковых обвязок. MCP (Model Context Protocol) создан ровно для этого: один стандартный интерфейс, через который агент подключается к любой системе, а сама система подключается к любому клиенту. Разбираемся, как устроен протокол, как написать сервер и — обязательно — почему сервер MCP надо воспринимать как новую сетевую точку входа.

Проблема, которую решает MCP

Каждая интеграция — это код: HTTP-клиент, схема аргументов, обработка ошибок, пагинация, авторизация. Пишется он дважды, если у тебя два клиента: агенты в LangChain и ассистент в редакторе IDE. При десяти внутренних системах это двадцать реализаций, которые разъезжаются по обработке ошибок и по формату ответа.

Аналогия, которая обычно срабатывает: MCP — это USB для ИИ. Клавиатура, диск и принтер — разные устройства с разными протоколами внутри, но подключаются к одной и той же розетке. Именно это и делает протокол: не универсальный API ко всему, а единая форма описания «что я умею» и «вызови меня с такими аргументами». Нужен был именно этот слой совместимости, а не очередная попытка сделать серебряную пулю.

Что конкретно даёт стандарт:

  • Написал MCP-сервер для своей БД — он работает с Claude Desktop, с агентом на LangGraph, с редактором и с любым другим MCP-клиентом.
  • Список инструментов приезжает к клиенту автоматически: новый инструмент появляется без изменения кода агента и без релиза клиента.
  • Схемы аргументов приезжают машинночитаемыми — это тот же JSON Schema, который уже используется в tool calling, только доставлен стандартным способом.
  • Клиент изолирует сервер от себя: сервер не видит системный промпт, историю диалога и ключ модели.

Архитектура: хост, клиент, серверы

Три сущности, и их важно не путать.

Сущность Что это Пример
Хост Приложение, в котором живёт пользователь и агент: оркестрирует цикл, хранит историю, держит ключи и политики Claude Desktop, Cursor, Open WebUI, твой сервис с LangGraph
Клиент По одному на каждый подключённый сервер, внутри процесса хоста. Отвечает за JSON-RPC, жизненный цикл, авторизацию Невидим для тебя, это внутренняя механика хоста
Сервер Процесс, предоставляющий доступ к системе: инструменты, ресурсы, промпты Твой cmdb_server.py, готовый сервер файловой системы

Сервер не знает, какая модель работает и кто пользователь. Клиент не знает, что внутри системы. Связь — только через протокол, и это главное архитектурное свойство: интеграция с внутренней системой пишется один раз.

Сервер предоставляет три вида «примитивов»:

Примитив Кто инициирует Что это Пример
Tools Модель (агент) Действие с побочным эффектом или запросом данных get_cmdb(hostname), restart_vm(name)
Resources Приложение (пользователь или хост) Данные, которые читаются как контекст, по URI docs://runbooks/failover.md, cmdb://app01
Prompts Пользователь Готовый шаблон промпта с параметрами incident_report(service, severity)

Плюс два механизма, которые сервер может вызвать у хоста: sampling — попросить хост сгенерировать ответ моделью (сервер не держит ключ), и elicitation — запросить дополнительные данные у пользователя. На практике их используют единицы, но именно они объясняют, почему протокол живёт в обе стороны.

iЗаметка

Resources и Tools часто путают. Разница в том, кто решает, когда их использовать: инструмент выбирает модель, ресурс подставляет приложение или пользователь. Инструмент может менять состояние, ресурс — нет.

Транспорт: stdio и HTTP

Свойство stdio Streamable HTTP
Где живёт сервер Локальный процесс, запущенный хостом Отдельный сервис, доступный по сети
Как говорит JSON-RPC построчно через stdin/stdout Один HTTP-эндпоинт: POST для сообщений, GET для потока (SSE)
Типичное применение Локальные утилиты: файлы, репозиторий, локальная БД Серверные интеграции: внутренние API, CMDB, корпоративный поиск
Авторизация Права пользователя, от имени которого запущен хост Токены, OAuth, mTLS на вашей стороне
Изоляция Процесс, но с правами пользователя Отдельная сессия, сетевые политики, честный ACL

Практическое правило: stdio — для всего, что живёт на машине пользователя; HTTP — для всего, что живёт в твоём контуре. Смешивать их специально не нужно. Старый транспорт HTTP+SSE (два отдельных эндпоинта) объявлен устаревшим в редакции протокола 2025-03-26; если встречаешь сервер на нём — это версия постарее.

На stdio есть ловушка, о которой стоит знать заранее: сервер запускается как дочерний процесс хоста и наследует его права. Сервер «чтение файлов», подключённый к Claude Desktop, запущенный из твоей учётной записи, получает доступ ко всему, что доступно тебе, — включая .env, ключи и домашнюю папку. Ограничение прав здесь не настройка, а дизайн: лекция 14.

Жизненный цикл сессии

Всё общение — JSON-RPC 2.0. Последовательность одна и та же для любого сервера.

json
1// 1. Клиент открывает сессию: объявляет версию протокола и свои возможности
2{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
3  "protocolVersion":"2025-06-18",
4  "capabilities":{"roots":{"listChanged":true},"sampling":{}},
5  "clientInfo":{"name":"internal-assistant","version":"1.4.0"}}}
6
7// 2. Сервер отвечает: его версия, его примитивы и подсказка для модели
8{"jsonrpc":"2.0","id":1,"result":{
9  "protocolVersion":"2025-06-18",
10  "capabilities":{"tools":{"listChanged":true},"resources":{},"prompts":{}},
11  "serverInfo":{"name":"internal-cmdb","version":"0.7.2"},
12  "instructions":"Сервер только читает CMDB. Для изменений есть отдельный портал."}}
13
14// 3. Клиент подтверждает и спрашивает, что умеет сервер
15{"jsonrpc":"2.0","method":"notifications/initialized"}
16{"jsonrpc":"2.0","id":2,"method":"tools/list"}
17
18// 4. Вызов инструмента: имя + аргументы по объявленной схеме
19{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{
20  "name":"get_cmdb","arguments":{"hostname":"app01.corp"}}}
21
22// 5. Результат: массив блоков контента. isError=true — не исключение,
23//    а нормальный ответ с текстом ошибки, который модель может переработать
24{"jsonrpc":"2.0","id":3,"result":{"content":[
25  {"type":"text","text":"{\"owner\":\"infra\",\"env\":\"prod\",\"os\":\"Ubuntu 24.04\"}"},
26  {"type":"image","data":"<base64 png>","mimeType":"image/png"}],
27  "isError":false}}

Обрати внимание на две вещи. Первое: isError — не флаг сбоя протокола, а содержимое ответа; агент продолжит разговор. Второе: контент не обязан быть строкой — это массив блоков, в том числе картинок. График с узлом или скриншот интерфейса отдаётся так же, как текст, и модель его разбирает.

MCP-сервер на Python

Официальный SDK (mcp) прячет JSON-RPC за декораторами. Сервер ниже поднимается за час и покрывает три типовых инструмента внутреннего ассистента.

bash
1python -m venv .venv
2.venv/Scripts/Activate.ps1        # Windows; на Linux — source .venv/bin/activate
3pip install mcp
python
1# cmdb_server.py — MCP-сервер внутреннего ассистента
2import json, os, sqlite3
3from pathlib import Path
4from mcp.server.fastmcp import FastMCP
5
6mcp = FastMCP("internal-assistant", instructions="Только чтение. Изменений здесь нет.")
7
8RUNBOOKS = Path(os.getenv("RUNBOOKS_DIR", "./runbooks")).resolve()
9ALLOWED = {p.resolve() for p in RUNBOOKS.glob("*.md")}
10KB_PATH = os.getenv("KB_PATH", "kb.sqlite")
11CMDB_PATH = os.getenv("CMDB_PATH", "cmdb.json")
12
13
14@mcp.tool()
15def read_runbook(name: str) -> str:
16    """Читает регламент из папки runbooks по имени файла. Только чтение."""
17    path = (RUNBOOKS / name).resolve()
18    if path not in ALLOWED:              # защита от выхода за пределы папки
19        return f"Регламент {name} не найден. Доступны: " + ", ".join(sorted(p.name for p in ALLOWED))
20    return path.read_text(encoding="utf-8")[:8000]
21
22
23@mcp.tool()
24def search_kb(query: str, top: int = 5) -> list[dict]:
25    """Ищет по внутренней базе знаний и возвращает заголовки и выдержки."""
26    con = sqlite3.connect(KB_PATH)
27    try:
28        rows = con.execute(
29            "SELECT id, title, substr(body, 1, 400) FROM docs "
30            "WHERE body LIKE ? ORDER BY id LIMIT ?",
31            (f"%{query}%", top),          # только плейсхолдеры, никакой конкатенации
32        ).fetchall()
33    finally:
34        con.close()
35    return [{"id": r[0], "title": r[1], "excerpt": r[2]} for r in rows]
36
37
38@mcp.tool()
39def get_cmdb(hostname: str) -> dict:
40    """Карточка узла из CMDB: владелец, среда, ОС, стенд."""
41    with open(CMDB_PATH, encoding="utf-8") as fh:
42        card = json.load(fh).get(hostname.lower())
43    return card or {"error": f"узел {hostname} не найден"}
44
45
46@mcp.resource("docs://runbooks/list")
47def runbook_index() -> str:
48    """Список доступных регламентов — агент читает это как контекст."""
49    return "\n".join(sorted(p.name for p in ALLOWED))
50
51
52@mcp.prompt()
53def incident_report(service: str, severity: str = "P2") -> str:
54    """Шаблон отчёта об инциденте для службы эксплуатации."""
55    return (
56        f"Составь отчёт об инциденте по сервису {service}, severity {severity}. "
57        "Разделы: влияние, хронология, причина, действия, предотвращение."
58    )
59
60
61if __name__ == "__main__":
62    mcp.run(transport="stdio")            # удалённый вариант: mcp.run("streamable-http")

Запуск для проверки от руки — сервер читает JSON-RPC из stdin, поэтому его можно запустить как обычную программу:

bash
1pip install mcp
2export KB_PATH=kb.sqlite CMDB_PATH=cmdb.json RUNBOOKS_DIR=./runbooks
3python cmdb_server.py

Проверка клиентом и подключение

Клиентский SDK показывает, что сервер действительно рабочий — до того, как ты потратишь час на настройку IDE:

python
1# probe.py — проверить сервер: хендшейк, список инструментов, тестовый вызов
2import asyncio, json
3from mcp import ClientSession, StdioServerParameters
4from mcp.client.stdio import stdio_client
5
6
7async def main():
8    params = StdioServerParameters(command="python", args=["cmdb_server.py"],
9                                   env={"KB_PATH": "kb.sqlite", "CMDB_PATH": "cmdb.json"})
10    async with stdio_client(params) as (read, write):
11        async with ClientSession(read, write) as session:
12            info = await session.initialize()
13            print("сервер:", info.serverInfo.name, info.serverInfo.version)
14            tools = await session.list_tools()
15            for t in tools.tools:
16                print(f"- {t.name}: {t.description}")
17            res = await session.call_tool("get_cmdb", {"hostname": "app01.corp"})
18            print(json.dumps(res.content[0].text, ensure_ascii=False))
19
20asyncio.run(main())

Подключение к клиенту — файл конфигурации, где указываются команда, аргументы и переменные окружения:

json
1// %APPDATA%\Claude\claude_desktop_config.json  (Windows)
2// ~/Library/Application Support/Claude/claude_desktop_config.json  (macOS)
3{
4  "mcpServers": {
5    "internal-assistant": {
6      "command": "C:\\LLMops\\.venv\\Scripts\\python.exe",
7      "args": ["C:\\LLMops\\cmdb_server.py"],
8      "env": {
9        "KB_PATH": "C:\\LLMops\\kb.sqlite",
10        "CMDB_PATH": "C:\\LLMops\\cmdb.json",
11        "RUNBOOKS_DIR": "C:\\LLMops\\runbooks",
12        "CMDB_TOKEN": "${CMDB_TOKEN}"
13      }
14    }
15  }
16}

Тот же формат конфигурации используют Cursor (.cursor/mcp.json), VS Code (.vscode/mcp.json) и Zed. Клиенты с поддержкой удалённых серверов через HTTP добавляют блок с type: "http" и url — для них ещё нужна авторизация, а это отдельная история.

!Внимание

В env этого файла лежат учётные данные в открытом виде, а сам файл читает локальный пользователь. Токены от CMDB и базы знаний хранятся в менеджере секретов, в конфиг попадает только ссылка. Если токен всё-таки оказался в claude_desktop_config.json — считай его скомпрометированным и ротируй.

Если у тебя не MCP-клиент, а обычный OpenAI-совместимый, используют мост: процесс принимает /v1/chat/completions, сам ходит в MCP-серверы и отдаёт модели список инструментов в привычном формате tools. Так работает mcp-proxy. Это рабочий приём для стыковки агента на голом HTTP-клиенте из предыдущей лекции с миром MCP.

Как выбирать: ручной код, LangChain или MCP

Критерий Инструменты в своём коде LangChain / LlamaIndex MCP
Гибкость Максимальная Высокая Ограничена примитивами протокола
Переиспользование между агентами Каждому агенту своя копия Общий код в проекте Один сервер — все клиенты
Время на первую интеграцию 30–60 минут 15–30 минут 40–90 минут + описания примитивов
Контроль прав и аудита Полный, всё в своём коде Полный, но размазан по обёрткам Отдельный процесс: свои права, свой лог, своя сетка
Замена клиента/фреймворка Переписываешь интеграцию Переписываешь или мигрируешь Ничего: сервер остаётся
Вклад в кодовую базу Строки в каждом агенте Строки в проекте Отдельный маленький сервис + конфиги
Внешние потребители Нет Нет Любой MCP-клиент, включая чужие

Практическое правило: если интеграция нужна одному агенту — пиши в коде; если двум и больше — оформляй MCP-сервер. Мост, который позволяет конвертировать существующие функции в MCP-сервер, стоит рассмотреть раньше, чем ты напишешь третью копию одного и того же HTTP-клиента.

Что есть из коробки

Эталонные серверы от Anthropic задали тон, и на их основе появились десятки готовых реализаций. Типовой набор для внутреннего ассистента:

Сервер Что даёт О чём думать перед подключением
Файловая система Чтение/запись файлов в заданной папке Ограничивай корень, иначе получишь доступ ко всей машине
Git Статус, диффы, коммиты, история Пишет в репозиторий — требует правки на запись
PostgreSQL / SQLite Выполнение запросов Только read-only роль, никаких произвольных DROP
Браузер (Playwright/Puppeteer) Навигация, скриншоты, извлечение Выход в интернет: агент читает враждебные страницы
Slack Поиск по сообщениям, отправка Отправка — действие с последствиями, нужен человек
Поиск и память Семантический поиск, долговременная память Стандартный векторный стор — удобно, но следи за составом данных
⚡Осторожно

Референсный репозиторий с примерами серверов пережил реорганизацию: часть серверов помечена как устаревшая и вынесена в архив, актуальные сборки живут в сообществе и в реестре MCP. Перед боевым использованием смотри дату последнего коммита и открытые issues — «готовый сервер» с коммитом двухлетней давности это техдолг, а не экономия времени.

Сервер MCP — это новая точка входа

Главная мысль лекции для того, кто отвечает за безопасность контура. MCP-сервер получает вызовы извне (от модели, от пользователя, от промпт-инъекции в данных), выполняет их с правами, которые выдал, и возвращает результат в контекст модели. Формально это то же самое, что веб-сервис с административными функциями. Значит, и относиться надо так же:

  • Отдельный сервис-аккаунт с минимальными правами — не твоя учётка, не root, не доменный админ.
  • Read-only там, где запись не нужна. restart_vm в ассистенте по умолчанию — выключенная.
  • Сетевые политики: сервер ходит только туда, куда обязан, и не имеет доступа в сегмент AD.
  • Отдельные политика и лог. Каждый вызов инструмента — запись в аудит.
  • Проверка аргументов по схеме на стороне сервера, даже если модель уже проверила: схема — это контракт, а не пожелание.
  • Ограничение по объёму и времени: без него сервер — это способ положить базу через SELECT без LIMIT.

Разбор этих мер по пунктам — в следующей лекции.

Зрелость стандарта

Честно: стандарт молодой. Он быстро растёт — новая редакция протокола выходит несколько раз в год, примитивы добавляются, транспорт HTTP+SSE устарел за полгода, — но это означает конкретные практические последствия.

Риск Что делать
Сервер на старой редакции не заводится в новый клиент Фиксировать protocolVersion в логах и в конфиге, тестировать обновление в CI
Смена поведения при обновлении SDK Пиновать версии, прогонять probe.py и golden-набор после апгрейда
Ограниченная поддержка со стороны вендоров Не строить единственную точку отказа: у хозяина должен быть запасной путь без MCP
Примитивы плохо покрывают нужные сценарии Считать MCP одним из способов интеграции, а не единственным

Практический совет по эксплуатации: держи серверы MCP отдельными маленькими сервисами с собственными Dockerfile, docker-compose, тестами и правами. Тогда обновление SDK — это пересборка одного контейнера, а не обновление всего агентного стека.

Где это ломается

  • Поставил сервер файловой системы с корнем / или с домашней папкой. Дальше агент читает .env, ключи и конфиги. Это самая частая история ущерба из MCP, и она не требует злодея — достаточно неудачного описания инструмента.
  • Токены в claude_desktop_config.json. Файл читается локальным пользователем и попадает в бэкапы и скриншоты. Ротация не помогает, если не убрать причину.
  • stdio-сервер запускается от пользователя-администратора. Он получает права домена, Hyper-V и сетевых папок. Отдельный непривилегированный пользователь обязателен.
  • Ошибка инструмента как исключение протокола. Сервер отвечает isError: true с текстом, а не роняет сессию; иначе один битый аргумент обрывает весь разговор.
  • Версионный шторм. Обновили mcp в проде без golden-набора — половина инструментов перестала вызываться из-за изменений в схемах.
  • tools/list возвращает 60 инструментов. Модель теряется, выбирает не то, контекст пухнет. Держи на сервере 5–8 осмысленных инструментов, а не зеркало всей системы.
  • Ресурсы и инструменты смешаны. Ресурс, который меняет состояние, обходит модель подтверждения пользователя — пользователь не видит операции в интерфейсе.
  • Готовый сторонний сервер без ревью. Он получает твой контекст и имеет сетевой доступ. Перед подключением читай исходники — это обычный npm/pip-пакет с привилегиями.

Чек-лист понимания

🛠 Практика
Напиши MCP-сервер с тремя инструментами (чтение runbook из папки, поиск по внутренней базе знаний, карточка узла из CMDB), запусти его через stdio, проверь списком инструментов из клиента и подключи к клиенту через JSON-конфиг.
