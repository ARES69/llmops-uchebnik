Предыдущая лекция дала тебе хранилище долговечного: там лежат данные, их нельзя терять, ими можно делать транзакции. Redis — противоположный полюс. Он хранит то, что можно потерять и нужно восстановить за миллисекунды: ответы LLM, счётчики лимитов, распределённые блокировки, очереди задач индексации. Разница не в том, «какая база лучше», а в том, что происходит при потере данных: от потери кэша страница просто станет медленнее, а потеря очереди индексации означает, что документы навсегда останутся непроиндексированными. Эта лекция — про то, как выбирать режим исчезновения данных осознанно.

Зачем Redis в LLM-системе

Четыре задачи, ради которых Redis появляется в проекте, и ни одна из них не про «скорость в целом»:

  1. Кэш ответов LLM. Повторный вопрос с тем же промптом не должен стоить токенов. Это самая дорогая оптимизация во всём проекте: вопрос «как сбросить пароль в AD», который задают двадцать человек в день, можно обслуживать нулём вызовов модели.
  2. Лимиты и квоты. Rate limit, лимит токенов на пользователя, дневной бюджет арендатора. Счётчики должны считаться атомарно и жить секунды-минуты, а не годы.
  3. Блокировки и защита от гонок. Два воркера не должны одновременно индексировать один документ и не должны одновременно списывать один и тот же лимит токенов.
  4. Очереди. Задачи индексации, переиндексации, батчевой обработки — то, что можно выполнить не мгновенно, но нельзя потерять.
Свойство Redis PostgreSQL из предыдущей лекции
Ответ на один ключ ~0.1 мс единицы-десятки мс, зависит от запроса
Транзакции нет, есть атомарные команды и Lua полноценные, ACID
Хранение в памяти, с потенциальной записью на диск на диске, с кэшем в памяти
Что теряется при падении кэш — ничего, очередь — задачи всё, если нет бэкапа
Поиск по векторам Redis Stack, но это отдельный оверхед pgvector, в той же базе

Установка и базовая настройка

bash
1apt install -y redis-server
2systemctl enable --now redis-server
3redis-cli ping                      # PONG
4redis-cli INFO server | grep -E 'redis_version|uptime_in_seconds'

Ключевые параметры, которые надо осознанно выставить, а не оставить дефолтами:

conf
1# /etc/redis/redis.conf — только то, что относится к контуру LLM-системы
2bind 127.0.0.1 ::1
3port 6379
4protected-mode yes
5
6# пароль для всех команд
7requirepass S3cr3t-For-Redis-Only
8masterauth S3cr3t-For-Redis-Only
9
10# лимит памяти и политика вытеснения — см. раздел ниже
11maxmemory 2gb
12maxmemory-policy allkeys-lru
13
14# персистентность
15save ""
16appendonly no
17
18# только для наблюдаемости, не для логирования промптов
19slowlog-log-slower-than 10000
20latency-monitor-threshold 100
bash
1redis-cli -a '***' CONFIG GET maxmemory maxmemory-policy
2redis-cli -a '***' CONFIG REWRITE        # сохранить в файл, иначе переживёт только рестарт
3redis-cli -a '***' INFO memory
4redis-cli -a '***' INFO stats
!Внимание

redis-cli -a 'пароль' оставляет пароль в истории команд и в выводе ps на всей машине. Для прода используй REDISCLI_AUTH в переменной окружения или redis-cli --askpass, а пароль храни так же, как остальные секреты из лекции про безопасность.

Если Redis должен быть доступен из контейнеров или с другого узла — bind 0.0.0.0 в связке с файрволом и паролем, и только так. Голый Redis без пароля в сети, где есть хоть одна чужая машина, — это не «незащищённый сервис», а открытый доступ ко всем кэшам и к семантическому кэшу с ответами, попадавшим в кэш по чужому запросу.

Аутентификация: пароль и ACL

Один requirepass на всех — это когда Redis один, пользователь один и команда одна. В LLM-системе потребуется минимум три разных уровня доступа: приложение-RAG, фоновый индексатор, мониторинг и нештатный просмотр. Им нужны разные команды и разный blast radius.

Что настраиваешь Как Зачем
Общий пароль requirepass быстрый старт, одна роль
Пользователь без прав ACL SETUSER monitor on >nopass ~monitor:* +ping +info мониторинг не видит данные
Пользователь только на чтение +@read -@write -@dangerous дашборд читает кэш, но не может его очистить
Публикация по TLS acl setuser app on >pass ~app:* отдельный секрет на приложение
Запрет опасных команд rename-command FLUSHALL "" отключение сноса базы ключом, попавшим в промпт
bash
1# пользователь приложения: только свои ключи, без опасных команд
2redis-cli -a '***' ACL SETUSER app on '>S3cret-App-Pass' '~app:*' \
3  '+@read' '+@write' '-@dangerous' '-eval' '-flushall'
4
5# пользователь мониторинга: только чтение, только свой префикс
6redis-cli -a '***' ACL SETUSER monitor on '>S3cret-Mon-Pass' '~monitor:*' '+ping' '+info' '+@read'
7
8# сервисный пользователь без пароля — только из unix-сокета
9redis-cli ACL SETUSER internal on nopass ~internal:* +@read +@write
10
11redis-cli -a '***' ACL LIST
12redis-cli -a '***' ACL WHOAMI
13redis-cli -a '***' ACL GETUSER app
⚡Осторожно

ACL SETUSER app on >пароль ... в командной строке оставляет пароль в истории. Создавай пользователя с временным паролем и меняй сразу: ACL SETUSER app on >tmp ..., затем ACL SETUSER app >настоящий-пароль. Ещё лучше — генерируй пароль и подставляй его из менеджера секретов при развёртывании, а не храни в репозитории.

ACL-ключи паттернами (~app:*) — главный аргумент за ACL против общего пароля: приложение, у которого случится SQL-инъекция-через-промпт, не сможет прочитать чужие ключи и не сможет вызвать FLUSHALL. Это ровно та граница, о которой шла речь в лекции про агентов: агентный код получает собственный, узкий, наблюдаемый доступ.

Структуры данных: что брать под задачу LLM-системы

Структура Команды Когда применять в ИИ-системе
String SET/GET, SET NX EX, INCR/INCRBY кэш ответа LLM, счётчик токенов, флаг «индексация идёт»
Hash HSET/HGETALL, HINCRBY состояние задачи индексации (прогресс, этап, ошибка), профиль пользователя
List LPUSH/RPOP, BRPOP простая очередь с ограничением длины, лог последних N событий
Set SADD/SISMEMBER, SMEMBERS множество тегов документа, множество активных сессий, дедупликация промптов
Sorted Set ZADD, ZRANGEBYSCORE, ZRANGEBYSCORE ... LIMIT sliding window counter, очередь по приоритету, «документы, протухшие позже N минут»
Stream XADD, XREADGROUP, XACK надёжная очередь задач с подтверждениями и повторной доставкой
Bitmap SETBIT/BITCOUNT дешёвый учёт «был ли этот промпт» за 90 дней

Большинство новичков в Redis используют только String и Hash, а потом удивляются, что очередь на List теряет задачи при перезапуске. Смотри на структуру как на выбор между простотой и гарантиями: List прост и ничего не гарантирует, Stream сложнее и даёт подтверждения, повторную доставку и несколько потребителей.

bash
1r() { redis-cli -a '***' --no-auth-warning "$@"; }
2
3r SET llm:cache:8f2a '{'answer'}' 'текст ответа' EX 3600
4r TTL llm:cache:8f2a                                  # осталось жить
5
6r HSET job:doc-77 status running stage embedding processed 1200
7r HGETALL job:doc-77
8
9r SADD doc:77 acl-groups corp-all domain-admins
10r SISMEMBER doc:77 domain-admins
11
12r ZADD ratelimit:user42 1760300000000 req-1
13r ZRANGEBYSCORE ratelimit:user42 1760300000000 +inf LIMIT 0 100
14
15r XADD indexq '*' doc_id doc-77 tenant 42 priority 5
16r XLEN indexq

Время жизни: EXPIRE и распределённая блокировка

Ключ без TTL в Redis — это утечка памяти, которая проявится через месяц в самый неподходящий момент. Всё, что можно восстановить, должно иметь срок жизни, заданный явно.

SET NX EX — атомарная операция «поставить, только если ключа нет». Это и есть распределённая блокировка:

bash
1# взять блокировку документа на индексацию: 10 минут максимум
2r SET lock:index:doc-77 worker-3 NX EX 600
3# OK — блокировку получили; (nil) — её уже держит другой воркер

Два правила, без которых такая блокировка бесполезна. Первое: значение блокировки должно быть уникальным — идентификатор воркера. Иначе воркер, чей TTL истёк, но он ещё жив, освободит чужую блокировку. Второе: освобождать надо только свою, проверяя значение. Проверка и удаление должны быть одной атомарной операцией:

lua
1-- release_lock.lua — освободить, только если мы её держим
2if redis.call("GET", KEYS[1]) == ARGV[1] then
3  return redis.call("DEL", KEYS[1])
4end
5return 0
bash
1r EVAL "$(cat release_lock.lua)" 1 lock:index:doc-77 worker-3

Политика вытеснения памяти: maxmemory

Когда Redis упирается в maxmemory, он начинает вытеснять ключи по политике, и от того, какая политика выбрана, зависит, что именно ты потеряешь.

Политика Что вытесняется Для чего годится Для чего не годится
noeviction ничего, пишет ошибку клиенту Redis как единственное хранилище данных кэш под нагрузкой при нехватке памяти
allkeys-lru любой ключ, реже всего используемый кэш ответов LLM, дешёвый кэш всё, что нельзя потерять
allkeys-lfu любой ключ, реже всего используемый по частоте кэш с явно «горячими» ключами нестационарный трафик
volatile-lru только ключи с TTL смешанный набор, где важные ключи без TTL если забудешь поставить TTL, важный ключ не вытеснится, но вытеснится мусор
volatile-ttl ключи с TTL, с наименьшим остатком короткоживущие блокировки почти ни для чего
bash
1r CONFIG SET maxmemory 2gb
2r CONFIG SET maxmemory-policy allkeys-lru
3r INFO memory | grep -E 'used_memory_human|maxmemory_human|mem_fragmentation_ratio'
⚠Важно

Смешивать в одном инстансе данные, которые нельзя потерять, и кэш, который можно, нельзя: политика одна на весь инстанс. allkeys-lru на очереди задач индексации с noeviction на сессиях означает две конфигурации, а значит два инстанса. Отдельный Redis на кэш, отдельный на очереди — дешевле, чем потерять очередь при нехватке памяти.

Наблюдаемость памяти:

bash
1r INFO memory | grep -E 'used_memory_peak|maxmemory_policy|mem_fragmentation'
2r --bigkeys                                              # 10 самых тяжёлых ключей
3redis-cli --memkeys -a '***' -i 0.1                     # доля памяти по типам структур

mem_fragmentation_ratio выше 1.5 — верный признак того, что максимум памяти отдан allocator'у, но используется мало. Решается перезапуском, а не увеличением лимита.

Персистентность: RDB против AOF

RDB (снапшот) AOF (лог команд)
Что пишет состояние на момент снимка каждую команду
Потеря данных при аварии всё после последнего снимка до секунды (зависит от appendfsync)
Размер на диске 1 файл, компактно растёт, нужна перезапись
Нагрузка на CPU/IO пиковая при сохранении постоянная небольшая
Восстановление быстрое: один файл построчное, дольше
conf
1save 900 1
2save 300 10
3appendonly yes
4appendfsync everysec        # компромисс: теряем до секунды, не теряем производительность
5auto-aof-rewrite-percentage 100

Выбор по назначению инстанса. Для кэша ответов не включать ничего: save "" и appendonly no — кэш после перезапуска просто прогреется за пару минут, а ты экономишь до 40% CPU и не получаешь риск повреждённого AOF. Для очереди задач AOF обязателен: потерять непроиндексированные документы нельзя. Для блокировок и лимитов персистентность бессмысленна: истёкший TTL всё равно должен истечь.

bash
1r CONFIG GET appendonly save appendfsync
2r BGREWRITEAOF                                  # фоновая перезапись, без блокировки
3r INFO persistence | grep -E 'rdb_bgsave_in_progress|aof_rewrite_in_progress'

Репликация: когда она нужна

Одиночный Redis — единая точка отказа. Но поднимать кластер ради кэша в LLM-системе с 20 пользователями — неправильный размен. Сначала спроси, что будет, если Redis пропадёт на час:

  • кэш ответов — приложение деградирует до прямых вызовов модели. Дорого (токены), но работает. Значит, репликация не нужна, нужен мониторинг;
  • rate limit — без счётчиков лимит перестаёт работать, начинается перерасход бюджета. Значит, нужен Sentinel или два инстанса с переключением;
  • очередь — индексация встаёт, документы копятся. Значит, нужен Sentinel, потому что потерять очередь нельзя.
Механизм Что решает Порог применения
Репликация REPLICAOF читатели не мешают записи, копия для кэша уже есть поток чтения, который можно развести
Sentinel автоматическое переключение мастер-реплики один инстанс нельзя терять
Cluster шардирование по 16 384 слотам один инстанс не влезает в память
Внешний кэш (CDN, in-process) снять нагрузку ответы одинаковы для всех
bash
1# репликация в два клика
2redis-cli -a '***' REPLICAOF 10.10.10.21 6379
3redis-cli -a '***' INFO replication
4
5# sentinel: отдельный конфиг, автоматика на стороне клиента
6sentinel monitor llmcache 10.10.10.20 6379 2
7sentinel failover llmcache          # ручное переключение для проверки

Redis Cluster — сознательно не рассматриваю для этого класса задач: шардирование влечёт за собой CROSSSLOT-ограничения (мульти-ключевые операции и Lua только в пределах одного слота, поэтому ключи хешируют тегом {llm}), а выигрыш появляется только когда один инстанс физически не влезает в память. В LLM-системе обычно влезает.

Rate limit: два алгоритма и почему Lua

Rate limit — первое, ради чего ставят Redis в проекте с API. Наивная реализация через INCR и EXPIRE неверна: два окна приходят одновременно, первый ставит TTL, второй увеличивает счётчик — и лимит перестаёт быть лимитом. Нужен либо Lua, либо одна транзакция с MULTI (но MULTI не спасает от гонки между чтением и записью, в отличие от Lua).

Алгоритм Как считает Плюс Минус
Fixed window счётчик сбрасывается по границе окна дёшево, одна операция всплеск 2x лимита на границе окон
Sliding window counter два ведра: текущее и предыдущее, усреднение точная граница, две операции нужна синхронизация по времени
Token bucket ведро с постоянным притоком токенов разрешает всплески, естественно для LLM два лишних состояния в ключе
Локальный счётчик в процессе счётчик в памяти приложения ноль задержки не работает при нескольких репликах
lua
1-- /opt/llmops/lua/sliding_window.lua
2-- KEYS[1] — ключ окна, ARGV: now_ms, window_ms, limit, member
3-- Возвращает: allowed, remaining, retry_after_ms
4redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, tonumber(ARGV[1]) - tonumber(ARGV[2]))
5local count = redis.call('ZCARD', KEYS[1])
6local limit = tonumber(ARGV[3])
7if count >= limit then
8  local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
9  local retry_after = tonumber(ARGV[2])
10  if oldest[2] then
11    retry_after = (tonumber(oldest[2]) + tonumber(ARGV[2])) - tonumber(ARGV[1])
12  end
13  return {0, 0, math.ceil(retry_after)}
14end
15redis.call('ZADD', KEYS[1], tonumber(ARGV[1]), ARGV[4])
16redis.call('PEXPIRE', KEYS[1], tonumber(ARGV[2]))
17return {1, limit - count - 1, 0}
lua
1-- /opt/llmops/lua/token_bucket.lua
2-- ARGV: now_ms, rate_per_sec, capacity, cost
3local key = KEYS[1]
4local now_ms, rate, cap, cost = tonumber(ARGV[1]), tonumber(ARGV[2]),
5                                tonumber(ARGV[3]), tonumber(ARGV[4])
6local state = redis.call('HMGET', key, 'tokens', 'ts')
7local tokens, ts = tonumber(state[1]), tonumber(state[2])
8if tokens == nil then tokens, ts = cap, now_ms end
9tokens = math.min(cap, tokens + (math.max(0, now_ms - ts) / 1000) * rate)
10if tokens >= cost then
11  tokens = tokens - cost
12  redis.call('HSET', key, 'tokens', tokens, 'ts', now_ms)
13  redis.call('PEXPIRE', key, math.ceil((cap / rate) * 1000))
14  return {1, math.floor(tokens), 0}
15end
16redis.call('HSET', key, 'tokens', tokens, 'ts', now_ms)
17return {0, math.floor(tokens), math.ceil((cost - tokens) / rate * 1000)}
bash
1# обязательно одним EVAL, а не серией команд
2redis-cli -a '***' --eval /opt/llmops/lua/sliding_window.lua rl:user42:chat \
3  , $(date +%s%3N) 60000 20 req-$RANDOM
4# 1) (integer) 1
5# 2) (integer) 14
6# 3) (integer) 0
7
8# token bucket под токены LLM: стоимость запроса = оценка числа токенов в промпте
9redis-cli -a '***' --eval /opt/llmops/lua/token_bucket.lua tb:user42:tokens \
10  , $(date +%s%3N) 1000 6000 3200
11# 1) (integer) 1
12# 2) (integer) 2800
13# 3) (integer) 0
⚠Важно

Почему именно Lua, а не EVAL с несколькими командами из приложения: Redis выполняет скрипт целиком, ни один другой клиент не может вклиниться между его командами. Если окно считать из приложения тремя запросами, между ZCARD и ZADD успеет вклиниться второй клиент — и он тоже получит allowed. Логика лимита обязана жить на стороне Redis. То же касается списания квоты токенов: HINCRBY без проверки лимита позволяет двум параллельным запросам потратить вдвое больше.

Кэширование ответов LLM: ключ, TTL, безопасность

Ключ кэша — это не «хеш вопроса». Это хеш всего, что влияет на ответ, плюс того, кто его спросил:

text
1llm:{tenant}:v1:{sha256(user_id + acl_version + model + temperature
2                    + top_p + prompt_version + question_normalized)}

Что должно быть в ключе и почему:

Компонент Зачем в ключе Что будет без него
tenant_id изоляция арендаторов утечка ответа между клиентами
идентичность пользователя или версия прав один и тот же вопрос даёт разные ответы пользователь А получает ответ, сгенерированный для пользователя Б
модель и снапшот смена модели меняет ответ после деплоя все ответы из кэша — от старой модели
параметры (temperature, top_p, max_tokens) влияют на результат «детерминированный» ответ при temperature=0.7
версия промпта промпт меняется при доработке RAG после правки промпта пользователи получают старые ответы
не включать: время запроса, stream-флаг, номер сессии не влияют на содержание ключ перестанет повторно находиться, кэш бесполезен
python
1# /opt/llmops/cache.py
2import hashlib, json
3import redis
4
5r = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True,
6                 username="app", password="…")          # ACL, не общий requirepass
7
8def cache_key(*, tenant_id, user_id, acl_version, model, prompt_version,
9              question, temperature=0.0):
10    payload = json.dumps(
11        [tenant_id, user_id, acl_version, model, prompt_version,
12         temperature, question.strip().lower()],
13        sort_keys=True, separators=(",", ":"), ensure_ascii=False,
14    )
15    return f"llm:{tenant_id}:v1:{hashlib.sha256(payload.encode()).hexdigest()}"
16
17def get_cached(**kw) -> dict | None:
18    raw = r.get(cache_key(**kw))
19    return json.loads(raw) if raw else None
20
21def put_cached(value: dict, *, ttl=3600, **kw) -> None:
22    r.set(cache_key(**kw), json.dumps(value, ensure_ascii=False), ex=ttl)
⚡Осторожно

Кэш ответов LLM — это утечка данных по построению: он хранит то, что было сказано одному человеку, и отдаёт это другому, если ключ совпал. Два обязательных условия: идентичность пользователя внутри ключа, а не «снаружи, в коде вызова», и ACL-версия в ключе — при отзыве права документ мог пропасть из выдачи, а ответ о нём остался бы в кэше. Инвалидация: INCR llm:{tenant}:aclver одной командой делает все старые ключи неиспользуемыми, а не нужно обходить их.

Семантический кэш идёт дальше: он ищет не по точному совпадению вопроса, а по близости эмбеддинга. Ключ строится по модели эмбеддингов, округлённым координатам вектора и tenant, а перед возвратом сверху проверяется косинусное расстояние — «точное совпадение вопроса или соседнее достаточно».

python
1# /opt/llmops/semantic_cache.py — упрощённо, без индекса
2def semantic_get(question_vec, tenant_id: str, embed_model: str, threshold=0.97):
3    bucket = quantized_bucket(question_vec)             # округление координат -> ключ
4    key = f"sem:{tenant_id}:{embed_model}:{bucket}"
5    candidates = r.zrange(key, 0, 9, withscores=True)    # недавние кандидаты
6    for raw in candidates:
7        cand = json.loads(raw)
8        if cosine_sim(question_vec, cand["vec"]) >= threshold:
9            r.zincrby(key, 1, raw)                      # поднимаем популярное
10            r.expire(key, 86400)
11            return cand["answer"]
12    return None
13
14def semantic_put(question_vec, answer: str, tenant_id: str, embed_model: str):
15    bucket = quantized_bucket(question_vec)
16    key = f"sem:{tenant_id}:{embed_model}:{bucket}"
17    r.zadd(key, {json.dumps({"vec": question_vec, "answer": answer}): time.time()})
18    r.zremrangebyscore(key, 0, time.time() - 86400)     # не хранить больше суток
19    r.expire(key, 86400)

У семантического кэша два риска, которые надо назвать до внедрения. Первый — ложное срабатывание: вопрос «как удалить пользователя» поймает ответ на «как отключить пользователя», потому что векторы близки, а смысл разный. Отсюда высокий порог и проверка самим LLM в спорных случаях. Второй — тот же вопрос от другого пользователя: ключ обязан содержать tenant и уровень прав, иначе семантический кэш становится каналом утечки ответов, содержащих имена, суммы и внутренние названия.

Очереди: Redis Streams

List — очередь без гарантий: подтверждений нет, при падении воркера задача теряется, один потребитель. Stream — очередь с журналом: каждая запись имеет id, есть группы потребителей, есть подтверждение, есть повторная доставка зависшего.

bash
1r XADD indexq '*' doc_id doc-77 tenant 42 priority 5
2r XGROUP CREATE indexq indexers '$' MKSTREAM          # создать группу потребителей
3r XREADGROUP GROUP indexers worker-1 COUNT 10 BLOCK 5000 STREAMS indexq '>'
4r XACK indexq indexers 1757568000000-0
5r XPENDING indexq indexers                            # сколько висит без подтверждения
6r XAUTOCLAIM indexq indexers worker-1 0 60000 COUNT 10  # забрать зависшее после падения

Жизненный цикл одной задачи индексации: XADD при поступлении документа, XREADGROUP забирает воркер, воркер сначала ставит семантическую блокировку lock:index:doc-77 через SET NX EX, затем индексирует, пишет прогресс в HSET job:doc-77 stage embedding, и только после успешной записи в Postgres делает XACK. Если XACK не выполнен — сообщение вернётся другому воркеру через XAUTOCLAIM, и идемпотентность апстрима (детерминированный chunk_id из лекции про Postgres) сделает повторную обработку безвредной.

Свойство Redis Streams RabbitMQ Kafka
Подтверждение и redelivery да да (поколения, DLX) offset, без redelivery из коробки
Маршрутизация по ключу нет (потребители забирают всё) routing keys, exchange partition по ключу
Несколько потребителей на задачу через отдельные группы да конкурирующие читатели партиции
Объём и пропускная средние средние высокие, журнал событий
Операционная сложность ноль, уже в инфраструктуре отдельный сервис кластер из трёх сервисов

Streams — честный выбор для задач индексации: их десятки в минуту, терпеть потерю нельзя, а эксплуатировать ещё один кластер ради них не хочется. Kafka оправдана, когда поток измеряется тысячами сообщений в секунду и он нужен как источник для нескольких независимых потребителей — аналитика, обучение, аудит.

2import redis, time

Где это ломается

  • Ключ кэша без идентификатора пользователя. Два сотрудника задают одинаковый вопрос, один получает ответ, сгенерированный по правам другого. Это утечка данных, а не оптимизация, и заметят её юристы, а не мониторинг.
  • INCR + EXPIRE в две команды из приложения. Между ними другой клиент успевает увеличить счётчик, TTL ставится один раз вторым запросом, и окно живёт не по расписанию. Лимит перестаёт быть лимитом. Лечится Lua-скриптом из лекции.
  • Один Redis и для кэша, и для очереди. maxmemory-policy одна на инстанс. При нехватке памяти allkeys-lru вытеснит незафиксированные задачи индексации вместе с кэшем. Два инстанса дешевле потери пачки документов.
  • Включили персистентность «на всякий случай» на кэш. AOF пишет каждую команду, журнал растёт, фоновые BGREWRITEAOF едят CPU на том же инстансе, что обслуживает запросы. Для кэша save "" и appendonly no — правильное решение, а не компромисс.
  • Блокировка без значения и без проверки при освобождении. TTL истёк, первый воркер ещё работает, второй взял ту же блокировку, первый пришёл и удалил её своим DEL. Второй индексирует без защиты. Лечится SET NX EX с уникальным значением и Lua-освобождением.
  • Очередь на LPUSH/BRPOP. Воркер упал после BRPOP — задача исчезла безвозвратно. Для индексации документов это тихая потеря данных, которую заметят через неделю по жалобам на поиск.
  • FLUSHALL в проде. Ключ с командой, пришедший из промпта, нода автоматизации или забытый тест — и кэш, счётчики лимитов и состояния задач обнулены. rename-command FLUSHALL "" и -@dangerous для пользователя приложения.
  • Redis в одной сети с приложением без пароля. bind 0.0.0.0 + protected-mode no — это открытый доступ ко всем ответам LLM и ко всем счётчикам лимитов для любой машины в подсети.
  • Ключи без TTL. Разовое забытое EXPIRE на ключе с суточным приростом — и через месяц Redis не влезает в память, а maxmemory-policy noeviction для очереди означает, что запись падает с ошибкой.
  • INFO и KEYS * в проде. KEYS * блокирует Redis на время всей выборки — это отказ в обслуживании. Только SCAN с курсором.
