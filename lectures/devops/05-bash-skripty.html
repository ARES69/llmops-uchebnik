Скрипт на bash — это код, который живёт в проде дольше, чем любой релиз. Скрипт деплоя, написанный «на бегу» и запущенный из crontab, через год становится частью инфраструктуры: его никто не читал, но все боятся тронуть. Разница между однострочником из интернета и Production-ready скриптом — не в длине, а в том, как он ведёт себя при ошибке. Эта лекция про поведение.

Shebang и почему не /bin/sh

Первая строка — #!, ядро читает её, чтобы понять интерпретатор:

bash
1#!/usr/bin/env bash

#!/bin/bash — работает, но сломается в системах без /bin (встречается в некоторых дистрибутивах и в контейнерах с минимальным образом). /usr/bin/env ищет bash в $PATH, это переносимо. Всегда начинай с /usr/bin/env bash и заканчивай:

bash
1set -euo pipefail
2IFS=$'\n\t'

Всегда ставь # в начале строки перед комментарием. Файл с BOM, CRLF или пропущенным shebang будет отвергнут systemd-юнитом.

Строгий режим: set -euo pipefail

Три флага, каждый закрывает свой класс ошибок. Разбираем отдельно, потому что set -e — источник самого неочевидного поведения в bash.

-e (errexit): выход при ошибке

Прекращает скрипт, если команда вернула ненулевой код.

-u (nounset): ошибка на неопределённой переменной

Без него echo $TYPO молча печатает пустую строку, и через три строки ты разбираешь, почему скрипт сделал не то. С -u скрипт падает сразу: «MY_APP_PORT: unbound variable».

-o pipefail: ошибка в любой части конвейера

Без него код возврата конвейера — это код последней команды:

bash
1false | echo ok        # код 0 — пайплайн «успешен», хотя первая часть упала
2set -o pipefail
3false | echo ok        # код 1 — теперь ложь видна
⚠Важно

Без pipefail в CI-пайплайне json=$(curl -s $URL | jq .status) спокойно вернёт пустоту при недоступном API и продолжит работать с null. Это не ошибка — это тихое расхождение с продакшном. pipefail делает пайплайн честным.

Где set -e НЕ работает

Это надо знать дословно, иначе скрипт будет падать там, где ты не ждёшь, или — что хуже — не падать там, где должен.

Ситуация Почему set -e не сработает Что делать
команда в условии if условие по определению не должно валить скрипт проверяй явно
команда в && / ` ` цепочке кроме последней в цепочке проверяй $?
перенаправление в цикле for f in $(find ...) не полагайся на -e
$(...) в присваивании ошибка в подстановке проверяй результат явно
bash
1# ТАК ПРАВИЛЬНО
2if ! grep -q 'ERROR' "$LOG"; then
3  echo "ошибок нет"
4fi
5
6# ТАК НЕПРАВИЛЬНО (и не сработает под set -e)
7grep -q 'ERROR' "$LOG" && echo "есть ошибки"
8grep -q 'ERROR' "$LOG"
9
10# РАБОЧИЙ ВАРИАНТ для цепочек
11grep -q 'ERROR' "$LOG" || { echo "ошибок нет"; exit 0; }

Ключевое правило: set -e — это страховка от цепных ошибок, а не логика программы. Условия, которые определяют поведение, пиши явно через if и проверяй код возврата. set -e ловит только то, что ты не предусмотрел.

Ловушка set -e с if ! cmd

Распространённая ошибка — писать if ! command; then error; exit 1; fi для команд, где ! инвертирует успех в ошибку. Работает корректно, но теряет код возврата, и ты не можешь отличить «файл не найден» от «доступ запрещён». В set -e сочетание if ! cmd без сохранения кода — потеря информации.

bash
1if ! docker ps -q | grep -q "$name"; then
2  echo "контейнер $name не найден" >&2
3  exit 1
4fi

Здесь grep может вернуть 2 (ошибка доступа), а ты думаешь «нет контейнера». Всегда, когда важна причина, проверяй раздельно:

bash
1docker ps -q | grep -q "$name"
2case $? in
3  0) echo "найден" ;;
4  1) echo "не найден" >&2; exit 1 ;;
5  *) echo "ошибка проверки" >&2; exit 2 ;;
6esac

Переменные и подстановки

Конструкция Что делает
${VAR} значение переменной
"$VAR" значение в кавычках — всегда так
${VAR:-default} значение или default, если пусто
${VAR:?сообщение} ошибка с сообщением, если пусто
${VAR:=default} значение или присвоить default
${#VAR} длина строки
${VAR:0:10} подстрока
${VAR#prefix} убрать префикс
${VAR%.log} убрать суффикс
${#ARR[@]} число элементов массива
${ARR[@]} / "${ARR[@]}" все элементы
${ARR[0]} первый элемент
${ARR[@]:0:3} срез: первые три
bash
1BASE_URL="${BASE_URL:-https://api.example.com}"
2: "${API_TOKEN:?API_TOKEN обязателен}"     # упадёт сразу, если не задан
3
4FILES=("$HOME"/data/*.csv)                 # массив с кавычками внутри
5echo "файлов: ${#FILES[@]}"
6printf '%s\n' "${FILES[@]:0:3}"            # первые три
7for f in "${FILES[@]}"; do echo "$f"; done
8
9basename="${LOGFILE%.log}"                # без суффикса
10stripped="${LOGFILE#*/}"                  # без директории
⚡Осторожно

Массив пишется так: ARR=(one two three) — без пробела перед =. Это синтаксическая ошибка в bash. И "${ARR[@]}" в кавычках обязателен: без кавычек элементы с пробелами разобьются на отдельные аргументы.

Условия: [[ ]] против [ ]

Что [ (test) [[ (bash test)
Это внешняя программа встроенная конструкция bash
Регулярки нет =~
Логика && || && ||, слова как операнды
Скорость медленнее быстрее (нет fork)
Рекомендация для совместимости с sh всегда в bash-скриптах
bash
1[[ -f "$f" ]]          # файл существует
2[[ -d "$d" ]]          # каталог
3[[ -n "$s" ]]          # строка непустая
4[[ -z "$s" ]]          # строка пустая
5[[ "$a" == "$b" ]]     # равенство
6[[ "$a" != "$b" ]]
7[[ "$a" -gt 10 ]]      # арифметическое: -gt -lt -ge -le -eq -ne
8[[ "$port" =~ ^[0-9]+$ ]]   # проверка, что это число
9[[ -x "$f" && -r "$f" ]]    # комбинация
10
11# ВАЖНО: [[ ]] не нужно экранировать, [ ] нужно
12[ "$a" = "x y" ]       # тут нужны кавычки
✨Подсказка

Валидация ввода через [[ =~ ]] — первая линия обороны скрипта, который будет вызван с аргументами от cron или от соседнего скрипта: [[ $PORT =~ ^[0-9]+$ ]] || { echo "порт должен быть числом" >&2; exit 1; }.

bash
1# функции
2log() {
3  local level="$1"; shift

7retry() {
8  local tries="$1" delay="$2"; shift 2
9  local n=1
10  until "$@"; do
11    (( n >= tries )) && { log ERROR "не удалось: $*"; return 1; }
12    log WARN "попытка $n/$tries: $*"
13    sleep "$delay"; (( n++ ))
14  done
15}
16

local — обязателен для переменных внутри функций, иначе они перезапишут глобальные. shift — убрать первый позиционный аргумент, чтобы $@ были только «настоящими».

Аргументы скрипта

bash
1#!/usr/bin/env bash
2set -euo pipefail
3
4# $0 — путь к скрипту, $# — количество, "$@" — все аргументы, "$*" — склеенные
5# $1, $2 ... — по позициям, $? — код возврата последней команды
6shift   # убрать первый аргумент (обычно подкоманду)
7
8usage() {
9  cat <<EOF
10Использование: $0 <host> <port> [-t таймаут]
11EOF
12}
13
14HOST="${1:?укажите хост}"
15PORT="${2:?укажите порт}"
16shift 2
17TIMEOUT=5
18while [[ $# -gt 0 ]]; do
19  case "$1" in
20    -t) TIMEOUT="$2"; shift 2 ;;
21    -h|--help) usage; exit 0 ;;
22    *) echo "неизвестный аргумент: $1" >&2; usage; exit 1 ;;
23  esac
24done

${1:?} и ${2:?} — валидация обязательных аргументов: скрипт падает с понятным сообщением, а не с host: command not found двумя строками ниже.

⚠Важно

curl -sS — обязательная пара: -s глушит прогресс-бар, -S показывает ошибки, которые -s проглотил бы. Для API-вызовов добавляй --fail-with-body или --fail: без него HTTP 500 вернёт код 0, и твой скрипт посчитает несуществующий ответ валидным. И всегда --max-time, иначе зависший API навсегда остановит скрипт.

bash
1# curl: -sS молчаливый, но ошибки видны
2resp=$(curl -sS --fail-with-body --max-time 10 -H "Authorization: Bearer $TOKEN" "$URL") \
3  || { echo "API недоступен" >&2; exit 3; }
4
5# jq: парсим JSON безопасно
6ver=$(echo "$resp" | jq -r '.version // empty') \
7  || { echo "невалидный JSON" >&2; exit 4; }
8[[ -n "$ver" ]] || { echo "нет поля version" >&2; exit 4; }
Проверка Команда
валидный JSON echo "$r" | jq -e . >/dev/null
поле существует echo "$r" | jq -e 'has("status")'
тип правильный echo "$r" | jq -e '.items | type == "array"'
достать значение echo "$r" | jq -r '.items[].id'
красивый вывод echo "$r" | jq .
из массива в TSV echo "$r" | jq -r '.items[] | [.id, .name] | @tsv'

trap: уборка при любом выходе

Скрипт может упасть где угодно. trap гарантирует, что временные файлы уйдут, а lock снимется — даже по Ctrl+C (SIGINT), kill (SIGTERM) или при ошибке из-за set -e.

bash
1#!/usr/bin/env bash
2set -euo pipefail
3
4TMPDIR_CREATED=""
5LOCKFILE="/var/lock/myapp-backup.lock"
6
7cleanup() {
8  local rc=$?
9  # сначала убрать lock, потом — временное (порядок важен при ошибке)
10  [[ -n "$TMPDIR_CREATED" ]] && rm -rf "$TMPDIR_CREATED"
11  rm -f "$LOCKFILE"
12  log INFO "завершено с кодом $rc"
13  exit "$rc"     # сохранить исходный код!
14}
15
16trap cleanup EXIT           # при любом выходе, включая ошибку
17trap 'log WARN "прервано пользователем"; exit 130' INT
18trap 'log WARN "получен SIGTERM"; exit 143' TERM
19
20log() { printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}"; }
21
22# Проверка lock-файла: не запущен ли уже другой экземпляр?
23if ! ( set -o noclobber; echo $$ > "$LOCKFILE" ) 2>/dev/null; then
24  log WARN "уже запущен другой экземпляр (pid $(cat "$LOCKFILE" 2>/dev/null))"
25  exit 0
26fi
27TMPDIR_CREATED=$(mktemp -d /tmp/myapp-backup.XXXXXX)
28log INFO "начало, временный каталог $TMPDIR_CREATED"
⚡Осторожно

В cleanup первой строкой пиши local rc=$?. Если этого не сделать, код возврата функции cleanup (скорее всего 0) перезапишет код, с которым скрипт завершался — и systemd увидит «успех» там, где был провал. Очень неприятный баг, потому что скрипт всё делает правильно, а systemctl status показывает active (exited).

Идемпотентность и lock-файл

Идемпотентный скрипт — тот, который можно запустить дважды и третий раз, и результат будет тем же. Для бэкапа, деплоя и миграции это обязательное свойство: cron упадёт, ты перезапустишь systemd-юнит, ночной запуск случится дважды.

Приём Как
mkdir как атомарный lock mkdir "$LOCK" 2>/dev/null || exit 0
noclobber перенаправление в файл с set -o noclobber — атомарно
flock `flock -n 9 exit 0` с дескриптором 9
дата в имени архивы не перезаписываются: backup-$(date +%F).sql.gz
проверка перед работой «уже существует — выходим» или «заменяем атомарно»
bash
1# flock: канонический способ
2(
3  flock -n 9 || { echo "уже выполняется"; exit 0; }
4  # здесь работа
5) 9>/var/lock/myapp-backup.lock
6
7# атомарная замена: пишем во временное, потом mv (mv атомарен в пределах ФС)
8tmp=$(mktemp)
9mysqldump ... > "$tmp" && gzip "$tmp" && mv "$tmp" /backups/latest.sql.gz
✨Подсказка

flock -n 9 || exit 0 — правильный паттерн для cron-задачи: если предыдущий запуск ещё не закончился, новый просто выходит, не падает и не создаёт второй экземпляр. Для systemd-юнитов lock не нужен — там этим занимается сам systemd, Restart=on-failure не даст запуститься второму.

Практика: два рабочих скрипта

Скрипт 1: health-check с правильным exit-кодом

bash
1sudo tee /usr/local/bin/healthcheck > /dev/null <<'EOF'
2#!/usr/bin/env bash
3set -euo pipefail
4
5readonly SCRIPT_NAME="${0##*/}"
6readonly LOG="/var/log/healthcheck.log"
7readonly URL="${1:?укажите URL для проверки}"
8readonly MAX_TIME="${2:-5}"
9
10log() {
11  printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" | tee -a "$LOG"
12}
13
14body=$(curl -sS --fail-with-body --max-time "$MAX_TIME" "$URL" 2>&1) && rc=0 || rc=$?
15
16case "$rc" in
17  0)
18    log OK "$URL отвечает: ${body:0:120}"
19    exit 0
20    ;;
21  6|7)  # не удалось разрешить хост / не удалось подключиться
22    log CRIT "$URL недоступен (curl rc=$rc): $body"
23    exit 1
24    ;;
25  28)  # таймаут
26    log CRIT "$URL не ответил за ${MAX_TIME}s"
27    exit 1
28    ;;
29  22)  # --fail: HTTP-ошибка
30    log WARN "$URL вернул HTTP-ошибку: $body"
31    exit 1
32    ;;
33  *)
34    log WARN "curl rc=$rc: $body"
35    exit 1
36    ;;
37esac
38EOF
39sudo chmod 755 /usr/local/bin/healthcheck
40
41# проверка
42/usr/local/bin/healthcheck https://api.example.com/healthz
43/usr/local/bin/healthcheck https://несуществующий.домен ; echo "код: $?"
iЗаметка

Обрати внимание на ... && rc=0 || rc=$?. Это самый надёжный способ поймать код возврата команды, не ломая set -e. Альтернатива — if ! cmd; then rc=$? (теряет код), поэтому используй именно форму с &&/||.

Скрипт 2: бэкап с trap и проверкой

bash
1sudo tee /usr/local/bin/pg-backup > /dev/null <<'EOF'
2#!/usr/bin/env bash
3set -euo pipefail
4
5readonly DEST="/var/backups/postgres"
6readonly RETENTION_DAYS=7
7readonly LOCK="/var/lock/pg-backup.lock"
8
9log() { printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}"; }
10
11cleanup() {
12  local rc=$?
13  [[ -n "${TMP:-}" ]] && rm -f "$TMP"
14  rm -f "$LOCK"
15  log INFO "завершено, код $rc"
16  exit "$rc"
17}
18trap cleanup EXIT
19trap 'log WARN "прервано"; exit 130' INT
20trap 'log WARN "SIGTERM"; exit 143' TERM
21
22# Атомарный lock: если папка создалась — мы первые
23mkdir "$LOCK" 2>/dev/null || { log INFO "уже выполняется"; exit 0; }
24
25mkdir -p "$DEST"
26readonly STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
27readonly FINAL="$DEST/pg-$STAMP.sql.gz"
28TMP=$(mktemp /tmp/pg-backup.XXXXXX)
29
30log INFO "начало бэкапа -> $FINAL"
31PGPASSWORD="${PGPASSWORD:?задайте PGPASSWORD}" \
32  pg_dumpall --clean --if-exists -h 127.0.0.1 -U postgres \
33  | gzip -9 > "$TMP"
34
35# Проверяем архив ДО того, как назовём его финальным именем
36if ! gzip -t "$TMP"; then
37  log ERROR "архив повреждён — финальное имя не присваиваем"
38  exit 1
39fi
40[[ $(stat -c %s "$TMP") -gt 1024 ]] || { log ERROR "подозрительно мал"; exit 1; }
41
42mv "$TMP" "$FINAL"
43chmod 640 "$FINAL"
44log INFO "готово: $(du -h "$FINAL" | cut -f1)"
45
46log INFO "удаление бэкапов старше $RETENTION_DAYS дней"
47find "$DEST" -name 'pg-*.sql.gz' -mtime +$RETENTION_DAYS -print -delete
48log INFO "осталось файлов: $(find "$DEST" -name 'pg-*.sql.gz' | wc -l)"
49EOF
50sudo chmod 755 /usr/local/bin/pg-backup
51sudo chmod 700 /var/lock 2>/dev/null || true
52
53/usr/local/bin/pg-backup
54sudo -u postgres /usr/local/bin/pg-backup   # не запустится: пароль не передан
!Внимание

Порядок в бэкапе критичен: сначала во временный файл, потом проверка, потом mv на финальное имя. Если сначала писать в финальное имя, обрыв на

середине pg_dumpall оставит файл, который выглядит как валидный бэкап, пока не попадёт в ротацию. mv в пределах одной ФС атомарен — читатель никогда не увидит половину файла под финальным именем.

Подключение к systemd

Скрипты из лекции про процессы и systemd запускаются через юнит Type=oneshot + RemainAfterExit=yes. Юнит наследует set -euo pipefail не от скрипта, а от юнита — код возврата скрипта systemd читает сам. Проверь, что скрипт завершается осмысленным кодом:

bash
1sudo tee /etc/systemd/system/healthcheck.service > /dev/null <<'EOF'
2[Unit]
3Description=Проверка внешнего эндпоинта
4After=network-online.target
5
6[Service]
7Type=oneshot
8ExecStart=/usr/local/bin/healthcheck https://api.example.com/healthz 5
9
10[Install]
11WantedBy=multi-user.target
12EOF
13sudo systemctl daemon-reload
14sudo systemctl start healthcheck.service
15systemctl status healthcheck.service

Хорошие практики — сводка

  • set -euo pipefail + IFS=$'\n\t' в первых строках каждого скрипта.
  • Все переменные в кавычках: "$VAR", "${ARR[@]}".
  • readonly для констант, local для переменных функций.
  • Константы в верхнем регистре, переменные цикла — в нижнем.
  • Имена переменных: имя_функции_переменная (LOG_FILE_MAX_SIZE).
  • trap ... EXIT для уборки, с local rc=$? первым действием.
  • Логи на stdout — их перехватит systemd; файловые логи — только если нужно.
  • Все сообщения об ошибках в stderr: >&2.
  • Валидация всех $1 до того, как что-то сделано.
  • --fail и --max-time у каждого curl, --connect-timeout у каждого nc.
  • flock или mkdir-lock от двойного запуска.
  • Проверка результата (gzip -t, jq -e, sha256sum) до того, как файл признан успешным.
  • mktemp -d для временных файлов вместо предсказуемых /tmp/myscript.tmp.
  • Никаких rm -rf $VAR — только rm -rf -- "$DIR" с проверкой, что переменная не пустая.

Где это ломается

  • set -e без понимания, где он не работает. Условие в if не роняет скрипт — «проверка» молча всегда проходит. Пиши логику в if, страховку оставь -e.
  • rm -rf $DIR/ без кавычек. При пустой переменной — rm -rf /. Пиши rm -rf -- "${DIR:?}": : заставит скрипт упасть, а не удалить корень.
  • Конкатенация вместо проверки exit-кода. cmd; do_something — ошибка cmd проглочена. Пиши cmd || { log ERROR; exit 1; }. И $? не сразу: cmd; echo "ошибка: $?" после if уже покажет 0. Записывай rc=$? немедленно или используй cmd && rc=0 || rc=$?.
  • Cleanup теряет код возврата. Без local rc=$? в cleanup systemd увидит exited (status 0) вместо реального кода. Десятки минут ложной диагностики.
  • curl без --fail. HTTP 500 или 404 возвращают код 0. Скрипт разбирает тело и падает в jq с невнятным сообщением. Всегда --fail.
  • Бэкап без проверки. Архив, который не открывается, хуже отсутствующего: он занимает место и создаёт иллюзию безопасности. gzip -t обязателен.
  • Скрипт в crontab без проверки результата. Cron не скажет, что упало. Всегда заворачивай в юнит с journalctl или пиши в лог через >>. Кстати, chmod +x без shebang даёт Exec format error — юнит падает сразу, и это самый безобидный из диагностируемых случаев.
  • Разбор JSON через grep. Один лишний пробел в JSON от API — и скрипт решил, что данных нет. jq -r и только jq.
