Высокая доступность и балансировка

Как спроектировать отказоустойчивость без переплаты: уровни резервирования, L4/L7-балансировка, health-check, VRRP с keepalived и честный разговор про одну виртуальную машину

Модуль A закончен базовым Linux и сетью. Теперь поднимем уровень: как сделать так, чтобы система переживала отказ отдельного узла и не теряла пользователей. Это лекция про архитектурные решения, а не про команды — и именно она даёт тебе язык, на котором ты будешь говорить с руководством про деньги. Многие решения, которые выглядят как «усложнение», на самом дешевле альтернативы по простоям.

Что такое отказоустойчивость на языке бизнеса

Высокая доступность (High Availability) — способность системы продолжать работать при отказе одного или нескольких компонентов. Не «скорость», не «масштаб» — именно продолжать работать.

Инженеру эту тему переводят на язык руководства через три числа:

Термин Полное имя Простыми словами Пример для API-сервиса
RTO Recovery Time Objective «за сколько минут после аварии сервис должен снова работать» 15 минут
RPO Recovery Point Objective «сколько данных мы готовы потерять за последний инцидент» 5 минут
SLO Service Level Objective «какой процент запросов должен успешно обрабатываться за месяц» 99,9% (0,1% = ~43 минуты простоя в месяц)
⚠Важно

RPO определяется частотой бэкапов и репликации, а не темпой работы сервиса. Если бэкап раз в сутки — твой RPO равен 24 часам, и никакие «проверенные бэкапы» это не исправят. Если синхронная репликация — RPO равен нулю, но RTO и стоимость растут. Это первая развилка любого проектирования HA, и её нужно обсуждать с руководством до покупки железа.

Показатель Что означает Компромисс
RTO 5 минут автопереключение (VRRP, кластер) сложнее и дороже
RTO 4 часа ручной failover по runbook дёшево, но ночные инциденты
RPO 0 синхронная репликация задержка записи, шанс недоступности на отказ
RPO 1 час асинхронная репликация дешевле, теряем до часа

Три уровня резервирования

Не каждый сервис одинаково критичен, и резервировать всё одинаково — деньги в никуда.

Уровень Что резервируем Стоимость Пример
Узлы (hardware/VM) сама машина средняя две ВМ вместо одной, отдельный хост Proxmox
Сервисы приложение (несколько инстансов) низкая-средняя 3 инстанса API за nginx
Данные состояние: БД, объёмы высокая репликация PostgreSQL, сетевое хранилище
Уровень Даёт Не даёт
Только бэкапы восстановление после потери всего непрерывность во время восстановления
Бэкапы + репликация сохранность данных, меньше RPO автоматическое переключение
Репликация + балансировщик автоматический failover защита от падения всего кластера
Кластер в K8s / VCS самовосстановление, антиаффинити не спасает от отказа зоны/хоста целиком
iЗаметка

Порядок вложений всегда такой: сначала бэкапы с реально проверенным восстановлением, потом репликация, потом балансировщик, и только потом сложные кластеры. Балансировщик при одной ноде и отсутствии бэкапов — это дорогая косметика поверх пустоты.

Балансировка: L4 против L7

L4 (транспортный) L7 (прикладной)
Что понимает TCP/UDP-соединения, IP HTTP-заголовки, URL, cookies, Host
Алгоритмы round-robin, least-conn, ip_hash, weighted те же + по URL, по заголовку, по cookie
Может маршрутизировать /api → бэкенд-A, /web → B нет да
Снимает TLS нет (просто пробрасывает) да
Понимает WebSocket пробрасывает как есть да, апгрейд
Требования к бэкенду ноль обычный HTTP-сервер
Потеря на TLS-терминации нет есть (CPU балансировщика)
Примеры HAProxy, nginx stream, L4-балансировщики GCP/AWS nginx http, HAProxy http, Envoy, Traefik
✨Подсказка

Практическое правило: если бэкенды сами терминируют TLS (например, LLM-инференс за HTTPS, Kubernetes--ingress) — L4 балансировщик дешевле и прозрачнее. Если нужно маршрутизировать по URL, терминировать TLS один раз и не дублировать сертификаты на каждом узле — L7.

Алгоритмы

Алгоритм Как выбирает Когда применять Опасность
round-robin по кругу бэкенды равнозначны, сессий нет мёртвый бэкенд получает запросы
least_conn наименее загруженный по открытым соединениям запросы разной длительности медленное решение при коротких запросах
ip_hash хеш IP клиента → один бэкенд нужна корзина-сессия без sticky-cookie неравномерно при NAT у клиентов
least_time по времени отклика бэкенды разной мощности чужая метрика
sticky cookie NGINX добавляет cookie route сессии приложения балансировщик перестаёт быть умным при разных cookie

Health-check — без него балансировка вредна

Это самая частая причина, по которой «мы поставили балансировщик, и стало хуже». Балансировщик без health-check отправляет трафик в упавший бэкенд. Упавший бэкенд отвечает медленно или не отвечает, а балансировщик об этом не знает.

Что проверяем Что должно быть Параметры
Процесс жив TCP-порт отвечает быстрый, грубый
Приложение отвечает HTTP 200 на /healthz основной
Зависимости живы БД, внешний API отвечают дорогой, но честный
Параметр Значение по умолчанию Рекомендация
interval 10 с 5–10 с — баланс между реакцией и нагрузкой
timeout 1 с не больше interval
fails 3 2–3; меньше — ложные срабатывания
max_fails / fall (nginx) 1 / 10 с сколько раз подряд до признания мёртвым
max_fails=0 — выключает проверку полностью — не делай этого
⚡Осторожно

Health-check по / вместо /healthz — ошибка: если приложение отдаёт HTML и медленно (например, рендерит страницу), проверка будет таймаутиться, и балансировщик снимет живой бэкенд. Отдельный лёгкий /healthz, который не ходит в базу (или ходит, но с коротким таймаутом), — правильный выбор.

nginx
1upstream llm_api {
2    least_conn;
3
4    server 10.0.0.11:8000 max_fails=3 fail_timeout=10s;
5    server 10.0.0.12:8000 max_fails=3 fail_timeout=10s;
6    server 10.0.0.13:8000 backup;   # включается, только если основные мёртвы
7
8    # периодическая проверка
9    keepalive 32;
10}
11
12server {
13    listen 80;
14    location = /healthz {
15        access_log off;
16        return 200 "ok\n";
17        add_header Content-Type text/plain;
18    }
19    location / {
20        proxy_pass http://llm_api;
21        proxy_set_header Host              $host;
22        proxy_set_header X-Real-IP         $remote_addr;
23        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
24        proxy_set_header X-Forwarded-Proto $scheme;
25        proxy_next_upstream error timeout http_502 http_503;
26        proxy_next_upstream_timeout 10s;
27        proxy_connect_timeout 2s;
28    }
29}
yaml
1# HAProxy: проверка более гибкая (можно проверять содержимое ответа)
2frontend api_front
3    bind *:80
4    mode http
5    default_backend llm_api
6
7backend llm_api
8    mode http
9    balance leastconn
10    option httpchk GET /healthz
11    http-check expect status 200
12    server app1 10.0.0.11:8000 check inter 5s fall 3 rise 2
13    server app2 10.0.0.12:8000 check inter 5s fall 3 rise 2

proxy_next_upstream в nginx — то, что делает round-robin терпимым к падению одного бэкенда: если первый вернул ошибку/таймаут, nginx попробует следующий в том же запросе, и пользователь не заметит падения одного узла.

keepalived: плавающий VIP на двух нодах

Проблема, которую решает keepalived: у клиентов и других сервисов должен быть один стабильный адрес. Если у балансировщиков два IP и клиент «прибит» к одному из них, то падение этого узла = полная недоступность, пока не переключишь DNS (а это минуты из-за кэша).

VRRP (Virtual Router Redundancy Protocol) решает это: обе ноды (ноды с плавающим адресом) обмениваются служебными пакетами. Пока мастер жив — он обслуживает VIP. Когда мастер пропал — вторая нода через ~3 секунды берёт VIP на себя. Клиент ничего не замечает, адрес тот же.

bash
1sudo apt install keepalived
conf
1# /etc/keepalived/keepalived.conf
2vrrp_script check_nginx {
3    script "/usr/local/bin/check-backend.sh"
4    interval 2          # каждые 2 с
5    timeout 1
6    fall 2              # 2 неудачи подряд — считаем ноду мёртвой
7    rise 2
8    weight -20          # приоритет уменьшится, если бэкенд за этой нодой плох
9}
10
11vrrp_instance VI_LLM {
12    state MASTER               # MASTER на первой, BACKUP на второй
13    interface enp0s8            # интерфейс, на котором живёт VIP
14    virtual_router_id 51        # уникален в пределах L2-сегмента (совпадает на обеих нодах)
15    priority 100                # выше = лучший мастер
16    advert_int 1                # как часто объявлять себя мастером (сек)
17
18    authentication {
19        auth_type PASS
20        auth_pass devops-ha     # меняй, если будешь использовать
21    }
22
23    virtual_ipaddress {
24        10.0.0.50/24 dev enp0s8   # плавающий IP
25    }
26
27    unicast_src_ip 10.0.0.11     # явные unicast-адреса: работает и без multicast
28    unicast_peer {
29        10.0.0.12
30    }
31
32    track_script {
33        check_nginx
34    }
35
36    notify_master "/usr/local/bin/notify.sh MASTER"   # лог/оповещение о переключении
37    notify_backup "/usr/local/bin/notify.sh BACKUP"
38}
bash
1# /usr/local/bin/check-backend.sh — от чего именно зависит нода
2#!/usr/bin/env bash
3# Нода жива, только если локальный бэкенд отвечает
4curl -sf --max-time 2 http://127.0.0.1:8000/healthz > /dev/null
bash
1# Проверка и запуск
2sudo systemctl enable --now keepalived
3sudo journalctl -u keepalived -f            # видно переключения
4ip -br addr | grep 10.0.0.50                # где сейчас VIP
5
6# проверка: останови nginx на мастере
7sudo systemctl stop nginx
8sleep 5
9ip -br addr | grep 10.0.0.50                # VIP переехал на BACKUP-ноду
⚠Важно

keepalived — это ARP-механизм. Он отвечает на ARP-запрос «кто такой 10.0.0.50?». Это значит: (1) обе ноды должны быть в одном L2-сегменте; (2) он не работает через NAT и не работает в некоторых облаках — AWS/GCP, где у каждой ВМ свой ENI и ответ на чужой ARP нельзя подделать. Если ты в облаке или ноды за разными VLAN — бери облачный managed load balancer (AWS ALB, GCP L7 ILB) или DNS-балансировку с коротким TTL. keepalived — решение для bare-metal и для локального Proxmox-контура, и это ровно твой случай.

Конфигурация второй ноды

Вторая нода отличается тремя вещами: state BACKUP, меньший priority и unicast_peer с адресом первой. Всё остальное — идентично. virtual_router_id и virtual_ipaddress должны совпадать.

conf
1vrrp_instance VI_LLM {
2    state BACKUP
3    interface enp0s8
4    virtual_router_id 51
5    priority 90          # меньше, чем у мастера
6    advert_int 1
7    authentication { auth_type PASS  auth_pass devops-ha }
8    virtual_ipaddress { 10.0.0.50/24 dev enp0s8 }
9    unicast_src_ip 10.0.0.12
10    unicast_peer { 10.0.0.11 }
11    track_script { check_nginx }
12}
Симптом Причина Решение
VIP не появляется ни на одной ноде keepalived не запущен, ошибка в конфиге journalctl -u keepalived, keepalived --config-check
VIP мигает туда-сюда прерывистая сеть или health-check нестабилен увеличь fall, упрости проверку, проверь unicast
Клиенты видят VIP, но не отвечают ARP проходит, а nginx на VIP-ноде не слушает проверь, что state MASTER совпадает с тем, кто реально взял VIP
Работает в Proxmox, не работает на «боевом» хосте разные VLAN/L2 keepalived требует общий L2

DNS-балансировка и её минусы

Самый дешёвый «балансировщик» — несколько A-записей на одно имя. DNS-сервер отдаёт их по кругу (Round Robin DNS).

text
1api.example.com. IN A 10.0.0.11
2api.example.com. IN A 10.0.0.12
3api.example.com. IN A 10.0.0.13
Плюс Минус
ноль стоимости и ноль кода нет health-check — в выдачу попадают мёртвые IP
работает где угодно, в том числе в облаке клиент запомнил IP (кеш) и долбится в мёртвый
мгновенная «реакция» на изменение неравномерная нагрузка: часть клиентов на одном IP
клиенту не нужен DNS для failover TTL ограничивает скорость отката
⚡Осторожно

Round Robin DNS — не балансировщик, а раздача адресов. Проблема в том, что клиент (браузер, приложение, LLM-шлюз) один раз зарезолвил IP и держит его до истечения TTL. Если 11-й узел из 12 умер, те, кто на него попал, получат ошибку до истечения TTL — независимо от того, что DNS уже отдаёт хорошие адреса. Для критичных сервисов DNS RR не подходит; он годится для «разгрузить дешёвый CDN» и для некритичного статики.

Если нужен балансировщик в облаке и без единой точки отказа — бери управляемый: GCP Cloud Load Balancing, AWS ALB/NLB, Azure Load Balancer. Они дороже, но делают ровно то, что невозможно сделать на одной ВМ: переживают падение самой ноды балансировщика.

Антипаттерн: «всё в одной ВМ»

Самая частая архитектура новичка и самая дорогая по факту. Один Ubuntu в Proxmox, где крутится nginx, приложение, PostgreSQL, Redis, Grafana. Это не HA, это концентрация риска: отказ этого узла = полная остановка, а починить можно только перезагрузкой.

!Внимание

Первый шаг к исправлению — не HA-кластер, а контейнеризация: упаковать каждый сервис в свой образ (Docker) и начать поднимать их раздельно. Один контейнер = один процесс = один понятный docker logs. Само по себе это не даёт отказоустойчивости (контейнеры всё ещё живут на той же ВМ), но это минимальная цена за то, чтобы через неделю ты мог перенести один сервис на вторую ноду и не переписывать его заново.

Проблема Как выглядит
Одна точка отказа упала ВМ — упало всё
Ресурсный конфликт сборка/бэкап БД тормозит API
Невозможен деплой без простоя релиз приложения = остановка сервиса
Непонятно, что сломалось ОДНА машина = нельзя сравнить с «эталоном»

Правильная декомпозиция (минимум, который даёт реальный HA на две ВМ):

bash
1# Нода A (10.0.0.11): балансировщик + бэкенд приложения
2# Нода B (10.0.0.12): балансировщик + бэкенд приложения
3# ВМ AD (10.0.0.5): контроллер домена — НЕ трогаем, он singleton по своей природе
4# СУБД: либо PostgreSQL primary+replica (две отдельные ВМ),
5#       либо внешняя управляемая БД
6# Общие данные: сетевое хранилище (NFS) ТОЛЬКО для статики;
7#               для состояния — репликация БД, не общая ФС
Решение Когда подходит Стоимость
две ВМ + keepalived + общий БД LLM-шлюз без состояния 2 средние ВМ
три ВМ (2 app + 1 db с репликой) приложение с состоянием в БД 3 ВМ
K8s из 3+ нод масштабирование и сложный failover дороже, см. лекцию про Kubernetes
managed-сервисы БД/LB нет своих компетенций в HA по факту, но платно
✨Подсказка

Правило для решений по HA: каждая лишняя нода должна снижать RTO, а не просто добавлять железо. Если добавление второй ноды не уменьшает RTO (потому что нет дешёвого failover) — это не HA, а дорогое резервирование. Сначала определи целевые RTO/RPO, потом подбирай механизм под них.

Где это ломается

  • keepalived без track_script. Если он только следит за тем, что процесс keepalived жив, то при падении nginx VIP остаётся на мёртвой ноде, и failover не происходит. Health-check — обязательная часть.
  • Round Robin DNS назван «балансировкой». Клиенты держат IP из кэша, часть сидит на мёртвом узле до истечения TTL. Это не failover, это лотерея.
  • Health-check по /, который ходит в базу. База под нагрузкой — все бэкенды «мертвы», балансировщик отключает всех. Сбросили ноду, потому что endpoint был тяжёлым. Делай лёгкий /healthz.
  • Балансировщик в одной ВМ с приложением. Упал хост — упал и балансировщик. Балансировщик должен быть либо в паре (keepalived), либо внешний/managed.
  • Один server в upstream с max_fails=0. Это отключённая проверка, а балансировщик, который не проверяет, вредит больше, чем отсутствие балансировщика.
  • Сессии без sticky при нескольких инстансах. Пользователь логинится, его сессия живёт на app1, следующий запрос попадает на app2 — «вышел». Либо делай сессии stateless (cookie с JWT), либо sticky.
  • keepalived в облаке без managed LB. ARP-подмена не работает в AWS/GCP. Симптом: VIP назначен, но трафик идёт «в никуда». Нужен ALB/NLB.
  • backup-сервер в upstream без проверки. Nginx переключится на backup только если все основные отмечены недоступными. «Плохой» основной при этом исключается — но не сразу.

Чек-лист понимания

🛠 Практика
Собери схему HA из двух Ubuntu-ВМ в твоём Proxmox: общий VIP через keepalived, nginx или HAProxy как балансировщик с health-check, и проверь, что при остановке одного узла VIP переезжает, а трафик идёт только в живой бэкенд.
