Сеть — это единственная часть системы, где ты физически не можешь увидеть причину. Диск виден в df, процесс — в htop, а вот «пакет не дошёл» нужно доказывать. Практическая ценность этой лекции — алгоритм: когда у тебя Connection refused или «сайт не открывается», ты идёшь по фиксированной цепочке от своего интерфейса наружу и находишь, на каком шаге цепочка рвётся. Все примеры рассчитаны на твой контур: Proxmox-хост, Ubuntu-ВМ, Windows AD.

Четыре уровня вместо семи

Модель OSI из семи уровней — академическая. Инженеру достаточно понимать, на каком уровне живёт проблема, и в четырёх строках:

Уровень Что описывает Что чинишь этим уровнем Инструменты
Приложение HTTP, SSH, DNS, LDAP что говорит сервис curl, dig, openssl
Транспорт TCP, UDP, порты соединение не устанавливается ss, nc, tcpdump
Сеть IP-адреса, маршруты, шлюз «нет маршрута», «хост недоступен» ip, ping, traceroute
Канальный MAC, ARP, Ethernet не находится шлюз ip neigh, arp
✨Подсказка

Модель OSI всё ещё полезна, когда ты читаешь чужой разбор: «L3-проблема» — это маршрутизация, «L4-проблема» — это порт. Но тратить на неё час до начала диагностики — расточительство. Сначала ping, потом думай, где именно оборвалось.

Интерфейсы и адреса

В Linux имя интерфейса не предсказуемо (eth0, enp3s0, ens18 — в зависимости от того, как презентует гипервизор), поэтому всегда смотри список, а не предполагай.

bash
1ip -br addr                       # кратко: имя, адрес, up/down
2ip addr                           # подробно, с масками
3ip -br link                       # состояние портов
4ip route                          # таблица маршрутов: default через X dev Y
5ip neigh                          # ARP-кэш: кто на каком MAC
6nmcli dev status                  # статус через NetworkManager
Поле в ip addr Что означает
inet 10.0.0.15/24 адрес и маска: /24 = 255.255.255.0
inet6 fe80::... link-local IPv6, есть у всех интерфейсов
mtu 1500 максимальный размер пакета (см. ниже)
state UP / DOWN administratively up против фактического
ether aa:bb:cc:dd:ee:ff MAC-адрес

Частые сценарии. В твоём Proxmox Ubuntu обычно получает адрес по DHCP. Если адрес «пропал» после ребута — смотри, не забыт ли netplan:

bash
1sudo netplan get                       # текущая конфигурация
2ls /etc/netplan/
3sudo netplan apply                     # применить
4sudo netplan try                      # безопасно: откатит, если связь пропала
⚡Осторожно

netplan apply на удалённой ВМ с единственным интерфейсом и опечаткой в конфиге = потеря доступа по SSH. На сервере, куда ты не можешь подойти физически, используй только netplan try: он применяет временно и сам откатывает, если подтверждение не пришло вовремя.

MAC-адрес и ARP — зачем

MAC-адрес работает только внутри одного L2-сегмента (одной сети, одного VLAN). Когда ты пингуешь 10.0.0.1 (свой шлюз), ARP спрашивает «какой MAC у 10.0.0.1?» и кеширует ответ. Для адреса за пределами сети ARP уже не нужен — там работает шлюз по умолчанию.

bash
1ip neigh show                        # ARP-кэш: IP -> MAC -> состояние
2ping -c1 -W1 10.0.0.1
3ip neigh show 10.0.0.1

Состояние FAILED или INCOMPLETE означает, что ARP-ответ не пришёл: неверная подсеть, неправильная маска, или ARP отфильтрован. Это L2-проблема — ping не сработает, хотя сеть вроде бы «есть».

Маршруты и трассировка

Порядок действий: сначала проверь, что ты сам видишь сеть.

bash
1ip route get 10.20.30.40            # каким маршрутом пойдёт пакет к адресу
2ping -c 3 10.20.30.1               # шлюз
3ping -c 3 1.1.1.1                  # внешний адрес (ICMP может быть закрыт!)
4ping -c 3 google.com               # проверка DNS + внешней связности
5traceroute -n 10.20.30.40           # без DNS-резолвов, на hop'ах видны адреса
6tracepath 10.20.30.40               # то же, но без установки пакета
⚠Важно

ping на внешний адрес может не отвечать, и это не значит, что сети нет. Многие провайдеры и файрволы режут ICMP на границе. Проверяй связность портом: nc -zv 1.1.1.1 443 или curl -sS https://1.1.1.1. Ошибка ping: Destination Host Unreachable — вот это уже про маршрут.

Читать traceroute нужно уметь: * в начале — ICMP до первого хопа запрещён, это нормально. Если * появляется с середины и не проходит — вот она твоя точка обрыва. Узлы после точки обрыва тоже могут не отвечать, потому что им не на что ответить.

Порты: что где живёт

Номер порта — это число в заголовке транспортного уровня, 1–65535. «Сервис на порту 389» означает «TCP-соединение на порт 389 любого адреса».

Порт Протокол Сервис Комментарий для твоего контура
22 TCP SSH как ты сейчас подключаешься к Ubuntu
53 TCP/UDP DNS резолвится имена AD; не перекрывай
80 TCP HTTP nginx, Let's Encrypt HTTP-челлендж
88 TCP/UDP Kerberos AD: аутентификация в домене
123 UDP NTP рассинхрон времени ломает Kerberos и TLS
389 TCP LDAP AD: поиск в каталоге
443 TCP HTTPS самый ходовой
514 UDP Syslog если собираешь логи с ВМ
636 TCP LDAPS AD: LDAP поверх TLS
3306 TCP MySQL никогда не открывай в интернет
5432 TCP PostgreSQL
5672 TCP AMQP RabbitMQ
6379 TCP Redis
8000 TCP Proxmox VE веб-интерфейс у тебя один из этих портов
8006 TCP Proxmox VE API/SPICE
9100 TCP node_exporter метрики Prometheus
3000 TCP Grafana
9090 TCP Prometheus
9100–9150 TCP Percona/XtraDB Cluster
iЗаметка

Про AD запомни главное: порты 88, 389, 636, 53 должны быть открыты между рабочими станциями и DC, и между DC и контроллерами домена (для репликации — динамические RPC-порты). Если Ubuntu-сервер ходит в AD по имени, ему нужен DNS (53), а не «просто LDAP». Когда DNS не работает, ты получишь Temporary failure in name resolution, а не connection refused — и диагностика пойдёт не туда.

Кто слушает

bash
1ss -tulpn                              # все слушающие сокеты с PID и именем
2ss -tulpn 'sport = :443'               # фильтр по порту
3ss -tanp state established              # активные соединения
4ss -s                                   # короткая статистика
5sudo netstat -tulpn                    # если стоит net-tools, вывод привычнее
6sudo lsof -i -P -n | grep LISTEN       # альтернатива, медленнее на большом хосте
Флаг ss Что показывает
-t / -u TCP / UDP
-l только слушающие (LISTEN)
-p процесс и его PID (нужен root)
-n вместо имён — числовые адреса и порты
-a все сокеты, включая не слушающие
⚡Осторожно

Полезно помнить: 0.0.0.0:8080 — сервис слушает все интерфейсы, включая публичный. 127.0.0.1:8080 — только локально. Разница между этими двумя строками стоит одного инцидента безопасности. Для внешнего сервиса, который должен быть доступен только из локальной сети, привязывайся к адресу интерфейса, а не к 0.0.0.0.

Проверка конкретного порта

bash
1nc -zv 10.20.30.40 389       # TCP: успех = open, refused = порт закрыт
2nc -zvu 10.20.30.40 53       # UDP: unreliable для приложений, но для DNS сойдёт
3timeout 3 bash -c '</dev/tcp/10.20.30.40/636' && echo open   # без nc
Ответ nc Что это значит Что делать
succeeded / open порт открыт проблема выше по стеку (TLS, протокол)
Connection refused порт закрыт, RST вернулся сервис не слушает или файрвол REJECT
timed out пакеты теряются файрвол DROP или маршрут
No route to host нет маршрута проверь ip route

Этот треугольник (open / refused / timeout) — половина сетевой диагностики. refused говорит «маршрут есть, сервер ответил отрицательно». timeout говорит «пакет не дошёл или ответ не вернулся».

DNS: как резолвится имя

Когда ты пишешь curl https://ad.company.local, происходит:

  1. Из кэша (nscd/systemd-resolved) — если есть TTL, ответ мгновенный.
  2. /etc/hosts — проверяется первым, минуя DNS целиком.
  3. /etc/resolv.conf — адреса DNS-серверов, которые туда попали.
  4. Рекурсивный запрос корневому серверу → TLD → авторитативному.
  5. В твоём случае авторитативный сервер — твой Windows AD DC, если это company.local. Или корпоративный DNS. Или 8.8.8.8.
bash
1dig ad.company.local                # полный ответ с флагами
2dig +short ad.company.local         # только ответ, для скриптов
3dig @10.0.0.10 ad.company.local     # конкретный DNS-сервер
4dig ad.company.local A              # только A-записи
5dig ad.company.local @dc01.company.local
6dig +trace example.com              # путь резолва от корня, для отладки
7nslookup ad.company.local           # простой вариант
8host ad.company.local               # ещё проще
Флаг в ответе Значение
NOERROR успех
NXDOMAIN имени не существует
SERVFAIL сервер не смог ответить (часто — проблема с зоной)
REFUSED сервер не отвечает на запросы от тебя

/etc/hosts против resolv.conf

Файл Приоритет Что делает
/etc/hosts выше DNS статическое сопоставление, для внутренних имён
/etc/resolv.conf ниже список DNS-серверов и домен поиска
bash
1cat /etc/resolv.conf
2resolvectl status                  # systemd-resolved: реальная картина
3sudo resolvectl flush-caches       # сбросить кэш
4sudo resolvectl query ad.company.local
⚡Осторожно

/etc/resolv.conf часто перезаписывается NetworkManager или systemd-resolved при каждом переподключении. Правь netplan или /etc/systemd/resolved.conf, а не сам resolv.conf — иначе твои изменения исчезнут через час. Если нужно железобетонное сопоставление имён AD — это /etc/hosts или nsswitch.conf с mdns4_minimal/sss, но для нескольких десятков имён хостов /etc/hosts поддерживать вручную невозможно.

TTL, кэш и «почему старый сервер ещё живёт»

TTL (Time To Live) — сколько секунд DNS-ответ можно переиспользовать. По умолчанию 300–3600 секунд, но бывает и 86400.

Сценарий: ты переехал api.company.com со старого сервера на новый. Через минуту половина клиентов идёт на старый IP, потому что у них в кэше ответ с TTL 3600. Альтернативный сценарий хуже: забыл сменить A-запись — у клиентов в кэше старый адрес, они идут туда, там ничего, и ты не понимаешь, почему «у меня всё работает локально, а у пользователей нет».

⚠Важно

Перед сменой A-записи заранее снижай TTL до 60–300, и жди максимальный текущий TTL, чтобы все кэши протухли. Только потом меняй запись. Возврат TTL назад делай через сутки, а не сразу.

Порядок лечения: dig +short имя @8.8.8.8 (снаружи), dig +short имя (локально), разница = проблема в локальном DNS или в split-horizon; resolvectl flush-caches после правки; и проверка в нескольких местах — из дома, из контура, с телефона.

tcpdump: смотреть пакеты глазами

tcpdump — прибор, который превращает «не работает» в конкретное «запрос ушёл, ответа не было».

bash
1sudo tcpdump -i any -nn -c 20 'tcp port 389'          # первые 20 пакетов на 389
2sudo tcpdump -i any -nn 'host 10.20.30.40 and not port 22'   # к хосту, без ssh
3sudo tcpdump -i any -nn -A 'tcp port 80'              # ASCII-полезная нагрузка
4sudo tcpdump -i any -nn -w /tmp/cap.pcap              # запись в файл
Флаг Что делает
-i any все интерфейсы (иначе нужен конкретный: ip -br link)
-nn не резолвить ни имена, ни порты — числа, без задержек на DNS
-c N остановиться после N пакетов (без него tcpdump не завершится сам)
-A печатать содержимое пакетов текстом
-w сохранить в pcap для Wireshark

Три состояния TCP, которые объясняют всё

Когда ты делаешь nc -zv 10.20.30.40 389, в tcpdump ты увидишь одну строку:

Что видишь Что значит Причина
Flags [S] — SYN ушёл, ответа нет SYN-RECV: пакет пропал файрвол DROP, неверный маршрут, хост выключен
Flags [S.] ... [R] — SYN, потом RST RST: соединение отказано порт закрыт на хосте, ничего не слушает
Flags [S] ... [S.] ... [A] Handshake соединение установлено, проблема выше по стеку
bash
1# диагностика «LDAP не отвечает»:
2sudo tcpdump -i any -nn 'host 10.20.30.40 and tcp port 389'
3# в соседнем окне:
4nc -zv 10.20.30.40 389
Пакет Диагноз
SYN ушёл, ответа нет 10 секунд SYN-RECV: DROP на пути, ARP не проходит, хост мёртв
SYN → RST порт закрыт: systemctl status slapd, ss -tulpn | grep 389
SYN → SYN-ACK → RST на переговорах порт открыт, но сервис рвёт соединение: смотри его логи
SYN → SYN-ACK → ACK → данные → RST соединение прошло, рвёт приложение: TLS, аутентификация, таймаут
✨Подсказка

Если tcpdump показывает SYN-RECV и ты точно знаешь, что порт открыт на цели, — почти всегда виноват межсетевой экран: он отбрасывает пакет молча, без RST, и приложение не получает отказа, а просто ждёт. Проверяй ufw status verbose и nft list ruleset на каждом узле пути.

MTU: когда большие пакеты не проходят

MTU — максимальный размер IP-пакета. В твоём контуре это ещё и ping -M do: современный Linux по умолчанию фрагментирует большие пакеты, поэтому «у меня всё работает», а у клиента с VPN — нет.

bash
1ip link show dev eth0 | grep mtu
2ping -M do -s 1472 1.1.1.1     # 1472 + 20 (IP) + 8 (ICMP) = 1500
3ping -M do -s 1420 1.1.1.1     # 1420 + 28 = 1448, запас под VPN
4traceroute -M --mtu 10.20.30.40

Если ping -M do -s 1472 проходит, а -s 1473 — нет, MTU ровно 1500. Если -s 1472 не проходит, а -s 1420 проходит — у тебя на пути туннель с MTU 1448 (типично для WireGuard и IPSec).

Симптом Вероятная причина
SSH работает, но scp большого файла зависает MTU, ICMP блокируется
VPN-клиенты не открывают сайты, TCP-соединение есть MTU + блок ICMP «fragmentation needed»
curl зависает на больших ответах MTU

Hairpin NAT: проблема домашнего контура

Сценарий: у тебя домашний роутер, снаружи api.home.arpa смотрит на твой внешний IP. Внутренний ноутбук идёт на api.home.arpa, DNS отдаёт ему внешний адрес. Пакет уходит на роутер, тот пытается отправить его в ту же подсеть, откуда он пришёл, — и отбрасывает.

Отсюда: снаружи работает, изнутри не работает. Это и есть Hairpin NAT (он же NAT Loopback).

bash
1# диагноз: с сервера работает, с клиента — нет
2curl -v http://api.home.arpa/            # с ВМ
3curl -v --resolve api.home.arpa:80:192.168.1.50/ http://api.home.arpa/   # с клиента
Решение Как
Включить NAT loopback в роутере зависит от вендора, у OpenWrt — option nat_loopback 1
Split-horizon DNS внутренним отдавай 192.168.1.50, внешним — внешний IP
/etc/hosts на клиенте быстро, но не масштабируется
Проброс портов напрямую самый устойчивый для одного сервиса
iЗаметка

В учебной и тестовой среде Hairpin NAT лучше не «лечить» настройкой роутера, а обходить через внутренний DNS: на внутреннем сервере DNS отдаёт 192.168.1.50 для внутреннего имени, на публичном — внешний адрес. Это правильная архитектура, и она же решает задачу с TTL.

Порядок диагностики

Когда что-то не работает, иди по цепочке сверху вниз и не переходи к следующему шагу, пока текущий не даст ясный ответ.

# Проверка Команда Ответ «плохо» значит
1 свой интерфейс и адрес ip -br addr ты не в той сети / интерфейс down
2 шлюз ping -c2 <gw> L2: маска, ARP, кабель, VLAN
3 внешний адрес ping -c2 1.1.1.1, nc -zv 1.1.1.1 443 нет маршрута или всё режут
4 DNS dig +short имя /etc/resolv.conf, DNS-сервер, зона
5 конкретный хост ping, nc -zv хост порт маршрут или файрвол
6 конкретный порт nc -zv → ss -tulpn на цели сервис не слушает
7 что в пакетах tcpdump SYN-RECV = DROP, RST = закрыт
8 приложение curl -v, логи сервиса TLS, auth, таймаут, баг
⚠Важно

Каждая проверка должна давать однозначный ответ. «Похоже работает» в сетевой диагностике — это отсутствие результата. Если ты не можешь сказать, где именно цепочка оборвалась, ты не диагностируешь, а гадаешь — и тратишь время на проверку того, что заведомо работает.

✨Подсказка

Эту цепочку стоит загнать в скрипт с ненулевым кодом возврата на каждом шаге, иначе через полгода ты будешь вбивать восемь команд руками в три часа ночи. Как написать такой скрипт правильно — в лекции про Bash.

Где это ломается

  • «Всё пингуется, значит сеть в порядке». ICMP и TCP используют разные коды и разные правила фильтрации. Закрытый ICMP при полностью рабочем интернете — норма для части провайдеров. И наоборот: ping проверяет DNS и ICMP, nc — только порт. Ошибся в интерпретации — потратил час не на ту причину.
  • Кэш DNS после переезда. Адрес сменился, а у половины клиентов старый IP ещё в кэше. Признак: у тебя работает, у одного сотрудника — нет. Лечение: TTL, flush-caches, проверка снаружи через dig @8.8.8.8.
  • Правка /etc/resolv.conf руками. Перезаписывается NetworkManager. Правь netplan или resolved.conf.
  • Файрвол с REJECT вместо DROP. REJECT отвечает RST, и ты видишь «connection refused», хотя правило задумано как «тихо запретить». Наружу — DROP, внутри — REJECT (быстрее отладка).
  • Сервис слушает только 127.0.0.1. curl localhost работает, снаружи connection refused. Проверяй ss -tulpn, а не «работает/не работает».
  • MTU при включённом WireGuard/IPSec. Забывают при диагностике, потому что ping фрагментирует и скрывает проблему. Проверяй ping -M do -s.
  • Время «поехало». Разошедшиеся часы дают две несовместимые картины мира: TLS-сертификаты кажутся невалидными, Kerberos отказывает в аутентификации, логи не складываются в одну историю. Проверь timedatectl на обеих сторонах. Похожий класс проблем — смена MAC-адреса после пересоздания интерфейса в Proxmox, когда в ARP-кэше остался старый: лечится ip neigh flush.
