Эта лекция — ключевая практическая работа всего DevOps-трека. До неё ты умел собирать метрики в теории: Prometheus и PromQL, дашборды, логи и алерты. После неё у тебя есть работающая система наблюдаемости на твоём контуре: Proxmox-гипервизор, Ubuntu-серверы и Windows AD DC. Материал рассчитан на два-три вечера, потому что часть шагов требует перезагрузки и прав администратора домена. Если у тебя нет доступа к Proxmox прямо сейчас — читай и собирай конфиги в стенде: все примеры воспроизводимы.

Слои наблюдаемости

Главная ошибка при мониторинге виртуализированного контура — смотреть только внутрь гостя. Тогда классическая фраза «AD тормозит» превращается в гадание: то ли контроллер домена перегружен, то ли гипервизор отбирает у него CPU, то ли деградировал диск под виртуальной машиной, то ли умер вентилятор и всё встало на thermal throttling.

Правильный подход — три независимых слоя. Каждый отвечает на свой вопрос, и у каждого своя точка отказа:

Слой Источник Что видим Чего не видим
Железо SMART (smartctl/smartd), ipmitool, lm-sensors состояние дисков, температуру, вентиляторы, отказ PSU что происходит на уровне ОС
Гипервизор API Proxmox, node_exporter на хосте, QEMU-статистика steal/iowait, память и swap хоста, загрузка ВМ, balloon что происходит внутри гостя
Гость node_exporter в Ubuntu, windows_exporter в Windows процессы, диски, службы, доменные метрики перегрузку со стороны гипервизора

Порядок диагностики всегда сверху вниз. Если pve01 показывает 25% steal — тебе не нужно подниматься внутрь ВМ вообще, проблема в гипервизоре. Если steal 0, а внутри гостя iowait 60% — иди в гость. Именно поэтому метрики гипервизора собираются первыми, а не последними.

⚠Важно

Внешние метрики ВМ из API Proxmox (cpu, mem, netin, diskread) показывают нагрузку, которую гипервизор наблюдает снаружи, а не то, что происходит внутри. Внутри ВМ может висеть процесс с дедлоком, который снаружи выглядит как «ВМ спит, CPU 0%». Это дыра, которую закрывает только агент в госте — и частично qemu-guest-agent.

Слой 1: железо — SMART и температура

Что можно получить без специального софта

В Proxmox smartmontools уже стоит, и вместе с ним идёт демон smartd, который умеет сам рассылать отчёты. Сначала посмотри, что уже есть, и не переустанавливай:

bash
1smartctl -a /dev/sda | head -40
2smartctl --scan-open
3systemctl status smartd --no-pager
4cat /etc/smartd.conf

Дефолтный /etc/smartd.conf в Proxmox близок к этому — сканирование атрибутов раз в сутки плюс длинный self-test раз в неделю:

bash
1# /etc/smartd.conf — после правки
2DEVICESCAN -a -o on -S on \
3  -s (S/../.././02|L/../../6/03) \
4  -m exec /usr/local/bin/smartd-notify.sh \
5  -M exec /usr/local/bin/smartd-notify.sh

Зачем -m exec вместо почты: отчёт попадает не в почтовый ящик, а в файл, который превращается в метрику. Настоящая почта на root@ в типовом контуре либо не настроена, либо ушла в спам и через полгода про неё забыли — это самая частая причина, по которой про диск узнают после его смерти.

bash
1# /usr/local/bin/smartd-notify.sh — вызывается smartd, $1 = устройство, stdin = отчёт
2#!/bin/bash
3OUTDIR=/var/lib/node_exporter/textfile_collector
4mkdir -p "$OUTDIR"
5DEV=$(echo "$1" | tr '/' '_')
6cat >> "$OUTDIR/smartd_${DEV}.prom" <<EOF
7# HELP node_smart_report Устройство: $1
8# TYPE node_smart_report gauge
9EOF
10grep -E '^[A-Za-z_0-9]+:' >> "$OUTDIR/smartd_${DEV}.prom"
11exit 0
bash
1chmod +x /usr/local/bin/smartd-notify.sh
2install -d -m 0755 /var/lib/node_exporter/textfile_collector
3systemctl restart smartd
iЗаметка

Имена метрик, которые textfile-коллектор создаст из этого файла, зависят от версии node_exporter. Не угадывай их — посмотри: curl -s localhost:9100/metrics | grep -i smart. Дальше пиши алерты по фактическим именам. Разница между поколениями экспортёров — источник половины «не работает, хотя должно».

Альтернатива: smartctl_exporter

Если не хочется писать скрипты — есть готовый prometheus-community/smartctl_exporter. Он поднимает HTTP-эндпоинт и сам забирает отчёты из smartd, который при этом настроен на -m exec в его адрес:

bash
1docker run -d --name smartctl-exporter --restart unless-stopped \
2  -v /dev:/dev:ro \
3  -p 9102:9102 \
4  prom/smartctl-exporter:0.9.0 --verbose
yaml
1# фрагмент prometheus.yml
2  - job_name: smart
3    static_configs:
4      - targets: ['pve01:9102']
5    relabel_configs:
6      - source_labels: [device]
7        target_label: device

Чего node_exporter не умеет принципиально

node_exporter — софтовый сборщик. Он не имеет права читать регистры материнской платы и контроллера вентиляторов. Он физически не видит:

  • температуру материнской платы и VRM;
  • скорость вентиляторов;
  • состояние вентиляторов блока питания;
  • температуру SSD (кроме тех значений, что есть в SMART-атрибутах).

Вариантов два, и это надо проговорить честно:

Вариант Когда применять Что получишь
ipmi_exporter сервер с BMC/IPMI (материнка с IPMI, серверная платформа, IPMI-карта) температуры всех датчиков, вентиляторы, статус PSU, температура процессора
lm-sensors + textfile белая материнка без BMC температура CPU (coretemp), иногда вентиляторы — если драйвер их отдаёт
Ничего офисный ПК без датчиков в драйвере только температура диска из SMART-атрибута 194/190
bash
1apt install lm-sensors
2sensors-detect --auto
3sensors

Кривая sensors-textfile.sh превращает вывод в метрики. Парсер здесь намеренно простой: вывод sensors на разных платах разный, и ты всё равно будешь его дописывать под свою материнку.

bash
1cat >/usr/local/bin/sensors-textfile.sh <<'EOF'
2#!/bin/bash
3OUT=/var/lib/node_exporter/textfile_collector/sensors.prom
4install -d -m 0755 "$(dirname "$OUT")"
5TMP="${OUT}.$$"
6{
7  echo "# HELP hw_sensor_temperature_celsius Температура датчиков, C"
8  echo "# TYPE hw_sensor_temperature_celsius gauge"
9  echo "# HELP hw_sensor_fan_rpm Скорость вентиляторов, RPM"
10  echo "# TYPE hw_sensor_fan_rpm gauge"
11  sensors 2>/dev/null | awk '
12    /^[A-Za-z0-9_-]+:/ { chip=$0; sub(/:.*/,"",chip); next }
13    /°C/ {
14      key=$1; val=$3; gsub(/°C/,"",val); gsub(/\(.*/,"",val);
15      if (chip != "" && chip != "Adapter" && val != "")
16        printf "hw_sensor_temperature_celsius{chip=\"%s\",sensor=\"%s\"} %s\n", chip, key, val;
17    }
18    /RPM/ {
19      key=$1; val=$3; gsub(/RPM/,"",val); gsub(/\(.*/,"",val);
20      if (chip != "" && val != "")
21        printf "hw_sensor_fan_rpm{chip=\"%s\",fan=\"%s\"} %s\n", chip, key, val;
22    }'
23} > "$TMP"
24mv "$TMP" "$OUT"
25EOF
26chmod +x /usr/local/bin/sensors-textfile.sh
27echo '*/5 * * * * root /usr/local/bin/sensors-textfile.sh' >/etc/cron.d/sensors-textfile
28/usr/local/bin/sensors-textfile.sh && cat /var/lib/node_exporter/textfile_collector/sensors.prom
!Внимание

Если датчиков нет — это не проблема скрипта. Софтом температуру материнской платы не получить. Правильные варианты: IPMI-карта, BMC-модуль или внешний USB-датчик температуры. Дальше мониторинг дисков по SMART и всё. Не выдумывай «нормальную температуру» из ничего — это ложное чувство защищённости.

Слой 2: гипервизор — метрики Proxmox без агента

Штатный список внешних metric-серверов Proxmox — Graphite, InfluxDB и OpenTelemetry. Prometheus в этом списке нет, плагин для Prometheus тоже. Вариантов было два: ставить агента-экспортёра на сам гипервизор либо разговаривать с API напрямую. Второй путь дешевле и надёжнее — API Proxmox сам по себе очень стабильная вещь.

Токен с минимальными правами

Ключевая идея: пользователь без пароля, роль только на чтение, доступ выдан напрямую токену, а не через пользователя. Именно прямое назначение позволяет отключить privilege separation и не дать токену унаследовать права сверх нужных.

bash
1# 1. пользователь без пароля и без прав
2pveum user add pveexporter@pve
3
4# 2. минимальная роль: только аудит узлов, ВМ и хранилищ
5pveum role add ProxmoxAudit -privs "Sys.Audit,VM.Audit,Datastore.Audit"
6
7# 3. роль пользователю
8pveum aclmod / -user pveexporter@pve -role ProxmoxAudit
9
10# 4. роль напрямую токену — обязательное условие для --privsep 0
11pveum aclmod / -user pveexporter@pve -token pvexport -role ProxmoxAudit
12
13# 5. сам токен
14pveum user token add pveexporter@pve pvexport --privsep 0

Команда выведет две строки: token ID: pveexporter@pve!pvexport и value: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx. Их нужно сохранить сейчас — значение второй раз не показывается.

bash
1install -d -m 0700 /etc/pve-exporter
2echo 'pveexporter@pve!pvexport=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx' \
3  >/etc/pve-exporter/token
4chmod 0600 /etc/pve-exporter/token
5
6curl -s -H "Authorization: PVEAPIToken=$(cat /etc/pve-exporter/token)" \
7  https://$(hostname -f):8006/api2/json/nodes/$(hostname)/status | head -c 200

Что конкретно отдают нужные эндпоинты — это и есть карта твоей наблюдаемости гипервизора:

Эндпоинт Ключевые поля Что это значит
/nodes/{node}/status cpu (доля 0–1), wait (доля iowait), idle, loadavg[3], memory{total,used}, swap, rootfs{total,used,avail}, ksm{shared}, uptime, cpuinfo{cpus} состояние самого хоста
/nodes/{node}/qemu список ВМ: vmid, name, status инвентарь
/nodes/{node}/qemu/{vmid}/status/current cpu (доля), mem, maxmem, balloon, netin, netout (байт/с), diskread, diskwrite (байт/с), uptime, status, ha нагрузка конкретной ВМ снаружи
/nodes/{node}/disks/list health, model, serial, size, wearout (NVMe), smart (если включён smartplug) износ дисков, если есть smartplug
⚡Осторожно

Поля cpu, mem в /status/current — это среднее с прошлого опроса (примерно за минуту), а не моментальное значение. Не пытайся строить по ним панель с шагом 15 секунд: получишь ступеньки и решишь, что метрика «сглаживается». Для высокочастотных вещей внутри ВМ нужен агент в госте, для внешнего вида — node_exporter на самом гипервизоре.

Экспортёр на стандартной библиотеке

Дальше — весь экспортёр целиком. Никаких pip-зависимостей: Python 3 на Proxmox уже есть, файл кладётся рядом с системными, запускается из systemd. Метрики отдаёт в стандартном текстовом формате, который понимает любой Prometheus.

python
1#!/usr/bin/env python3
2# /opt/pve-exporter/pve_exporter.py
3# Метрики Proxmox VE API -> Prometheus. Только стандартная библиотека.
4import json, os, re, socket, ssl, urllib.request
5from http.server import BaseHTTPRequestHandler, HTTPServer
6
7HOST    = os.environ.get("PVE_HOST", socket.getfqdn())
8BIND    = os.environ.get("PVE_BIND", "0.0.0.0")
9PORT    = int(os.environ.get("PVE_PORT", "9103"))
10NODE    = os.environ.get("PVE_NODE", socket.gethostname())
11CA      = os.environ.get("PVE_CA", "/etc/pve/pve-root-ca.pem")
12VERIFY  = os.environ.get("PVE_VERIFY", "1") == "1"
13TOKEN   = open("/etc/pve-exporter/token").read().strip()
14
15ctx = ssl.create_default_context(cafile=CA if os.path.exists(CA) else None)
16if not VERIFY:
17    ctx.check_hostname = False
18    ctx.verify_mode = ssl.CERT_NONE
19
20dirty = re.compile(r"[^a-zA-Z0-9_]")
21
22
23def esc(v):
24    return dirty.sub("_", str(v))
25
26
27def api(path):
28    req = urllib.request.Request("https://%s:8006%s" % (HOST, path))
29    req.add_header("Authorization", "PVEAPIToken=" + TOKEN)
30    with urllib.request.urlopen(req, context=ctx, timeout=10) as r:
31        return json.load(r)["data"]
32
33
34def node_metrics(node):
35    d = api("/api2/json/nodes/%s/status" % node)
36    lb = 'node="%s"' % esc(node)
37    load = d.get("loadavg") or [0, 0, 0]
38    out = [
39        "pve_api_up 1",
40        "pve_cpu_ratio{%s} %.4f" % (lb, float(d.get("cpu") or 0)),
41        "pve_iowait_ratio{%s} %.4f" % (lb, float(d.get("wait") or 0)),
42        "pve_load1{%s} %.3f" % (lb, float(load[0])),
43        "pve_load5{%s} %.3f" % (lb, float(load[1])),
44        "pve_load15{%s} %.3f" % (lb, float(load[2])),
45        "pve_uptime_seconds{%s} %d" % (lb, int(d.get("uptime") or 0)),
46    ]
47    for part in ("memory", "swap", "rootfs"):
48        blk = d.get(part) or {}
49        for key in ("total", "used", "avail"):
50            if key in blk:
51                out.append("pve_%s_%s_bytes{%s} %d" % (part, key, lb, int(blk[key])))
52    if d.get("ksm"):
53        out.append('pve_ksm_shared_bytes{%s} %d' % (lb, int(d["ksm"].get("shared") or 0)))
54    if d.get("cpuinfo"):
55        out.append('pve_cpu_cores{%s} %d' % (lb, int(d["cpuinfo"].get("cpus") or 1)))
56    return out
57
58
59def vm_metrics(node):
60    out = []
61    for vm in api("/api2/json/nodes/%s/qemu" % node):
62        st = api("/api2/json/nodes/%s/qemu/%s/status/current" % (node, vm["vmid"]))
63        lb = 'id="%s",name="%s",node="%s"' % (
64            vm["vmid"], esc(st.get("name") or "vm"), esc(node))
65        mem = int(st.get("mem") or 0)
66        maxmem = int(st.get("maxmem") or 0)
67        out += [
68            'pve_qemu_info{%s,status="%s"} 1' % (lb, esc(st.get("status") or "")),
69            "pve_qemu_up{%s} %d" % (lb, 1 if st.get("status") == "running" else 0),
70            "pve_qemu_cpu_ratio{%s} %.4f" % (lb, float(st.get("cpu") or 0)),
71            "pve_qemu_mem_bytes{%s} %d" % (lb, mem),
72            "pve_qemu_maxmem_bytes{%s} %d" % (lb, maxmem),
73            "pve_qemu_mem_used_ratio{%s} %.4f" % (lb, mem / maxmem if maxmem else 0.0),
74            "pve_qemu_balloon_bytes{%s} %d" % (lb, int(st.get("balloon") or 0)),
75            "pve_qemu_netin_bytes_per_second{%s} %.1f" % (lb, float(st.get("netin") or 0)),
76            "pve_qemu_netout_bytes_per_second{%s} %.1f" % (lb, float(st.get("netout") or 0)),
77            "pve_qemu_diskread_bytes_per_second{%s} %.1f" % (lb, float(st.get("diskread") or 0)),
78            "pve_qemu_diskwrite_bytes_per_second{%s} %.1f" % (lb, float(st.get("diskwrite") or 0)),
79            "pve_qemu_uptime_seconds{%s} %d" % (lb, int(st.get("uptime") or 0)),
80        ]
81    return out
82
83
84def disk_metrics(node):
85    out = []
86    try:
87        disks = api("/api2/json/nodes/%s/disks/list" % node)
88    except Exception:
89        return out
90    for dsk in disks:
91        dev = esc(dsk.get("devpath"))
92        lb = 'node="%s",dev="%s"' % (esc(node), dev)
93        out.append('pve_disk_info{%s,health="%s"} 1' % (lb, esc(dsk.get("health") or "UNKNOWN")))
94        out.append("pve_disk_size_bytes{%s} %d" % (lb, int(dsk.get("size") or 0)))
95        if dsk.get("wearout") is not None:
96            out.append("pve_disk_wear_percent{%s} %.1f" % (lb, float(dsk["wearout"])))
97        for attr, val in re.findall(r"(\w+)_value=([0-9]+)", dsk.get("smart") or ""):
98            out.append('pve_disk_smart_attr{%s,attr="%s"} %s' % (lb, attr.lower(), val))
99    return out
100
101
102class Handler(BaseHTTPRequestHandler):
103    def do_GET(self):
104        if self.path.split("?")[0] not in ("/", "/metrics", "/healthz"):
105            self.send_error(404)
106            return
107        try:
108            body = "\n".join(node_metrics(NODE) + vm_metrics(NODE) + disk_metrics(NODE))
109            code = 200
110        except Exception as exc:
111            body = "pve_api_up 0\n# %s\n" % str(exc).replace("\n", " ")
112            code = 503
113        raw = body.encode("utf-8")
114        self.send_response(code)
115        self.send_header("Content-Type", "text/plain; version=0.0.4; charset=utf-8")
116        self.send_header("Content-Length", str(len(raw)))
117        self.end_headers()
118        self.wfile.write(raw)
119
120    def log_message(self, *args):
121        pass
122
123
124if __name__ == "__main__":
125    HTTPServer((BIND, PORT), Handler).serve_forever()

Тонкости, на которых обычно спотыкаются:

  • PVE_HOST должен совпадать с SAN в сертификате узла. Если не совпадает — поставь PVE_VERIFY=0 и запри доступ файрволом, но не оставляй открытым в сеть.
  • pve_disk_smart_attr заполняется только если в UI узла у диска включён smartplug: Datacenter → Storage → Disks → выбрать диск → Use for SMART check.
  • Эндпоинт раскрывает инвентарь ВМ. Держи 9103 на управляющей сети и не пробрасывай наружу.

node_exporter на самом гипервизоре

API Proxmox не отдаёт steal time — а это главный индикатор «хост отбирает ресурсы у гостя». Steal есть только в /proc/stat, то есть в node_exporter. Ставь его на самом хосте, иначе половина самой полезной метрики гипервизора теряется.

3systemctl enable --now prometheus-node-exporter
4curl -s localhost:9100/metrics | grep -E '^node_cpu_seconds_total|^node_scrape_collector'

Слой 3b: гость Windows AD DC

Почему это самая сложная часть

Контроллер домена — не «ещё одна Windows-машина». У него есть состояние, которое нельзя пересоздать из образа: база NTDS.dit, SYSVOL, учётные записи, SID-ы, учётные записи компьютеров. Залил такой ВМ из дешёвого бэкапа «месячной давности» — получил рассинхрон репликации, отсутствующих пользователей и объяснения пользователям, почему их «уволили» полгода назад.

Отсюда два правила, которые надо принять до установки экспортёра:

  1. У всех метрик windows_exporter английские имена даже в русской локали Windows. Ищи windows_ad_..., а не windows_домен_.... Авторинговые коды событий при этом остаются цифрами — 4625 это 4625 в любой локали.
  2. Установка требует прав администратора домена, а не локального администратора.

Дыра, которую надо закрыть: рост NTDS.dit

Это причина №1 тормозов Active Directory на маленьком контуре, и ни один штатный коллектор её не показывает. Механизм такой: при загрузке DC весь NTDS.dit (а он может быть 20–40 ГБ) читается в память. Пока он влезает в кэш — всё быстро. Перестал влезать — каждая операция логина идёт на диск, и AD «встаёт колом», хотя CPU и сеть в норме.

Что сделать: раз в 5–15 минут измерять размер файла и класть его в textfile-коллектор. Заодно посчитаем события, которые о нём же говорят.

powershell
1# C:\ProgramData\ad-textfile\ad-custom.ps1
2# Кладёт кастомные метрики AD в textfile-коллектор windows_exporter.
3$ErrorActionPreference = 'Stop'
4$OutDir  = 'C:\Program Files\windows_exporter\textfile_collector'
5$OutFile = Join-Path $OutDir 'ad_custom.prom'
6$TmpFile = "$OutFile.tmp"
7
8$L = New-Object 'System.Collections.Generic.List[string]'
9
10$L.Add('# HELP ad_ntds_dit_size_bytes Размер базы данных Active Directory, байты')
11$L.Add('# TYPE ad_ntds_dit_size_bytes gauge')
12$Dit = Get-Item 'C:\Windows\NTDS\ntds.dit' -ErrorAction SilentlyContinue
13if ($Dit) {
14    $L.Add(('ad_ntds_dit_size_bytes {0}' -f $Dit.Length))
15    $L.Add('# HELP ad_ntds_dit_age_hours Часов с последней записи в NTDS.dit')
16    $L.Add('# TYPE ad_ntds_dit_age_hours gauge')
17    $L.Add(('ad_ntds_dit_age_hours {0}' -f ([math]::Round(((Get-Date) - $Dit.LastWriteTime).TotalHours, 2))))
18} else {
19    $L.Add('ad_ntds_dit_size_bytes 0')
20}
21
22$L.Add('# HELP ad_sysvol_free_bytes Свободно на системном томе, байты')
23$L.Add('# TYPE ad_sysvol_free_bytes gauge')
24$Vol = Get-CimInstance Win32_LogicalDisk -Filter "DeviceID='C:'"
25$L.Add(('ad_sysvol_free_bytes {0}' -f $Vol.FreeSpace))
26
27$L.Add('# HELP ad_directory_service_events События журнала Directory Service за 15 минут')
28$L.Add('# TYPE ad_directory_service_events gauge')
29foreach ($Code in 4000, 4013, 4028, 4615) {
30    $N = @(Get-WinEvent -FilterHashtable @{
31        LogName = 'Directory Service'; Id = $Code
32        StartTime = (Get-Date).AddMinutes(-15)
33    } -ErrorAction SilentlyContinue).Count
34    $L.Add(('ad_directory_service_events{{code="{0}"}} {1}' -f $Code, $N))
35}
36
37$L.Add('# HELP ad_failed_logon_total Неуспешные входы за 15 минут')
38$L.Add('# TYPE ad_failed_logon_total gauge')
39$Fail = @(Get-WinEvent -FilterHashtable @{
40    LogName = 'Security'; Id = 4625
41    StartTime = (Get-Date).AddMinutes(-15)
42} -ErrorAction SilentlyContinue).Count
43$L.Add(('ad_failed_logon_total {0}' -f $Fail))
44
45$L.Add('# HELP ad_textfile_script_up Скрипт отработал успешно')
46$L.Add('# TYPE ad_textfile_script_up gauge')
47$L.Add('ad_textfile_script_up 1')
48
49[System.IO.File]::WriteAllLines($TmpFile, $L)
50Move-Item -Force $TmpFile $OutFile

Значения кодов: 4000 и 4013 — внутренняя ошибка службы каталога, чаще всего проблемы с базой или нехватка памяти при выделении; 4028 — общая внутренняя ошибка БД NTDS, обычно следствие рассинхрона времени или рассогласования CN; 4615 — контроллер домена не смог получить доступ к журналу безопасности; 4625 — неуспешный вход (нужен ещё аудит «Logon/Logoff», на контроллере домена он включён по умолчанию). Если хочешь читать описания на своей локали — wevtutil gp Directory Service /lf:true | findstr /C:"0x" /C:4000.

Задание по расписанию. Короткий вариант — одна команда:

powershell
1New-Item -ItemType Directory -Force -Path C:\ProgramData\ad-textfile | Out-Null
2# положи сюда ad-custom.ps1, затем:
3schtasks /Create /SC MINUTE /MO 10 /TN "ad-custom-textfile" /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\ad-textfile\ad-custom.ps1" /RU SYSTEM /RL HIGHEST /F

Через Register-ScheduledTask — правильнее: задача видна в планировщике, у неё есть история и нормальная обработка ошибок.

2  -Argument '-NoProfile -ExecutionPolicy Bypass -File C:\ProgramData\ad-textfile\ad-custom.ps1'

qemu-guest-agent и почему он нужен

Без агента гипервизор не получает от гостя ничего, кроме данных о нагрузке. Отсюда — две конкретные дыры:

  1. Неточная память. Если у гостя не включён balloon, mem в API покажет всю выделенную память, даже если гость использует треть. Для планирования ёмкости это враньё.
  2. Нет согласованных бэкапов и заморозки. Агент умеет fsfreeze/fsthaw — без него снапшот делается «на живую», и об этом ещё будет лекция о бэкапах, но уже в следующей.
bash
1apt install qemu-guest-agent
2systemctl enable --now qemu-guest-agent
3echo -e "nameserver 10.10.10.1\nsearch corp.example.com" >/etc/resolv.conf.d/ad.conf

В Windows госте — qemu-ga.msi из ISO Proxmox, служба QEMU Guest Agent. После установки в веб-интерфейсе ВМ появится IP из гостя, а в конфигурации можно включить Balloon Device.

⚠Важно

Агент не заменяет метрики изнутри гостя. Он закрывает технический пробел между хостом и ВМ. Реальные метрики процессов, дисков и домена даёт только экспортёр, запущенный внутри гостя. Одно без другого — дыра.

Проверка под нагрузкой: не жди аварии

Алерт, который ни разу не срабатывал, не работает. Проверь каждый сценарий дешёвым способом — подставь значения через expr:

promql
1# имитация недоступного узла
2up{job="pve-node"} == 0
3
4# имитация диска, заполненного на 92%
5(node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.15
6
7# реальная проверка порога по подставленному значению
8vector(1) > bool 0.5

Алгоритм: выбрал правило → выставил метрику в заведомо плохое значение через временный textfile-файл или pushgateway → убедился, что алерт перешёл в firing → убрал. Пока это не сделано, правило считается гипотезой.

ВМ «зависла», но CPU 0% гипервизор pve_qemu_cpu_ratio, pve_qemu_up steal на хосте, состояние ВМ в UI
Всё тормозит на одном хосте гипервизор pve_load15 / pve_cpu_cores steal, iowait, pve_memory_*
Растёт задержка чтения на хосте железо smartctl -a, pve_disk_info NVMe wearout, замена кабеля/диска
Гость медленный, хост спокоен гость node_load15 внутри гостя node_filesystem_*, node_memory_MemAvailable_bytes
Метрики ВМ пустые, а ВМ работает гость не установлен экспортёр файрвол, сетевая доступность, авторизация
Резкий рост 4625 AD ad_failed_logon_total аудит: откуда идут попытки, 4624 рядом

Где это ломается

  • Токен без --privsep 0 и без ACL на сам токен. Команда pveum user token add падает с невнятной ошибкой про права. Причина — не выданные токену права, а не пользователю.
  • Установил smartd, но не настроил -m exec. По умолчанию отчёты уходят письмом на root, которого никто не читает. Диск с деградирующими секторами живёт месяцами.
  • Упёрся в лимит API. Экспортёр делает по запросу на каждую ВМ плюс список. На 200 ВМ это 200+ запросов каждые 15 секунд, и pveproxy начинает отдавать 429. Смягчается увеличением scrape_interval для этого job и кэшированием инвентаря.
  • Текст на русском в имени метрики. Значения лейблов и подписи в .prom должны быть в UTF-8; проверенные имена — латиницей. Метрика с пробелом в имени молча не импортируется.
  • Windows-метрики ищутся на русском. Имена всегда английские, независимо от локали. Час на потерянный поиск.
  • Пароль Prometheus к windows_exporter в конфиге открытым текстом. Держи password_file — этот файл попадает в бэкап и в Git, а пароль из него — в историю.
  • Алерт на avg вместо max_over_time. Короткие пики, которые ломают вход в домен на минуту, никогда не пересекут порог по среднему.
  • Скрипт NTDS.dit запускается, но файл не появляется. Проверь три вещи: каталог textfile_collector существует, задача реально отработала (Get-ScheduledTaskInfo), имя файла заканчивается на .prom. Плюс — запись должна идти во временный файл с последующим Move-Item, иначе коллектор периодически читает наполовину записанный файл.
