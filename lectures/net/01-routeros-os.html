Ты умеешь администрировать Linux: там есть файловая система, процессы, сервисы, права. Через неделю так же спокойно ты должен чувствовать себя на MikroTik — а он устроен иначе. Здесь нет файловой системы в привычном смысле (хотя /file есть), нет пользователей ОС, нет файлов конфигурации, которые можно открыть и отредактировать. Есть одно дерево, в котором каждая настройка — узел. Если ты поймёшь это дерево, ты поймёшь всё остальное: почему add возвращает *1A, почему конфиг без @ и = нечитаем, почему /export — это пригодный для Git файл, а WinBox — нет.

RouterOS — это не «коробка с интерфейсом»

RouterOS — монолитная операционная система, на которой работают и домашний hEX, и промышленный CCR2004, и облачный CHR. Разница только в процессоре, количестве портов и скорости. Ядро одно, конфигурационное дерево одно, синтаксис команд один. Это хорошо: научился на одном устройстве — работаешь на всех.

Второе отличие от Linux — RouterOS не сохраняет конфиг в файле. То, что ты видишь в WinBox, в CLI или в REST API, — это представление состояния операционной системы в памяти. Файл появляется только когда ты его сам создаёшь: /export file=... или /system backup save. Отсюда следует важное: «сохранить настройки» в терминах Linux не существует. Каждая команда add/set уже применена. Это меняет психологию: ты не редактируешь файл и не применяешь его, ты вызываешь системный вызов.

⚠Важно

Из этого следует главное практическое свойство RouterOS: конфигурация — дерево с идентификаторами, а значит, она сериализуется в текст, diff-ится в Git, применяется скриптом и проверяется автоматически. Ровно этим мы и займёмся в лекции про автоматизацию.

Всё — путь в дереве

Каждая настройка RouterOS живёт по пути. /ip — корень подсистемы IP, /ip address — список адресов, /ip firewall filter — список правил межсетевого экрана, /system package update — менеджер обновлений.

routeros
1/ip                          # подсистема IP
2/ip address                  # список адресов на интерфейсах
3/ip address print            # что назначено сейчас
4/ip route                    # таблица маршрутизации
5/ip route print detail       # с подробностями
6/ip firewall filter          # правила фильтрации пакетов
7/ip firewall nat             # правила трансляции адресов
8/ip dns                      # DNS-резолвер
9/ip dhcp-server              # DHCP-серверы
10/system                     # системные настройки
11/system clock                # время и NTP
12/system log                  # журнал
13/system script               # пользовательские скрипты
14/system scheduler            # расписание
15/interface                   # список интерфейсов
16/interface bridge            # мосты (программные коммутаторы)
17/interface wireguard        # WireGuard-туннели
18/interface list              # именованные группы интерфейсов

В CLI ты работаешь в текущей точке дерева. Команда cd /ip firewall перемещает тебя туда навсегда — пока не напишешь cd /. Это единственное состояние сессии, которое нужно держать в голове, и источник половины ошибок вида «почему оно не нашло /interface».

routeros
1/interface print             # сокращение: без ведущего слэша = cd + print
2print                        # повторить для текущего узла
3..                           # вверх на уровень
4cd /ip/firewall/filter       # перейти в узел
5/                            # в корень, короткий путь
✨Подсказка

Синтаксис ? работает прямо в терминале и экономит часы жизни. Набери /ip address add и нажми Enter — RouterOS подскажет допустимые параметры и их значения. Набери /ip и ? — получишь весь список поддеревьев. Это работает одинаково в v6 и v7, и это честнее, чем гуглить по памяти.

Три способа управления

Способ Как это устроено Где применять Ограничение
WinBox родной GUI, свой бинарный протокол поверх TCP первичная настройка, незнакомое железо, спасение после сброса ручная работа, изменения не попадают в Git, не масштабируется на 20 устройств
CLI через SSH ssh admin@10.10.10.1, дальше команды вида /ip address add ... всё повторяемое, скрипты, пайплайны, Ansible синтаксис запоминается плохо, ошибка применяется сразу
REST API HTTP(S) поверх /rest/..., ответы в JSON массовые изменения, мониторинг, автоматизация из Python нужна отдельная учётка и TLS, ошибка в скрипте тиражируется на все устройства
ssh ... /ip address print одна команда, вывод в stdout, без интерактива быстрые скрипты, Ansible command нельзя вводить несколько команд подряд
⚠Важно

У CLI есть одно свойство, которого нет в WinBox: Safe Mode. В WinBox изменения применяются, но пока ты не подтвердил — они откатываются. В CLI такого нет вообще. Это главная причина, по которой опасные правки делают через WinBox или через скрипт с /system backup save первым шагом.

Первый вход: пользователь, SSH, сервисы

Заводская настройка MikroTik — худшая практика безопасности в сетях: включены telnet, ftp, www (80), api (8728) без TLS, у пользователя admin без пароля, WinBox доступен всем, кто знает адрес. Для лаборатории это удобно, для офиса — это открытая дверь, которая стоит каждому, кто просканирует твою подсеть.

Порядок действий: сначала создай пользователя и проверь, что можешь войти им, потом закрывай всё остальное. Иначе потеряешь доступ.

routeros
1# 1. Посмотреть, что вообще включено
2/ip service print
3
4# 2. Создать пользователя (group=full — полный доступ, available-from — только с этой сети)
5/user add name=netops group=full available-from=192.168.88.0/24 password="ДлинныйПароль2026!"
6
7# 3. Только теперь гасим небезопасное
8/ip service set telnet disabled=yes
9/ip service set ftp disabled=yes
10/ip service set www disabled=yes
11/ip service set api disabled=yes
12/ip service set api-ssl disabled=yes
13
14# 4. SSH — оставляем, но ограничиваем адресом и уводим со стандартного порта
15/ip service set ssh available-from=192.168.88.0/24 port=2222
16
17# 5. Проверить, кто сейчас залогинен
18/user active print

Порты по умолчанию: ftp 21, ssh 22, telnet 23, www 80, www-ssl 443, winbox 8291, api 8728, api-ssl 8729. Точный набор строк в выводе /ip service отличается между версиями и меняется, если ты сам что-то переставил, поэтому сверяйся с print, а не с памятью.

⚠Важно

available-from (раньше называлось address) не прячет порт. Клиент с чужого адреса по-прежнему устанавливает TCP-соединение, и роутер сразу закрывает его, не обслуживая. Порт остаётся видимым в скане, то есть «скрытая» служба всё равно привлекает внимание. Чтобы закрыть её по-настоящему, нужен ещё и drop в цепочке input. Это две независимые вещи: список адресов — про удобство, файрвол — про безопасность.

Службы в /ip/service удалить нельзя — только отключить или перенастроить. Это недостаток, из-за которого, например, «лишний» www приходится гасить, а не удалять.

⚡Осторожно

Меняй port у ssh после того, как убедился, что вход на новом порту работает. Последовательность «сменил порт — потерял доступ» встречается на каждом втором устройстве, обычно у того, которое стоит в другой комнате. И всегда держи открытой сессию WinBox как страховку: перезагрузку по кнопке питания не отменить конфигом.

Для мониторинга и автоматизации заведи отдельного пользователя с минимальными правами. Набор встроенных групп (full, read, write, test, rest-api, api, password, policy, sensitive, winbox, ssh, ftp, romon) и список политик отличаются между v6 и v7 — посмотри /user group print на своём устройстве перед тем, как создавать свою группу.

routeros
1/user group print
2/user add name=monitor group=read available-from=192.168.88.0/24 password="..."
3/ip service set www-ssl available-from=192.168.88.0/24

Идентификаторы: почему print даёт такую кашу

Команда add возвращает номер позиции во внутреннем дереве. Так выглядит вывод в терминале:

routeros
1[admin@MikroTik] > /ip address add address=192.168.88.1/24 interface=ether2
2[admin@MikroTik] > /ip address print
3Flags: X - disabled, I - invalid, D - dynamic
4 0   address            network         interface
5 1   192.168.88.1/24    192.168.88.0    ether2

Ноль и единица слева — это не номера строк, а внутренние идентификаторы (в выводе с подробностями они видны как .id=*A, *B в v6 и как .id=*1A, *2B в v7; звёздочка означает «ещё не сохранено»). Они не меняются при удалении соседа и не совпадают с порядком отображения. Это ровно то, из-за чего /export выглядит нечитаемо: он печатает add interface=ether2 address=192.168.88.1/24 network=192.168.88.0, а человек хочет видеть «192.168.88.1 на ether2».

routeros
1/ip address print detail        # вот это читаемо: с флагами и свойствами
2/ip address print as-value      # список значений — пригодится в скриптах
3/interface print detail where name~"ether"
4/system history print           # что ты вообще запускал в этой сессии
✨Подсказка

print без detail показывает только не-default значения. Отсюда бывает неприятный сюрприз: ты создал адрес, а в print его «нет». Он есть, просто все свойства совпадают с умолчаниями либо вывод урезан по колонкам. Прежде чем сомневаться — набери print detail.

Если тебе нужен «человеческий» дамп состояния, готовый для Git и для сравнения двух устройств, — это /export. Разбору /export, /import и бэкапам посвящена лекция про автоматизацию, а пока запомни одну вещь: конфигурацию MikroTik умеют хранить в Git, и это меняет всё.

Интерфейсы и адреса

Интерфейсы в RouterOS бывают физическими (ether1, ether2) и логическими (bridge1, vlan10, wireguard0, pppoe-wan, lo). Логический интерфейс существует, пока существует объект в соответствующем поддереве: удалил /interface bridge — исчез и интерфейс, и все адреса на нём. Трёхуровневая модель (порты → мост → VLAN) разобрана отдельно в следующей лекции, здесь — только базовая грамматика.

routeros
1/interface print
2/interface ethernet print
3/interface ethernet monitor ether2 once      # link, скорость, rx/tx за интервал
4
5/ip address
6add address=10.10.10.1/24 interface=ether1 network=10.10.10.0 comment="WAN"
7add address=10.10.20.1/24 interface=bridge1 network=10.10.20.0 comment="LAN"
8add address=10.10.99.1/32 interface=lo comment="loopback для управления и VRF"
9
10/interface print detail where name="ether1"
11/ip address print detail

Параметр network= добавляет запись в таблицу маршрутов для твоей подсети. Без него RouterOS всё равно создаст подключённый маршрут при назначении адреса, но с параметром это видно в конфиге и в таблице маршрутов явно. /32 на lo — приём, который позволяет иметь «собственный» адрес, не привязанный к физическому порту: на него вешают routing-mark-правила, под него делают политики и NAT. Это дешёвый аналог VRF — настоящий VRF в RouterOS тоже есть (/ip route add vrf-interface=...), но для большинства задач lo-адреса достаточно.

Статические маршруты

routeros
1/ip route print
2/ip route add dst-address=0.0.0.0/0 gateway=203.0.113.1 distance=1 comment="ISP-1"
3/ip route add dst-address=0.0.0.0/0 gateway=198.51.100.1 distance=10 comment="ISP-2"
4/ip route add dst-address=10.10.99.0/24 gateway=10.10.20.1 distance=1 comment="к ДМЗ"
5/ip route check-gateway=ping dst-address=0.0.0.0/0

Порядок выбора маршрута в RouterOS: сначала побеждает самая длинная маска. При одинаковой маске сравнивается таблица маршрутизации (routing-table), потом distance, потом scope/target-scope. Маршруты с одинаковыми параметрами балансируются (ECMP) по потокам. Практический вывод: если «маршрут есть, а трафик идёт не туда» — сначала проверь, нет ли более специфичного маршрута, и только потом думай про приоритет.

Политика маршрутизации: routing-mark

Когда один и тот же набор адресов должен уходить в разные интерфейсы (резервный канал, отдельный провайдер для гостей, трафик к партнёрскому туннелю), заводи отдельную таблицу маршрутизации, правило, которое в неё отправляет трафик, и маршрут внутри.

routeros
1/routing table
2add name=to_backup fib comment="резервный канал"
3
4/routing rule
5add src-address=10.10.30.0/24 action=lookup-only-in-table routing-table=to_backup
6
7/ip route
8add dst-address=0.0.0.0/0 gateway=198.51.100.1 distance=1 routing-table=to_backup
9
10# Проверка
11/routing table print
12/ip route print where routing-table=to_backup

Альтернатива — метка в межсетевом экране: /ip firewall mangle add chain=prerouting routing-mark=to_backup, а маршрут с таким же routing-mark. Работает, но помечает пакет раньше и затрагивает больше всего трафика; для «одной подсети в другой канал» /routing rule понятнее.

routing-mark и routing-table — самая частая причина фразы «маршрут есть, но интернет пропал после изменений». Пакет уходит не туда, куда ты смотришь в /ip route print, потому что он попал в другую таблицу. Проверяется одной командой: /ip route print where routing-table=to_backup.

NAT: masquerade — это не src-nat

NAT в RouterOS живёт в /ip firewall nat и состоит из двух цепочек. srcnat обрабатывается на выходе пакета, dstnat — на входе, до маршрутизации.

routeros
1/interface list
2add name=WAN
3add name=LAN
4
5/interface list member
6add list=WAN interface=ether1
7add list=WAN interface=pppoe-wan
8
9/ip firewall nat
10add action=masquerade chain=srcnat out-interface-list=WAN
11add action=dst-nat chain=dstnat protocol=tcp dst-port=8443 in-interface-list=WAN \
12    to-addresses=10.10.20.10 to-ports=8443 comment="reverse proxy на nginx"
Что Как работает Когда применять
action=masquerade адрес берётся у интерфейса на выходе в момент обработки пакета WAN с динамическим адресом, PPPoE, несколько WAN
action=src-nat to-addresses=... адрес фиксирован в правиле статический публичный IP, предсказуемый вид пакетов снаружи
action=dst-nat перенаправление входящего порта внутрь публикация сервиса в интернет
action=redirect загнать трафик на сам роутер DNS, прокси, «умный» выход через самого себя

masquerade и src-nat решают одну задачу, но не идентичны:

  • Состояние. src-nat не зависит от состояния интерфейса: адрес зашит в правило. masquerade пересчитывает маску при каждом изменении адреса, поэтому работает с PPPoE.
  • Proxy ARP. src-nat (и dst-nat) может создавать ARP-запись для транслируемого адреса — и это используется, когда провайдер пробрасывает на тебя IP-блок и ждёт ответа по ARP на эти адреса. masquerade не создаёт ARP-записей ни для чего, кроме собственных адресов роутера. Если у тебя именно такая схема («провайдер дал /29 и велел отвечать на ARP») — masquerade не сработает, нужен src-nat с диапазоном.
  • Производительность. Разница на слабом железе при десятках тысяч соединений измерима, но не является главным аргументом: главный — предсказуемость.
⚡Осторожно

dst-nat без «обратного пути» даёт классический Hairpin NAT: снаружи сервис виден, изнутри — нет, потому что пакет от клиента к твоему же внешнему адресу уходит на роутер и там же отбрасывается. Разбор этого случая — в лекции про сетевую диагностику.

Межсетевой экран: три цепочки и порядок правил

В RouterOS ровно три цепочки. input — пакеты, адресованные самому роутеру. forward — пакеты, идущие через роутер (от клиента наружу или наоборот). output — пакеты, порождённые самим роутером (пинги, обновления, скрипты).

Три свойства, которые ломают всё новичкам:

  1. Правила проверяются сверху вниз, первое совпадение выигрывает. Порядок строк значит всё.
  2. Политики по умолчанию нет. Если ни одно правило не совпало, пакет идёт дальше и в конце принимается. Поэтому финальный drop — не паранойя, а гигиена: без него ты полагаешься на то, что сегодня в цепочке нет случайного accept.
  3. Нет отдельного правила «тот, кто не подошёл под предыдущие, отваливается». Такой приём (iif ! -oif), как в iptables, в RouterOS не работает.
routeros
1/ip firewall filter
2add chain=input action=accept connection-state=established,related comment="быстрый путь обратно"
3add chain=input action=drop connection-state=invalid comment="битые пакеты"
4add chain=input action=accept protocol=icmp comment="ping и traceroute"
5add chain=input action=accept in-interface=bridge1 src-address=10.10.10.0/24 comment="управление"
6add chain=input action=drop in-interface=ether1 comment="всё остальное с WAN"
7
8add chain=forward action=fasttrack-connection connection-state=established,related \
9    comment="разгрузка на аппаратный обработчик, где поддерживается"
10add chain=forward action=accept connection-state=established,related
11add chain=forward action=drop connection-state=invalid
12add chain=forward action=accept connection-state=new out-interface-list=WAN
13add chain=forward action=drop connection-state=new in-interface-list=WAN comment="initiator из интернета"
!Внимание

Строка accept in-interface=bridge1 src-address=10.10.10.0/24 обязана идти выше drop in-interface=ether1. Поменяй их местами — и ты потеряешь доступ к устройству. Это причина №1 среди всех обращений вида «включил firewall и всё сломалось». Вторая по частоте — включение fasttrack до того, как настроены правила: он пропускает пакеты мимо части проверок и мимо очередей, и в mangle ты потом не увидишь свой трафик.

fasttrack-connection ускоряет установленные соединения на аппаратном уровне, но исключает их из дальнейшей обработки в mangle и из очередей. Если тебе нужен QoS, connection-mark или подсчёт по маршрутам — сначала настрой это, и только потом включай fasttrack. В RouterOS 7 у правила fasttrack-connection есть дополнительный параметр hw-offload=yes, который переносит разгрузку на переключающий чип; на части моделей он не поддерживается, и проверять надо только через счётчики байтов и /interface bridge port print, а не по наличию строки в конфиге.

✨Подсказка

Безопасный способ отлаживать правила — добавить счётчики и смотреть, что набралось. Ниже про это отдельно; сначала доведи правила до логической полноты без drop, проверь работоспособность, и только потом закрывай.

Счётчики — главный диагностический приём

RouterOS ведёт счётчики пакетов и байт на каждом правиле. Это самый быстрый способ понять, какое правило срабатывает и где обрывается путь.

routeros
1/ip firewall filter print stats
2/ip firewall filter print stats where bytes>0          # только те, что что-то видели
3/ip firewall filter print stats where chain=input
4/ip firewall filter reset-counters                    # обнулить и смотреть на дельту
5/ip firewall connection print                         # текущие сессии и их state
6/ip firewall filter monitor                           # счётчики в реальном времени

Рабочий приём: обнули счётчики, попроси пользователя нажать «обновить страницу», посмотри print stats — строка с ненулевым счётчиком и есть та, которая отрезала трафик. Без этого приёма диагностика превращается в угадывание.

Ещё быстрее — встроенный сниффер прямо в CLI. Он показывает, что именно проходит через цепочку, вместе с содержимым пакета:

routeros
1/ip firewall filter add chain=forward action=log prefix="DROP " log=yes \
2    protocol=tcp dst-port=443 disabled=yes
3/ip packet sniffer set file-name=capture.pcap interface=ether1
4/ip packet sniffer start

Встроенные инструменты и обновление

routeros
1/tool ping 1.1.1.1 count=4                          # или просто /ping 1.1.1.1 count=4
2/tool ping 10.10.10.1 count=4 routing-mark=to_backup
3/tool traceroute 10.10.20.50 count=1
4/tool bandwidth-test address=10.10.10.5
5/tool mac-server                                      # кто отвечает на этот MAC
6/interface bridge monitor bridge1 once
7/ip arp print
8/log print where topics~"firewall"
9/log print where message~"pppoe"

Обновление и откат — разные вещи, и их регулярно путают.

routeros
1/system package update set channel=stable
2/system package update info                           # что доступно
3/system package update install
4/system routerboard upgrade check-for-updates once
5/system routerboard upgrade                           # прошивка устройства, не пакетов

/system package update обновляет пакеты ОС (такие как wireguard, ppp), а /system routerboard upgrade — саму прошивку платы. Для багфиксов безопасности нужны оба.

⚠Важно

Обновляйся. Не как ритуал, а по конкретной причине: в RouterOS была волна эксплуатируемых уязвимостей — например, CVE-2023-30799 («FancyRD»), wormable RCE, закрытый патчами в конкретных ветках, и CVE-2018-14847, обходившая WinBox через обход пути. Патчи не выкатывались всем одинаково, поэтому «у меня последняя стабильная» — не аргумент. Смотри список advisory MikroTik и обновляйся на версию, которая его закрывает. Откат прошивки по сети — отдельная процедура с downgrade через консоль и восстановлением через reset-configuration, не рассчитывай на неё.

Откат, который реально спасает, делается до изменений:

routeros
1/system backup save name=before-change encryption=aes password="..."
2/system backup print
3/file print
4/system reset-configuration no-defaults=yes skip-backup=yes   # ядерная кнопка

/system backup save кладёт бинарный файл на само устройство. Он бесполезен, если устройство перестало грузиться, и он не содержит приватных ключей в открытом виде. Рабочий контур бэкапов — выгружать /export и /system backup save наружу по расписанию; разбор этого — в лекции про автоматизацию.

Где это ломается

  • «После enable всё пропало». Самая частая причина — правило drop для WAN, поставленное выше правила для локальной сети. Второй по частоте — смена порта SSH без проверки. Третий — fasttrack, включённый до того, как выстроены правила.
  • print не показывает только что созданный объект. print без detail отсекает default-значения. Проверяй print detail или /export, и не делай выводов о том, что настройка не применилась.
  • masquerade вместо src-nat, когда провайдер требует proxy ARP. Маскарадин не создаёт ARP-записей, и внешние адреса остаются «немыми».
  • Правило на удалённую сеть оказалось короче, чем локальная. Маршрут 10.10.20.0/24 через туннель проиграет подключённому маршруту /24 — и не проиграет, а просто не будет выбран: сначала всегда выигрывает самая длинная маска. Прежде чем добавлять маршрут, посмотри /ip route print where dst-address in 10.10.0.0/16 — есть ли уже подходящий.
  • Маршрут есть, трафик идёт не туда. Проверяй routing-mark и routing-table, а не только /ip route print без фильтров.
  • /export без show-defaults «теряет» настройки. Он опускает всё, что совпадает с умолчанием, и не содержит runtime-состояния: динамических маршрутов, DHCP-аренд, активных сессий. Для «полного снимка» есть /system backup save.
  • Закрыли api, а автоматизация отвалилась. Если ты закрыл api-ssl заранее, до того как настроил сертификат и учётку, REST API недоступен. Порядок: сначала учётка и сертификат, потом отключение старого.
  • Забыли про related. Правило accept connection-state=established,related в цепочке input — обязательное. Без related не заработают FTP в пассивном режиме и часть VPN-протоколов, которые выглядят как отдельный исходящий поток.
  • Закрыли ICMP целиком. accept protocol=icmp нужен не для красоты: без него ломается работа traceroute, PMTU-обнаружение и часть NAT-механизмов.

Чек-лист понимания

🛠 Практика
Возьми тестовый MikroTik (подойдёт бесплатный CHR — Cloud Hosted Router) или второе устройство в контуре: закрой telnet/ftp/www, создай пользователя с доступом только из адреса 10.10.10.0/24, настрой WAN с masquerade и базовый input-фильтр, проверь счётчики через /ip firewall filter print stats и сделай /system backup save перед любыми дальнейшими экспериментами.
