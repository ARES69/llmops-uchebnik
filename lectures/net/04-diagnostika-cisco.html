Это самая практичная лекция модуля. Три предыдущие дали тебе настройку, безопасность и отказоустойчивость — но настройка проверяется не «правильностью конфига», а тем, что сеть не ломается в неподходящий момент. Всё, что изучалось в DevOps-треке про диагностику Linux, здесь работает один в один, только терминал другой. Разница одна: в Linux ты спрашиваешь ip -br addr, а здесь — show ip interface brief, и ответ у них одинаковый.

Методология: идти по уровням и не перепрыгивать

Диагностика сети — это бинарный поиск: ты либо локализовал проблему на уровне, либо ещё не локализовал. Каждый шаг обязан дать однозначный ответ: работает этот уровень или нет. Не можешь сказать — значит не проверил.

Уровень Вопрос Команда Ответ «плохо»
1. Физика порт поднят, ошибок нет? show ip interface brief, show interfaces status down, или administratively down
1. Физика есть ли ошибки на счётчиках? show interfaces Gi1/0/10 CRC, runts, giants, input errors
2. Канал порт в правильном VLAN? trunk на месте? show vlan brief, show interfaces switchport не тот VLAN, VLAN не в trunk
2. Канал канал EtherChannel собрался? show etherchannel summary s, а не P
3. Сеть ARP резолвится? show ip arp Incomplete, пусто
3. Сеть маршрут есть и верен? show ip route, show ip route <адрес> нет маршрута, уходит не туда
4. Связность пингуется? ping, traceroute 100% loss
5. Конфиг что на самом деле настроено? show run | section <интерфейс> не то, что ты думал
6. Ресурсы не забит ли CPU? show processes cpu sorted процесс на 90%+
6. Ресурсы что было в логах? show logging событие в момент жалобы
7. Пакеты что реально идёт по проводу? SPAN + tcpdump/Wireshark пакетов нет или они не те
⚠Важно

Не перепрыгивай уровни. Очень частая ошибка — начать с ping и traceroute, когда на интерфейсе 40 000 CRC. Пинг не пройдёт всегда, и ты потратишь час на «маршрутизацию», хотя дело в кабеле, который пережат дверью.

Уровень 1: состояние портов

bash
1show ip interface brief
2# Interface              IP-Address      OK? Method Status                Protocol
3# GigabitEthernet1/0/1   unassigned      YES NVRAM  administratively down down
4# GigabitEthernet1/0/10  unassigned      YES NVRAM  up                    up
5# Vlan99                 10.10.99.2      YES NVRAM  up                    up

Колонки Status и Protocol читаются так:

Status Что значит
up линк есть, интерфейс administratively up
administratively down выключен вручную командой shutdown. Это не «обрыв кабеля»
down линка нет: кабель, порт на той стороне, оптический модуль
err-disabled выключен политикой: bpduguard, port-security violation, storm-control

Разница между administratively down и down критична. Первое — ты (или кто-то) выключил порт командой. Второе — физика. Частая история: «коммутатор не видит компьютер», а порт administratively down — кто-то месяц назад убрал из эксплуатации и забыл.

Подробная сводка по портам — быстрее, чем ip interface brief, когда надо посмотреть сразу все:

bash
1show interfaces status
2# Port      Name               Status       Vlan       Duplex  Speed  Type
3# Gi1/0/1   user-anna          connected    10           a-full  a-1000 10/100/1000BaseTX
4# Gi1/0/16  UNUSED             disabled     1            a-full  a-1000 10/100/1000BaseTX

Колонка Name — это description. Именно поэтому он был не «для галочки»: при диагностике ты по этой таблице за секунду видишь, какой порт к кому относится, без открытия конфига.

Уровень 1: счётчики ошибок

Это главный признак проблемы с кабелем, оптикой или наводками на линии. Именно здесь находится ответ на вопрос «почему сеть тормозит, а всё вроде живо».

bash
1show interfaces GigabitEthernet1/0/10 | include errors|CRC|runts|giants
2# 5 minute input rate 8500000 bits/sec, 1000 packets/sec
3# 0 input errors, 0 CRC, 0 frame, 0 overrun, 0 ignored
4# 0 packets output, 0 collisions, 0 interface restarts

Читай этот блок построчно — каждое число ниже означает конкретную вещь:

Счётчик Что означает Вероятная причина
CRC контрольная сумма не сошлась кабель, разъём, наводки, оптика, заземление
input errors сумма всех ошибок на входе смотри детализацию ниже
runts кадры короче минимума (менее 64 байт) дуплекс-mismatch, неисправный NIC
giants кадры длиннее максимума неверный MTU, jumbo-фреймы на обычном порту
frame неверная длина или CRC физика, битые пары
collision столкновения кадров дуплекс-mismatch (на оптике бывают всегда 0)
overrun не успевает обработать, кадр отброшен перегрузка процессора, слишком малый буфер
no buffer закончился входной буфер перегрузка канала, uplink медленнее потока
ignored отброшено без счётчика переполнения перегрузка
✨Подсказка

Счётчики накапливаются с момента последней перезагрузки или последнего clear counters. «Были ошибки когда-то» и «ошибки идут прямо сейчас» — разные вещи. Чтобы отличить: посмотри show version | include uptime, запиши текущие значения, подожди 10–15 минут и посмотри снова. Если счётчик растёт — проблема активная. Если стоит — она была, возможно при монтаже.

Точечный сброс счётчиков (clear counters или clear counters interface Gi1/0/10) обнуляет их на интерфейсе. Пользуйся этим осознанно: сбросил — потерял историю, которая могла объяснять вчерашнюю жалобу.

Скорость и дуплекс

bash
1show interfaces GigabitEthernet1/0/10 | include speed|duplex
2# Full-duplex, 1000Mb/s, media type is 10/100/1000BaseTX

Расхождение скорости/дуплекса между двумя концами — классическая причина «интернет медленный, но пингуется». Один порт настроен на 100 half, другой на 100 full: кадры начинают сталкиваться, collision растёт, TCP уходит в переповторные передачи, скорость падает в разы, а порт при этом up/up и дублекс по show interfaces status выглядит нормально.

Ситуация Что делать
оба порта гигабитные автосогласование (autoneg) нормально
порт 100 Мбит, ручной speed/duplex оба конца должны быть ручными и одинаковыми
один autoneg, один ручной на 100 работать не будет — autoneg не увидит фиксированное значение
gigabit + ручной speed избыточно: 1000BASE-T всегда full duplex

show interfaces status покажет a-full a-1000 (a = autonegotiated) или full 100 (жёстко). Если на одном конце a-, а на другом без a- — вот оно.

iЗаметка

Auto-MDIX на портах GigabitEthernet есть почти везде: коммутатор сам определит, что воткнут кроссовый (cross-over) патч, и развернёт пары. На 10/100 портах Auto-MDIX бывает только на части моделей. Если гигабитный порт не поднимается — попробуй заменить патч на прямой (один конец — RJ45 «компьютерный»). Старые модели без Auto-MDIX требуют именно прямого кабеля.

Уровень 2: VLAN, порты и trunk

bash
1show vlan brief
2# VLAN Name                             Status    Ports
3# ---- -------------------------------- --------- -------------------------------
4# 1    default                          active    Gi1/0/24
5# 10   USERS                            active    Gi1/0/1, Gi1/0/2
6# 20   SERVERS                          active    Gi1/0/9
7# 99   MGMT                             active

Колонка Ports — это активные порты в этом VLAN. Здесь видно типичную ошибку: VLAN 99 (management) пустая в колонке Ports — SVI на неё есть, но портов в VLAN нет, значит ни один access-порт туда не выведен.

bash
1show interfaces trunk
2# Port        Mode         Encapsulation  Status        Native vlan
3# Gi1/0/24    on           802.1q         trunking      999
4# Port        Vlans allowed on trunk
5# Gi1/0/24    10,20,99

Читай две вещи: Native vlan — должно совпадать с настройкой на дальней стороне; Vlans allowed — должен содержать все нужные VLAN. Если нужного VLAN нет, вот и причина «Wi-Fi есть, а интернета нет» (разбор инцидента в конце).

Что реально настроено на порту

bash
1show interfaces GigabitEthernet1/0/10 switchport
2# Name: user-anna
3# Switchport: Enabled
4# Mode: Access
5# Access Mode VLAN: 10 (Active)
6# Trunking Native Mode VLAN: 1 (Inactive)
7# Operational Mode: Access

Эта команда показывает реальную конфигурацию порта, а не то, что ты думаешь. Сравни два вывода:

Что подозреваешь Что покажет команда Диагноз
порт в VLAN 10 Access Mode VLAN: 10 (Active) всё хорошо
порт в VLAN 10 Access Mode VLAN: 1 (Inactive) VLAN 10 удалён или не создан, порт упал в VLAN 1
порт в VLAN 10 Operational Mode: Trunking кто-то сделал его trunk'ом
порт trunk Mode: Trunk, Vlans allowed: 10,20 VLAN 30 потерян при перезаписи списка

Слово (Inactive) после VLAN — самое важное в этом выводе: значит, VLAN объявлен в конфигурации порта, но отсутствует в базе VLAN. Порт молча переходит в VLAN 1 и работает не так, как задумано.

bash
1show etherchannel summary
2# Group  Port-channel  Protocol    Ports
3# 1      Po1(SU)         LACP       Gi1/0/22(P)   Gi1/0/23(P)

Буквы в скобках: P — порт в канале, s/S — suspended (приостановлен, не входит), I/D — standalone (не согласовался), H — hot-standby в EtherChannel 128. Связка SU в имени — S suspended + U in use. Если видишь (SU) с одним портом вместо двух — второй не согласовался.

Уровень 3: ARP и L3

bash
1show ip arp
2# Protocol  Address          Age (min)  Hardware Addr   Type   Interface
3# Internet   10.10.20.254          12   0000.0e07.ac14  ARPA   Vlan20
4# Internet   10.10.20.50           -    aabb.ccdd.eeff  ARPA   Vlan20
5# Internet   10.10.20.60           0   (incomplete)     ARPA

Записи в состоянии (incomplete) — ARP-запросы, на которые не пришёл ответ. Пакет отправился, но адрес не резолвится: этот узел не отвечает на ARP, находится в другой подсети, или между тобой и им фильтр. Практически это значит: L3 работает не полностью, пинга до этого адреса не будет.

Часто incomplete — временное состояние, и через пару секунд оно исчезает. Если оно держится — это проблема.

bash
1show ip arp | include Incomplete
2show arp | include Incomplete
⚡Осторожно

clear arp-cache (некоторые платформы: clear arp-cache dynamic) сбрасывает всю ARP-таблицу. После этого все узлы начинают шлеть ARP заново — кратковременный «шторм» ARP и потеря первых пакетов у всех. Это нормальный лечебный приём при «залипшем» ARP, но не делай его первым шагом: чаще всего он ничего не даёт, потому что ARP и так переотправляется сам.

Уровень 4: пинг и трассировка

Обычный ping в IOS работает в два шага — сначала он спрашивает имя через DNS, поэтому есть расширенный режим, где ты сам указываешь параметры.

bash
1# обычный — можно указать имя, ping идёт 5 пакетов
2ping 10.10.20.1
3
4# расширенный — полный контроль
5ping
6----> ping 10.10.20.50 repeat 100 source Vlan20
7Sending 100, 100-byte ICMP Echos to 10.10.20.50, timeout is 2 seconds:
Параметр Значение
repeat N сколько пакетов (по умолчанию 5)
source X с какого интерфейса или адреса отправлять (проверка политики маршрутизации)
size N размер пакета в байтах
df-bit не фрагментировать (проверка MTU на пути)
timeout N таймаут в секундах
data N размер payload

Формат ответа, который нужно читать:

bash
1ping 10.10.20.50 repeat 10
2# ! . ! . ! . ! . ! .
3# Success rate is 50 percent (5/10)
Символ Значение
! успех
. таймаут (потеря)
U unreachable (маршрута нет или ACL)
C потеря конфигурации
⚠Важно

Пинг самому себе ничего не доказывает. ping 10.10.20.1 с маршрутизатора, у которого этот IP на интерфейсе, проверяет лишь обработчик пакетов — пакет вообще не уходит в сеть. Полезная проверка — пинговать себя снаружи: с ноутбука пинговать адрес интерфейса, с маршрутизатора пинговать клиента. Пинг должен идти с чужого устройства, а не «сам с себя».

traceroute — карта пути. Обрати внимание на ICMP: hop'ы часто не отвечают на пинг (ICMP режут), но отвечают на traceroute (или наоборот). Звёздочки в начале нормальны.

bash
1traceroute 8.8.8.8
2traceroute 8.8.8.8 probe 2 timeout 1

Главный навык: фильтрация вывода

show running-config на реальном коммутаторе — это тысячи строк. Без фильтрации ты либо ничего не найдёшь, либо утонешь. Это не косметика, это основной рабочий приём.

bash
1show running-config | include vlan
2show running-config | exclude description
3show running-config | section interface GigabitEthernet1/0/10
4show running-config | begin interface Vlan99
5show running-config | count vlan
Фильтр Что делает Когда применять
| include <строка> только строки, содержащие подстроку найти нужную настройку среди тысяч
| exclude <строка> всё, кроме подходящих убрать шум (no description, logging)
| begin <строка> от первой совпавшей строки до конца когда нужен хвост конфига
| section <заголовок> блок от заголовка до следующего заголовка настройка одного интерфейса или ACL
| count <строка> сколько строк совпало быстрая метрика
| redirect file flash:cfg.txt сохранить в файл приложить к тикету
| tee file flash:cfg.txt сохранить, не теряя вывод на экране то же, но смотришь и сохраняешь

Примеры, которые пригодятся конкретно тебе:

bash
1# что настроено на спорном порту
2show running-config | section interface GigabitEthernet1/0/10
3
4# все trunk-порты и их native VLAN
5show running-config | include switchport trunk native
6
7# проверка: включён ли telnet где-нибудь
8show running-config | include telnet
9
10# сколько вообще портов и что с ними
11show interfaces status
12
13# только ошибки на всех интерфейсах
14show interfaces | include CRC
15
16# сохранить конфиг перед правкой
17show running-config | redirect flash:backup-before-change.txt
iЗаметка

Фильтры | работают в привилегированном EXEC-режиме и доступны не везде. На части платформ (некоторые supervisor, старые IOS) | section или | tee не поддерживаются. Если фильтр не сработал — повтори без него и пролистай глазами, либо используй перенаправление в файл и grep на своей стороне.

DNS: «интернет есть, а сайты не открываются»

Эта фраза почти всегда означает DNS, а не интернет.

bash
1show ip dns            # кэш резолвов
2show ip dns server     # какие DNS прописаны (на части платформ)
3ping google.com        # если не резолвится — DNS
4show running-config | include ip domain
bash
1ip domain lookup              # ВКЛЮЧИТЬ резолв имён в CLI (по умолчанию включено)
2ip domain name company.local
3ip domain name-server 8.8.8.8 8.8.4.4
⚡Осторожно

Команда no ip domain lookup (частая в «безопасных» конфигах) отключает резолв имён в CLI. После неё ping google.com не сработает, а новичек решит, что DNS сломан в сети. Если не понимаешь, зачем она выключена — не выключай.

Управление DNS-серверами на самом устройстве (ip domain name-server, ip name-server) — это DNS-клиент для самого коммутатора (его syslog, NTP, проверки лицензий), а не DNS-сервер для пользователей. Не путай.

Симптом Вероятная причина Первая команда
ping 1.1.1.1 работает, ping google.com — нет DNS не отвечает / неверные серверы show ip dns, ping по имени
ping 10.10.20.1 не работает, но ping по имени — нет DNS работает, L3 сломан show ip arp, show ip route
Всё работает, но syslog не приходит DNS-имя сервера не резолвится show logging | include DNS

CPU, память и логи

bash
1show processes cpu sorted | exclude 0.00
2# CPU utilization for five seconds: 82%/24%; one minute: 79%; five minutes: 76%
3# PID Runtime(ms)   Invoked  uSecs   5Sec   1Min   5Min TTY Process
4# 128     131072      845120   155.1 22.83% 21.06% 19.80%   0 IP Input
5# 147      98304      221456   444.0 18.42% 17.88% 16.72%   0 BGP Router

Выше 80% — проблема, и обычно видно, какой процесс. Типичные виновники: IP Input (слишком много пакетов, идёт process switching), BGP Router (большой префикс-лист), Spanning Tree (петля или частые topology change).

bash
1show processes memory sorted
2show version            # uptime, образ, объём памяти
3show memory statistics
4show logging
Показатель Норма Тревога
CPU 5 min до 40% свыше 80% устойчиво
Загрузка CPU «за последние 5 секунд» — скачки с Hogging означают перегрузку процесса
Свободная память — падает на десятки МБ за час
iЗаметка

show processes cpu sorted требует включённого ip accounting? Нет — сортировка по CPU работает всегда, а вот точные счётчики пакетов по интерфейсам (show ip interface в части с трафиком) зависят от платформы. Не удивляйся, что часть ISR считает трафик грубо, а 9300 точно.

show logging — буфер системных сообщений. Здесь видно, что произошло в момент, когда жаловались: порт упал, кто-то вошёл, произошло изменение STP, истёк сертификат.

bash
1show logging | include LINK|SPANTREE|SEC
2show logging | count

Буфер переполняется по кругу — старые записи исчезают. Размер настраивается:

bash
1logging buffered 32768
2logging host 10.10.99.50
3logging source-interface Loopback0
4logging trap informational

Точный порядок аргументов у logging buffered (сначала размер или сначала уровень) зависит от версии IOS. Всегда сверяйся: logging buffered ? — это дешевле, чем потерять историю инцидента.

⚠Важно

Если инцидент повторяется — включи отправку syslog на отдельный хост сразу. Буфер на самом коммутаторе перезаписывается за часы или дни активности, и ты потеряешь ровно ту минуту, о которую идёт спор с пользователем.

Медленная сеть: как локализовать

«Всё работает, но медленно» — самая трудная категория, потому что нет одного события, которое можно найти в логах.

Шаг 1. Сравни загрузку интерфейсов на пути. Смотри show interfaces на устройствах между источником и получателем, а не только там, где жалуются. Узкое место может быть на транзитном коммутаторе, о котором никто не думает:

bash
1show interfaces | include rate|errors
2# GigabitEthernet1/0/24   95000000 bits/sec, 9500000 packets/sec

Бит/сек на транковом порту выше 80% от его скорости — вот и причина. Остальные участники страдают от очередей.

Шаг 2. Сравни момент жалобы с загрузкой. Попроси пользователя точно сказать время («в 14:20»), посмотри логи и счётчики за это время. Если жалобы приходят ровно в 14:00–15:00 — это бэкап, антивирус или что-то по расписанию, а не «сеть тормозит вообще».

Шаг 3. Проверь CPU маршрутизатора. Если маршрутизатор на 90%, он не успевает форвардить — и это выглядит как «сеть тормозит», хотя каналы свободны.

Шаг 4. Ищи дуплекс-mismatch и ошибки. Из предыдущего уровня — collision, runts, input errors.

Шаг 5. Ищи широковещание и шторм. show mac address-table count и подозрительное количество arp неполных записей — признак петли или залипающего клиента.

«Сеть пропадает на 5 минут» и потом сама

Этот симптом почти всегда один из пяти:

Причина Как подтвердить Что делать
изменение топологии STP (кто-то воткнул коммутатор) show logging | include SPANTREE, show spanning-tree BPDU Guard (см. лекцию о безопасности)
port-security violation → err-disable show logging | include PORT_SECURITY, show interfaces status (err-disabled) sticky + err-disable recovery
отвал аплинка (аппаратная или оптика) show logging | include LINK, show interfaces (счётчики) резервирование, EtherChannel
чужой DHCP-сервер / исчерпание пула show ip dhcp server statistics, show ip dhcp conflict ip helper-address со всех VLAN, защита management
HSRP-флап / переключение show standby brief, show logging | include HSRP проверить timers, preemption delay
⚠Важно

Прежде чем лезть в настройки — посмотри логи за момент сбоя. Если логи не ведутся централизованно, начни прямо сейчас: это и есть разница между диагностикой за минуту и за неделю. Про метрики, логи и трейсы как три столпа — в лекции об observability, про то, что именно собирать с сетевого оборудования, — в лекции о мониторинге сети.

Перехват трафика на коммутаторе: SPAN

Когда уровни выше ничего не дали, нужен «микроскоп» — копия трафика с одного порта на другой, где стоит ноутбук с Wireshark.

bash
1monitor session 1 source interface GigabitEthernet1/0/5
2monitor session 1 destination interface GigabitEthernet1/0/24

Это SPAN (Switched Port ANalyzer). Источник — порт, который смотрим; приёмник — порт, куда сливается копия. На Catalyst 9K можно зеркалить и VLAN:

bash
1monitor session 1 source vlan 20
2monitor session 1 destination interface GigabitEthernet1/0/24 encapsulation dot1q 2000

Для удалённого перехвата (RSPAN) — когда сниффер на другом коммутаторе:

bash
1vlan 999
2 name RSPAN-DEST
3monitor session 1 source interface GigabitEthernet1/0/5
4monitor session 1 destination remote vlan 999
5remote-span vlan 999
bash
1show monitor session 1
2no monitor session 1          # не забудь убрать, когда закончил
⚡Осторожно

Порт-приёмник перестаёт передавать полезный трафик — его выход полностью отдан под зеркало. Если это порт, через который ты подключён к самому коммутатору, ты потеряешь сессию. Никогда не ставь destination на порт, через который сидишь.

SPAN не копирует широковещание и multicast с порта назначения обратно в источник (loop-защита), поэтому то, что ты увидишь, может отличаться от реальной картины в деталях. Это нормально и обычно не мешает диагностике.

На MikroTik это делается иначе — пакет-сенсором или зеркалированием на уровне чипа (у CRS-серии):

text
1/tool sniffer start file-name=capture.pcap interface=bridge1

На российских коммутаторах Eltex, Cisco и Maipu — механизм зеркалирования (SPAN/port mirroring) настраивается на уровне VLAN или портов с указанием источника и направления; синтаксис отличается от Cisco, поэтому сверяйся с руководством именно своей модели. Сравнение платформ — в лекции про RouterOS.

Захват с ноутбука

Ноутбук подключаешь кабелем в порт-приёмник, ставишь promiscuous-режим и снимаешь пакеты. Wireshark сам умеет всё:

bash
1# или из командной строки
2tcpdump -i eth0 -s 0 -w dump.pcap
3# во время воспроизведения проблемы
4# затем:
5wireshark dump.pcap
⚠Важно

Без promiscuous-режима на сетевом интерфейсе ты видишь только кадры, адресованные именно твоему MAC. Ethernet-карты фильтруют всё остальное на аппаратном уровне, и Wireshark покажет почти пустой захват. Включай promisc (в Wireshark: Edit → Preferences → Interfaces → ☑ Promiscuous mode). Это самая частая причина «зеркалирование настроено, а пакетов нет».

Практика: разбор инцидента

Вводные. В офисе на 3-м этаже перестал работать интернет через гостевой Wi-Fi (VLAN 30, Wi-Fi контроллер и точки доступа подключены к коммутатору SW-3F). Точки видны в контроллере, SSID раздаётся, но клиенты получают адреса и не могут выйти в интернет. Жалобы с 14:20. Утром работало.

Ты идёшь по уровням:

Уровень 1 — физика. Все порты up, ошибок нет.

bash
1show ip interface brief
2# Vlan30   10.10.30.1   YES NVRAM  up   up
3show interfaces status
4# Gi1/0/24  UPLINK-to-core  connected  trunk  a-full a-1000
5show interfaces GigabitEthernet1/0/24 | include CRC|input errors|runts|giants
6# 0 input errors, 0 CRC, 0 runts, 0 giants

Вывод: физика в порядке. Идём дальше. (Сразу отметай: если бы тут были CRC — смотри кабель до uplink'а и дальше, до ядра.)

Уровень 2 — канальный. Это ключевой шаг.

bash
1show vlan brief
2# 30   GUEST   active    (Ports пусто — так и должно быть для Wi-Fi)
3show interfaces trunk
4# Port       Mode   Encaps  Status     Native vlan
5# Gi1/0/24   on     802.1q  trunking   999
6# Vlans allowed on trunk
7# Gi1/0/24   10,20,99          <-- VLAN 30 отсутствует!

Вывод: VLAN 30 не разрешён на аплинке. Весь трафик гостевой сети упирается в uplink и дальше не идёт. Точки доступа при этом живы (они в management-VLAN), контроллер видит клиентов (он в management-VLAN), а вот гостевой интернет — нет. Симптом полностью объяснён.

Уровень 3 — сеть. Проверяем, что L3-часть тоже не сломана:

bash
1show ip arp | include 10.10.30
2show ip route 10.10.30.0
3ping 10.10.30.1          # SVI, ping в пределах устройства - работает
4ping 10.10.30.50 repeat 5 source Vlan30   # клиентский узел - нет ответа

Вывод: маршрут к сети есть (она подключена через SVI Vlan30), ARP не резолвится — согласовано с уровнем 2: кадры просто не доходят до точек.

Уровень 4–5 — проверяем, что именно настроено:

bash
1show running-config | section interface GigabitEthernet1/0/24
2show running-config | begin interface GigabitEthernet1/0/24

Видим строку switchport trunk allowed vlan 10,20,99. Значит, либо VLAN 30 никогда не добавляли, либо кто-то переписал список. Исправляем:

bash
1interface GigabitEthernet1/0/24
2 switchport trunk allowed vlan add 30
3end
4write memory

Проверка после правки:

bash
1show interfaces trunk    # Vlans allowed: 10,20,30,99
2ping 10.10.30.50 repeat 5 source Vlan30

Уровни 6–7 — для полноты картины. show processes cpu sorted на ядре покажет норму: узкое место не в загрузке, а в списке VLAN. SPAN на Gi1/0/24 подтвердит визуально: в захвате только теги 10, 20, 99, ни одного 30.

Что предотвратило бы это. Разрешить весь нужный диапазон одной строкой и закрепить изменение через конфиг-менеджмент, а не руками. И общий принцип: сначала show — потом configure. В данном случае show interfaces trunk ответил за 10 секунд.

Где это ломается

  • Начинать с ping. Пинг ничего не говорит, пока не исключены физика и канальный уровень. Приоритет: интерфейс up → ошибки → VLAN/trunk → ARP → пинг.
  • Путать administratively down и down. Первое — ручной shutdown, второе — нет линка. Ищи в show running-config | section interface ....
  • Смотреть show run и не смотреть фактическое состояние. Конфиг может говорить одно, а порт — работать иначе. show interfaces switchport покажет правду, а (Inactive) у VLAN объяснит, почему.
  • Накопившиеся счётчики ошибок. «Были CRC когда-то» и «CRC растут сейчас» — разное. Смотри аптайм, сравнивай значения через интервал.
  • Сбросить счётчики и потерять историю. clear counters уничтожает единственное доказательство вчерашнего инцидента. Сначала сохрани (show interfaces | redirect flash:errs.txt), потом сбрасывай.
  • SPAN на порт, через который подключён. Потеряешь сессию. Destination должен быть свободным портом.
  • Захват без promiscuous. Почти пустой pcap на SPAN — проверь promiscuous первым делом, а не «зеркалирование сломано».
  • Фильтры |, которые не работают. На части платформ | section или | tee не поддержаны — повтори без фильтра или сохрани в файл и grep у себя.
  • Отсутствие syslog. Буфер logging круговой и мелкий. Если инцидент повторится, а логов нет — расследование закончится ничем. Настрой отправку на отдельный хост.
