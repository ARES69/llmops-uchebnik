Это последняя лекция модуля. Первые три дали хранилища: данные и вектора в Postgres, кэш и очереди в Redis, права и политики в Active Directory. Осталось связать это в процессы, которые сами срабатывают по событиям. Именно это делает n8n — визуальный конструктор интеграций с self-hosted-версией, то есть Zapier, который живёт в твоём контуре, а не у внешнего вендора. Разбирать его будем на сценарии, который у тебя точно будет: «новый вопрос в Telegram → поиск по базе знаний → ответ с источниками → если ответа нет, эскалация человеку».

## Что такое n8n и когда он нужен

n8n — конструктор, в котором ты собираешь **воркфлоу**: направленный граф из триггеров, нод и условий. Он self-hosted, то есть запускается на твоём сервере, хранит данные в твоей Postgres и ходит только в твои системы. Для on-premise контура это главный аргумент: SaaS-автоматизация не может обращаться к внутренним сервисам и не должна получать их данные.

| Что автоматизируют через n8n | Пример в LLM-контуре |
| --- | --- |
| Триггер из внешнего источника | вопрос в Telegram, новый тикет, папка с новыми документами |
| Вызов LLM-сервиса | RAG-запрос к локальному Ollama/vLLM через OpenAI-совместимый API |
| Ветвление | нашлось в базе знаний → ответ; не нашлось → эскалация |
| Запись в системы | ответ в чат, запись в Jira, строка в `usage_events` для биллинга |
| Периодические процессы | ночная переиндексация, отчёт по токенам за неделю |

> [!IMPORTANT]
> Первое правило: **n8n — это оркестратор, а не приложение**. Он должен
> вызывать твои сервисы, а не содержать логику, которая живёт только в
> нём. Логика, ценность которой зависит от бизнеса, — в коде, в Git,
> под ревью. В n8n живёт маршрутизация.

### Когда n8n НЕ нужен

Простой тест: если процесс умещается в один запрос к API и две строки кода, n8n в нём только мешает. Конкретные случаи, где код лучше:

- процесс требует **цикла с ветвлениями, зависящими от результата модели** — это агент, и его цикл лучше видно в коде, чем в нодах;
- нужны **строгие права** на внутренние ресурсы, выдаваемые декларативно и проходящие ревью (как в [лекции про фреймворки агентов](mlops/12-agent-frameworks.md));
- нужна **наблюдаемость**: трассировка каждого шага, метрики по шагам, golden-набор регрессий на промпте — в n8n ты этого не получишь, а в оркестраторе без трассировки инцидент не расследуется;
- нужна **идемпотентность и очередь с повторами** уровня Kafka.

## Установка self-hosted через Docker

Разворачивается как три контейнера: Postgres, Redis и сам n8n. Compose-структуры разбирались в [лекции про Docker Compose](devops/09-docker-compose.md), здесь — конкретная конфигурация.

```yaml
# /opt/n8n/docker-compose.yml
services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: n8n
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U n8n"]
      interval: 10s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    command: ["redis-server", "--requirepass", "${REDIS_PASSWORD}", "--maxmemory", "256mb", "--maxmemory-policy", "noeviction"]

  n8n:
    image: docker.n8n.io/n8nio/n8n:1.94.1        # версия зафиксирована — см. об обновлениях
    restart: unless-stopped
    ports:
      - "127.0.0.1:5678:5678"                     # наружу не выставляем, только для прокси
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_started }
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_PORT: 5432
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      REDIS_HOST: redis
      REDIS_PORT: 6379
      REDIS_PASSWORD: ${REDIS_PASSWORD}
      QUEUE_BULL_REDIS_HOST: redis
      QUEUE_BULL_REDIS_PASSWORD: ${REDIS_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_SECURE_COOKIE: "false"                  # только потому что впереди nginx с TLS
      N8N_HOST: n8n.corp.example.com
      N8N_PORT: 5678
      N8N_PROTOCOL: https
      WEBHOOK_URL: https://n8n.corp.example.com/
      GENERIC_TIMEZONE: Europe/Moscow
      TZ: Europe/Moscow
      N8N_DIAGNOSTICS_ENABLED: "false"
      N8N_VERSION_NOTIFICATIONS_ENABLED: "false"
      N8N_TEMPLATES_ENABLED: "false"
      N8N_PERSONALIZATION_ENABLED: "false"
      N8N_BLOCK_ENV_ACCESS_IN_NODE: "true"        # нода Code не читает твоё окружение
      N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS: "true"
      EXECUTIONS_MODE: regular
      N8N_RUNNERS_ENABLED: "false"
      N8N_LOG_LEVEL: info
    volumes:
      - n8n_data:/home/node/.n8n
      - /opt/n8n:/opt/custom-nodes:ro

volumes:
  pgdata:
  n8n_data:
```

```bash
cd /opt/n8n
umask 077
openssl rand -hex 32 > .env.postgres && openssl rand -hex 32 > .env.redis && openssl rand -hex 32 > .env.key
cat .env.postgres .env.redis .env.key > .env && chmod 600 .env

docker compose up -d
docker compose logs -f n8n | tail -40
curl -s http://127.0.0.1:5678/healthz
```

> [!WARNING]
> `N8N_ENCRYPTION_KEY` — самый важный секрет во всей этой конструкции.
> Все credentials (пароли от Telegram, API-ключи, строки подключения к БД)
> хранятся в базе в **зашифрованном** виде этим ключом. Потеря ключа =
> потеря всех credentials без возможности восстановления: в дампе базы
> лежит шифротекст, который никто не расшифрует. Ключ хранится в менеджере
> секретов и в бэкапе **вместе** с дампом базы, а не рядом с ним.

## Не выставляй n8n в интернет напрямую

Прямой `ports: - "5678:5678"` в интернет — это дыра. За последними версиями n8n тянется линейка CVE, включая обход аутентификации и выполнение кода; n8n — это инструмент, который по своей природе умеет ходить в твои внутренние системы. Единственная допустимая схема: n8n слушает `127.0.0.1` (как в конфиге выше), наружу — только обратный прокси с TLS и аутентификацией.

```conf
# /etc/nginx/conf.d/n8n.conf
upstream n8n_upstream { server 127.0.0.1:5678; keepalive 16; }

server {
    listen 443 ssl http2;
    server_name n8n.corp.example.com;

    ssl_certificate     /etc/letsencrypt/live/n8n.corp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/n8n.corp.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # базовая аутентификация перед приложением: n8n сам по себе не rate limit'ит вход
    auth_basic           "n8n";
    auth_basic_user_file /etc/nginx/n8n.htpasswd;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Frame-Options DENY always;
    client_max_body_size 32m;

    location / {
        proxy_pass         http://n8n_upstream;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;             # долгие LLM-вызовы
        proxy_send_timeout 300s;
    }

    # вебхуки: отдельный location, без basic-auth, но с лимитом запросов
    location /webhook/ {
        limit_req zone=n8n_wh burst=10 nodelay;
        proxy_pass http://n8n_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# /etc/nginx/conf.d/n8n-ratelimit.conf — перед n8n.conf
limit_req_zone $binary_remote_addr zone=n8n_wh:10m rate=5r/s;
```

```bash
htpasswd -c /etc/nginx/n8n.htpasswd admin
nginx -t && systemctl reload nginx
curl -I https://n8n.corp.example.com/          # 401 без basic-auth — так и должно быть
```

Дополнительно: включи двухфакторную аутентификацию для пользователей n8n, заведи отдельного пользователя-администратора и отдельных пользователей-разработчиков без прав редактирования всех воркфлоу, ограничь `N8N_LISTEN_ADDRESS` и не открывай порт в UFW. Шаги по hardening — в [лекции про безопасность инфраструктуры](devops/20-bezopasnost-infrastruktury.md).

## Архитектура воркфлоу

Любой воркфлоу — это пять элементов:

| Элемент | Что это | Пример |
| --- | --- | --- |
| Триггер | точка входа, порождает выполнение | сообщение в Telegram, `POST /webhook/ingest`, расписание |
| Ноды обработки | шаги между триггером и действием | HTTP-запрос к RAG, парсинг JSON, нода агента |
| Условия | ветвление по данным или результату | «есть ли источники», «кто автор вопроса» |
| Действия | то, что меняет состояние внешней системы | отправка сообщения, запись в БД |
| Настройки | таймауты, повторы, права, порядок выполнения | `maxTries`, `onError`, `executionOrder` |

Важное свойство n8n: **выполнение по умолчанию останавливается на ошибке**. Нода, упавшая с HTTP 500, завершает прогон и не отправляет ответ. Это правильное поведение по умолчанию, но в интеграциях с внешними системами (модель, Telegram) его надо переопределять точечно: `onError: continueRegularOutput` у ноды HTTP, чтобы следующая нода увидела код ошибки и обработала его явно.

### Ноды, которые нужны в LLM-контуре

| Нода | Что делает | Где применяется |
| --- | --- | --- |
| **Telegram Trigger** | новое сообщение | вход для корпоративного бота |
| **Webhook** | HTTP-вызов извне | приём событий из другой системы |
| **Schedule Trigger** | по расписанию | ночная переиндексация, отчёт |
| **HTTP Request** | любой вызов по HTTP | RAG-сервис, внутренний API, метрики |
| **OpenAI / Chat Model** | вызов LLM через OpenAI-совместимый API | локальный vLLM или Ollama |
| **AI Agent** | агентный цикл с инструментами (LangChain внутри) | многошаговые задачи; в n8n — с осторожностью |
| **Vector Store** + **Question and Answer Chain** | RAG по Qdrant/pgvector | ответ по базе знаний |
| **PostgreSQL** | запросы к своей БД | чтение метаданных, запись `usage_events` |
| **If / Switch / Merge** | ветвление | «нашлось / не нашлось» |
| **Code** | произвольный JS | парсинг, но доступ к env ограничен флагом выше |

Ключевая связка с курсом: нода **OpenAI Chat Model** умеет ходить по OpenAI-совместимому API, а значит твой локальный Ollama или vLLM из [темы локального serving](mlops/10-lokalnyj-serving.md) подключается как «другой провайдер» — с указанием base URL. Никакого облака, только внутренний контур. Нода **Vector Store** даёт RAG-шаг готовым компонентом, и это второй по важности повод иметь n8n.

## Сценарий: RAG-бот в Telegram

Собираем полный воркфлоф. Логика: сообщение → фильтр (только личные чаты, только текст) → RAG-запрос к внутреннему сервису → если есть ответ с источниками, отправляем ответ со ссылками → если нет, эскалация живому оператору → в любом случае пишем метрику в `usage_events`.

Импорт: **Workflows → Import from File**. Перед импортом создай credentials для Telegram и для HTTP (или замени их в готовом воркфлоу) — credentials не переносятся внутри файла, они хранятся отдельно и шифруются ключом из `.env`.

```bash
# проверка RAG-сервиса до подключения ноды — без этого отладка в UI бессмысленна
curl -s -X POST http://rag-api:8000/v1/answer \
  -H 'Content-Type: application/json' \
  -d '{"question":"как сбросить пароль учётки в AD","user_id":"1","top_k":5}' | python -m json.tool
```

Обрати внимание на три решения в этой конструкции. Первое: `X-Request-Id` с `$execution.id` — по нему воркфлот связывается с логами RAG-сервиса, и это ровно то, чего не хватает при расследовании инцидента. Второе: эскалация уходит живому оператору **с текстом вопроса**, то есть в очередь на разбор попадает то, на что система не ответила, — из этих данных потом рождается задача на доиндексацию. Третье: метрика пишется в обоих ветвях, включая эскалацию, иначе в аналитике будут только успешные ответы.

## n8n против кода и против SaaS

| Критерий | n8n (self-hosted) | Python / LangGraph | Zapier / Make |
| --- | --- | --- | --- |
| Скорость сборки прототипа | **часы**, без разработчика | дни | часы |
| Гибкость | средняя: JS в ноде Code, HTTP-запросы | **полная** | низкая |
| Читаемость логики | визуально, но на 40 нод это каша | **тесты, типизация, ревью** | визуально |
| Наблюдаемость и трассировка | слабая, логи в интерфейсе | **полная, метрики, трейсы** | своя |
| Обработка ошибок и ретраи | настройки на ноде, без политик по типу ошибки | **своя логика, DLQ** | ограниченно |
| Юнит-тесты | невозможны | **возможны** | невозможны |
| CI/CD и code review | нет, экспорт JSON в Git — единственный вариант | **обычный пайплайн** | нет |
| Безопасность и права | риск: одна нода HTTP Request может ходить куда угодно | **декларативные права, отдельный сервис-аккаунт** | данные уходят вендору |
| Стоимость | сервер, который у тебя уже есть | зарплата разработчика | $20–$150 за тариф + утечка контекста наружу |
| On-premise интеграции | **да** | да | нет |

> [!IMPORTANT]
> Главное различие — не в цене, а в контроле. В коде права ноды
> выдаются декларативно, проходят ревью и покрываются тестами. В n8n
> нода «HTTP Request» получает права того, кто её нарисовал, и никакого
> механизма, который запретит ей ходить в AD или в бэкап-хранилище, нет.
> Поэтому правило простое: **агент с правами на AD, почту или базу — это
> код**, как и сказано в [лекции про агентные фреймворки](mlops/12-agent-frameworks.md).

Когда n8n всё-таки правильный выбор:

- процесс линейный, с одним-двумя ветвлениями;
- интеграции нет в готовом API, но есть HTTP;
- исполнитель — бизнес-пользователь, а не разработчик, и ему нужно менять логику самому;
- процесс заменяет ручную рутину и должен быть запущен **сегодня**, а не через спринт.

Когда нужен код: циклы агента, поток с гарантиями доставки, обработка тысяч событий в сутки, требования к аудиту и трассировке, доступ к критичным ресурсам.

## Эксплуатация

| Параметр | Значения | Что выбрать тебе |
| --- | --- | --- |
| `EXECUTIONS_MODE` | `regular` / `queue` / `internal` | `regular` для одного инстанса, `queue` — как только появляется второй |
| `QUEUE_MODE` (в worker) | очередь через Redis | включается вместе с `EXECUTIONS_MODE=queue` на всех узлах |
| `N8N_SECURE_COOKIE` | `true` по умолчанию | `false` **только** если впереди TLS-прокси, иначе cookie не поставится |
| `N8N_ENCRYPTION_KEY` | 64 hex-символа | генерировать, хранить в секретах, бэкапить вместе с БД |
| `N8N_BLOCK_ENV_ACCESS_IN_NODE` | `true` | включить всегда: нода Code не должна читать окружение |

Режим очереди добавляет отдельный worker-контейнер. Он же решает проблему долгих выполнений: в `regular` режиме тяжёлый запрос к модели занимает единственный worker и блокирует остальные воркфлоу.

```yaml
  n8n-worker:
    image: docker.n8n.io/n8nio/n8n:1.94.1
    command: worker
    restart: unless-stopped
    depends_on: [n8n, redis]
    environment:
      EXECUTIONS_MODE: queue
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      QUEUE_BULL_REDIS_HOST: redis
      QUEUE_BULL_REDIS_PASSWORD: ${REDIS_PASSWORD}
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      N8N_SECURE_COOKIE: "false"
```

```bash
# бэкап: дамп БД + ключ шифрования + каталог данных — одним скриптом по cron
BACKUP=/backup/n8n/$(date +%F)
mkdir -p "$BACKUP" && chmod 700 "$BACKUP"
docker compose exec -T postgres pg_dump -U n8n -Fc n8n > "$BACKUP/n8n.dump"
cp /opt/n8n/.env "$BACKUP/.env"
docker run --rm -v n8n_data:/data -v "$BACKUP":/backup alpine \
  tar czf /backup/custom-nodes-and-config.tgz -C /data .
```

Обновления. Версию в `docker-compose.yml` фиксируй явно и обновляй планово: между минорными версиями меняются имена параметров, структура данных очереди и поведение нод. Процедура: бэкап → поднять стенд с копией БД → импортировать воркфлоу → прогнать критичные сценарии → только потом переключать прод. Автообновление при старте контейнера (`n8n` сам подтягивает новую версию) в проде включать нельзя.

```bash
docker compose pull && docker compose up -d
docker compose logs --tail=100 n8n | grep -iE "error|warn"
curl -s http://127.0.0.1:5678/healthz
```

Наблюдаемость: логи n8n идут в stdout, поэтому они свозятся тем же стеком, что и в [лекции про Grafana и Loki](devops/17-grafana-loki-alerty.md). Плюс `GET /metrics` и раздел **Executions** в интерфейсе, где по прогону видно, на какой ноде остановилось выполнение и с каким вводом.

## Грабли

- **Бесконечный цикл.** Нода «Webhook» вызывает сам триггер этого же воркфлоу. Симптом — сотни прогонов за минуту и счёт за токены. Всегда проверяй: триггер смотрит наружу (Telegram, расписание) или внутрь (есть `Call Webhook` обратно в свой URL).
- **Необработанная ошибка.** Падение ноды молча останавливает прогон, пользователь не получает ответа и не знает, что делать. Обрабатывай явно: `onError: continueRegularOutput` и ветка «сообщить пользователю, что система занята».
- **Секреты в воркфлоу.** Пароль или токен, вписанный в поле URL или тело запроса, попадает в экспорт JSON, в историю выполнений и в бэкап. Всегда credentials, никогда — строка.
- **n8n как единая точка отказа.** Если через него проходит путь к корпоративному порталу и он лежит — лежит всё. Держи критичные интеграции в коде с отдельным развёртыванием, а n8n оставь для вспомогательных процессов.
- **Всё в режиме `regular` на одной машине.** Обновление контейнера — это остановка всех процессов на минуты. Планируй окно, как для любого прода.
- **Бесконечный рост базы.** n8n хранит историю выполнений со всеми входами и ответами — там окажутся персональные данные и промпты. Настрой `EXECUTIONS_DATA_PRUNE=true`, `EXECUTIONS_DATA_MAX_AGE=336` (две недели) и `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`.

## Практика: разобрать воркфлоу по шагам

Собираем всё вместе и проверяем по пунктам. Это 60–90 минут работы.

1. Подними стек по compose-файлу из лекции, проверь `curl http://127.0.0.1:5678/healthz`.
2. Создай owner-аккаунт, включи 2FA, заведи второго пользователя без доступа к администрированию.
3. Импортируй JSON воркфлота, создай credentials Telegram, проверь, что ноды зелёные.
4. Подними локальный OpenAI-совместимый endpoint и проверь RAG-запрос `curl` до того, как подключать ноду.
5. Прогони сценарий: вопрос с ответом в базе → бот отвечает со ссылками; вопрос без ответа → оператор получает эскалацию.
6. Проверь `executions_data_prune`: после прогонов база не растёт бесконечно.
7. Сделай бэкап и **восстанови его в отдельную БД** — единственная проверка бэкапа, которая что-то доказывает.

Где в этом воркфлоте применяются правила безопасности из [лекции про безопасность агентов](mlops/14-bezopasnost-agentov.md):

| Правило | Как выглядит в воркфлоте |
| --- | --- |
| Минимальные права | нода `PostgreSQL` — только `SELECT` на представление `usage_events`, никакого `DELETE` |
| Секреты вне воркфлоу | Telegram-токен и пароли — в credentials, зашифрованных `N8N_ENCRYPTION_KEY` |
| Проверка ввода | нода `If` отсекает не-текст и неверный формат до вызова модели |
| Лимит шагов и стоимости | условие по `user_id` + rate limit на прокси, а не «вежливая просьба» в промпте |
| Журнал каждого действия | `$execution.id` в `X-Request-Id` сквозь все сервисы + нода `Метрика ответа` |
| Отказоустойчивость | `retryOnFail: true, maxTries: 2` на HTTP-нодах, эскалация человеку в ветке «нет ответа» |
| Отзыв доступа | отзыв прав в AD влияет на `user_id` из Telegram — доступ проверяется на стороне RAG-сервиса, а не в n8n |

Обрати внимание на последнюю строку: **решение о доступе принимает сервис, а не оркестратор**. n8n передаёт `user_id` и получает ответ; проверка прав лежит в RAG-сервисе, где она пишется в логи и тестируется. Если проверку оставить в n8n, через полгода её забудут обновить при смене модели прав — и никто не заметит.

## Где это ломается

- **Выставил `ports: 5678:5678` наружу и закрыл паролем UI.** Пароль от UI не защищает API вебхуков и exec-ноды. Порт должен слушать `127.0.0.1`, наружу — только прокси с TLS.
- **Потерял `N8N_ENCRYPTION_KEY`.** Все credentials в базе нечитаемы. Их можно пересоздать, но восстановить пароль, который был только там, нельзя. Храни ключ в менеджере секретов и бэкапь вместе с дампом.
- **Секрет в поле URL.** Виден в экспорте JSON, в истории выполнений и в бэкапе. Всё, что можно, — через credentials.
- **Цикл воркфлоу.** `Webhook` → нода, вызывающая тот же `Webhook`. Счёт за токены растёт, а заметить это можно только по метрике вызовов модели.
- **Ошибка ноды молча проглочена.** Пользователь не получил ответа и не понимает, что сломалось. Обрабатывай ошибку как данные и сообщай пользователю.
- **Обновил n8n без бэкапа БД.** Схема очереди и параметры меняются между версиями; откат — только из дампа, который не сделан.
- **Один инстанс в `regular` на все процессы.** Плановое обновление останавливает корпоративные процессы. Минимум — режим `queue` с отдельным worker.
- **Нода `Code` с доступом к `$env`.** С данным флагом нода не видит переменные окружения, включая пароли. Без флага — это чтение секретов из воркфлоу.
- **Исторические прогоны с промптами и персональными данными копятся месяцами.** Утечка через бэкап или через доступ администратора n8n. Настрой prune и ограничь, кто видит executions.
