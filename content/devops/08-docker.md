До этого ты настраивал Linux и Bash руками: apt, systemd, конфиги, [скрипты из лекции 05](devops/05-bash-skripty.md). Такая ручная настройка воспроизводится только через твою память и заметки — стоит один раз сделать, и на другой машине то же самое не заработает. Docker решает ровно эту проблему: упаковать приложение вместе со всей средой в переносимый артефакт. Разбираем, как он устроен изнутри — потому что «работает у меня» и «работает у всех» на Docker отличаются порядком строк в Dockerfile.

## Зачем контейнеры и чем они отличаются от виртуалки

Виртуальная машина — это эмуляция целого компьютера. Контейнер — это процесс Linux, которому через *namespaces* выделили собственное видимое подмножество системы (файловая система, PID, сеть, hostname, пользователи), а через *cgroups* — квоты на CPU и память. Никакой эмуляции процессора, никакой гостевой ОС. Отсюда вся разница в экономике:

| Критерий | Виртуальная машина | Контейнер |
| --- | :---: | :---: |
| Граница изоляции | Аппаратная, гипервизор | Процессная, namespaces + cgroups |
| Ядро ОС | Своё, внутри гостя | Общее с хостом |
| Время запуска | Секунды-десятки секунд | Сотни миллисекунд |
| Размер гостя | Гигабайты, десятки гигабайт | Десятки-сотни мегабайт |
| Плотность на ноде | 10-40 ВМ | Сотни-тысячи контейнеров |
| Изоляция | Близка к физическому серверу | Уровень процесса, пробить проще |
| Нужен ли Docker внутри | Нет | Да |
| Сетевой доступ | Через отдельный виртуальный свитч | Через bridge/veth, NAT |

Практический смысл для тебя: виртуалку ты ставишь, чтобы изолировать ОС — в твоём Proxmox это Windows AD от Linux-хостов. Контейнер ты ставишь, чтобы изолировать *приложение* — десяток версий одного и того же сервиса на одной Ubuntu-машине без конфликтов по портам и библиотекам.

> [!IMPORTANT]
> Контейнер — это не «маленькая виртуалка». Это процесс с ограничениями. Отсюда
> и сила (плотность, скорость), и слабость (общее ядро, ограниченная изоляция).

## Архитектура Docker: кто с кем говорит

В системе есть шесть сущностей, и важно понимать их разделение:

- **Клиент** — `docker` в терминале. Сам ничего не делает, ходит по REST API в демон.
- **Демон** — `dockerd`. Хранит образы, управляет контейнерами, слоями, сетями. Слушает unix-сокет `/var/run/docker.sock`.
- **Образ** (`image`) — неизменяемый шаблон из слоёв. Читается через `docker images`.
- **Контейнер** (`container`) — запущенный экземпляр образа плюс тонкий записываемый слой сверху.
- **Реестр** (`registry`) — хранилище образов: Docker Hub, GHCR, ECR, Harbor. Образ в нём адресуется как `registry/namespace/name:tag`.
- **Dockerfile** — текстовый рецепт сборки, из которого получается образ.

| | Образ | Контейнер |
| --- | --- | --- |
| Что это | Шаблон из read-only слоёв | Процесс + writable-слой |
| Состояние | Не меняется | Меняется и умирает вместе с контейнером |
| Команда | `docker images` | `docker ps` |
| Что делать в проде | Только пересоздавать | Создавать, удалять, пересоздавать |

Сокет `docker.sock` — важный объект безопасности. Доступ к нему эквивалентен root-доступу на хост: кто может писать в сокет, может запустить контейнер с примонтированной корневой ФС. В Kubernetes это выливается в то, что сервис-аккаунт с правом работать с подами — это потенциально доступ ко всему кластеру. Не выдавай доступ к сокету бездумно, особенно в CI-раннерах.

```bash
docker version                 # клиент и сервер
docker info                    # драйверы хранилилища, cgroup, доступная память
docker pull nginx:1.27-alpine
docker run -d --name web -p 8080:80 nginx:1.27-alpine
docker ps
docker logs -f web
docker exec -it web sh
docker stop web
docker rm web
docker system df               # сколько места заняли образы, контейнеры, тома, кэш сборки
```

## Слои и кэш — вот где Docker отличается от магии

Каждая инструкция `Dockerfile` создаёт **слой**. Слои неизменяемые, каждый ссылается на предыдущий — получается цепочка. Docker кэширует каждый слой по хэшу: содержимое инструкции плюс хэш результата предыдущих слоёв. Если при сборке инструкция совпала с закэшированной, она не выполняется, а берётся из кэша.

Отсюда правило, которое экономит тебе часы в день: **то, что меняется часто, идёт в конец**. Код приложения меняется на каждом коммите, зависимости — раз в неделю. Значит, зависимости должны копироваться и устанавливаться раньше кода.

```dockerfile
# ПЛОХО: любой коммит пересобирает зависимости, потому что COPY . . меняет слой
COPY . .
RUN pip install -r requirements.txt
```

```dockerfile
# ХОРОШО: requirements.txt меняется редко — слой с зависимостями берётся из кэша
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Тот же принцип с системными пакетами: `apt-get install` медленный, поэтому он идёт раньше всего изменяемого. А `COPY . .` с шаблоном исключений ставь в самый конец.

Вторая половина этой механики — **`RUN apt update` и `RUN apt install` должны быть в одной строке**. `apt-get update` пишет индекс пакетов в файловую систему. Если это отдельная инструкция, индекс кэшируется отдельным слоем. Через неделю в репозитории выходит новая версия библиотеки, кэш-слою Update уже нет — он лежит, а `install` запускается против старого индекса и падает с «Version '...' not found». Или, что хуже, ставит несовместимую версию, и это всплывает через месяц на проде.

```dockerfile
# ПЛОХО: индекс пакетов кэшируется отдельно и устаревает
RUN apt-get update
RUN apt-get install -y curl

# ХОРОШО: одна транзакция, индекс не сохраняется
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
```

> [!IMPORTANT]
> Правило: одна `RUN` — одна логическая операция. Установил — почисти. Скачал —
> распаковал в тот же слой, а не в следующий. Последний «мусорный» слой из кэша
> не выкинут, он навсегда в образе.

Посмотреть, что реально попало в кэш и сколько весит каждый слой:

```bash
DOCKER_BUILDKIT=1 docker build --progress=plain -t api:1 .
docker history --no-trunc api:1
```

В выводе BuildKit строка `CACHED` напротив инструкции — это подтверждение, что кэш сработал. Если после правки порядка инструкций сборка стала 8 минут вместо 40 секунд — значит, тяжёлая зависимость уехала ниже `COPY`.

## Dockerfile: инструкции, которые ты будешь писать каждый день

| Инструкция | Что делает | Частая ошибка |
| --- | --- | --- |
| `FROM` | Базовый образ | `latest` вместо зафиксированной версии |
| `WORKDIR` | Рабочий каталог, создаётся при отсутствии | Путают с `RUN cd` — тот не сохраняется |
| `COPY` | Копирует файлы из контекста сборки | Копируют раньше зависимостей |
| `RUN` | Выполняет команду на этапе сборки | Разбивают транзакции на несколько слоёв |
| `USER` | Переключает пользователя для последующих инструкций | Забывают — контейнер под root |
| `EXPOSE` | Документирует порт | Считают, что это открывает порт наружу |
| `ENV` | Переменная окружения, видна в рантайме | Пишут туда пароли |
| `ARG` | Переменная только на этапе сборки | Путают с `ENV` |
| `CMD` | Команда запуска по умолчанию | Пишут в shell-форме |
| `ENTRYPOINT` | Точка входа, не заменяется аргументами | Путают с `CMD` |
| `VOLUME` | Объявляет точку монтирования | Думают, что это создаёт данные |

**`ENV` против `ARG`.** `ENV` попадает в метаданные контейнера, его видно в `docker inspect .Config.Env`, и он наследуется потомками. `ARG` существует только во время сборки и виден в `docker history` как есть. Никогда не клади секреты в `ARG` — они останутся в слое.

**`EXPOSE` — это документация.** Порт наружу открывается только через `-p`. Никакой сетевой безопасности `EXPOSE` не даёт.

**`CMD` против `ENTRYPOINT`.** `CMD` — команда по умолчанию, которую можно переопределить аргументами `docker run image ...`. `ENTRYPOINT` — фиксированная точка входа. На практике в 95% случаев тебе нужен `ENTRYPOINT` как запуск приложения, а `CMD` как аргументы по умолчанию.

И главный нюанс — **форма записи**. Exec-форма `CMD ["python", "-m", "api"]` запускает процесс напрямую, он становится PID 1 и получает сигналы. Shell-форма `CMD python -m api` запускает `/bin/sh -c "python -m api"`, и PID 1 — это shell, который **не пробрасывает** SIGTERM приложению. При `docker stop` приложение не успевает закрыть соединения и дописать данные, деплой срывается по таймауту, и его убивают SIGKILL. Для всего, что работает в проде, используй exec-форму.

## Многоступенчатая сборка

Сборка нужна, чтобы получить бинарники и зависимости, но компилятор, заголовки и менеджер пакетов в рантайме не нужны. Оставлять их в финальном образе — это сотни мегабайт лишнего и лишняя поверхность атаки. Решение: несколько `FROM` в одном Dockerfile, а наружу отдаётся только последняя стадия.

```dockerfile
# Стадия 1 — сборщик: тут есть компилятор, наружу уйдут только готовые wheel-файлы
FROM python:3.12-slim AS builder
ENV PIP_DISABLE_PIP_VERSION_CHECK=1 PIP_NO_CACHE_DIR=1
WORKDIR /build
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip wheel --wheel-dir /wheels -r requirements.txt

# Стадия 2 — рантайм: ни компилятора, ни apt, ни исходников
FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PATH=/home/app/.local/bin:$PATH
RUN groupadd -r app && useradd -r -g app -u 10001 -d /home/app app
WORKDIR /app
COPY --from=builder /wheels /wheels
COPY requirements.txt .
RUN pip install --no-index --find-links=/wheels -r requirements.txt \
 && rm -rf /wheels
COPY --chown=app:app src ./src
USER app
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Читай стадию 2 построчно: `PYTHONUNBUFFERED=1` — чтобы логи не залипали в буфере и `docker logs` показывал их в реальном времени; `--no-index --find-links` — установка строго из локальной папки, без обращения в интернет (воспроизводимость и безопасность сборки); `--chown` — файлы принадлежат непривилегированному пользователю сразу; `USER app` — финальная точка, после неё ничего не должно требовать прав root.

Сборка по умолчанию оставляет в образе **только последнюю стадию**. Промежуточные можно собрать отдельно для отладки: `docker build --target builder -t api:builder .`.

### Минимальный образ: slim, alpine, distroless

| Вариант | Размер (для Python) | Внутри | Когда брать |
| --- | --- | --- | --- |
| `python:3.12-slim` | ~150 МБ | glibc, apt есть | База по умолчанию |
| `python:3.12-alpine` | ~45 МБ | musl, пакетный менеджер apk | Экономия памяти и места |
| `gcr.io/distroless/...` | ~30 МБ | нет shell, нет apt | Максимальная безопасность |

**Alpine — не бесплатный выигрыш.** У него libc `musl`, а не `glibc`. Часть бинарных wheel-пакетов (numpy, cryptography, grpcio, psycopg) собрана под glibc и в Alpine падает с `ImportError` или работает неверно. Если столкнулся — либо ставь `gcompat` и `libstdc++`, либо возвращайся на slim. Меньший образ не стоит нестабильной сборки.

**Distroless** — это образ, из которого вырезали всё: нет `/bin/sh`, нет `apt`, нет curl. Приложение не может ничего испортить, потому что у него нет инструментов. Плата: `docker exec -it c sh` не работает, отлаживаться приходится отдельным образом с тегом `:debug`.

> [!TIP]
> Правило для прода: статический бинарь (Go, Rust, Python после `pip install` в slim) —
> финальная стадия на slim. Если готов отказаться от shell-отладки — distroless.
> Никогда не бери alpine «просто потому что легче».

## `.dockerignore`: кэш и безопасность в одном файле

Контекст сборки — это всё, что лежит в каталоге, из которого ты запускаешь `docker build`. `COPY . .` забирает всё, включая `.git`, `.venv`, `.env` и бэкапы. Это раздувает образ и **класть в образ секреты**, которые лежали рядом с кодом.

```
.git
.venv
venv
__pycache__
*.pyc
.pytest_cache
.mypy_cache
.env
.env.*
*.pem
tests
README.md
Dockerfile
docker-compose.yml
```

Проверь, что мусор не утёк внутрь:

```bash
docker history --no-trunc api:1 | grep -Ei 'password|token|secret|key'
```

## Тома и bind-mount

Данные внутри контейнера умирают вместе с контейнером (`docker rm`). Три способа их сохранить:

| Тип | Что это | Когда |
| --- | --- | --- |
| tmpfs | В оперативной памяти | Временные файлы, кэш |
| Volume | Управляемый Docker каталог (обычно `/var/lib/docker/volumes`) | Базы данных, состояние |
| Bind mount | Каталог хоста, примонтированный как есть | Разработка, конфиги, доступ с хоста |

```bash
docker volume create pgdata
docker run -d --name db \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

# разработка: код с хоста, контейнерный интерпретатор
docker run --rm -v /opt/llmops/api:/app -w /app python:3.12-slim \
  pip install -r requirements.txt

docker volume ls
docker volume inspect pgdata
```

> [!CAUTION]
> Bind mount перекрывает содержимое пути в контейнере целиком. Примонтировал
> не туда — получил пустое приложение и «у меня не воспроизводится». И наоборот:
> пустой каталог на хосте Docker заэкранизирует и смонтирует как пустой, а
> не покажет ошибку.

## Права в контейнере: почему не root

Контейнер под root — это не «немного менее безопасно». Если не включены user namespaces, UID 0 внутри контейнера совпадает с UID 0 на хосте, и доступ к примонтированным каталогам у процесса полный.

Вторая, более частая проблема — **владельцы файлов**. Контейнер под root пишет в bind mount, файлы появляются на хосте с UID 0. Потом ansible, rsync или бэкап от твоего обычного пользователя не могут их прочитать, и ты получаешь невоспроизводимую проблему с правами, которую чинишь руками и забываешь.

```bash
docker run --rm -v /opt/llmops:/app alpine touch /app/root-owned.txt
ls -ln /opt/llmops/root-owned.txt
# -rw-r--r-- 1 0 0 ... root-owned.txt
```

> [!IMPORTANT]
> В образе всегда финальный `USER <непривилегированный>`, с числовым UID
> (10001, 999 и т.п.). Хосту он примонтирует каталог, который уже имеет
> нужного владельца, и ты не ловишь грабли с правами на следующем шаге пайплайна.

Если процессу всё-таки нужно писать в том, что создано root, задавай UID явно: `docker run --user 10001:10001 ...`. Не используй `chmod 777` — это не решение, это отказ от контроля.

## Теги, `latest` и работа с реестром

Тег — это указатель на мутабельный объект. `latest` не значит «самая новая версия», это просто тег без семантики, у которого свои правила кэширования на клиентах. Для прода он плох по трём причинам: нельзя откатиться на конкретную версию, нельзя доказать, что крутится, и нельзя заранее протестировать ровно то, что поедет в прод.

Рабочая схема для тебя: тег = версия приложения + короткий коммит; в реестр пушишь по тегу; в Kubernetes в `image:` указываешь **digest** (`@sha256:...`) — он неизменяем по определению.

```bash
docker tag api:1 registry.example.com/llmops/api:1.4.2
echo "$REGISTRY_TOKEN" | docker login registry.example.com -u ci --password-stdin
docker push registry.example.com/llmops/api:1.4.2
docker pull registry.example.com/llmops/api@sha256:9f2c...abc
```

> [!WARNING]
> `docker login -p ПАРОЛЬ` отправляет пароль в историю bash и в вывод `ps`,
> где его видят все пользователи хоста. Только `--password-stdin` с
> переменной окружения. Токен реестра — это доступ к публикации кода, его
> утечка не менее критична, чем утечка ключа к API.

## Практика: FastAPI в multi-stage

Создай лабораторный проект:

```bash
mkdir -p ~/labs/docker-api/src/api
cd ~/labs/docker-api
printf 'fastapi==0.115.0\nuvicorn==0.30.6\n' > requirements.txt
```

`src/api/main.py`:

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/healthz")
def healthz():
    return {"status": "ok"}
```

`Dockerfile`:

```dockerfile
FROM python:3.12-slim AS builder
WORKDIR /build
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip wheel --wheel-dir /wheels -r requirements.txt

FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
RUN groupadd -r app && useradd -r -g app -u 10001 app
WORKDIR /app
COPY --from=builder /wheels /wheels
COPY requirements.txt .
RUN pip install --no-index --find-links=/wheels -r requirements.txt \
 && rm -rf /wheels
COPY --chown=app:app src ./src
USER app
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "src.api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Сборка и проверка:

```bash
docker build -t api:1 .
docker history api:1                      # сколько весит каждый слой
docker run --rm api:1 id                  # должно быть uid=10001(app), не root
docker run -d --name api -p 8000:8000 api:1
curl -s localhost:8000/healthz
docker stop api && docker rm api
```

Затем проверь кэш: измени `src/api/main.py`, добавь `print()` в обработчик, пересобери и посмотри в выводе, какие слои помечены `CACHED`. Колёса собираться не должны — они не менялись.

Дальше — несколько контейнеров, связанных сетью, поднимаются уже не вручную: это [Docker Compose, лекция 09](devops/09-docker-compose.md).

## Где это ломается

1. **`COPY . .` стоит раньше установки зависимостей.** Каждый пуш кода пересобирает все пакеты. Сборка 8 минут вместо 40 секунд, и через месяц никто не помнит, почему пайплайн такой медленный.
2. **`apt-get update` и `apt-get install` в разных слоях.** Индекс пакетов закеширован, через неделю сборка падает с «Version not found» — и падает только у того, кто запустил билд первым.
3. **`CMD python -m api` в shell-форме.** SIGTERM не доходит до приложения, graceful shutdown не работает, деплой убивают по таймауту, недописанные данные теряются.
4. **`latest` в проде.** Вечером пятницы `docker pull` притащил другой бинарь под тем же именем. Отката нет — старый тег перезаписан, и diff «ничего не менял» не помогает.
5. **Контейнер под root + bind mount.** Файлы на хосте принадлежат root: бэкап, ansible и вторая машина не могут их прочитать. Проблема всплывает не в момент деплоя, а через две недели, в другом инструменте.
6. **Нет `.dockerignore`.** `COPY . .` уносит в образ `.env`, `.git` и `.venv`. Образ раздувается до гигабайта, а `docker history` показывает секреты в открытом виде.
7. **Alpine «потому что меньше».** `ImportError` на бинарном wheel, который на slim ставился годами. Экономия 100 МБ не стоит нестабильной сборки.
8. **Пустой кэш Docker в CI.** Каждый билд с нуля — это лишние 10 минут на коммит. Лечится пробросом кэша BuildKit через `--cache-from`/`--cache-to`, об этом в лекциях про CI/CD.
