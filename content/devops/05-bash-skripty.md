Скрипт на bash — это код, который живёт в проде дольше, чем любой релиз. Скрипт
деплоя, написанный «на бегу» и запущенный из crontab, через год становится
частью инфраструктуры: его никто не читал, но все боятся тронуть. Разница между
однострочником из интернета и Production-ready скриптом — не в длине, а в том,
как он ведёт себя при ошибке. Эта лекция про поведение.
---

## Shebang и почему не `/bin/sh`

Первая строка — `#!`, ядро читает её, чтобы понять интерпретатор:

```bash
#!/usr/bin/env bash
```

`#!/bin/bash` — работает, но сломается в системах без `/bin` (встречается в
некоторых дистрибутивах и в контейнерах с минимальным образом). `/usr/bin/env`
ищет `bash` в `$PATH`, это переносимо. Всегда начинай с `/usr/bin/env bash` и
заканчивай:

```bash
set -euo pipefail
IFS=$'\n\t'
```

Всегда ставь `#` в начале строки перед комментарием. Файл с BOM, CRLF или
пропущенным shebang будет отвергнут systemd-юнитом.

## Строгий режим: set -euo pipefail

Три флага, каждый закрывает свой класс ошибок. Разбираем отдельно, потому что
`set -e` — источник самого неочевидного поведения в bash.

### `-e` (errexit): выход при ошибке

Прекращает скрипт, если команда вернула ненулевой код.

### `-u` (nounset): ошибка на неопределённой переменной

Без него `echo $TYPO` молча печатает пустую строку, и через три строки ты
разбираешь, почему скрипт сделал не то. С `-u` скрипт падает сразу: «MY_APP_PORT:
unbound variable».

### `-o pipefail`: ошибка в любой части конвейера

Без него код возврата конвейера — это код **последней** команды:

```bash
false | echo ok        # код 0 — пайплайн «успешен», хотя первая часть упала
set -o pipefail
false | echo ok        # код 1 — теперь ложь видна
```

> [!IMPORTANT]
> Без `pipefail` в CI-пайплайне `json=$(curl -s $URL | jq .status)` спокойно
> вернёт пустоту при недоступном API и продолжит работать с `null`. Это не
> ошибка — это тихое расхождение с продакшном. `pipefail` делает пайплайн
> честным.

### Где `set -e` НЕ работает

Это надо знать дословно, иначе скрипт будет падать там, где ты не ждёшь, или
— что хуже — не падать там, где должен.

| Ситуация | Почему `set -e` не сработает | Что делать |
| --- | --- | --- |
| команда в условии `if` | условие по определению не должно валить скрипт | проверяй явно |
| команда в `&&` / `||` цепочке | кроме последней в цепочке | проверяй `$?` |
| перенаправление в цикле | `for f in $(find ...)` | не полагайся на `-e` |
| `$(...)` в присваивании | ошибка в подстановке | проверяй результат явно |

```bash
# ТАК ПРАВИЛЬНО
if ! grep -q 'ERROR' "$LOG"; then
  echo "ошибок нет"
fi

# ТАК НЕПРАВИЛЬНО (и не сработает под set -e)
grep -q 'ERROR' "$LOG" && echo "есть ошибки"
grep -q 'ERROR' "$LOG"

# РАБОЧИЙ ВАРИАНТ для цепочек
grep -q 'ERROR' "$LOG" || { echo "ошибок нет"; exit 0; }
```

Ключевое правило: **`set -e` — это страховка от цепных ошибок, а не логика
программы.** Условия, которые определяют поведение, пиши явно через `if` и
проверяй код возврата. `set -e` ловит только то, что ты не предусмотрел.

### Ловушка `set -e` с `if ! cmd`

Распространённая ошибка — писать `if ! command; then error; exit 1; fi` для
команд, где `!` инвертирует успех в ошибку. Работает корректно, но **теряет
код возврата**, и ты не можешь отличить «файл не найден» от «доступ запрещён».
В `set -e` сочетание `if ! cmd` без сохранения кода — потеря информации.

```bash
if ! docker ps -q | grep -q "$name"; then
  echo "контейнер $name не найден" >&2
  exit 1
fi
```

Здесь `grep` может вернуть 2 (ошибка доступа), а ты думаешь «нет контейнера».
Всегда, когда важна причина, проверяй раздельно:

```bash
docker ps -q | grep -q "$name"
case $? in
  0) echo "найден" ;;
  1) echo "не найден" >&2; exit 1 ;;
  *) echo "ошибка проверки" >&2; exit 2 ;;
esac
```

## Переменные и подстановки

| Конструкция | Что делает |
| --- | --- |
| `${VAR}` | значение переменной |
| `"$VAR"` | значение в кавычках — **всегда так** |
| `${VAR:-default}` | значение или default, если пусто |
| `${VAR:?сообщение}` | ошибка с сообщением, если пусто |
| `${VAR:=default}` | значение или присвоить default |
| `${#VAR}` | длина строки |
| `${VAR:0:10}` | подстрока |
| `${VAR#prefix}` | убрать префикс |
| `${VAR%.log}` | убрать суффикс |
| `${#ARR[@]}` | число элементов массива |
| `${ARR[@]}` / `"${ARR[@]}"` | все элементы |
| `${ARR[0]}` | первый элемент |
| `${ARR[@]:0:3}` | срез: первые три |

```bash
BASE_URL="${BASE_URL:-https://api.example.com}"
: "${API_TOKEN:?API_TOKEN обязателен}"     # упадёт сразу, если не задан

FILES=("$HOME"/data/*.csv)                 # массив с кавычками внутри
echo "файлов: ${#FILES[@]}"
printf '%s\n' "${FILES[@]:0:3}"            # первые три
for f in "${FILES[@]}"; do echo "$f"; done

basename="${LOGFILE%.log}"                # без суффикса
stripped="${LOGFILE#*/}"                  # без директории
```

> [!CAUTION]
> Массив пишется так: `ARR=(one two three)` — **без** пробела перед `=`. Это
> синтаксическая ошибка в bash. И `"${ARR[@]}"` в кавычках обязателен: без
> кавычек элементы с пробелами разобьются на отдельные аргументы.

## Условия: `[[ ]]` против `[ ]`

| Что | `[` (test) | `[[` (bash test) |
| --- | --- | --- |
| Это | внешняя программа | встроенная конструкция bash |
| Регулярки | нет | `=~` |
| Логика | `&& \|\|` | `&& \|\|`, слова как операнды |
| Скорость | медленнее | быстрее (нет fork) |
| Рекомендация | для совместимости с `sh` | **всегда в bash-скриптах** |

```bash
[[ -f "$f" ]]          # файл существует
[[ -d "$d" ]]          # каталог
[[ -n "$s" ]]          # строка непустая
[[ -z "$s" ]]          # строка пустая
[[ "$a" == "$b" ]]     # равенство
[[ "$a" != "$b" ]]
[[ "$a" -gt 10 ]]      # арифметическое: -gt -lt -ge -le -eq -ne
[[ "$port" =~ ^[0-9]+$ ]]   # проверка, что это число
[[ -x "$f" && -r "$f" ]]    # комбинация

# ВАЖНО: [[ ]] не нужно экранировать, [ ] нужно
[ "$a" = "x y" ]       # тут нужны кавычки
```

> [!TIP]
> Валидация ввода через `[[ =~ ]]` — первая линия обороны скрипта, который
> будет вызван с аргументами от cron или от соседнего скрипта:
> `[[ $PORT =~ ^[0-9]+$ ]] || { echo "порт должен быть числом" >&2; exit 1; }`.

## Циклы и функции

```bash
# for по списку
for host in web1 web2 web3; do
  ping -c1 -W1 "$host" >/dev/null && echo "$host up" || echo "$host down"
done

# for по C-стилю
for ((i = 0; i < 5; i++)); do
  echo "итерация $i"
done

# for по glob
for conf in /etc/nginx/sites-enabled/*.conf; do
  echo "--- $conf"
done

# while read — построчная обработка
while IFS= read -r line; do
  [[ -z "$line" ]] && continue
  echo "строка: $line"
done < /etc/hosts

# while по exit-коду команды
while ! nc -z "$HOST" "$PORT"; do
  echo "жду $HOST:$PORT"
  sleep 2
done
```

> [!CAUTION]
> `read -r` без `-r` обрезает обратные слэши, и пути с `\` или ввод с
> экранированием испортятся молча. `-r` почти всегда нужен.
> `IFS=` — чтобы не резать по пробелам при чтении строк с пробелами.

```bash
# функции
log() {
  local level="$1"; shift
  printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$level" "$*"
}

retry() {
  local tries="$1" delay="$2"; shift 2
  local n=1
  until "$@"; do
    (( n >= tries )) && { log ERROR "не удалось: $*"; return 1; }
    log WARN "попытка $n/$tries: $*"
    sleep "$delay"; (( n++ ))
  done
}

retry 3 5 curl -sf http://localhost:8080/healthz
```

`local` — обязателен для переменных внутри функций, иначе они перезапишут
глобальные. `shift` — убрать первый позиционный аргумент, чтобы `$@` были
только «настоящими».

## Аргументы скрипта

```bash
#!/usr/bin/env bash
set -euo pipefail

# $0 — путь к скрипту, $# — количество, "$@" — все аргументы, "$*" — склеенные
# $1, $2 ... — по позициям, $? — код возврата последней команды
shift   # убрать первый аргумент (обычно подкоманду)

usage() {
  cat <<EOF
Использование: $0 <host> <port> [-t таймаут]
EOF
}

HOST="${1:?укажите хост}"
PORT="${2:?укажите порт}"
shift 2
TIMEOUT=5
while [[ $# -gt 0 ]]; do
  case "$1" in
    -t) TIMEOUT="$2"; shift 2 ;;
    -h|--help) usage; exit 0 ;;
    *) echo "неизвестный аргумент: $1" >&2; usage; exit 1 ;;
  esac
done
```

`${1:?}` и `${2:?}` — валидация обязательных аргументов: скрипт падает с
понятным сообщением, а не с `host: command not found` двумя строками ниже.

## Коды возврата и обработка ошибок

```bash
cmd
rc=$?          # сразу, пока код не перезаписан
if cmd; then
  echo "успех"
else
  rc=$?
  case "$rc" in
    2) echo "плохие аргументы" ;;
    7) echo "не удалось подключиться" ;;
    28) echo "таймаут" ;;
    *) echo "ошибка $rc" ;;
  esac
  exit "$rc"
fi

# || для обязательного шага
mkdir -p "$DIR" || { echo "нет прав на $DIR" >&2; exit 1; }
```

| Код | Значение |
| --- | --- |
| 0 | успех |
| 1 | общая ошибка / usage |
| 2 | неверные аргументы |
| 3 | временная ошибка (можно повторить) |
| 126 | файл найден, но не исполняемый |
| 127 | команда не найдена |
| 128+N | убит сигналом N |
| 255 | ошибка самого скрипта |

> [!IMPORTANT]
> `curl -sS` — обязательная пара: `-s` глушит прогресс-бар, `-S` показывает
> ошибки, которые `-s` проглотил бы. Для API-вызовов добавляй `--fail-with-body`
> или `--fail`: без него HTTP 500 вернёт код 0, и твой скрипт посчитает
> несуществующий ответ валидным. И всегда `--max-time`, иначе зависший API
> навсегда остановит скрипт.

```bash
# curl: -sS молчаливый, но ошибки видны
resp=$(curl -sS --fail-with-body --max-time 10 -H "Authorization: Bearer $TOKEN" "$URL") \
  || { echo "API недоступен" >&2; exit 3; }

# jq: парсим JSON безопасно
ver=$(echo "$resp" | jq -r '.version // empty') \
  || { echo "невалидный JSON" >&2; exit 4; }
[[ -n "$ver" ]] || { echo "нет поля version" >&2; exit 4; }
```

| Проверка | Команда |
| --- | --- |
| валидный JSON | `echo "$r" \| jq -e . >/dev/null` |
| поле существует | `echo "$r" \| jq -e 'has("status")'` |
| тип правильный | `echo "$r" \| jq -e '.items \| type == "array"'` |
| достать значение | `echo "$r" \| jq -r '.items[].id'` |
| красивый вывод | `echo "$r" \| jq .` |
| из массива в TSV | `echo "$r" \| jq -r '.items[] \| [.id, .name] \| @tsv'` |

## trap: уборка при любом выходе

Скрипт может упасть где угодно. `trap` гарантирует, что временные файлы
уйдут, а lock снимется — даже по `Ctrl+C` (SIGINT), `kill` (SIGTERM) или при
ошибке из-за `set -e`.

```bash
#!/usr/bin/env bash
set -euo pipefail

TMPDIR_CREATED=""
LOCKFILE="/var/lock/myapp-backup.lock"

cleanup() {
  local rc=$?
  # сначала убрать lock, потом — временное (порядок важен при ошибке)
  [[ -n "$TMPDIR_CREATED" ]] && rm -rf "$TMPDIR_CREATED"
  rm -f "$LOCKFILE"
  log INFO "завершено с кодом $rc"
  exit "$rc"     # сохранить исходный код!
}

trap cleanup EXIT           # при любом выходе, включая ошибку
trap 'log WARN "прервано пользователем"; exit 130' INT
trap 'log WARN "получен SIGTERM"; exit 143' TERM

log() { printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}"; }

# Проверка lock-файла: не запущен ли уже другой экземпляр?
if ! ( set -o noclobber; echo $$ > "$LOCKFILE" ) 2>/dev/null; then
  log WARN "уже запущен другой экземпляр (pid $(cat "$LOCKFILE" 2>/dev/null))"
  exit 0
fi
TMPDIR_CREATED=$(mktemp -d /tmp/myapp-backup.XXXXXX)
log INFO "начало, временный каталог $TMPDIR_CREATED"
```

> [!CAUTION]
> В `cleanup` **первой строкой** пиши `local rc=$?`. Если этого не сделать,
> код возврата функции `cleanup` (скорее всего 0) перезапишет код, с которым
> скрипт завершался — и systemd увидит «успех» там, где был провал. Очень
> неприятный баг, потому что скрипт всё делает правильно, а `systemctl status`
> показывает `active (exited)`.

## Идемпотентность и lock-файл

**Идемпотентный** скрипт — тот, который можно запустить дважды и третий раз,
и результат будет тем же. Для бэкапа, деплоя и миграции это обязательное
свойство: cron упадёт, ты перезапустишь systemd-юнит, ночной запуск случится
дважды.

| Приём | Как |
| --- | --- |
| `mkdir` как атомарный lock | `mkdir "$LOCK" 2>/dev/null \|\| exit 0` |
| `noclobber` | перенаправление в файл с `set -o noclobber` — атомарно |
| `flock` | `flock -n 9 || exit 0` с дескриптором 9 |
| дата в имени | архивы не перезаписываются: `backup-$(date +%F).sql.gz` |
| проверка перед работой | «уже существует — выходим» или «заменяем атомарно» |

```bash
# flock: канонический способ
(
  flock -n 9 || { echo "уже выполняется"; exit 0; }
  # здесь работа
) 9>/var/lock/myapp-backup.lock

# атомарная замена: пишем во временное, потом mv (mv атомарен в пределах ФС)
tmp=$(mktemp)
mysqldump ... > "$tmp" && gzip "$tmp" && mv "$tmp" /backups/latest.sql.gz
```

> [!TIP]
> `flock -n 9 || exit 0` — правильный паттерн для cron-задачи: если
> предыдущий запуск ещё не закончился, новый просто выходит, не падает и не
> создаёт второй экземпляр. Для systemd-юнитов lock не нужен — там этим
> занимается сам systemd, `Restart=on-failure` не даст запуститься второму.

## Практика: два рабочих скрипта

### Скрипт 1: health-check с правильным exit-кодом

```bash
sudo tee /usr/local/bin/healthcheck > /dev/null <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

readonly SCRIPT_NAME="${0##*/}"
readonly LOG="/var/log/healthcheck.log"
readonly URL="${1:?укажите URL для проверки}"
readonly MAX_TIME="${2:-5}"

log() {
  printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}" | tee -a "$LOG"
}

body=$(curl -sS --fail-with-body --max-time "$MAX_TIME" "$URL" 2>&1) && rc=0 || rc=$?

case "$rc" in
  0)
    log OK "$URL отвечает: ${body:0:120}"
    exit 0
    ;;
  6|7)  # не удалось разрешить хост / не удалось подключиться
    log CRIT "$URL недоступен (curl rc=$rc): $body"
    exit 1
    ;;
  28)  # таймаут
    log CRIT "$URL не ответил за ${MAX_TIME}s"
    exit 1
    ;;
  22)  # --fail: HTTP-ошибка
    log WARN "$URL вернул HTTP-ошибку: $body"
    exit 1
    ;;
  *)
    log WARN "curl rc=$rc: $body"
    exit 1
    ;;
esac
EOF
sudo chmod 755 /usr/local/bin/healthcheck

# проверка
/usr/local/bin/healthcheck https://api.example.com/healthz
/usr/local/bin/healthcheck https://несуществующий.домен ; echo "код: $?"
```

> [!NOTE]
> Обрати внимание на `... && rc=0 || rc=$?`. Это самый надёжный способ поймать
> код возврата команды, не ломая `set -e`. Альтернатива — `if ! cmd; then rc=$?`
> (теряет код), поэтому используй именно форму с `&&`/`||`.

### Скрипт 2: бэкап с trap и проверкой

```bash
sudo tee /usr/local/bin/pg-backup > /dev/null <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

readonly DEST="/var/backups/postgres"
readonly RETENTION_DAYS=7
readonly LOCK="/var/lock/pg-backup.lock"

log() { printf '%s [%s] %s\n' "$(date -u +%FT%TZ)" "$1" "${*:2}"; }

cleanup() {
  local rc=$?
  [[ -n "${TMP:-}" ]] && rm -f "$TMP"
  rm -f "$LOCK"
  log INFO "завершено, код $rc"
  exit "$rc"
}
trap cleanup EXIT
trap 'log WARN "прервано"; exit 130' INT
trap 'log WARN "SIGTERM"; exit 143' TERM

# Атомарный lock: если папка создалась — мы первые
mkdir "$LOCK" 2>/dev/null || { log INFO "уже выполняется"; exit 0; }

mkdir -p "$DEST"
readonly STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
readonly FINAL="$DEST/pg-$STAMP.sql.gz"
TMP=$(mktemp /tmp/pg-backup.XXXXXX)

log INFO "начало бэкапа -> $FINAL"
PGPASSWORD="${PGPASSWORD:?задайте PGPASSWORD}" \
  pg_dumpall --clean --if-exists -h 127.0.0.1 -U postgres \
  | gzip -9 > "$TMP"

# Проверяем архив ДО того, как назовём его финальным именем
if ! gzip -t "$TMP"; then
  log ERROR "архив повреждён — финальное имя не присваиваем"
  exit 1
fi
[[ $(stat -c %s "$TMP") -gt 1024 ]] || { log ERROR "подозрительно мал"; exit 1; }

mv "$TMP" "$FINAL"
chmod 640 "$FINAL"
log INFO "готово: $(du -h "$FINAL" | cut -f1)"

log INFO "удаление бэкапов старше $RETENTION_DAYS дней"
find "$DEST" -name 'pg-*.sql.gz' -mtime +$RETENTION_DAYS -print -delete
log INFO "осталось файлов: $(find "$DEST" -name 'pg-*.sql.gz' | wc -l)"
EOF
sudo chmod 755 /usr/local/bin/pg-backup
sudo chmod 700 /var/lock 2>/dev/null || true

/usr/local/bin/pg-backup
sudo -u postgres /usr/local/bin/pg-backup   # не запустится: пароль не передан
```

> [!WARNING]
> Порядок в бэкапе критичен: сначала во временный файл, потом **проверка**,
> потом **mv** на финальное имя. Если сначала писать в финальное имя, обрыв на
 середине `pg_dumpall` оставит файл, который выглядит как валидный бэкап, пока
 не попадёт в ротацию. `mv` в пределах одной ФС атомарен — читатель никогда
 не увидит половину файла под финальным именем.

### Подключение к systemd

Скрипты из лекции [про процессы и systemd](devops/03-processy-i-systemd.md)
запускаются через юнит `Type=oneshot` + `RemainAfterExit=yes`. Юнит наследует
`set -euo pipefail` не от скрипта, а от юнита — код возврата скрипта systemd
читает сам. Проверь, что скрипт завершается осмысленным кодом:

```bash
sudo tee /etc/systemd/system/healthcheck.service > /dev/null <<'EOF'
[Unit]
Description=Проверка внешнего эндпоинта
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/bin/healthcheck https://api.example.com/healthz 5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl start healthcheck.service
systemctl status healthcheck.service
```

## Хорошие практики — сводка

- `set -euo pipefail` + `IFS=$'\n\t'` в первых строках каждого скрипта.
- Все переменные в кавычках: `"$VAR"`, `"${ARR[@]}"`.
- `readonly` для констант, `local` для переменных функций.
- Константы в верхнем регистре, переменные цикла — в нижнем.
- Имена переменных: `имя_функции_переменная` (`LOG_FILE_MAX_SIZE`).
- `trap ... EXIT` для уборки, с `local rc=$?` первым действием.
- Логи на stdout — их перехватит systemd; файловые логи — только если нужно.
- Все сообщения об ошибках в stderr: `>&2`.
- Валидация всех `$1` до того, как что-то сделано.
- `--fail` и `--max-time` у каждого `curl`, `--connect-timeout` у каждого `nc`.
- `flock` или `mkdir`-lock от двойного запуска.
- Проверка результата (`gzip -t`, `jq -e`, `sha256sum`) до того, как файл
  признан успешным.
- `mktemp -d` для временных файлов вместо предсказуемых `/tmp/myscript.tmp`.
- Никаких `rm -rf $VAR` — только `rm -rf -- "$DIR"` с проверкой, что переменная
  не пустая.

## Где это ломается

- **`set -e` без понимания, где он не работает.** Условие в `if` не роняет
  скрипт — «проверка» молча всегда проходит. Пиши логику в `if`, страховку
  оставь `-e`.
- **`rm -rf $DIR/` без кавычек.** При пустой переменной — `rm -rf /`. Пиши
  `rm -rf -- "${DIR:?}"`: `:` заставит скрипт упасть, а не удалить корень.
- **Конкатенация вместо проверки exit-кода.** `cmd; do_something` — ошибка `cmd`
  проглочена. Пиши `cmd || { log ERROR; exit 1; }`. И `$?` не сразу:
  `cmd; echo "ошибка: $?"` после `if` уже покажет 0. Записывай `rc=$?`
  немедленно или используй `cmd && rc=0 || rc=$?`.
- **Cleanup теряет код возврата.** Без `local rc=$?` в `cleanup` systemd увидит
  `exited (status 0)` вместо реального кода. Десятки минут ложной диагностики.
- **`curl` без `--fail`.** HTTP 500 или 404 возвращают код 0. Скрипт
  разбирает тело и падает в jq с невнятным сообщением. Всегда `--fail`.
- **Бэкап без проверки.** Архив, который не открывается, хуже отсутствующего:
  он занимает место и создаёт иллюзию безопасности. `gzip -t` обязателен.
- **Скрипт в crontab без проверки результата.** Cron не скажет, что упало.
  Всегда заворачивай в юнит с `journalctl` или пиши в лог через `>>`.
  Кстати, `chmod +x` без shebang даёт `Exec format error` — юнит падает сразу,
  и это самый безобидный из диагностируемых случаев.
- **Разбор JSON через `grep`.** Один лишний пробел в JSON от API — и скрипт
  решил, что данных нет. `jq -r` и только `jq`.
