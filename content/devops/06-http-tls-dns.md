Мысленно HTTP — это просто текстовый протокол поверх TCP: клиент пишет
запрос, сервер отвечает. Всё усложнение начинается, когда этот текст должен
пересекать публичную сеть. Именно там появляются TLS-сертификаты, цепочки
доверия, SNI, редиректы, заголовки, которые nginx обязан прокинуть, и
загадочное «502 Bad Gateway». Эта лекция — практический минимум, который
позволяет не бояться HTTPS.

## Из чего состоит URL и как устроен HTTP

```text
https://api.example.com:8443/v1/chat/completions?stream=true&model=llama3#anchor
  │     │                  │      │                  │           │         └─ якорь на странице (браузер)
  │     │                  │      │                  │           └─────────── query string
  │     │                  │      │                  └───────────────────── путь (path)
  │     │                  │      └──────────────────────────────────────── порт (необязателен)
  │     │                  └─────────────────────────────────────────────── хост (домен)
  │     └────────────────────────────────────────────────── схема
  └─────────────────────────────────────────────────────────── протокол
```

Запрос состоит из старт-строки, заголовков и (опционально) тела:

```bash
curl -v https://api.example.com/v1/chat 2>&1 | head -20
```

```http
> GET /v1/chat HTTP/1.1            ← метод, путь, версия
> Host: api.example.com            ← обязательный заголовок для HTTP/1.1
> User-Agent: curl/8.5.0
> Accept: application/json

< HTTP/1.1 200 OK                  ← статус
< Content-Type: application/json
< Content-Length: 128
```

### Методы

| Метод | Семантика | Идемпотентный | Безопасно ли повторять |
| --- | --- | :---: | :---: |
| `GET` | получить, без изменения состояния | да | да |
| `POST` | создать/выполнить действие | нет | нет |
| `PUT` | заменить ресурс целиком | да | да |
| `PATCH` | изменить часть ресурса | нет | нет |
| `DELETE` | удалить | да | да |
| `HEAD` | как GET, но без тела | да | да |
| `OPTIONS` | какие методы поддержаны, CORS | да | да |

> [!IMPORTANT]
> Идемпотентность — не академическое свойство, а требование безопасности.
> **Ретрай-логика** в твоём коде (и в коде LLM-шлюза, который вызывает внешний
> API) почти всегда полагается на неё: повторный `POST` может создать две
> платёжные транзакции или два чата. Если операция не идемпотентна, вводи
> `Idempotency-Key` — заголовок, который сервер использует для дедупликации.

### Коды ответов — с конкретикой

| Класс | Семантика | Примеры |
| --- | --- | --- |
| **2xx** | успех | `200 OK`, `201 Created`, `202 Accepted`, `204 No Content` |
| **3xx** | перенаправление | `301` навсегда, `302` временно, `304` не изменилось (кэш) |
| **4xx** | ошибка клиента | `400` невалидный запрос, `401` нет аутентификации, `403` нет прав, `404` нет такого ресурса, `408` таймаут клиента, `409` конфликт, `413` слишком большое тело, `429` превышен лимит |
| **5xx** | ошибка сервера | `500` внутренняя, `502` шлюз получил негодный ответ, `503` недоступно временно, `504` таймаут шлюза |

Разница между `401` и `403` регулярно путают: `401 Unauthorized` — «покажи, кто
ты» (нужна аутентификация, приложение должно вернуть 401 с `WWW-Authenticate`),
`403 Forbidden` — «я знаю, кто ты, и всё равно нет» (аутентификация прошла,
прав нет). И та, и другая — ошибка клиента, сервер исправен.

### Заголовки, которые важны инженеру

| Заголовок | Зачем |
| --- | --- |
| `Host` | какому виртуальному хосту адресован запрос (HTTP/1.1) |
| `Authorization` | `Bearer <token>` или `Basic <base64>` |
| `Content-Type` | формат тела: `application/json`, `text/plain` |
| `Accept` | что клиент готов принять |
| `Content-Length` / `Transfer-Encoding: chunked` | размер тела или потоковая передача |
| `Cache-Control` | `no-store`, `max-age=60`, `private`, `no-cache` |
| `Connection` | `keep-alive` для переиспользования TCP-соединения |
| `X-Forwarded-For` / `X-Real-IP` | реальный IP клиента за прокси |
| `X-Forwarded-Proto` | `https` или `http` — чтобы приложение знало схему |
| `Server` | кто отвечает (nginx, nginx/1.24.0) |
| `Strict-Transport-Security` | HSTS |

```bash
# посмотреть заголовки запроса и ответа
curl -I https://api.example.com/healthz       # только заголовки (HEAD)
curl -sv https://api.example.com/healthz 2>&1 | grep -E '^[<>]'
curl -sS -X POST https://api.example.com/v1/chat \
  -H 'Authorization: Bearer sk-...' \
  -H 'Content-Type: application/json' \
  -d '{"model":"llama3","messages":[{"role":"user","content":"hi"}]}' | jq
```

> [!TIP]
> `curl -sv` (или `-v` с `-o /dev/null`) — твой основной инструмент отладки
> HTTP. Он показывает весь обмен: заголовки, редиректы (с `--location`), TLS
> handshake и тело ответа. Большинство «ничего не работает» решаются за две
> минуты с `-v`.

## HTTPS = HTTP внутри TLS

Когда ты пишешь `https://`, браузер или `curl`:

1. Устанавливает TCP-соединение на порт 443.
2. **TLS handshake**: клиент и сервер согласуют версию протокола, набор
   шифров (cipher suite) и ключи сессии; сервер показывает **сертификат**.
3. Клиент проверяет сертификат: подписан ли доверенным CA, не истёк ли, совпадает
   ли домен.
4. Если всё сошлось — внутри зашифрованного канала идёт обычный HTTP.

### Что внутри сертификата

| Поле | Что значит | Что проверять |
| --- | --- | --- |
| `Subject / CN` | Common Name — домен | устарело, смотри SAN |
| `SAN` | Subject Alternative Names — все домены | **главное поле** для проверки |
| `Issuer` | кто выдал | CA, которому доверяет клиент |
| `Not Before / Not After` | срок действия | **истечение = полный отказ** |
| `Serial`, `Signature` | идентификатор и подпись CA | криптографическая цепочка |
| `Key Usage` | для чего можно использовать | `Digital Signature`, `Key Enciphering` |
| `Extended Key Usage` | для чего именно | `serverAuth` обязателен |

```bash
# полная информация о сертификате
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null
openssl x509 -noout -text -in cert.pem

# то же одной строкой
echo | openssl s_client -connect api.example.com:443 -servername api.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# проверить цепочку и срок
openssl s_client -connect api.example.com:443 -servername api.example.com \
  -verify_return_error </dev/null
```

| Код возврата `openssl s_client` | Значение |
| --- | --- |
| `Verify return code: 0 (ok)` | всё в порядке |
| `self signed certificate` | сертификат не подписан CA |
| `unable to get local issuer certificate` | нет промежуточного сертификата в цепочке |
| `certificate has expired` | истёк срок |
| `hostname mismatch` | SAN не содержит имени, которое ты запросил |

### Цепочка доверия и почему нужен `fullchain.pem`

Файл `cert.pem` — только твой сертификат. Браузеру нужно проверить его
подпись, а подпись сделана не корневым, а **промежуточным** CA (intermediate).
Путь проверки:

```text
корневой CA (в магазине ОС/браузера, не отправляется)
   └── промежуточный CA (intermediate)
         └── сертификат твоего домена  ← вот что проверяет клиент
```

> [!CAUTION]
> Самая частая ошибка в настройке TLS: указать в конфиге **только свой
> сертификат**. Браузер и мобильные клиенты (которые хранят только корневой CA)
> скажут `unable to get local issuer certificate`. Нужен `fullchain.pem` — файл
> с сертификатом **плюс** промежуточными, в порядке от твоего к корню.
> Let's Encrypt даёт именно `fullchain.pem`, и его нужно использовать.

### Самоподписанный сертификат: когда можно, когда нельзя

Самоподписанный сертификат — тот, где issuer = subject. Он не вызывает
доверия у браузера, и ошибка `self signed certificate` у пользователя.

| Ситуация | Самоподписанный | Вывод |
| --- | --- | --- |
| Доступ к внутреннему сервису с одной машины (curl -k) | допустимо | |
| Доступ между своими ВМ, где ты один контролируешь CA | **лучший вариант** | `mkcert`, `step-ca`, корпоративный CA |
| Доступ к AD/LDAPS от рабочих машин в домене | можно, если выпущен через **AD CS** и установлен в хранилище «Доверенные корневые центры» | |
| Внутренний портал для 50 сотрудников в домене | лучше через AD CS | |
| Публичный сайт, доступный из интернета | **нельзя** | Let's Encrypt |
| Сервис, где есть 2–3 стационарных потребителя API | можно, если по HTTP | TLS без доверия хуже, чем HTTP |

> [!IMPORTANT]
> Для внутреннего контура есть два правильных пути. Первый: выпустить свой CA
> и раздать его корневой сертификат на все машины (в домене — через GPO в
> хранилище «Доверенные корневые центры сертификации»). Второй: использовать
> `mkcert` на своей машине, он автоматически создаст локальный CA и
> `localhost.crt`. Третий, самый простой для внутренних HTTP-сервисов, —
> **оставить HTTP**: шифрование без проверки цепочки создаёт ложное чувство
> безопасности и добавляет точки отказа. Решай по таблице, а не по ощущениям.

```bash
# выпуск локального сертификата для разработки (админ машины)
mkcert -install                      # свой CA в системное хранилище
mkcert -cert-file api.local.crt -key-file api.local.key api.local localhost 127.0.0.1
sudo cp api.local.crt /etc/nginx/ssl/
sudo cp api.local.key /etc/nginx/ssl/
sudo chown root:root /etc/nginx/ssl/api.local.key
sudo chmod 600 /etc/nginx/ssl/api.local.key
```

## Let's Encrypt и certbot

ACME — протокол автоматической выдачи сертификатов. В двух словах: certbot
доказывает серверу Let's Encrypt, что он действительно владеет доменом
(HTTP-челлендж или DNS-челлендж), и получает сертификат с коротким сроком
(90 дней) **бесплатно**. Короткий срок — не минус: это компромисс, чтобы
компрометация CA не убивала сотни тысяч сайтов одномоментно.

| Плагин | Как доказывает | Нужен ли порт 80 | Подходит |
| --- | --- | :---: | --- |
| `--nginx` | временный файл-челлендж в конфиге nginx | да, если не настроен редирект | сервер с nginx |
| `--webroot` | файл в каталоге, который отдаёт веб-сервер | да, если этот каталог доступен | nginx с известным root |
| `--standalone` | certbot сам поднимает HTTP-сервер | да, порт должен быть свободен | без веб-сервера |
| `--dns-*` | TXT-запись в DNS | нет | wildcard-домены, внутренние DNS |

```bash
# установка и выпуск для nginx
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d api.example.com -d www.example.com

# проверка: тестовая среда (не тратит лимит)
sudo certbot certonly --nginx -d api.example.com --dry-run

# посмотреть сертификаты и сроки
sudo certbot certificates
sudo ls -l /etc/letsencrypt/live/api.example.com/

# принудительное обновление сейчас
sudo certbot renew --force-renewal
systemctl list-timers | grep certbot     # таймер автообновления
sudo systemctl status certbot.timer
```

| Файл в `/etc/letsencrypt/live/<домен>/` | Что это |
| --- | --- |
| `fullchain.pem` | сертификат + цепочка — **это указывай в nginx** |
| `privkey.pem` | приватный ключ, права 600, никогда не копируй наружу |
| `cert.pem` | только сертификат, без цепочки |
| `live/` | симлинки на актуальные версии в `archive/` |
| `renewal/` | конфигурация для продления |

Автопродление: таймер `certbot.timer` дважды в сутки запускает `certbot renew`,
который продлевает сертификат, если до истечения меньше 30 дней. После
продления нужно сказать nginx, чтобы он перечитал сертификаты:

```ini
# /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh (chmod +x)
#!/usr/bin/env bash
/usr/sbin/nginx -t && /usr/bin/systemctl reload nginx
```

> [!CAUTION]
> Ставь `deploy-hook` **всегда**. Renew успешно обновит файл, а nginx
> продолжит отдавать старый сертификат из памяти — без `reload` он загружает
> сертификат только при старте. Через 90 дней у тебя истекает сертификат,
> который на диске свежий.

## nginx как обратный прокси

Проксирование — приём, когда nginx принимает соединение от клиента и сам
делает запрос к бэкенду. Две причины: единая точка входа с TLS и заголовками,
и возможность спрятать бэкенд за локальным интерфейсом.

Минимальный рабочий конфиг:

```nginx
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_stapling on;
    ssl_stapling_verify on;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    client_max_body_size 25m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        proxy_connect_timeout 5s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;

        proxy_buffering on;
        proxy_buffer_size 16k;
    }

    location = /healthz {
        access_log off;
        proxy_pass http://127.0.0.1:8000/healthz;
    }
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}
```

### Почему заголовки `X-Forwarded-For` и `X-Real-IP` обязательны

nginx меняет источник соединения: бэкенд видит `127.0.0.1`, а не клиентский
IP. Без этих заголовков бэкенд не сможет записать в логи реальный IP, и вся
ваша аналитика наблюдаемости покажет, что все запросы приходят с localhost.
Это обесценивает rate limiting, геоаналитику и расследование инцидентов.

| Заголовок | Что содержит |
| --- | --- |
| `X-Real-IP` | адрес непосредственного клиента прокси |
| `X-Forwarded-For` | вся цепочка прокси, через запятую; `$proxy_add_x_forwarded_for` **добавляет** `$remote_addr` |
| `X-Forwarded-Proto` | исходная схема (`http`/`https`) |
| `Host` | имя, которое запрашивал клиент — бэкенд строит по нему ссылки |

> [!IMPORTANT]
> Третий прокси в цепочке перезапишет `X-Forwarded-For`, а не добавит. Для
> внешнего балансировщика (Cloudflare, ELB) нужно `proxy_set_header
> X-Forwarded-For $http_x_forwarded_for` или явная стратегия. Если стоит CDN —
> доверяй только последнему элементу цепочки, иначе IP клиента подделывается
> тривиально.

Приложение должно доверять этому заголовку **только** от своего прокси —
иначе любой может прислать `X-Forwarded-For` и подделать свой адрес.

### Keep-alive, HTTP/2 и кэширование

`Connection: keep-alive` — переиспользование одного TCP-соединения для многих
запросов. Без него на каждый запрос — новый TLS handshake, и latency
съедается на установке соединения. nginx сам управляет этим, но важно знать:
`proxy_http_version 1.1` **обязателен** вместе с пустым
`proxy_set_header Connection ""` — иначе бэкенд отвечает на HTTP/1.0, и
keep-alive ломается.

| Директива | Что делает |
| --- | --- |
| `keepalive_timeout 65;` | сколько держать idle-соединение |
| `client_max_body_size 25m;` | лимит тела запроса (413 при превышении) |
| `proxy_buffering on;` | nginx читает ответ целиком и отдаёт клиенту (быстрее для клиента) |
| `proxy_buffering off;` | для streaming-ответов LLM, иначе буферизация прячет поток |
| `gzip on;` | сжатие текстовых ответов |

> [!NOTE]
> Стриминг — это как раз то, что нужно для LLM-шлюза: `text/event-stream` или
> chunked-ответы. С `proxy_buffering on` nginx ждёт, пока бэкенд закончит весь
> ответ, и пользователь не видит ни одного токена до конца генерации. Для
> `/v1/chat/completions` с `stream: true` нужно либо выключить буферизацию, либо
> настроить её по времени: `proxy_buffering off` в `location /v1/`.

## «По HTTP работает, по HTTPS — 502»: диагностика

Это самый частый симптом настройки TLS. Твоя диагностика — пять шагов:

| Шаг | Команда | Что увидишь |
| --- | --- | --- |
| 1. nginx в порядке? | `sudo nginx -t` | синтаксис, пути к сертификатам |
| 2. конфиг применён? | `sudo nginx -T \| grep -A5 server_name` | реальный конфиг |
| 3. бэкенд отвечает напрямую? | `curl -sv http://127.0.0.1:8000/healthz` | отказ или 200 |
| 4. что в логе nginx? | `sudo tail -50 /var/log/nginx/error.log` | точная причина |
| 5. что видно снаружи? | `curl -sv https://api.example.com/healthz` | TLS-ошибка или 502 |

```bash
# причины 502 по логам
sudo grep -E 'upstream|SSL' /var/log/nginx/error.log | tail -20
```

| Сообщение в `error.log` | Причина | Решение |
| --- | --- | --- |
| `connect() failed (111: Connection refused)` | бэкенд не слушает на указанном порту | `ss -tulpn \| grep 8000`, проверь, что он на `127.0.0.1` |
| `connect() failed (113: No route to host)` | бэкенд на другом хосте, нет маршрута | проверь `ip route` с nginx-хоста |
| `no live upstreams` | бэкенд в `down` по health-check | смотри конфиг upstream |
| `SSL_do_handshake() failed` | бэкенд говорит HTTP, а nginx ждёт HTTPS (или наоборот) | `proxy_pass http://` вместо `https://` |
| `upstream timed out` | бэкенд не уложился в `proxy_read_timeout` | увеличь таймаут или чини бэкенд |
| `cannot load certificate` | неверный путь или права на `privkey.pem` | `sudo nginx -t` скажет точно |

> [!TIP]
> Если 502 возникает **только** при обращении снаружи, а с `127.0.0.1` всё
> работает, добавь в конфиг временно `error_log ... debug;` и
> `worker_connections 1024`, затем смотри `/var/log/nginx/debug.log`. В 90%
> случаев ответ уже в обычном `error.log` — просто ищи по слову `upstream`.

> [!NOTE]
> Один бэкенд в `proxy_pass` — это не HA, это одна точка отказа. Как сделать
> несколько бэкендов за одним адресом, чтобы падение одного не было видно
> пользователю, — в [лекции про высокую доступность](devops/07-ha-i-balansirovka.md).

## Где это ломается

- **Указали `cert.pem` вместо `fullchain.pem`.** У тебя работает (браузер
  кешировал цепочку), у нового клиента — `unable to get local issuer
  certificate`. Проверяй всегда через чистый клиент:
  `openssl s_client -connect host:443 -servername host`.
- **Забыли reload после продления.** `certbot renew` обновил файлы, nginx
  продолжает отдавать старый. Deploy-hook решает. Сюда же — 443 открыт, а 80
  закрыт: ACME-челлендж идёт по HTTP, без порта 80 продление провалится, и
  через 60 дней всё упадёт уже с истёкшим сертификатом.
- **Истёк срок, а мониторинг молчит.** Проверяй срок заранее, предупреждение
  за 14 дней — не за день. Простой скрипт:
  `openssl s_client ... | openssl x509 -checkend $((14*86400)) -noout`.
- **`X-Forwarded-For` не прокинут.** Приложение пишет в лог `127.0.0.1`, и ты
  не можешь понять, кто ходил на API ночью.
- **Сертификат на `api.example.com`, а обращаются по IP.** SAN не содержит IP
  (в новых сертификатах только DNS-имена) — `hostname mismatch`. Для IP нужен
  отдельный сертификат или отключить проверку.
- **HSTS включили до того, как всё заработало по HTTPS.** Браузер запомнил
  «сюда только по HTTPS» на 6 месяцев. Если TLS сломался — у всех перестало
  открываться, и отключить это можно только из другого браузера или вручную.
  Начинай с малого `max-age=300` и расширяй, когда убедился.
- **`proxy_buffering on` для стриминга LLM.** Ответ приходит целиком после
  генерации, пользователь думает, что всё зависло.
- **Слишком широкие `ssl_protocols`.** `TLSv1` и `SSLv3` небезопасны. Только
  `TLSv1.2 TLSv1.3`.
- **`curl -k` в проде.** Это не «режим разработчика», это отключение
  проверки цепочки. Если ты добавил `-k` в скрипт, значит проблема с
  сертификатом не решена, а заглушена.
