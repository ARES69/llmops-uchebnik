Права доступа — это не академическая часть Unix, а операционная безопасность.
Когда в твоём контуре лежат ключи от LLM-провайдера, доступы к Proxmox и
конфигурация с паролем от внутреннего сервиса, то «кто и что может прочитать»
перестаёт быть теорией и становится вопросом, по которому придётся отвечать.
Вторая часть лекции — inode: механика, которая объясняет самый известный
парадокс Linux, из-за которого инциденты «диск полон, а файлов нет» тянутся
неделями.

## Каталоги Linux: что где лежит

FHS (Filesystem Hierarchy Standard) — не догма, а соглашение, на котором держатся
все дистрибутивы и весь софт. Знание его экономит время: вместо поиска «где
конфиг» ты идёшь сразу в нужный каталог.

| Путь | Что лежит | Пример из твоего контура |
| --- | --- | --- |
| `/` | корень, монтируется всегда | |
| `/etc` | конфигурация всей системы | `/etc/nginx/nginx.conf`, `/etc/hosts`, `/etc/systemd/system/` |
| `/var` | изменяемое: логи, базы, очереди | `/var/log`, `/var/lib/postgresql` |
| `/var/log` | логи всех служб | `/var/log/syslog`, `/var/log/nginx/error.log` |
| `/home` | домашние каталоги пользователей | |
| `/root` | домашний каталог root | |
| `/opt` | сторонний софт целиком | `/opt/myapp`, `/opt/grafana` |
| `/srv` | данные, отдаваемые по сети | бывает реже, чем `/opt` |
| `/tmp` | временные файлы, очищается | |
| `/usr` | программы и библиотеки, read-only по смыслу | `/usr/bin`, `/usr/local/bin` |
| `/bin`, `/sbin` | тоже программы, на `/usr` — симлинки | `/bin` → `/usr/bin` |
| `/proc` | виртуальная ФС: процессы и ядро | `/proc/<pid>/`, `/proc/meminfo` |
| `/sys` | виртуальная ФС: устройства и драйверы | |
| `/dev` | устройства: диски, сетевые, null | `/dev/sda`, `/dev/null` |
| `/boot` | ядро и initramfs | |
| `/etc/default/grub` | конфиг загрузчика GRUB | |

> [!IMPORTANT]
> `/proc`, `/sys` и `/dev` — не файлы на диске. Они генерируются ядром в памяти.
> «Удалить» `/proc` нельзя, его не существует как файла. Практический вывод:
> если ты ищешь причину через `find / -name ...`, всегда исключай `/proc`,
> `/sys` и `/dev`, иначе поиск зависнет намертво.

Проверить, что и куда смонтировано:

```bash
lsblk -f                        # диски и точки монтирования
df -h                           # использование по файловым системам
mount | column -t               # все монтирования, читаемо
findmnt / /var                  # что смонтировано в конкретный каталог
cat /proc/mounts                # низкоуровневый список, его читает systemd
```

| Команда | Отвечает на вопрос |
| --- | --- |
| `df -h` | сколько **файловой системе** нужно места (свободно / занято) |
| `du -sh /var/*` | сколько места занимает **конкретный каталог** |
| `stat file` | метаданные: размер, inode, владелец, время |
| `ls -i file` | номер inode файла |

Разница между `df` и `du` — не в реализации, а в семантике: `df` считает по
блокам, `du` обходит дерево. Если ответы расходятся — читайте про inode ниже.

## Разбор `ls -l`: права

Строка из десяти символов — это ответы на четыре вопроса сразу.

```text
-rwxr-xr--  1  devops  devops  4096  Jan 15 10:23  deploy.sh
│└┬┘└┬┘└┬┘   │  │       │       │       │           └── имя
│ │  │  │    │  │       │       │       └──── дата изменения
│ │  │  │    │  │       │       └───────── размер в байтах
│ │  │  │    │  │       └───────────────── группа-владелец
│ │  │  │    │  └───────────────────────── владелец
│ │  │  │    └──────────────────────────── число жёстких ссылок
│ │  │  └───────────────────────────────── права группы
│ │  └──────────────────────────────────── права остальных (other)
│ └─────────────────────────────────────── тип файла
└───────────────────────────────────────── права владельца (user)
```

| Тип | Что это |
| --- | --- |
| `-` | обычный файл |
| `d` | каталог |
| `l` | символическая ссылка |
| `L` | сокет |
| `c` / `b` | устройство символьное / блочное |

| Буква | Право | Для файла | Для каталога |
| --- | --- | --- | --- |
| `r` | читать | читать содержимое | перечислять имена |
| `w` | писать | менять содержимое | создавать и удалять **элементы** |
| `x` | исполнять | запускать | **заходить внутрь** и обходить |

Последний столбец — ловушка, на которой спотыкается половина новичков. Право `w`
на каталоге — это не «редактировать каталог». Это «создавать и удалять в нём
файлы». А право `r` без `x` даёт каталог, в котором видны имена, но нельзя
войти. Проверяется это так:

```bash
mkdir -p /tmp/priv-test && chmod 400 /tmp/priv-test   # r-- : имена видно
ls /tmp/priv-test        # видно, что пусто — ls работает
cd /tmp/priv-test        # Permission denied — нужен x
```

### chmod: символьный и восьмеричный

Символьный — когда меняешь один класс прав:

```bash
chmod u+x deploy.sh        # дать владельцу исполнение
chmod g-w config.yaml      # убрать запись у группы
chmod o=rw shared.txt      # установить права для остальных точно
chmod a+rx script.sh       # всем классам — чтение и исполнение
```

Восьмеричный — когда задаёшь всё сразу. Это форма, которую ты увидишь в
большинстве примеров:

| Значение | Буквы | Кто обычно использует |
| --- | --- | --- |
| `700` | `rwx------` | приватный ключ, `.ssh/config` |
| `750` | `rwxr-x---` | скрипты, доступные своей группе |
| `755` | `rwxr-xr-x` | исполняемые файлы, каталоги, публичные каталоги |
| `640` | `rw-r-----` | конфиги с секретами, читает владелец и группа |
| `600` | `rw-------` | `.env` с токенами, ключи приложений |
| `644` | `rw-r--r--` | обычные файлы, доступные всем на чтение |
| `775` / `664` | `rwxrwxr-x-` | общие рабочие каталоги для команды |

```bash
chmod 640 /etc/myapp/secrets.yaml     # конфиг с токеном
chmod +x deploy.sh                    # +x добавляет x всем, у кого есть r
chmod -R 755 /opt/myapp/public        # рекурсивно по каталогу
find /opt/myapp/config -name '*.yaml' -exec chmod 640 {} \;
```

> [!CAUTION]
> `chmod -R 777` на продакшне — это не «решить проблему с правами», а снять
> контроль над системой. Если что-то не работает, сначала посмотри в лог: там
> почти всегда написано, прав какого пользователя и на какой путь не хватило.
> `777` на каталоге даёт любому пользователю права удалять в нём файлы, включая
> чужие, — это уязвимость, а не настройка.

### chown и umask

Владелец меняется через `chown`, группа — через `chgrp` или ту же команду:

```bash
sudo chown devops:devops /opt/myapp
sudo chown -R devops:devops /opt/myapp
sudo chown -R devops: /opt/myapp       # только владелец, группа прежняя
sudo chgrp -R deploy /opt/myapp/config
```

> [!NOTE]
> Смена владельца файла **сбрасывает бит setuid**. Это защита ядра от
> классической атаки: пользователь создаёт setuid-скрипт, а root случайно
> запускает его — и получает root. После `chown` привилегия исчезает.

`umask` — маска, которая **вычитается** из 777 при создании файлов и из 777 при
создании каталогов. Значение `022` означает: новый файл получит 755, новый
каталог — 755.

```bash
umask                      # посмотреть текущую
umask 027                  # файлы 640, каталоги 750
echo 'umask 027' >> ~/.bashrc
touch /tmp/umask-test && ls -l /tmp/umask-test
```

| Маска | Файлы | Каталоги | Для чего |
| --- | --- | --- | --- |
| `022` | 644 | 755 | умолчание Debian/Ubuntu |
| `027` | 640 | 750 | рабочая среда с группой |
| `077` | 600 | 700 | приватные данные, ничего не светить наружу |

### Спец-биты

| Бит | Как ставится | Что делает | Живой пример |
| --- | --- | --- | --- |
| setuid | `chmod u+s`, `4xxx` | запуск с правами владельца файла | `passwd`, `ping`, `sudo` |
| setgid | `chmod g+s`, `2xxx` | каталог: новые файлы наследуют группу; файл: запуск с правами группы | общая рабочая папка |
| sticky | `chmod +t`, `1xxx` | из каталога удалить файл может только владелец файла или root | `/tmp`, `/var/tmp` |

```bash
ls -ld /tmp                    # drwxrwxrwt — буква t на месте x, sticky
ls -l $(which passwd)         # -rwsr-xr-x — setuid на passwd

# sticky на каталоге: пользователь не может удалить чужой файл
sudo mkdir /tmp/shared && sudo chmod 1777 /tmp/shared
# коллега создаёт файл, ты его не удалишь — сработает защита
```

Про `/tmp` стоит знать отдельно: sticky-бит там стоит по умолчанию, и это
единственная причина, по которой один пользователь не может снести файлы
другого. Он не спасает от переполнения `/tmp` — от этого спасает `systemd-tmpfiles`
и отдельный tmpfs, о котором пойдёт речь дальше в связке с HA.

### sudo и sudoers

`sudo` даёт выполнить команду от имени другого пользователя, но **не** является
самоцелью. Правильная настройка — выдать конкретные команды конкретному
инженеру, а не `NOPASSWD: ALL`.

```bash
sudo -l                        # что мне реально разрешено
sudo -u postgres psql          # выполнить от имени postgres
sudo -u root systemctl status nginx
```

Файл `/etc/sudoers` правится только через `visudo` — он валидирует синтаксис
перед записью, и это единственная причина, по которой нельзя писать в него
обычным редактором. Ошибка в этом файле режет тебе root до перезагрузки.

```bash
sudo visudo
```

Полезные записи:

```text
# перезапуск своего сервиса без пароля
devops ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp.service

# скрипт с полными правами, но доступ к его содержимому закрыт
devops ALL=(root) NOPASSWD: /usr/local/sbin/rotate-app-logs

# несколько команд через запятую — так КОМПАКТНЕЕ и его легче ревьюить
devops ALL=(root) NOPASSWD: /bin/systemctl reload nginx, \
            /bin/journalctl -u myapp *
```

> [!WARNING]
> `devops ALL=(root) NOPASSWD: ALL` — это пароль root без пароля. Правило
> `sudo tee /etc/sudoers.d/10-devops` тоже плохая идея: если у пользователя есть
> безпарольный `sudo` для всего, он может переписать сам sudoers. Минимум —
> конкретные команды; максимум — заворачивать сложную логику в отдельный
> root-owned скрипт, который сам делает `sudo`-проверки внутри.

Скрипт, который можно безопасно отдать в безпарольный sudo:

```bash
sudo tee /usr/local/sbin/rotate-app-logs > /dev/null <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
[[ $EUID -eq 0 ]] || { echo "нужны root-права" >&2; exit 1; }
find /var/log/myapp -name '*.log' -mtime +14 -delete
systemctl reload myapp.service
EOF
sudo chown root:root /usr/local/sbin/rotate-app-logs
sudo chmod 755 /usr/local/sbin/rotate-app-logs
```

Скрипт принадлежит root, писать в него инженер не может — значит, содержимое
команды, которую ему разрешили, нельзя подменить.

## Жёсткие и мягкие ссылки

| Свойство | Жёсткая `ln` | Мягкая `ln -s` |
| --- | --- | --- |
| Что делает | второе имя того же inode | указатель на путь |
| Может быть на каталог | нет | да |
| Может пересечь границу ФС | нет | да |
| Показывает `ls -l` | нет, выглядит как обычный файл | `l` и `-> /target` |
| Живёт ли после удаления оригинала | да (это тот же файл) | нет, превращается в битую ссылку |
| Что хранится | ничего, только запись в каталоге | путь в содержимом |

```bash
cd ~/lab2
echo "version 1" > current.log
ln    current.log hard.log     # жёсткая: второе имя
ln -s current.log soft.log    # мягкая: указатель

ls -li current.log hard.log soft.log   # -i показывает inode
rm current.log
cat hard.log                    # работает — тот же inode
cat soft.log                    # No such file — битая ссылка

# правильный «релизный» паттерн
mkdir -p /opt/myapp/releases/v1.2.0
ln -sfn /opt/myapp/releases/v1.2.0 /opt/myapp/current
```

Классический паттерн — **symlink flip**: рядом лежат версии, а `current`
переключается мгновенно, созданием новой ссылки. Откат — одна команда. Именно
на этом паттерне построены релизы Capistrano-стиля и часть Kubernetes-паттернов.

> [!CAUTION]
> `ln -s /path/to/dir/` — со слэшем на конце ссылка будет указывать на сам
> каталог, а не на содержимое. Без слэша — на содержимое. Ошибка в одном символе,
> и скрипт будет писать файлы в неожиданное место. Всегда проверяй результат
> через `readlink -f`.

```bash
readlink -f /opt/myapp/current     # куда реально указывает ссылка
ls -l /opt/myapp/current
```

### Симлинки в конфигах

Симлинк — стандартный способ «настоящего» переключения между окружениями:
`/etc/nginx/sites-enabled/site.conf` является симлинком на файл в
`sites-available`. В `systemd` тоже: `multi-user.target.wants/nginx.service`
— симлинк, созданный `systemctl enable`, который и означает «запускать при
загрузке». Подробно — в [лекции про systemd](devops/03-processy-i-systemd.md).

### mount и fstab

`fstab` (`/etc/fstab`) описывает, что монтировать при загрузке. Формат полей:

```text
устройство        точка     тип      опции                 дамп  проверка
/dev/sdb1         /var/lib  ext4     defaults,noatime       0      1
```

| Опция | Что делает |
| --- | --- |
| `defaults` | базовый набор: rw, suid, dev, exec, auto, async |
| `noatime` | не обновлять время доступа — прирост производительности на SSD |
| `nodiratime` | не обновлять и время изменения каталогов |
| `ro` | монтировать только для чтения |
| `noexec` | запрет запуск бинарников с этой ФС — для пользовательских данных |
| `nosuid` | игнорировать setuid/setgid — то же назначение |
| `nofail` | не ронять загрузку, если монтирование не удалось |

```bash
# проверить fstab без перезагрузки — обязательно перед reboot
sudo mount -a
findmnt --verify --verbose

# добавить диск
sudo blkid /dev/sdb                     # узнать UUID
echo 'UUID=xxxx-...  /srv/data  ext4  defaults,noatime,nofail  0  2' \
  | sudo tee -a /etc/fstab
sudo mount /srv/data

# временно перемонтировать с другими опциями
sudo mount -o remount,ro /var/lib
```

> [!CAUTION]
> Точка монтирования должна существовать **до** добавления в fstab, иначе
> система не загрузится. Опечатка в UUID — тоже. Всегда `mount -a` перед
> перезагрузкой; в виртуалке Proxmox это означает лишний reboot на неисправность,
> который никто не оценит.

## Inode: почему `df` и `du` расходятся

`du` обходит файлы и считает их размер. `df` смотрит на файловую систему и
считает занятые **блоки**. Это две разные величины, и между ними есть
законный зазор. У тебя **обязательно** будут инциденты, где `df -h` говорит
«100%», а `du -sh /` говорит «использовано 40%». Вот три причины.

### Причина 1: файлы удалены, но процессы их держат открытыми

Механизм такой. `rm` удаляет запись из каталога и уменьшает счётчик ссылок на
inode. Если у inode остались **открытые файловые дескрипторы** (открытые файлы,
активные `mmap`, сокеты), ядро не освобождает блоки — файла в ФС уже нет, а
место занято. Логи, ротация, tmpfs с распакованными файлами, процессы,
забывшие закрыть соединение с базой, — все они создают такую утечку.

```bash
# 1. видно, что диск полон
df -h /

# 2. видно, что по каталогам места немного
sudo du -sh /var/* 2>/dev/null | sort -h | tail

# 3. ищем дескрипторы на удалённые файлы: +L1 = ссылки == 1, т.е. имени нет
sudo lsof +L1
sudo lsof +L1 | awk '$5 > 1048576 {printf "%10.1f MB  %s\n", $5/1048576, $NF}'
```

`+L1` — ключ, который стоит запомнить: «файлы с числом ссылок меньше двух,
то есть на диске их уже нет».

```bash
# освободить место, не перезагружаясь: убить владельца дескриптора
sudo kill -TERM $(sudo lsof -t +L1)
# радикально, если это известный и безобидный процесс:
sudo systemctl restart myapp.service
```

> [!CAUTION]
> Убийство процесса освобождает место, но может означать потерю несохранённого
> состояния и простой сервиса. Сначала выясни, что это за процесс и можно ли
> его перезапустить без последствий. Если это `systemd-journald` — перезапуск
> безопасен. Если это `postgres` — сначала проверь, что реплика или бэкап есть.

### Причина 2: файлы в каталогах, которые `du` не обходит

Привилегированные каталоги вроде `/proc`, `/sys` дают `du` ошибки доступа.
Некоторые реализации при этом всё равно пишут в `stderr` и идут дальше, а
`du -sh /` с редиректом ошибок покажет «неполную» картину.

```bash
sudo du -shx / 2>/dev/null          # -x: не выходить за пределы ФС
sudo du -h --max-depth=1 / 2>/dev/null | sort -h
```

Флаг `-x` (one-file-system) стоит почти всегда: без него `du /` залезет в
`/proc`, `/sys`, `/dev/shm` и другие смонтированные файловые системы и выдаст
цифры, не имеющие отношения к твоему диску.

### Причина 3: зарезервированные блоки и разные размеры блоков

ext4 резервирует 5% (настраивается через `-m`) блоков под корень. Кроме того,
файл размером 1 КБ занимает целый блок 4 КБ. Миллион мелких файлов — это
4 гигабайта, хотя `du` покажет «1 ГБ».

```bash
# ищем потерянное место, учитывая блоки и inode
sudo tune2fs -l /dev/sda1 | grep -i 'reserved\|block count\|block size'
sudo debugfs -R 'stats' /dev/sda1 2>/dev/null | grep -i inode
```

### Причина 4 (редкая, но реальная): закончились inode

`df -i /` показывает использование inode отдельно от байтов. Миллион файлов по
100 байт каждый забивает таблицу inode при свободных гигабайтах, и создание
новых файлов падает с `No space left on device`, хотя `df -h` показывает
свободное место. Причина обычно — неудачно распакованный архив в `/var/lib`.

```bash
df -i /
sudo find /var/lib -xdev -type f 2>/dev/null | wc -l
```

mkdir -p ~/lab2 && cd ~/lab2

## Где это ломается

- **`chmod -R 777` как лекарство.** Не лечит ничего, открывает систему.
  Правильный путь: `journalctl -u <unit> | grep -i permission` → понять, от
  какого пользователя и к каку пути нет доступа → выдать точечные права.
- **Файлы, в которых ты «не ходил», а права слетели.** `chown` сбрасывает setuid,
  копирование через `cp` без `-p` не сохраняет права и временные метки. Отсюда
  «вчера скрипт запускался, сегодня Permission denied» после правки репозитория.
- **Рекурсивный `chmod` по `/` или `/etc`.** `sudo chmod -R 755 /etc` без
  исключений сносит права с приватных ключей и конфигов с секретами. Если нужно
  массово — обязательно с `-print` сначала, посмотри список, потом `-exec`.
- **Битый symlink, который не сломался сразу.** Приложение продолжает работать,
  потому что inode уже в памяти. Симлинк «указывает в никуда» — и через месяц
  после деплоя новой версии ты получаешь `FileNotFound`. Проверяй ссылки:
  `find /opt -xtype l`.
- **`NOPASSWD: ALL`.** Читается как «дать доступ к рестарту», работает как «дать
  root». В аудите это первое, на что смотрят.
- **Забытый `setuid` на скрипте.** Иногда «чтобы заработало» ставят `chmod
  u+s`. На bash-скриптах и на скриптах с `#!/bin/sh` это не работает так, как
  ожидают, а на интерпретируемых файлах — источник уязвимостей. Если нужен
  root — это `sudo` или обёртка в root-owned скрипт.
- **Закончились inode, а не байты.** `No space left on device` при
  `df -h`, показывающем свободные гигабайты. Проверяй `df -i /` до того, как
  начнёшь удалять файлы наугад.
