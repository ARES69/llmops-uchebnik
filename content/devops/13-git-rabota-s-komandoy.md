Ты руководишь IT-отделом, и рано или поздно встанет вопрос: где хранить конфигурацию Proxmox, скрипты бэкапа, плейбуки Ansible и Dockerfile'ы? Ответ — Git. Но дело не в «счётчике звёзд». Git — это первое, что делает возможным всё, о чём пойдёт речь дальше: CI/CD (это [лекция 14](devops/14-cicd-pipeliney.md)) — это автоматизация поверх коммитов. Нет коммита — нет пайплайна. Поэтому здесь разбираем Git не как список команд, а как модель: три области, неизменяемые объекты, указатели и ссылки между ними.

## Зачем нужна система контроля версий и чем Git отличается от SVN

И SVN, и Git хранят историю. Разница не в «лучше/хуже», а в архитектуре: **SVN — одна линия истории на сервере, Git — копия истории у каждого разработчика плюс сервер.** Отсюда вытекает всё остальное.

| Критерий | Subversion | Git |
| --- | :---: | :---: |
| Где живёт история | одна копия на сервере | полная копия у каждого |
| Ветка | дорогая копия директории | дешёвый указатель на коммит |
| Коммит | уходит на сервер сразу | локальный, пушится отдельно |
| Работа без сети | почти невозможна | полная |
| Конфликты | разрешаются на сервере, блокируют файлы | разрешаются локально, до пуша |
| Права на файл | хранятся в репозитории (ACL) | только бит `exec` |
| Права доступа | хранятся в репозитории | в настройках хоста |

Практический вывод для тебя: Git проигрывает SVN ровно в одном — **в дисциплине**. В SVN можно было нажать «забыть закоммитить» и получить блокировку файла на чужой стороне. В Git ты волен наделать мусора у себя — но ответственность за чистоту общей ветки теперь полностью на тебе.

## Три области: рабочая папка, индекс, репозиторий

Между файлами на диске и историей лежит **staging area** (индекс). Это буфер, и именно он делает Git мощным инструментом, а не «сохранялкой».

- **Working directory** — файлы, которые ты правишь прямо сейчас.
- **Index (staging)** — снимок того, что попадёт в следующий коммит.
- **Repository** — папка `.git`, вся история объектов.

```bash
git status                      # что изменено, что staged, что не отслеживается
git diff                        # рабочая папка vs индекс
git diff --cached               # индекс vs последний коммит
git add -p src/api/client.py    # добавить файл по кускам (hunk), интерактивно
git commit -m "fix(rbac): deny /admin without group membership"
git add -A && git commit        # всё разом — только для черновиков, не для прода
```

`git add -p` — команда, которая экономит больше всего времени при ревью. Ты можешь закоммитить исправление пароля отдельно от форматирования, и ревьюер увидит ровно то, что нужно обсуждать.

Ещё одна вещь, которую стоит один раз сделать руками, чтобы перестать бояться: посмотреть, что коммит — это **дерево файлов**, а репозиторий — **граф таких деревьев**, склеенных указателями.

```bash
git log --oneline --graph --all --decorate   # вся история, ветки и теги на одной картинке
git show 3f2a1c9                              # патч конкретного коммита
git show 3f2a1c9 --stat                       # только список изменённых файлов
git cat-file -p HEAD                          # сырой объект: автор, committer, родители, дерево
```

## Анатомия коммита и сообщения

Коммит содержит: дерево файлов, ноль или нескольких родителей, автора, committer, дату, сообщение. Хэш считается **из содержимого и из хэша родителя**. Отсюда следует неперебиваемое свойство: **любой коммит неизменяем**. Изменил файл — получишь другой хэш. Именно поэтому «взломать» историю в репозитории нельзя, а вот «переписать» — можно, об этом ниже.

Заголовок сообщения пишется по **Conventional Commits**, потому что из него потом машинно собирается changelog и решается, бампать ли мажорную версию.

```
feat(rag): add hybrid retrieval over the corporate wiki

Ранжирование только по BM25 проваливало на вопросах с аббревиатурами
и на длинных документах. Добавлен эмбеддинговый канал, веса 0.4 / 0.6,
подобраны на eval-set из 120 вопросов из тикетов.

Затрагивает RAG-пайплайн: меняется порядок выборки кандидатов.

Closes #418
```

Правило: **тело сообщения объясняет «почему», а не «что»** — «что» уже видно в диффе. Типы, которые реально используются: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`. Из `BREAKING CHANGE:` в теле семантический релиз понимает, что это мажорный бамп.

## Ветки: switch, merge и честный разговор о rebase

Ветка — это **подвижной указатель на коммит** плюс запись в reflog. Создать стоит микросекунды, поэтому в Git ветки не экономят, а стоят копейки.

```bash
git branch                       # список веток
git branch -vv                   # ветки + upstream + сколько коммитов ahead/behind
git switch -c fix/ntds-retention # создать и перейти (git checkout -b — устаревший синтаксис)
git switch main
git merge --no-ff feature/rag-hybrid -m "Merge hybrid retrieval"
```

### Fast-forward против настоящего merge

Представь: от `main` ушло 37 коммитов, твоя ветка отстала на 12 и не пересекается с ними. `git merge` **не создаст коммит вообще** — он передвинет указатель твоей ветки вперёд на 37 коммитов. Это fast-forward, и в `git log --oneline --graph` история выглядит идеально линейной.

Проблема в том, что ты **потерял информацию о факте ветвления**: не видно, что группа изменений была собрана отдельно, и нельзя откатить её одним коммитом.

`git merge --no-ff` заставляет Git создать настоящий merge-коммит с двумя родителями. Цена — merge-коммиты в истории, которые усложняют `git bisect` и ревью (приходится просить ревьюера смотреть только «свои» коммиты, а не весь merge). Практика: **для долгоживущих фич и релизных веток — `--no-ff`**, для ежедневных фиксов в trunk-based — по вкусу.

| | fast-forward | `--no-ff` | rebase |
| --- | :---: | :---: | :---: |
| История | линейная | линейная с merge-точками | линейная, чужие коммиты «подклеены» |
| Хэши чужих коммитов | не меняются | не меняются | **меняются** |
| Откат группы изменений | поштучно | один merge-коммит | поштучно или `reset` до маркера |
| Когда применять | ветка из `main`, без своих коммитов | долгие фичи, релизы | личная ветка, никем не виденная |

## Rebase: что он делает с историей

Здесь нужна честность, потому что «просто используй rebase» — это совет из интернета, который стоит людям работы.

**Что rebase делает технически.** Он берёт твои коммиты, вычисляет каждый как разницу к его родителю (patch), ставит их заново поверх нового tip `main` и **каждый раз создаёт новый коммит с новым хэшем**. Твои старые коммиты физически остаются в `.git`, но из ветки уходят — они живут в reflog и в других ветках, если на них кто-то ссылался.

**Чего rebase не делает.** Он не объединяет коммиты — это `squash`. Он не решает конфликты автоматически чаще, чем merge: при сильном пересечении кода rebase требует разрешить один и тот же конфликт N раз подряд, по одному на каждый свой коммит. И он не «чище» автоматически: если в твоей ветке 20 коммитов, а `main` ушёл на 500, у тебя будет 20 итераций разрешения конфликтов против одного `merge`.

**Почему нельзя ребейзить опубликованные ветки.** Хэш коммита зависит от хэша родителя. Rebase меняет родителя → меняется хэш. Сценарий:

1. Ты запушил `feature/x` с коммитами `A → B → C`.
2. Коллега сделал `git fetch` и видит `C` у себя.
3. Ты сделал `git rebase main` и получил `A → B → C'`, запушил `--force`.
4. У коллеги `C` и `C'` — **два разных коммита с одинаковым смыслом**. Дальше это либо merge-коммит с двумя почти одинаковыми изменениями (дубли в main), либо он потеряет свою работу, когда в следующий раз сделает `pull`.

**Rebase в ветке с открытым pull request** — худший вариант, потому что ломает сразу три вещи:

- ревьюер смотрел старый diff, а force-push подменил его новым; все его комментарии «привязаны» к строкам, которых больше нет;
- твои собственные коммиты, которые он уже одобрил, выглядят как «удалённые и добавленные заново» — PR засоряется;
- если в момент rebase кто-то успел запушить в ту же ветку, `--force` без `--force-with-lease` **удалит его коммит**.

```bash
git fetch origin
git switch feature/rag-hybrid
git rebase origin/main                    # перенести ветку на свежий main

# интерактивный: поменять порядок, склеить коммиты, переписать сообщение
git rebase -i origin/main

# во время конфликта — только три команды:
git status                                 # что не разрешено
git rebase --continue                     # разрешил — идём дальше
git rebase --abort                         # передумал — вернулись как было

# единственный флаг, который допустимо пушить в ветку с открытым PR
git push --force-with-lease
```

> [!IMPORTANT]
> Рабочее правило, которое снимает 90% проблем: **rebase разрешён только на том, что никто не видел**. Опубликовал ветку — живёшь с merge. Наружу (`main`, `develop`, релизные) — только fast-forward и `--no-ff`.

## Разрешение конфликтов: что происходит на самом деле

Git не может решить за тебя, что строка должна быть и `value = get_a()` и `value = get_b()`. Он останавливается и оставляет в файле оба варианта:

```python
def resolve_password(user):
<<<<<<< HEAD
    return vault.fetch_current(user)
=======
    return vault.fetch(user, version="v2")
>>>>>>> feature/rbac-hardening
```

`HEAD` — это сторона, в которую ты сливаешь (при rebase — новый `main`), нижняя — твоя. Дальше:

```bash
git status                                  # Git перечисляет конфликтные файлы
# редактируешь файлы: убираешь <<<<<<<, =======, >>>>>>> и оставляешь верный код
git diff --diff-filter=U                     # что именно не разрешено
git add src/vault.py                        # add = «я разрешил»
git rebase --continue                       # для merge: git commit
```

Важная деталь: `git add` здесь означает «этот файл разрешён», а не «просто добавить в индекс». Никакого отдельного `git resolved` в Git нет.

## Stash: временная парковка изменений

Нужен, чтобы посмотреть на другой ветке и не коммитить незаконченную работу.

```bash
git stash push -m "миграция WIP: переезд ntds_dit"
git stash list
git stash show -p stash@{0}          # что внутри
git stash pop                        # вернуть и удалить из стека
git stash drop stash@{1}
git stash push -u -m "untracked"    # включить неотслеживаемые файлы
```

`stash` лежит локально, в PR не попадает, в `git log` не виден. Это не «грязный стол», которым пользуются месяцами: если твоё WО не закоммичено к концу дня, оно забыто. Правило — stash живёт до обеда, дальше это баг в процессе.

## Remote: fetch против pull

Это самое частое непонимание у новичков и источник неожиданных merge-коммитов.

| | `git fetch` | `git pull` |
| --- | :---: | :---: |
| Забирает изменения | да | да |
| Меняет текущую ветку | нет | да (сливает или ребейзит) |
| Трогает рабочую папку | нет | да |
| Безопасен всегда | да | только на чистой ветке |
| Основное применение | «что там новенькое у других?» | обновить свою ветку |

```bash
git remote -v                              # список remotes и их URL
git clone git@gitlab.internal:infra/ansible.git
git fetch --all --prune                     # обновить все remotes, убрать удалённые ветки
git diff origin/main..main                  # что изменилось у других, но не у меня
git pull --rebase                           # pull без merge-коммита поверх моих коммитов
git push -u origin fix/ntds-retention       # -u = запомнить upstream, дальше просто git push
git push --set-upstream origin feature/x
```

`--prune` стоит делать почти всегда: без него удалённые на сервере ветки живут у тебя месяцами, и `git branch` превращается в кладбище.

## .gitignore и секреты

`.gitignore` фильтрует **только незакоммиченные** файлы. Если файл уже в истории — игнор на него не действует.

```gitignore
# Каталог в корне репозитория
/build/
# Любой файл с этим расширением в любом месте
*.log
*.p12
# Кэш Python
__pycache__/
.venv/
# Секреты — никогда
.env
.env.*
*.pem
# Ansible
*.retry
```

```bash
git check-ignore -v .env          # какое правило сработало
git rm --cached .env              # убрать из отслеживания, оставить в папке
git ls-files | grep -E '\.env|\.pem'   # найти всё, что уже протекло

# глобальные правила — свои, не для репозитория
git config --global core.excludesfile ~/.gitignore_global
```

> [!WARNING]
> Секрет, попавший в коммит, **больше не секрет**. Он в истории навсегда, он в клонах у всех, его нашли сканеры на GitHub. Действие — не «удалить файл», а **ротация**: выпустить новый пароль/токен, отозвать старый, и только потом убрать файл из HEAD.

## Работа в команде: pull request, ревью, защита ветки

Pull request — это не «кнопка Merge». Это **точка входа**: только здесь прогоняются проверки, только здесь обсуждается изменение и только здесь принимается решение о допустимости.

```bash
git switch -c fix/ntds-retention
# ... работа, коммиты ...
git push -u origin fix/ntds-retention
gh pr create --fill --base main
gh pr checks --watch          # смотреть, как идут обязательные проверки
gh pr merge --squash --delete-branch
```

Защита `main` настраивается в GitHub/GitLab и состоит из пяти пунктов, каждый из которых нужен:

- **Require status checks to pass** — нельзя смержить с красным пайплайном;
- **Require approvals** — для инфраструктурного репозитория разумно 2, для экспериментального — 1;
- **Require branches to be up to date** — линейная история, никаких «забытых» merge-коммитов;
- **Do not allow force pushes** — блокировка `--force` в `main`;
- **Do not allow deletions** — защита ветки от случайного удаления.

Что проверять на ревью, кроме «правильный ли код»:

- есть ли тест, который **падал бы без этого изменения** (прокомментируй фикс, запусти тест, убедись, что он стал красным);
- меняется ли публичный контракт — если да, есть ли план миграции;
- добавлены ли в `Dockerfile` зависимости без обоснования и пиннинг версий;
- попадают ли в образ секреты через `ARG`/`ENV` (это самая частая дыра в CI — разберём в [лекции 14](devops/14-cicd-pipeliney.md)).

## Стратегии ветвления: сравнение

| | GitFlow | Trunk-based | GitHub Flow |
| --- | :---: | :---: | :---: |
| Модель | долгие `develop` и `release`, хотфиксы в `main` | короткие ветки, живут меньше дня | одна feature-ветка → `main` → релиз |
| Слияние | по расписанию релиз-цикла | ежедневно, хоть ежечасно | PR в `main` |
| Откуда релиз | из `release/*` | из `main` | из `main` |
| Плюсы | явные фазы, удобно для релизного процесса с согласованиями | максимум частых интеграций, конфликты копятся мизерно | максимально просто, родная связка с GitHub |
| Минусы | ветки живут недели → дрейф, конфликты, «релизная анархия» | нужен зрелый CI, тесты и feature-флаги | нет окна стабилизации перед релизом |
| Кого предполагает | 10+ человек, релиз раз в квартал | 2–10 человек, релиз хоть каждый день | стартап, деплой на каждый PR |

**Почему в небольшой команде trunk-based проще.** Ветка в Git стоит почти ноль, а слияние — это операция в памяти. GitFlow держит код в состоянии, которого нет на сервере: у `develop` своя история, у `release` своя, и в момент релиза ты получаешь неделю конфликтов и месяц «почему на стенде работает, а в проде нет». При трёх людях, одном Proxmox-стенде и одной виртуалке AD дебаг-сервер всё это — чистые издержки.

Честное «но»: у trunk-based есть риск, что нестабильный код попадёт в `main`. Ответ — **не длинные ветки**, а feature-флаги и canary-раскатка. Длинная ветка лечит симптом ценой ещё одного большого слияния в конце.

## Теги, релизы и подпись коммитов

Тег — ещё один указатель. Обычный (lightweight) тег — просто ссылка на объект, **аннотированный** (`-a`) — полноценный объект с автором, датой, сообщением и подписью.

```bash
git tag -a v1.4.0 -m "release 1.4.0: hybrid retrieval, ntds retention fix"
git push origin --tags
git show v1.4.0                    # что внутри релиза
git tag -d v1.4.0-rc1              # удалить локально
git push origin :refs/tags/v1.4.0-rc1   # и удалить с сервера
```

Релиз = тег + changelog + подпись + артефакты, а не «ветка с названием v1.4».

Подпись GPG или SSH решает задачу авторства: по умолчанию любой может написать в коммите `Author: Иван Иванов`. С принудительной проверкой подписей на сервере (в GitHub это Rulesets → Require signed commits) **unsigned-пуш в `main` становится технически невозможен** — это и есть аудит.

```bash
gpg --list-secret-keys --keyid-format=long
git config --global user.signingkey 0xABCDEF0123456789
git config --global commit.gpgsign true
git config --global tag.gpgsign true
gpg --export --armor 0xABCDEF0123456789    # публичный ключ — в профиль на GitHub
git commit -S -m "chore: signed hotfix"   # разово подписать один коммит
git tag -s v1.4.0 -m "signed release"
```

Секретный ключ (с passphrase) — на машине разработчика и в зашифрованном secret'е CI. Открытый — на сервере и в профиле. Утечка закрытого ключа означает, что подписи больше ничего не доказывают.

## Как отменить сделанное: revert против reset

| | `git revert` | `git reset` |
| --- | :---: | :---: |
| Что делает | создаёт **новый** коммит, отменяющий указанный | двигает указатель ветки, **переписывает** историю |
| История | линейная, только дописывается | переписывается, старые коммиты осиротевают |
| Для опубликованного | безопасно | недопустимо |
| Когда применять | откат фичи в `main`, отзыв плохого коммита | переделать свой последний коммит в личной ветке |

```bash
git revert 9a1b2c3                        # откатить один коммит новым коммитом
git revert --no-commit 9a1b2c3 HEAD~1    # откатить диапазон, а коммит один
git revert --no-edit 9a1b2c3              # без редактора сообщения

# reset — только в ветке, которую никто не видел
git reset --soft HEAD~1                   # отменить коммит, изменения остались staged
git reset --mixed HEAD~1                  # + остались unstaged (по умолчанию)
git reset --hard origin/feature/rag       # рабочее: «откатить всё, что я тут наделал»
```

Страховка, которая спасает жизнь при неудачном `reset`:

```bash
git reflog                       # 20 последних перемещений HEAD
git reset --hard HEAD@{5}        # вернуться туда, где был 5 шагов назад
```

> [!CAUTION]
> `git reset --hard` **не спрашивает подтверждения и не бэкапит рабочую папку**. Единственная страховка — reflog (7 дней по умолчанию в свежей клонированной репе, до 90 дней в старых). Если хочешь страховку на годы — настрой `git config --global gc.reflogExpire 90d` и **делай `git bundle` перед рискованными операциями**.

## Где это ломается

1. **`git push --force` в ветку, которую уже кто-то fetch'нул.** Один человек теряет день работы. Исправление retroactively невозможно — только объяснить и перебазировать вручную.
2. **Rebase ветки с открытым PR.** Ревью на старых коммитах, force-push подменяет диф, часть замечаний ревьюера повисает в воздухе.
3. **Секрет в коммите.** `.gitignore` не поможет — нужен `git rm --cached`, но главное ротация: отозвать и перевыпустить.
4. **`git reset --hard` / `git checkout .` при несохранённой работе.** Файл удаляется без вопроса, из индекса и с диска.
5. **`git pull` в грязной ветке.** Получаешь merge-коммит поверх того, что даже не закоммичено, а `git pull --rebase` — конфликт с индексацией, которую он не подхватил.
6. **`git init` на сетевой шаре «чтобы все видели».** Папка `.git` не синхронизируется корректно, индексы и reflog разъезжаются. Нужен настоящий сервер (GitLab/Gitea) — шару можно использовать только для экспорта.
7. **Rebase 20+ коммитов поверх сильно ушедшего `main`.** Каждый конфликт решается заново. Спасает `git rerere` — запоминает решения и подставляет их автоматически.
8. **Слияние `develop` в `main` в последний день перед релизом.** Формально не ошибка, но это merge 500 коммитов, который невозможно откатить одной командой.
