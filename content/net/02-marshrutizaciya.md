Первая часть модуля научила тебя настраивать коммутатор. Теперь — устройство,
которое соединяет подсети между собой и решает, что делать, когда часть пути
отвалилась. Тут ловушка инженерного мышления: маршрутизацию изучают как список
протоколов, а она на самом деле решается тремя вопросами — **какой маршрут
выбрать**, **кто мне скажет, что он есть**, и **что будет, если провод оторвут**.
Все три разобраны ниже, а в конце — схема, ради которой всё это и затевается:
два маршрутизатора, два провайдера и требование «сеть не падает никогда».

## Таблица маршрутизации: как выбирается один маршрут из тысячи

Маршрутизатор не «знает сеть». Он держит таблицу маршрутов — список записей
вида «сеть, маска → куда отправлять». Каждый входящий пакет сверяется с этим
списком сверху вниз. Отбор идёт по трём критериям **строго по очереди**:

1. **Longest prefix match.** Из всех подходящих записей выбирается та, у которой
   самая длинная маска. `10.1.1.0/24` побеждает `10.0.0.0/8` всегда, независимо
   ни от чего остального. Это первый и единственный критерий, который важнее
   всего остального, — остальное даже не рассматривается.
2. **Administrative distance (AD).** Если длинных префиксов несколько, побеждает
   тот, у кого меньше AD — это «доверие» к источнику информации. Статический
   маршрут, который ты ввёл руками, всегда «ближе к истине», чем то, что
   сообщил протокол.
3. **Metric.** Если и префикс, и AD совпали (это почти всегда — один
   протокол, один маршрут), выбирается наименьшая метрика.

| Тип маршрута | AD на Cisco | Комментарий |
| --- | --- | --- |
| `connected` (прямо подключённая сеть) | 0 | не настраивается, появляется с адресом на интерфейсе |
| статический (`ip route`) | 1 | ты решил руками, IOS тебе доверяет |
| статический в `Null0` | 1 | «чёрная дыра», маршрут должен быть, но пакеты — в никуда |
| eBGP | 20 | внешний BGP с другим доменом |
| EIGRP | 90 | проприетарный Cisco |
| OSPF | 110 | стандартный, работает с любым вендором |
| IS-IS | 115 | стандартный, крупные сети операторов |
| iBGP | 200 | BGP внутри одного домена |

Отсюда прямое следствие, которое стоит запомнить: **статика (AD 1) всегда
побеждает OSPF (AD 110)**, если совпал префикс. Один оставленный в конфиге
`ip route` не даст OSPF перестроить маршрут — и через месяц никто не вспомнит,
откуда взялась эта строчка.

```bash
show ip route
show ip route static
show ip route 10.10.20.0
show ip route 10.10.20.0 longer-prefixes
```

Буква в начале строки — код протокола: `C` connected, `S` static, `O` OSPF,
`R` RIP, `D` EIGRP, `B` BGP, `L` per-port load balancing, `H` HSRP (на части
платформ IOS XE). Дальше идёт время жизни маршрута, метрика, затем список
интерфейсов, через которые реально пойдёт трафик.

## Статические маршруты и шлюз последней мили

Маршрут задаётся как «сеть → маска → следующий узел»:

```bash
ip route 10.10.20.0 255.255.255.0 192.168.1.1        # через IP-шлюз
ip route 10.10.20.0 255.255.255.0 GigabitEthernet0/0 # через интерфейс
ip route 10.10.30.0 255.255.255.0 192.168.1.2 200   # плавающий, AD 200
```

**Следующий узел или интерфейс** — не одно и то же, и разница практическая.
Вариант с интерфейсом не требует, чтобы шлюз был в твоей подсети: маршрутизатор
выполнит ARP для всех адресов в подключённой сети. Это экономит запись, но
приводит к **ICMP redirect** (маршрутизатор сообщает отправителю более короткий
путь) и к тому, что маршрут «залипает», если ARP перестал работать. Вариант с
IP-шлюзом корректнее: у пакета всегда есть конкретный следующий MAC.
Как правило, используй IP, а интерфейс — только когда IP-шлюз физически вне
достижимости (например, в другой broadcast-домен через прозрачный мост).

**Что означает `200` в конце.** Это administrative distance 200 — значение выше
110 (OSPF), но ниже 255. Маршрут с AD 200 существует в таблице, но постоянно
уступает любому другому с тем же префиксом и меньшим AD. Схема: основной путь
через провайдера A с AD 1, резервный через провайдера B с AD 200. Пока жива
основная линия — работает она. Основная пропала — в таблице не осталось ничего
для этого префикса, и маршрут переключается на резерв. Это **плавающий
маршрут**, и он работает без единого протокола маршрутизации.

```bash
ip route 0.0.0.0 0.0.0.0 203.0.113.1 1
ip route 0.0.0.0 0.0.0.0 198.51.100.1 200
```

> [!NOTE]
> Значение `200` для плавающего маршрута — соглашение, а не стандарт. Cisco
> предлагает как раз такое число, потому что оно заведомо хуже любого
> динамического протокола. Подойдёт любое, которое больше AD всех протоколов,
> которые ты хочешь видеть в приоритете, но меньше 255.

### Шлюз последней мили: две команды для разных устройств

```bash
# L2-коммутатор — только для служебного трафика самого коммутатора (syslog, SNMP, пинги)
ip default-gateway 10.10.99.1

# Маршрутизатор — настоящий маршрут по умолчанию
ip route 0.0.0.0 0.0.0.0 203.0.113.1
```

`ip default-gateway` не создаёт маршрут по умолчанию в смысле таблицы
маршрутизации — он говорит «отправляй пакеты сам, через эти интерфейсы». Для
коммутатора этого достаточно. На маршрутизаторе пиши только `ip route 0.0.0.0 0.0.0.0`
— иначе у тебя две сущности, которые конфликтуют при включении функции
маршрутизации на том же устройстве.

### Null0: «маршрут есть, но пакеты не пойдут»

```bash
ip route 10.10.50.0 255.255.0.0 Null0
```

Суммарный маршрут, который анонсируется, но трафик в него уходит в никуда.
Применяется как затычка: пока подсеть 10.10.50.0/16 не подключена, ты не хочешь
чтобы маршрутизатор отправлял туда пакеты по умолчанию, и не хочешь видеть в
логах ICMP unreachable от пользователей.

## OSPF: когда маршрутов много, а руками — нет

OSPF нужен там, где маршрутизаторов больше одного и топология меняется. Статика
масштабируется плохо: 5 маршрутизаторов — 10 точек, 20 — 190 пар, и ошибка в
любой строчке становится мистикой. OSPF решает это: маршрутизаторы сами
обмениваются картами сети и строят таблицы.

### Минимальная рабочая конфигурация

```bash
router ospf 1
 router-id 10.10.99.1
 log-adjacency-changes
 passive-interface default
 no passive-interface GigabitEthernet0/0
 network 10.10.99.0 0.0.0.255 area 0
 network 10.10.0.0 0.0.0.255 area 0
!
interface GigabitEthernet0/1
 description UPLINK-to-rtr2
 ip address 10.10.0.1 255.255.255.252
 ip ospf network point-to-point
```

Что здесь важно и где обычно ошибаются:

- **Wildcard-маска, а не обычная.** `network 10.10.99.0 0.0.0.255` означает
  «совпадают первые 24 бита». Маска `255.255.255.0` здесь была бы ошибкой —
  OSPF не примет такую строку. Wildcard — это побитовое отрицание маски.
- **`router-id`** — идентификатор маршрутизатора в OSPF. Задаётся вручную,
  потому что иначе выбирается автоматически (обычно наибольший loopback или
  IP физического интерфейса) и может измениться при добавлении интерфейса.
  Router ID не обязан быть реальным адресом в сети, но обязан быть уникальным
  и не меняться после старта.
- **`passive-interface default` + `no passive-interface <интерфейс>`** — самый
  важный паттерн в конфигурации OSPF. Passive-интерфейс **не отправляет
  hello-пакеты**, но всё равно участвует в OSPF и анонсирует свою сеть. Обратный
  эффект: маршрутизатор не будет устанавливать соседство с кем попало в сети,
  куда воткнут пользовательский порт, и не будет тратить CPU. Без этой пары
  команд каждый интерфейс шлёт 10 hello в секунду туда, где может быть
  вандал с ноутбуком.

### Как это работает (уровень понимания, без формул)

1. **Hello.** Маршрутизаторы на одном сегменте каждые несколько секунд
   кричат «я тут, мой router-id такой-то». Если соседа нет — маршрутизатор
   один на сегменте, ему можно быть DR (см. ниже).
2. **Соседство (adjacency).** Когда маршрутизаторы видят друг друга
   достаточное число раз, они признают друг друга соседями. Соседство
   устанавливается **только между соседями** — не между всеми.
3. **DR/BDR.** На широковещательном сегменте (Ethernet) три и более
   маршрутизатора — это проблема: обмениваться надо со всеми, это O(n²).
   Поэтому выбирается **Designated Router** и **Backup Designated Router**:
   все обмениваются LSA только с ними, а те уже рассылают. Выбор — по наивысшему
   router-id (приоритет и настройки тоже влияют). На выбранном DR меняется
   нагрузка: при добавлении маршрутизатора он может стать новым DR и прервать
   все соседства на 30–40 секунд. Отсюда практический совет: на канале
   «роутер — роутер» ставь `ip ospf network point-to-point` (или
   `point-to-multipoint`), и выбора DR не будет вовсе. На сегменте, где есть
   коммутатор и три маршрутизатора, выбора не избежать.
4. **LSA (Link State Advertisement)** — «объявление о состоянии связи»,
   база данных топологии. Каждый маршрутизатор строит из LSA одинаковую карту
   сети, прогоняет по ней алгоритм SPF (Дейкстры) и получает свою таблицу
   маршрутов. Отсюда название — link state: «я рассказываю о своих связях».
5. **Стоимость (cost).** Метрика в OSPF. Считается как
   «опорная полоса / полоса интерфейса». Дефолтная опорная полоса — 100 Мбит/с,
   поэтому канал 10 Гбит/с получает cost меньше единицы и округляется до 1, а
   канал 100 Мбит/с — тоже 1. **Они неразличимы.** Это реальная ошибка в
   реальных сетях: сеть 1 Гбит и 10 Гбит считаются одинаково, и трафик
   идёт не туда. Лечится настройкой:

```bash
router ospf 1
 auto-cost reference-bandwidth 100000    # в Мбит/с: 100G -> 100000
```

### Диагностические команды OSPF

```bash
show ip ospf neighbor
show ip ospf interface brief
show ip ospf neighbor detail
show ip ospf database
debug ip ospf adj                  # включать только на время правки
```

Соседства в статусе FULL — цель. Статусы `INIT`, `2-WAY`, `EXSTART`,
`EXCHANGE`, `LOADING` означают, что соседство в процессе или сломалось.
Состояние `2-WAY` (нашёл соседа, но не стал с ним полноценным соседом) —
частая картина, когда на канале больше двух маршрутизаторов и ты смотришь на
пару «свой — сосед». Если все видимые пары 2-WAY — ищи DR.

> [!WARNING]
> `debug ip ospf adj` на боевом маршрутизаторе в часы нагрузки способен уронить
> CPU на минуты. Включай только на пару секунд, только на одном интерфейсе и
> обязательно с `undebug all` сразу после. На слабом ISR это буквально i-cache
> overflow и перезагрузка.

### Area: зачем нужен «нулевой» уровень

OSPF делит сеть на **area**. Все area соединяются через **area 0** (backbone),
как через магистраль. Причина — размер: чем больше area, тем больше LSA
рассылает каждый, и тем дороже обсчёт SPF. Сети на 200–300 маршрутизаторов
делят на area'ы, и LSA между area'ми не рассылаются, а суммируются в один
абстрактный маршрут. Упрощённо:

| Тип area | Кто внутри | Что видит |
| --- | --- | --- |
| `area 0` | backbone | всё |
| `stub area` | только внутренние сети | не получает внешние маршруты, ходит через ABR |
| `totally stub` | минимальный leaf | не получает даже межзонных, один дефолт вместо всех |

Для сети небольшого офиса всё это лишнее. Один `area 0` — достаточное и
правильное решение.

## DHCP на маршрутизаторе

Чтобы не настраивать адрес на каждом новом телефоне и ноутбуке вручную,
маршрутизатор сам раздаёт адреса из пула. Команды:

```bash
ip dhcp excluded-address 10.10.10.1 10.10.10.20
!
ip dhcp pool LAN
 network 10.10.20.0 255.255.255.0
 default-router 10.10.20.1
 dns-server 10.10.20.1 8.8.8.8
 domain-name company.local
 lease 8
!
ip dhcp pool MGMT
 network 10.10.99.0 255.255.255.0
 default-router 10.10.99.1
 lease 8
```

**Критическая ошибка: не исключить адрес шлюза из пула.** Если адрес
`10.10.20.1` не исключён, DHCP-сервер выдаст его какому-нибудь устройству.
Это устройство отзовётся на пинг по адресу шлюза, маршрутизация у всех
сломается (или, что хуже и тише, ARP будет отвекать не тот интерфейс).
Исключать надо не только адрес шлюза, но и весь используемый диапазон:
статические серверы, управляющий VLAN, будущие точки AP.

Статическая привязка (постоянный адрес для принтера или телефона):

```bash
ip dhcp pool RESERVED-printer
 host printer-hall
 client-identifier 01a0.b9c1.d2e3.f4      # 01 = Ethernet, далее MAC
 ip address 10.10.20.50
```

> [!NOTE]
> `client-identifier` начинается с `01` — это OUI-подобный префикс для Ethernet,
> за ним идёт MAC без разделителей. На части платформ в пуле поддерживается и
> альтернативная форма через `hardware-address`, а на коммутаторах Catalyst
> DHCP-сервер не включается вовсе — там либо внешний сервер, либо ретрансляция
> запросов на маршрутизатор.

Ретрансляция (DHCP relay) — когда клиент и сервер в разных подсетях. Без неё
клиент шлёт широковещательный DHCPDISCOVER, который дальше broadcast-домена не
идёт. Включается на SVI-интерфейсе маршрутизатора:

```bash
interface Vlan20
 ip address 10.10.20.1 255.255.255.0
 ip helper-address 10.10.99.1        # адрес DHCP-сервера (сам relay)
```

Проверки:

```bash
show ip dhcp binding              # кто какой адрес получил
show ip dhcp server statistics    # счётчики: сколько discover, offer, request
show ip dhcp conflict             # конфликты (если ping-check выключен — пусто)
clear ip dhcp binding 10.10.20.50 # сбросить одну привязку, чтобы клиент получил новый адрес
debug ip dhcp server events      # точечный дебаг, безопаснее чем debug ip dhcp
```

> [!CAUTION]
> Полный `debug ip dhcp` на маршрутизаторе с большой сетью генерирует тысячи
> строк в секунду и сам по себе ухудшает ситуацию, которую ты диагностируешь.
> Если нужно — только `debug ip dhcp server events`, и сразу `undebug all`.

## HSRP: два маршрутизатора, один адрес для клиентов

Клиенты не должны знать, что шлюзов два. HSRP позволяет двум (и более)
маршрутизаторам разыграть **один виртуальный IP и один виртуальный MAC**:
активный обслуживает трафик, резервный молчит и слушает.

```bash
! --- на rtr1 (10.10.20.1) ---
interface Vlan20
 ip address 10.10.20.1 255.255.255.0
 standby version 2
 standby 1 ip 10.10.20.254
 standby 1 priority 110
 standby 1 preempt delay minimum 60
 standby 1 timers msec 250 msec 750
 standby 1 track 1 decrement 30
!

! --- на rtr2 (10.10.20.2) ---
interface Vlan20
 ip address 10.10.20.2 255.255.255.0
 standby version 2
 standby 1 ip 10.10.20.254
 standby 1 priority 100
 standby 1 preempt delay minimum 60
 standby 1 timers msec 250 msec 750
!

! --- трекинг "пропал uplink" на обоих ---
ip sla 1
 icmp-echo 8.8.8.8 source-interface GigabitEthernet0/1
 frequency 5
ip sla schedule 1 life forever start-time 0
track 1 ip sla 1 reachability
```

Что происходит в рантайме:

- **Active** — один маршрутизатор (по умолчанию с наивысшим приоритетом;
  при равенстве — с наибольшим IP). Он владеет виртуальным MAC, отвечает на
  ARP для 10.10.20.254, шлёт реальный трафик.
- **Standby** — второй. Отправляет hello, слушает, ждёт. Виртуальный ARP он
  не отвечает.
- **Равенство приоритетов** — побеждает больший IP. Если `preempt` включён,
  маршрутизатор с большим приоритетом вытесняет текущий активный.
- **`preempt delay minimum 60`** — пауза перед вытеснением, в секундах.
  Без неё при обратном переключении оба маршрутизатора на секунду становятся
  активными, ARP-таблица у коммутаторов «прыгает», и в сети рвутся соединения.
  Задержка позволяет коммутаторам спокойно обновить MAC-таблицу.
- **`track 1 decrement 30`** — если uplink пропал (IP SLA не получает ответ),
  приоритет падает на 30. 110 − 30 = 80 < 100 — rtr1 перестаёт быть активным,
  и маршрутизатор уходит в Standby **без падения самого интерфейса**. Это
  ключевая идея: HSRP реагирует не на «порт упал», а на «путь наружу не работает».
  Порт может быть up (светится), а провайдер по нему не пускает.
- **`standby version 2`** — включает мультикастный вариант вместо
  broadcast-решений (на старых версиях был unicast-режим). Обязателен, если
  в сети есть точки, которые не любят L2 broadcast. На современных платформах
  v2 — норма.

```bash
show standby brief
show standby vlan 20
show standby detail
```

| Режим | Смысл |
| --- | --- |
| `Active` | обслуживает трафик, владеет виртуальным MAC |
| `Listen` | видит hello соседа, ждёт |
| `Speak` | объявляет о себе, кладёт адрес |
| `Standby` | готов принять роль, не участвует |
| `Init` | не видит ни одного соседа HSRP — обычно конфиг разошёлся |

### HSRP, VRRP, GLBP: разница не в словах

| | HSRP | VRRP | GLBP |
| --- | --- | --- | --- |
| Кто | Cisco (проприетарный) | стандарт (RFC 3768/5798) | Cisco (проприетарный) |
| Активных шлюзов | 1 (active/standby) | 1 (master/backup) | **несколько** (AVG распределяет) |
| Виртуальный MAC | да | обычно нет (по умолчанию) | да |
| Балансировка | нет, только отказоустойчивость | нет | **да, по ARP-запросам** |
| Hello по умолчанию | 3 с, hold 10 с | 1 с, hold 3 с | 3 с |
| Интероперабельность | только Cisco | любой вендор | только Cisco |

VRRP — стандарт, поэтому работает между Cisco, MikroTik, Eltex, Juniper.
Отличие в дефолтах: VRRP быстрее срабатывает по умолчанию (1/3 с против 3/10 с),
поэтому две разные технологии не «дружат» без выравнивания таймеров. На
MikroTik это `/interface vrrp` (см.
[лекцию про RouterOS](01-routeros-os.md)) — там синтаксис принципиально другой,
но модель «виртуальный IP, один master» ровно та же.

## Схема: два маршрутизатора, два провайдера

Классическая задача: два канала в интернет от разных провайдеров, оба дорогие,
оба работают. Хочется и балансировку (оба оплачены!), и отказоустойчивость
(упал один — не упало всё), и чтобы обратный трафик возвращался тем же путём
(иначе провайдер справедливо отбросит пакеты по антиспуфингу).

### Решение 1: BGP (правильное для прод-центра)

Полноценный BGP требует от провайдера номера AS (ASN), согласования сессии по
TCP/179 и анонса префикса. Если провайдеры это дают — это единственный способ
получить настоящую отказоустойчивость: анонс `203.0.113.0/24` обоим, решение
приходит автоматически, приоритет настраивается через `local-preference` и
AS-path. Технически сложно и требует договорённости с провайдерами, в домашнем
контуре недоступно.

### Решение 2: статика + IP SLA + policy routing (то, что сделаешь ты)

```bash
! --- трекинг двух провайдеров ---
ip sla 1
 icmp-echo 8.8.8.8 source-interface GigabitEthernet0/1
 frequency 5
ip sla schedule 1 life forever start-time 0
track 1 ip sla 1 reachability

ip sla 2
 icmp-echo 1.1.1.1 source-interface GigabitEthernet0/2
 frequency 5
ip sla schedule 2 life forever start-time 0
track 2 ip sla 2 reachability

! --- плавающий маршрут по умолчанию ---
ip route 0.0.0.0 0.0.0.0 203.0.113.1 1 track 1
ip route 0.0.0.0 0.0.0.0 198.51.100.1 200 track 2

! --- балансировка: клиентов отдаём провайдеру A, серверы — провайдеру B ---
route-map SPB permit 10
 match ip address ACL-SERVERS
 set ip next-hop verify-availability 198.51.100.1 10 track 2
 set ip next-hop verify-availability 203.0.113.1 20 track 1

route-map SPB permit 20
 set ip next-hop verify-availability 203.0.113.1 10 track 1
 set ip next-hop verify-availability 198.51.100.1 20 track 2

ip policy route-map SPB
ip cef
```

Как это работает: `verify-availability` с весами (10 и 20) смотрит, какой
трек жив. Основной путь — вес 10; если он недоступен, трафик уходит на запасной
(вес 20). Так ты получаешь и отказоустойчивость, и распределение нагрузки:
клиенты идут к провайдеру A, серверы — к провайдеру B.

> [!NOTE]
> Политическая маршрутизация работает через CEF (Cisco Express Forwarding).
> Если `ip cef` выключен, `ip policy` не даст эффекта — пакеты пойдут по
> process-switching и route-map будет проигнорирован. Это частая причина
> «настроил, а не работает». На ISR CEF включён по умолчанию; на коммутаторах
> L3 серии Catalyst 9300 — тоже.

### Сравнение подходов к отказоустойчивости

| Подход | Что отслеживает | Время переключения | Сложность | Порог входа |
| --- | --- | --- | --- | --- |
| Статика (плавающий AD) | только факт пропадания маршрута в таблице | секунды | низкая | любой |
| Статика + IP SLA track | доступность внешнего IP через конкретный uplink | 5–15 с (по `frequency`) | средняя | ISR, Catalyst 9K |
| OSPF | падение интерфейса или соседства | 4–40 с (hello/dead) | средняя | любой |
| HSRP | доступность uplink через track | 0.25–0.75 с (если sub-second) или 10 с | средняя | Cisco |
| VRRP | то же, стандарт | 1–3 с по умолчанию | средняя | любой |
| GLBP | путь + распределение нагрузки | 3–12 с | средняя | Catalyst |
| BGP | состояние сессии с провайдером + анонсы | 3–90 с (таймеры) | высокая | нужен ASN и договор с провайдером |

Выбирай по простоту, а не по таблице: в офисе на 50 пользователей
«плавающий маршрут + HSRP» закрывает 95% инцидентов. BGP там — инженерный
 overkill, который к тому же требует месяц переписки с провайдерами.

## Где это ломается

- **`network` с обычной маской вместо wildcard.** `network 10.0.0.0 255.255.255.0
  area 0` не применится. Wildcard для /24 — `0.0.0.255`, то есть побитовое
  отрицание. Самая частая ошибка новичка и причина «OSPF не поднимается, а
  все команды вроде правильные».
- **Забытый `passive-interface default`.** Каждый интерфейс шлёт OSPF-hello
  туда, где может висеть пользовательский ноутбук, и зря грузит CPU. Правильный
  паттерн: `passive-interface default` в `router ospf`, а `no passive-interface`
  — только на линках, где реально есть сосед.
- **Не задали `router-id`.** Он выбирается автоматически и может смениться
  после добавления loopback или интерфейса — а смена router-id в OSPF
  перезапускает все соседства и пересчитывает всю базу.
- **Не исключили адрес шлюза из DHCP-пула.** Раздаётся самому себе, ARP
  «плавает», диагностика невозможна. Первый шаг при странном поведении сети —
  `show ip dhcp binding` и поиск адреса, совпадающего с адресом интерфейса или
  шлюза.
- **Забыли `track` на HSRP.** Приоритет настроен, но при падении только uplink'а
  (порт up, провайдер режет) active не меняется, потому что HSRP смотрит на
  интерфейс, а не на путь. Именно здесь нужен `track` с IP SLA.
- **Слишком агрессивные таймеры HSRP.** `timers msec 250 msec 750` при
  загруженном CPU дают ложные переключения: маршрутизатор не успевает отправить
  hello вовремя, второй считает его мёртвым и забирает роль. Два активных,
  MAC-таблица скачет, соединения рвутся. Начинай с дефолтных 3/10.
- **`no passive-interface default` без `area`.** Явный `area 0` на каждой
  `network` — обязателен. Без него маршрутизатор не запустит OSPF.
- **Асимметрия, которую никто не проверяет.** Один маршрут по умолчанию в
  одну сторону и другой — в обратную. `ping` в одну сторону работает, в другую
  нет. Все «проверки связи» проходят, трафик не проходит.
