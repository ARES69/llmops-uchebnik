> [!IMPORTANT]
> Дефолтная позиция в любом проекте с LLM: **дообучение — это последний шаг, а не первый**. Порядок по умолчанию: промпт → few-shot → RAG → смена модели → дообучение. Пропуск первых трёх шагов в 90 % случаев означает, что команда потратила месяцы и GPU-бюджет там, где хватило бы двух дней работы с промптом и корпусом.

## Дерево решений

Разберём ветки — по одной строке правила и по одной причине.

| Вопрос | Ответ | Решение | Почему |
| --- | --- | --- | --- |
| Модель не знает факта, которого нет в подсказке | нет | **RAG** | факт, попавший в веса, устареет молча |
| Модель знает факт, но отвечает не в том формате | знает | промпт + few-shot | формат — это демонстрация, а не знание |
| Модель не понимает терминологию компании | частично | словарь в промпте → few-shot → дообучение | словарь из 80 терминов дешевле любого обучения |
| Нужен стабильный тон и стиль ответов | не умеет | промпт → дообучение | тон плохо задаётся словами, хорошо — примерами |
| Промпт с few-shot не помещается в бюджет | помещается, но дорого | дообучение | обучение переносит формат в веса, промпт укорачивается |
| Ответ должен укладываться в жёсткий SLA по времени | не укладывается | дообучение + меньшая модель | меньший контекст и меньше вызовов дают латентность |
| Примеров качественного размеченного материала меньше 500 | мало | **СТОП** | дообчение на малом наборе ломает модель, а не улучшает |
| Данные нельзя отдавать наружу | — | on-prem инференс + LoRA локально | ограничение по приватности решается размещением, а не отказом |
| Нет GPU и нет бюджета на разметку | — | вариантов нет | RAG и промпт — единственное доступное |

> [!CAUTION]
> Самая частая ошибка в этом дереве — не ответить на нижний вопрос про объём данных. «Давайте обучим» почти всегда произносится раньше, чем кто-то посчитал, сколько есть примеров. Вторая по частоте ошибка — требование засунуть в веса **факты**: прайс, список сотрудников, регламент, версии ПО. Такие вещи протухают тихо, и заметить это можно только через месяцы эксплуатации. Факты живут в базе; в весах живёт поведение. Смешивать их нельзя.

## Сколько стоит дообучение

Здесь нужно считать четыре статьи, и три из них не про GPU.

| Статья | Во что выливается | Типичная величина для проекта на 1000 примеров |
| --- | --- | --- |
| **Данные** | поиск примеров, разметка, чистка, согласование с экспертом | 3–5 % от общей стоимости |
| **Разметка** | работа эксперта с инструкцией и проверкой результата | 30–40 % |
| **Вычисления** | GPU-часы на обучение + на оценку каждой версии | 5–15 % |
| **Инженерное время** | пайплайн, воспроизводимость, сервис, мониторинг | 20–30 % |
| **Поддержка** | переобучение при изменении домена, откат версий | **бесконечно, пока живёт продукт** |

Числа в таблице — порядок величины для типового пилота, а не норма. Они показывают главное: **разметка стоит дороже вычислений**, и именно поэтому проект убивается не отсутствием GPU, а отсутствием людей, готовых три месяца размечать примеры.

```python
# /opt/decision/fine_tune_cost.py — сметы «стоит ли обучать» до начала работ
import json
from dataclasses import dataclass, asdict


@dataclass
class Cost:
    label: str
    hours: float
    rate_per_hour: float          # внутренняя ставка: час инженера, час эксперта, час GPU

    @property
    def money(self) -> float:
        return round(self.hours * self.rate_per_hour, 0)


def estimate(n_examples: int = 1000,
             avg_tokens: int = 1200,
             epochs: int = 3,
             model_params_b: float = 7.0,
             gpu_rate_per_hour: float = 180.0,
             engineer_rate: float = 2400.0,
             expert_rate: float = 3500.0,
             tokens_per_second: float = 4000.0) -> dict:
    """Все числа заменяем на свои: gpu_rate берётся из фактического счёта облака,
    engineer_rate — из твоей ставки, expert_rate — из стоимости часа эксперта в компании."""
    # 1. Данные: поиск, отбор, чистка примеров
    search_hours = n_examples / 60 * 0.5               # ~30 примеров в час на поиск и отбор
    # 2. Разметка: 4 минуты на пример (прочитать, написать ответ, проверить, согласовать)
    label_hours = n_examples * 4 / 60
    # 3. GPU: токены эпохи, делим на реальную скорость обучения (не инференса)
    total_tokens = n_examples * avg_tokens * epochs
    gpu_hours = total_tokens / tokens_per_second / 3600 * 1.5   # +50% на потери и оценки
    # 4. Инженерное время: пайплайн, оценка, сервис, отладка — 3-5 недель
    eng_hours = 3 * 5 * 8

    costs = [
        Cost("подготовка данных", search_hours, engineer_rate),
        Cost("разметка", label_hours, expert_rate),
        Cost("GPU-часы (обучение + оценка)", gpu_hours, gpu_rate_per_hour),
        Cost("инженерное время (пайплайн, сервис, отладка)", eng_hours, engineer_rate),
    ]
    total = sum(c.money for c in costs)

    # Порог: дообчение имеет смысл только если оно заменяет собою заметную работу.
    # Здесь — 40 человеко-часов, которые тратятся на промпты, поддержку и переписывание.
    return {
        "items": [asdict(c) | {"money": c.money} for c in costs],
        "total_money": total,
        "gpu_hours": round(gpu_hours, 1),
        "human_hours": round(search_hours + label_hours + eng_hours, 1),
        "rule_of_thumb": ("обучение оправдано, если результат экономит больше 40 человеко-часов "
                         "в год И даёт прирост качества, который промпт дать не может"),
        "verdict": "считать дальше" if total < 400_000 else "дороже, чем год работы промпт-инженера",
    }


if __name__ == "__main__":
    for n in (500, 1000, 5000, 20000):
        est = estimate(n_examples=n)
        print(f"{n:>6} примеров  GPU-ч: {est['gpu_hours']:>6}  "
              f"чел-ч: {est['human_hours']:>7}  сумма: {est['total_money']:>10,.0f} руб.")
    print(json.dumps(estimate(), ensure_ascii=False, indent=2))
```

### Главный недостаток: модель стареет вместе с базой знаний

Это стоит проговорить отдельно, потому что именно на этом строится сравнение с RAG.

Дообученная модель знает факт **внутри весов**. Чтобы он изменился, нужно переобучить или дообучить заново: собрать новые примеры, обучить, оценить, выкатить, откатить при неудаче. Время цикла — недели, стоимость — повторная смета, риск — регресс на всём остальном.

RAG знает тот же факт **в индексе**. Чтобы он изменился, достаточно заменить файл в папке и дождаться инкрементальной переиндексации, о которой — в [лекции про документы и OCR](mlops/23-dokumenty-i-ocr.md). Время цикла — минуты, стоимость — почти ноль, риск — отсутствует, потому что прошлые версии остаются в истории и видно, что изменилось.

Аналогия, которую стоит использовать в разговоре с руководством: **дообучение — это «научить нового сотрудника процедуре», RAG — это «дать опытному сотруднику доступ к справочнику»**. Первое занимает месяц стажировки и отнимает время у наставника; второе занимает полчаса. Но когда процедура меняется каждый месяц — справочник выигрывает, а когда меняется раз в два года и это критичный навык — обучение окупается.

### Сравнение способов

| Критерий | Промпт | Few-shot | RAG | Дообучение (LoRA) |
| --- | --- | :---: | :---: | :---: |
| Стоимость внедрения | 1–3 дня | 2–5 дней | 2–4 недели | 1–3 месяца |
| Стоимость владения | низкая | низкая | низкая | **средняя и растёт** |
| Обновление знаний | минуты | минуты | минуты | недели и GPU-часы |
| Объяснимость ответа | нет | нет | **да, с цитатой** | нет |
| Риск регрессии | низкий | низкий | средний | **высокий** |
| Влияние на латентность и цену | растёт с длиной | растёт заметно | +1 вызов | **снижает**: короче промпт |
| Откат | `git revert` | `git revert` | смена снапшота | возврат к базовой модели |
| Требования к данным | нет | 5–20 примеров | корпус документов | 500–5000 примеров |

## Техническая часть: ровно столько, сколько нужно архитектору

Ты не будешь это писать, но обязан понимать, о чём говорит команда, когда приносит результат. Поэтому здесь — четыре определения и таблица памяти.

**SFT (дообучение с учётом инструкций)** — обучение модели на парах «задание → правильный ответ». Модель учится не фактам из ответов, а тому, **как** отвечать на задание такого типа. Отсюда главное свойство: факты из примеров в веса надёжно не западают, а вот формат, тон и структура — западают.

**PEFT (parameter-efficient fine-tuning)** — дообучение, при котором основные веса модели заморожены, а обучается маленькая добавка. Это ключ к дешевизне: не нужно хранить градиенты и состояния оптимизатора для 7 миллиардов параметров.

**LoRA** — конкретный метод PEFT: к каждому слою добавляются две низкоранговые матрицы (обычно ранг 8–64), которые и обучаются. При ранге 16 на 7B это около 0,1–0,5 % параметров модели. Основные веса заморожены и лежат на видеокарте только для чтения. Отсюда три практических следствия:

- **обучение одной карточки**, а не кластера — для 7B это 24 ГБ VRAM;
- **веса не меняются** — можно хранить десятки адаптеров по 50–150 МБ каждый и переключать их как конфиги;
- **откат мгновенный** — снял адаптер, и снова работает базовая модель.

**QLoRA** — LoRA плюс квантование базовых весов до 4 бит перед обучением. Квантование даёт не ускорение, а **экономию памяти**: база занимает 3,8 ГБ вместо 15 ГБ, и вместе с оптимизатором, активациями и чекпойнтами обучение 7B помещается в 12–16 ГБ, то есть на потребительскую карту. Потеря качества от 4-битного кванта для генерации текста обычно незаметна, но **она всегда есть**, поэтому финальную модель тестируют на своём наборе, а не объявляют по факту.

| Способ | Что обучается | VRAM для 7B | Доля обучаемых параметров | Когда берут |
| --- | --- | :---: | :---: | --- |
| Полное дообучение | все 7B | 80–160 ГБ, шардирование | 100 % | никогда в корпоративном проекте, где нет команды ML и знаний |
| LoRA, fp16 база | адаптеры | 20–28 ГБ | 0,1–0,5 % | рабочий дефолт для пилота |
| QLoRA, 4-бит база | адаптеры | 10–16 ГБ | 0,1–0,5 % | когда карты нет или их нужно много |
| PEFT + несколько задач | набор адаптеров | 20–28 ГБ + 100 МБ на задачу | — | одна база, несколько продуктов |

## Данные: единственный настоящий стоп-фактор

Прежде чем обсуждать методы, нужно ответить на вопрос про данные. Скрипт ниже даёт формальный ответ «идти / не идти» и экономит месяц работы, если данных нет.

```python
# /opt/decision/data_readiness.py — готовы ли данные к дообучению. Годится и для проверки
# обучающей выборки, и для контроля качества разметки перед каждым запуском.
import json
import re
from collections import Counter, defaultdict

import numpy as np

# Ключевые слова, по которым видно утечку: если они есть и в обучении, и в golden set,
# оценка после обобучения будет завышена, и вы примете неверное решение о дообучении.
LEAK_MARKERS = ("договор №", "заявка №", "приказ №", "сотрудник ", "телефон", "@company")


def load(path: str) -> list[dict]:
    return [json.loads(line) for line in open(path, encoding="utf-8") if line.strip()]


def readiness(train: list[dict], golden: list[dict], min_examples: int = 500,
              min_per_label: int = 30) -> dict:
    labels = Counter(r.get("label", "none") for r in train)
    texts = [r["input"] for r in train]
    dup = 1 - len(set(texts)) / max(len(texts), 1)
    lens = [len(t) for t in texts]

    golden_norm = {re.sub(r"\W+", " ", g["query"].lower()).strip() for g in golden}
    overlap = sum(1 for t in texts if re.sub(r"\W+", " ", t.lower()).strip() in golden_norm)
    pii = sum(1 for t in texts if any(m in t.lower() for m in LEAK_MARKERS))

    rare = {k: v for k, v in labels.items() if v < min_per_label}
    issues = []
    if len(train) < min_examples:
        issues.append(f"STOP: {len(train)} примеров, нужно минимум {min_examples}")
    if rare:
        issues.append(f"редкие классы (<{min_per_label} примеров): {list(rare)[:5]}")
    if dup > 0.15:
        issues.append(f"дубликаты во входных данных: {dup:.0%} — качество примеров низкое")
    if overlap:
        issues.append(f"утечка в golden set: {overlap} примеров совпадают — оценка будет завышена")
    if pii:
        issues.append(f"персональные данные в {pii} примерах — см. лекцию о 152-ФЗ")

    return {
        "n_train": len(train),
        "labels": dict(labels),
        "length_p50": int(np.percentile(lens, 50)) if lens else 0,
        "length_p95": int(np.percentile(lens, 95)) if lens else 0,
        "dup_ratio": round(dup, 3),
        "golden_overlap": overlap,
        "pii_examples": pii,
        "issues": issues,
        "verdict": "GO" if not issues else "NO-GO",
    }


if __name__ == "__main__":
    import sys
    rep = readiness(load(sys.argv[1]), load(sys.argv[2]))
    print(json.dumps(rep, ensure_ascii=False, indent=2))
    sys.exit(0 if rep["verdict"] == "GO" else 2)
```

Что даёт этот скрипт помимо формального вердикта:

- **видит утечку** между обучающей выборкой и golden set — самый опасный и самый неочевидный дефект: оценка выглядит отлично, а в проде модель оказывается ничем не лучше базовой;
- **видит дубликаты** — если 40 % примеров повторяют одну и ту же формулировку, дообучение выучит шаблон, а не навык;
- **видит дисбаланс** — десять примеров на редкий класс означают, что на этом классе модель станет хуже, а не лучше;
- **видит ПДн** — примеры уходят в обучение и потом в веса, откуда их нельзя будет удалить по отзыву согласия. Это не вопрос вкуса: см. [лекцию о персональных данных](ru/02-personalnye-dannye-152fz.md).

## Оценка результата: обязательный шаг, а не опция

Здесь действует то же правило, что и для промпта: **дообучение не считается успешным, пока не измерено на golden set**. Та же методика, тот же набор, те же пороги из [лекции про оценку](mlops/15-ocenka-llm.md). Разница в том, что сравниваются не два текста промпта, а два разных артефакта — базовая и дообученная модель, — и критерий один: дало ли обучение прирост **там, где промпт уже не помог**.

| Критерий «обучение дало выигрыш» | Порог-пример | Почему именно это |
| --- | :---: | --- |
| Прирост `format_valid` или `citation_valid` | +5 п.п. | поведение, а не знание — то, что обучение чинит лучше всего |
| Прирост `groundedness` на сложных категориях | +3 п.п. | понимание сложного контекста, а не запоминание |
| Снижение `refusal_ok` | **допустимо только осознанно** | часто дообучение **ухудшает** отказ: модель увереннее отвечает всегда |
| Падение общих категорий | не более −1 п.п. | переобучение под нишу — главный риск |
| Экономия | −30 % токенов на запрос при том же качестве | второй, часто недооценённый аргумент «за» |
| Латентность | p95 не хуже базовой | дообучение не должно ухудшать эксплуатацию |

> [!IMPORTANT]
> Отдельная метрика, которую надо смотреть всегда: **`refusal_ok` после дообучения почти всегда падает**. Модель, обученная на тысяче примеров, где вход всегда имел осмысленный ответ, перестаёт отказываться — она уверенно производит ответ в привычном формате даже тогда, когда данных нет. Система, которая после дообучения перестала говорить «не знаю», стала опаснее, чем до него: она потеряла единственный механизм, который отличал правду от правдоподобной выдумки.

## Переобучение под нишу: как его поймать

Главная техническая проблема дообучения — не в том, что модель не учится, а в том, что она учится слишком хорошо. Набор из 800 примеров из одного отдела, двух типов документов и трёх формулировок проблемы — это не обучение навыку, это переезд всей личности модели в этот отдел. На общих вопросах она начинает отвечать хуже, и это видно не сразу, потому что ваш golden set тоже может оказаться смещённым.

```python
# eval/compare_tuned.py — сравнение базовой и дообученной модели по категориям.
# Главная метрика здесь — не среднее, а ДЕЛЬТА ПО КАТЕГОРИЯМ: среднее прячет провал.
import json
import statistics
from collections import defaultdict

from openai import OpenAI

client = OpenAI()


def run(model_ref: str, golden: list[dict], retrieve, max_tokens: int = 600) -> dict:
    """model_ref: точная ревизия модели. Никаких плавающих алиасов — см. лекцию о пайплайнах."""
    per_cat = defaultdict(list)
    for row in golden:
        chunks = retrieve(row["query"], k=6)
        allowed = {c["chunk_id"] for c in chunks}
        resp = client.chat.completions.create(
            model=model_ref, temperature=0.0, max_tokens=max_tokens,
            response_format={"type": "json_object"},
            extra_body={"seed": 7},                     # один seed для обеих моделей
            messages=[{"role": "system", "content": SYSTEM},
                      {"role": "user", "content": build_user(row["query"], chunks)}],
        )
        raw = resp.choices[0].message.content
        from eval.metrics import check_format, refusal_detected   # из лекции про оценку
        fmt = check_format(raw, allowed)
        per_cat[row["category"]].append({
            "format_valid": float(fmt["format_valid"]),
            "citation_valid": float(fmt["citation_valid"]),
            "refusal_ok": float(refusal_detected(raw if fmt["parsed"] else "", row.get("should_refuse", False))),
            "tokens": resp.usage.prompt_tokens + resp.usage.completion_tokens,
        })
    return {cat: {k: round(statistics.fmean(r[k] for r in rows), 3) for k in rows[0]}
            for cat, rows in per_cat.items()}


def verdict(base: dict, tuned: dict, min_general_drop: float = 0.01) -> dict:
    deltas, regressions, improvements = {}, [], []
    for cat, b in base.items():
        t = tuned.get(cat, b)
        d = {k: round(t[k] - b[k], 3) for k in b}
        deltas[cat] = d
        # «Общие» категории — те, где в обучении не было ни одного примера.
        # Именно на них проявляется переобучение под нишу.
        if cat in GENERAL_CATEGORIES and any(v <= -min_general_drop for v in d.values()):
            regressions.append({"category": cat, **d})
        if d["citation_valid"] > 0.05 or d["format_valid"] > 0.05:
            improvements.append({"category": cat, **d})
    return {
        "deltas": deltas,
        "regressions_on_general": regressions,      # главный сигнал: ухудшилось то, что не учили
        "improvements": improvements,
        "decision": ("принять" if improvements and not regressions
                     else "принять с оговоркой" if improvements
                     else "отклонить"),
    }


GENERAL_CATEGORIES = {"приветствие", "вопрос_вне_базы", "общий_вопрос", "просьба_объяснить"}
```

Логика здесь в том, что **категории, на которых обучали, улучшатся почти гарантированно, и именно они делают средний прирост красивым**. Единственный честный вопрос — что стало с теми категориями, которых в обучении не было. Если они просели, ты обучил модель нише, а не задаче.

> [!CAUTION]
> Отдельный риск, который не ловится метриками: после дообучения модель начинает **уверенно выдавать то, чему её научили, даже когда это неприменимо**. Она не скажет «я не знаю, такого в примерах не было» — она достроит ответ по выученному шаблону, с правильной структурой и неверным содержанием. На RAG этот риск ограничен цитатой: не нашёл в контексте — сказал «не нашёл». Дообучение эту страховку убирает, потому что источником ответа становятся веса, а не документ.

## Практика: шаблон решения

Документ заполняется **до** того, как команда получит задание на обучение. Его ценность в том, что он переводит разговор из «давайте попробуем» в «вот цифры, вот критерий, вот когда мы остановимся».

```yaml
# /opt/decision/fine_tune_decision.md — шаблон решения. Заполняется полностью или не запускается.
title: Решение о дообучении <название задачи>
date: 2025-06-11
owner: <ты>

problem: >
  Что именно не работает сегодня. Одно предложение, с цифрой.
  Пример: "на категории 'договоры' citation_valid = 0.62, нужно ≥ 0.90".

baseline:
  model: qwen2.5-7b-instruct-2025-01
  prompt_set: prompts/answer-v7
  golden_run: "2025-06-10T08:00Z"
  metrics: {citation_valid: 0.62, format_valid: 0.97, refusal_ok: 0.55}

tried_before_fine_tuning:          # обязательный раздел: без него решение не рассматривается
  - step: промпт (инструкция + 4 примера)
    result: citation_valid 0.62 -> 0.71, токенов на запрос 1180 -> 2410
  - step: RAG (гибридный поиск + reranker + top-6)
    result: citation_valid 0.71 -> 0.86
  - step: доработка извлечения из документов (лекция 23)
    result: citation_valid 0.86 -> 0.89
  conclusion: >
    Оставшийся разрыв — в терминологии и структуре ответа, а не в поиске.
    Промпт дал +0.09 за +1000 токенов; дальше инструкция растёт, а прирост падает.

data:
  n_examples: 1200
  labeled_by: отдел кадров, 2 эксперта
  labeling_hours: 80
  labeled_with_pii: false
  golden_overlap: 0                 # проверено скриптом data_readiness.py
  class_balance: {стандарт: 700, нестандарт: 400, отказ: 100}

cost:                              # результат fine_tune_cost.py
  gpu_hours: 3.4
  money_total: 285000
  gpu_risk: "аренда карты на 3 дня, отказ проекта — потеря 0 руб."

success_criteria:                  # проверяется на том же golden set
  - metric: citation_valid
    category: договоры
    min: 0.92
  - metric: format_valid
    min: 0.99
  - metric: refusal_ok
    min: 0.80                    # НИЖЕ текущего 0.55 не падаем, но и не выше — следить за деградацией
  - metric: groundedness_on_general
    max_drop: 0.01
  - metric: tokens_per_request
    max: 2410                    # цель: ниже, чем с few-shot; если выше — обучение не оправдано

rollback:
  trigger: >
    любой порог не выполнен после двух попыток, ИЛИ регрессия на общих категориях больше 1 п.п.
  action: >
    Снять адаптер (базовая модель работает без изменений), вернуть prompts/answer-v7,
    оставить чекпойнт и отчёт в архиве проекта.

privacy:
  data_location: on-prem
  vendors_involved: none
  deletion_procedure: >
    Удаление чекпойнта и всех производных. ВНИМАНИЕ: факты, попавшие в веса, удалить
    нельзя — поэтому в обучающие примеры не включаются факты, а только форма и поведение.
```

Критерии приёмки решения — то, что превращает документ из формальности в защиту:

- [x] Проблема сформулирована одной фразой с цифрой, а не словом «качество»;
- [x] Показаны минимум три предпринятых шага с измеренным результатом каждого;
- [x] Объём данных проверен скриптом, утечка в golden set исключена;
- [x] Стоимость посчитана целиком, включая инженерное время и разметку;
- [x] Критерии успеха заданы числами до начала обучения;
- [x] Определён триггер и способ отката;
- [x] Проверено, что в веса не попадут данные, которые обязаны быть удаляемыми.

Если хоть один пункт не отмечен — решение не готово к запуску, и это не формальность: именно этими пунктами ты будешь защищаться через три месяца, когда окажется, что прирост был в пределах шума.

```bash
# Порядок действий, если решение принято (команда выполняет, ты контролируешь результат)
cd /opt/ml/ft
python /opt/decision/data_readiness.py train.jsonl eval/golden.jsonl || exit 1   # стоп-факторы

# 1. Базовый замер на golden set — точка отсчёта
python /opt/eval/run_eval.py --model qwen2.5-7b-instruct-2025-01 \
       --golden eval/golden.jsonl --out eval/base.json

# 2. Обучение LoRA/QLoRA (команда ML, ~3 GPU-часа на этом наборе)
accelerate launch train.py --config lora_config.py --data train.jsonl --out runs/r1

# 3. Точка после: та же методика, тот же набор, тот же seed
python /opt/eval/compare_tuned.py --base qwen2.5-7b-instruct-2025-01 \
       --tuned runs/r1/adapter --golden eval/golden.jsonl --seed 7

# 4. Публикация только при вердикте "принять"
cat eval/base.json | jq -r '.version'    # идентификатор релиза — тот же, что в теге и в метриках
```

## Где это ломается

1. **Обучают факты.** Прайс, список сотрудников, регламент в весах. Протухает молча, обнаруживается через месяцы, «лечится» только переобучением. Факты живут в RAG.
2. **Начинают с дообучения.** Пропущены промпт, few-shot и RAG — и команда три месяца учит то, что решалось текстом инструкции за день.
3. **Нет измерения «до».** Базовый прогон на golden set не сделан, сравнивать не с чем, прирост не измеряется, решение принимается «на глаз».
4. **Утечка между обучением и golden set.** Модель выучила тест — оценка отличная, в проде так же, как базовая. Ловится `data_readiness.py` за секунды, не делается никогда.
5. **Переобучение под нишу не отслеживается.** Смотрят на среднее по набору, где 90 % примеров из обучения. Среднее растёт, общие вопросы деградируют. Смотреть надо по категориям, которых в обучении не было.
6. **Отказ перестал работать, и это заметили пользователи.** Самая опасная деградация после дообучения: модель уверенно отвечает там, где раньше честно говорила «не знаю».
7. **Дообучение не вписывается в релизный процесс.** У промптов есть теги и откат из [пайплайнов LLMOps](mlops/17-llmops-pipeliney.md), у чекпойнта — папка на сервере. Откат занимает день вместо минуты, и в проде это означает инцидент.
8. **Разметка сделана «на глаз» одним человеком без критериев.** Модель выучила вкусы одного эксперта, а второй отдел сразу её не узнаёт.
9. **Смена базовой модели ломает адаптер.** Обновили `qwen2.5` на `qwen3`, адаптер от старой базы остался подключён, качество упало — и не сразу нашлось, где.
10. **Оценка «на глаз», слушая пять ответов.** Тот же грех, что и с промптами: выбирают то, что нравится, а не то, что правильно.
