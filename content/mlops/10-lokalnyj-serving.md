Предыдущая лекция закончилась формулой «сколько весов влезет и с какой скоростью прочитается». Теперь нужен ответ на вопрос, который волнует всех одинаково: **чем именно это запускать**. Рынок движков вырос, и они различаются не списком фич, а архитектурой: одни оптимизируют удобство разработчика, другие — многослойную нагрузку. Разница между ними на одной и той же модели и одной и той же карте может быть пятикратной.

Разберём пять движков честно, с цифрами, и закончим рабочим запуском.

## Ollama: минимум магии

Ollama сделана так, чтобы первая модель запустилась за минуту. Под катом — llama.cpp с GGUF-моделями и удобной обёрткой: своё хранилище, управление версиями, OpenAI-совместимый API, автоматический подбор кванта под твою память.

Ты уже работал с Ollama в [предыдущей лекции](mlops/08-llm-kak-ustroena.md). Зафиксируем ключевые команды, которых нет в большинстве гайдов.

```bash
# Установка на Linux — одной командой, ставится в /usr/local/bin
curl -fsSL https://ollama.com/install.sh | sh
systemctl enable --now ollama          # в Docker и на голом хосте — не забывай про автозапуск

# Управление моделями
ollama pull qwen2.5:7b                 # скачать
ollama list                            # что скачано и сколько занимает на диске
ollama show qwen2.5:7b                 # метаданные: контекст, квант, параметры
ollama cp qwen2.5:7b my-qwen:latest   # сделать копию-алиас
ollama rm qwen2.5:7b                   # удалить
ollama ps                              # что сейчас загружено в память

# Запуск интерактивно и однократно
ollama run qwen2.5:7b
echo "Сколько будет 17% от 8450?" | ollama run qwen2.5:7b

# Прямой вызов API — он OpenAI-совместим, базовый URL /v1
curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen2.5:7b","messages":[{"role":"user","content":"Привет"}]}'

# Нагрузочный замер: 20 запросов параллельно, показываем токенов в секунду
ollama run qwen2.5:7b --verbose "перечисли 10 городов России"
```

**Modelfile** — механизм кастомизации: можно задать свой системный промпт, параметры генерации и базовую модель, и всё это становится отдельной «моделью» с собственным именем.

```dockerfile
# Modelfile
FROM qwen2.5:7b

PARAMETER temperature 0.2
PARAMETER num_ctx 8192
PARAMETER stop "###"

SYSTEM """Ты — внутренний помощник ИТ-отдела. Отвечай по-русски, кратко, без воды.
Если не знаешь ответа — так и скажи прямо."""
```

```bash
ollama create it-helper -f ./Modelfile
ollama run it-helper "Как открыть общий доступ к папке в Windows 11?"
```

Разворачивание Ollama в Docker требует **двух** важных вещей, которые почти всегда забывают: volume для моделей (иначе они скачиваются заново при каждом пересоздании контейнера) и правильного порта.

```bash
docker volume create ollama

docker run -d --name ollama --restart unless-stopped \
  -p 11434:11434 \
  -v ollama:/root/.ollama \
  -e OLLAMA_KEEP_ALIVE=30m \
  -e OLLAMA_MAX_LOADED_MODELS=1 \
  -e OLLAMA_NUM_PARALLEL=4 \
  ollama/ollama:latest

docker exec -it ollama ollama pull qwen2.5:7b
curl -s http://localhost:11434/api/tags
```

Значение переменных, которые пригодятся:

| Переменная | Что делает | Рекомендация |
| --- | --- | --- |
| `OLLAMA_KEEP_ALIVE` | сколько секунд держать модель в памяти после последнего запроса | `30m` для прода; по умолчанию 5 минут — модель выгружается между пиками |
| `OLLAMA_MAX_LOADED_MODELS` | сколько моделей держать одновременно | `1` на одной карте: каждая следующая съедает VRAM |
| `OLLAMA_NUM_PARALLEL` | сколько запросов обрабатывать параллельно на одной модели | 2–4; на 24 ГБ с 7B-Q4 можно 4, на 8 ГБ — 1–2 |
| `OLLAMA_NUM_THREAD` | потоков CPU при генерации | не трогать на GPU |

**Где у Ollama кончается возможности, и где начинается боль.**

Она честно решает задачу «один разработчик, один GPU, ноль настройки». Но под нагрузкой продакшена начинаются вещи, которых в документации нет:

- **Ограниченный контроль над батчингом.** `OLLAMA_NUM_PARALLEL` — это один целочисленный параметр. Нет предиктивного планирования батча, нет учёта длины последовательностей, нет приоритетов. При смеси запросов «короткие + длинные» короткие ждут в общей очереди.
- **Каждый запрос заново проходит префикс**. Ollama умеет переиспользовать префикс в рамках одного запроса, но не между разными запросами с общим системным промптом. При типовом RAG с одним и тем же системным промптом в 500 токенов это заметная потеря.
- **KV-кэш управляется просто.** Нет тонкой настройки, нет префикс-кеша, нет разделения памяти между весами и кэшем.
- **Нет tensor parallelism.** Модель, которая не влезает на одну карту, требует либо квантования до потери качества, либо llama.cpp с послойным разделением (медленно через PCIe).
- **Ошибки — текстом в лог**, а не метриками. Для мониторинга нужен обходной путь.

Итог: **Ollama — это «сервис-обёртка для разработчика», а не «движок инференса для продакшна»**. Оставляй её на ноутбуках, в CI, в демо и в стендах для тестирования.

## vLLM: движок, построенный под нагрузку

vLLM создан в лаборатории Berkeley, и вся его архитектура выведена из одного наблюдения: **реальная LLM-система — это не один запрос, а десятки одновременных, с разной длиной входа и выхода.** Отсюда четыре инженерных решения.

**PagedAttention** — менеджер памяти для KV-кэша. Наивная реализация выделяет под каждую последовательность непрерывный блок памяти по максимальной длине контекста. Два запроса из 200 и 5000 токенов при окне 8K занимают 2×8192 токена — 98 % памяти впустую, плюс постоянная фрагментация. PagedAttention берёт идею из операционных систем: память режется на фиксированные блоки (страницы) и хранится в общем пуле. Аналог: выделение памяти кучами вместо страниц. Один запрос занимает ровно столько блоков, сколько нужно, и может расти без копирования.

**Непрерывный батчинг** (continuous batching). Статический батч ждёт, пока закончат все N запросов, включая один короткий. При 64 параллельных запросах это катастрофа: один длинный запрос задерживает 63 остальных. Непрерывный батч добавляет новый запрос в батч, как только освободился слот, и удаляет завершившийся — без пересборки. Именно это даёт vLLM 10–30× по сравнению с наивной реализацией, а не «лучше скомпилированные ядра».

**Префикс-кеш.** Системный промпт, инструкция и описание формата обычно **одинаковы для всех запросов** к данной модели. vLLM вычисляет блок-хаши префикса и переиспользует уже посчитанный KV для него. При системном промпте в 500–2000 токенов и RAG-инструкции это экономит и вычисления, и память — существенно.

**OpenAI-совместимый сервер.** Тот же `/v1/chat/completions`, тот же формат ответа, то есть приложение переезжает между Ollama, vLLM и облачным API сменой одной переменной окружения. Это не мелочь: это то, что делает возможным [API-шлюз](mlops/11-api-shlyuz.md).

### Запуск и флаги, которые реально важны

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --enable-prefix-caching \
  --port 8000
```

Разберём каждый флаг — это ровно то, что тебе понадобится при планировании ресурсов.

| Флаг | Что делает | Как выбирать значение |
| --- | --- | --- |
| `--dtype` | точность весов: `auto`, `half` (fp16), `bfloat16`, `fp8` | `auto` в большинстве случаев. Явно ставь `bfloat16`, когда знаешь, что модель на нём обучена и карта поддерживает. `fp8` — Hopper/Ada, экономит вдвое и почти не теряет качество |
| `--max-model-len` | максимальная длина контекста, которую движок будет обслуживать | **главный рычаг памяти**. Ставь ровно столько, сколько реально нужно, а не по спецификации модели |
| `--gpu-memory-utilization` | доля VRAM, которую движок забирает под себя | 0,85–0,92. Выше — риск OOM от фрагментации, ниже — не используешь карту |
| `--max-num-seqs` | сколько последовательностей одновременно живёт в батче | ограничение по KV-кэшу. Больше — выше суммарная скорость, но не выше латентность |
| `--enable-prefix-caching` | переиспользование общего префикса промптов | включай, если есть системный промпт, общий для всех запросов |
| `--tensor-parallel-size` | на сколько GPU разложить модель | = число весов, которое не влезает на одну карту. Считается по [формуле из лекции 9](mlops/09-gpu-vram-cena.md) |
| `--pipeline-parallel-size` | разбить по слоям между GPU | редко нужно, для очень больших моделей |
| `--quantization` | схема квантования: `awq`, `gptq`, `fp8`, `bitsandbytes` | для заранее квантованных моделей; для AWQ/GPTQ указывать не нужно, движок видит сам |

> [!IMPORTANT]
> `--max-model-len` и `--max-num-seqs` — это одна пара в уравнении памяти: KV-кэш пропорционален произведению «контекст × параллельные запросы». Повесил окно 128K на модель, у которой реально просят 4K, — отдал в 32 раза больше VRAM на кэш, чем нужно, и получил вдвое меньше параллельных запросов. Это первая причина «мы купили карту, а она не тянет».

Проверка, что сервер поднялся и отдаёт что-то полезное:

```bash
curl -s http://localhost:8000/v1/models | python -m json.tool

curl -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
        "model": "Qwen/Qwen2.5-7B-Instruct",
        "messages": [{"role":"user","content":"Что такое MIG?"}],
        "max_tokens": 200,
        "temperature": 0
      }' | python -c "import json,sys; d=json.load(sys.stdin); \
print(d['choices'][0]['message']['content']); print('USAGE:', d['usage'])"
```

Стриминг — не «красивая опция», а способ сделать ответ от 30 секунд ощутимым за 2 секунды. Именно он спасает продукт от ощущения зависания.

```bash
curl -N http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
        "model": "Qwen/Qwen2.5-7B-Instruct",
        "messages": [{"role":"user","content":"Напиши развёрнутый план из 10 шагов"}],
        "stream": true
      }'
# Поток идёт по HTTP чанками: data: {"choices":[{"delta":{"content":"1"}}]} ...
# Заканчивается строкой data: [DONE]
```

### vLLM в Docker

Официальные образы уже содержат CUDA, поэтому главное — пробросить GPU, смонтировать кэш моделей и не забыть про доступность порта.

```bash
docker volume create hf-cache

docker run -d --name vllm \
  --gpus '"device=0"' \
  --ipc=host \
  --shm-size=8g \
  -p 8000:8000 \
  -v hf-cache:/root/.cache/huggingface \
  -e HF_HOME=/root/.cache/huggingface \
  -e HUGGING_FACE_HUB_TOKEN="${HF_TOKEN}" \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-7B-Instruct \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 64 \
  --enable-prefix-caching

docker logs -f vllm
```

Три флага, без которых контейнер не заработает:

- `--gpus '"device=0"'` — передаёт в контейнер **одну** карту из нескольких. Без кавычек весь список уедет в docker-compose, где кавычки обязательны.
- `--ipc=host` и `--shm-size=8g` — подводка для распределённого исполнения и батчинга; без неё получаешь `Bus error` или падение на длинном контексте.
- том для `HF_HOME` — иначе 15 ГБ весов скачиваются заново при каждом рестарте контейнера.

В docker-compose то же самое:

```yaml
services:
  vllm:
    image: vllm/vllm-openai:latest
    ipc: host
    shm_size: "8gb"
    ports: ["8000:8000"]
    volumes:
      - hf-cache:/root/.cache/huggingface
    environment:
      HF_HOME: /root/.cache/huggingface
      HUGGING_FACE_HUB_TOKEN: ${HF_TOKEN}
    command: >
      --model Qwen/Qwen2.5-7B-Instruct
      --dtype auto
      --max-model-len 8192
      --gpu-memory-utilization 0.90
      --max-num-seqs 64
      --enable-prefix-caching
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

volumes:
  hf-cache:
```

Для Kubernetes вместо этого нужен отдельный pod с лимитами памяти GPU, как разбирается в [проделе Kubernetes](devops/11-kubernetes-prodvans.md).

## llama.cpp, TGI, SGLang: остальные три

**llama.cpp** — то, на чём стоит Ollama. C++ без зависимостей, работает на CPU, Metal, CUDA, Vulkan. Модели в GGUF, квантование до 2 бит. Главное свойство: **самый широкий выбор железа** — от Raspberry Pi до Mac с unified memory и до кластера с Offload на GPU. Главное ограничение: архитектура «одна последовательность» без непрерывного батчинга, поэтому на большой конкурентной нагрузке отстаёт от vLLM в разы.

**TGI** (Text Generation Inference, Hugging Face) — зрелый движок с хорошей интеграцией с экосистемой HF, поддержкой flash-attention, квантования, метрик Prometheus «из коробки» и поддержкой тензорного параллелизма. Исторически чуть уступал vLLM по пропускной способности, но разрыв сильно сократился. Выбирают, когда команда уже сидит на HF и ценит единый стек.

**SGLang** — молодой движок от команды Berkeley, построен вокруг радикально новой идеи: несколько вызовов модели объединяются в один **программный блок** (program), у которого общий префикс вычисляется один раз. Для агентных сценариев, где десятки вызовов LLM имеют одинаковую инструкцию и различаются только данными, это даёт ускорение в разы. На прямой вопрос «кто лучше» SGLang пока не ответил — но если у тебя агентная система с Fan-Out, стоит за ним следить.

## Сравнение движков

| Критерий | Ollama | vLLM | llama.cpp | TGI | SGLang |
| --- | --- | :---: | :---: | :---: | :---: |
| Пропускная способность под нагрузкой | средняя | **высшая** | низкая | высокая | высокая |
| Непрерывный батчинг | частичный | **да** | нет | да | да |
| PagedAttention (эффективный KV-кэш) | нет | **да** | частичный | да | да |
| Префикс-кеш | в рамках запроса | **да** | нет | да | **на уровне программы** |
| Управление VRAM | минимальное | **полное** | ручное | полное | полное |
| Tensor parallelism | нет | **да** | частичный | да | да |
| CPU-инференс | слабый | нет | **основной режим** | нет | нет |
| Поддержка моделей | GGUF через Ollama-репозиторий | HF, широкий выбор | GGUF | HF, широкий выбор | HF, широкий выбор |
| OpenAI-совместимый API | да | **да, эталон** | да | да | да |
| Метрики Prometheus | нет | **да** | нет | **да, из коробки** | да |
| Сложность эксплуатации | **минимум** | средняя | низкая | средняя | средняя |
| Кому подходит | один разработчик, ноутбук, CI, демо | **прод с конкурентной нагрузкой** | edge, CPU, оффлайн | прод, если команда на HF | агентные сценарии |

### Рекомендация по сценариям

| Сценарий | Что выбрать | Почему |
| --- | --- | --- |
| Один разработчик, ноутбук 16 ГБ, нужно «покрутить модель» | **Ollama** | минимум возни, авто-подбор кванта |
| Тесты в CI, короткие промпты | **Ollama** или llama.cpp | поднимается за секунды, не нужен GPU |
| Внутренний сервис с 10–30 одновременными пользователями | **vLLM** | непрерывный батчинг вместо очереди |
| Прод с конкурентной нагрузкой, SLA, 24/7 | **vLLM** | PagedAttention, метрики, параллелизм |
| Edge-устройство без дискретной GPU | **llama.cpp** | единственный реальный вариант |
| CPU-only, приватность, ночные батчи | **llama.cpp** | GGUF + CPU |
| Команда целиком на Hugging Face | **TGI** | единый стек, готовые метрики |
| Агентная система с множеством параллельных вызовов | **SGLang** (пробовать) | общий префикс на уровне программы |
| Промышленный 70B на нескольких GPU | **vLLM** или TGI | tensor parallelism из коробки |

## Где живут файлы моделей

Отдельная тема, на которой спотыкается каждый, кто впервые разворачивает в контейнере: **веса скачиваются автоматически, и это источник двух бед**.

1. **Холодный старт.** Контейнер без тома при каждом рестарте качает 15 ГБ заново. Деплой занимает 20 минут вместо 40 секунд, и если при этом нет интернета — вообще не поднимается.
2. **Тихое скачивание.** Подсказка «скачается при первом запуске» означает, что модель грузится во время деплоя, в момент, когда у тебя уже нет права на ошибку.

Решение — предсказуемое хранилище через `HF_HOME`:

```bash
# Единая точка для всех библиотек Hugging Face
export HF_HOME=/srv/models/hf
mkdir -p "$HF_HOME"

# Как vLLM это увидит
docker run --rm \
  -v /srv/models/hf:/root/.cache/huggingface \
  -e HF_HOME=/root/.cache/huggingface \
  vllm/vllm-openai:latest --model Qwen/Qwen2.5-7B-Instruct --help
```

Что ещё важно знать про хранилище:

- **Скачать заранее** — `huggingface-cli download Qwen/Qwen2.5-7B-Instruct --local-dir /srv/models/qwen2.5-7b`, затем запускать с локальным путём, а не с именем репозитория;
- **оффлайн-режим** — `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1` заставляют библиотеку не ходить в сеть. Если забыт токен или нет интернета, ты получаешь явную ошибку вместо 15-минутного ожидания;
- **снапшоты** — `~/.cache/huggingface/hub/models--Qwen--Qwen2.5-7B-Instruct/snapshots/` содержит готовые веса и позволяет держать несколько версий модели рядом, откатываясь за секунды;
- **приватные модели** требуют `HF_TOKEN`, который лучше хранить в секретах Kubernetes или в Vault, а не в образе и не в `docker-compose.yml` в репозитории;
- **альтернатива Hugging Face** — ModelScope (от Alibaba), зеркала и внутренние артефактории. В некоторых регионах доступ к huggingface.co нестабилен, и это самостоятельный риск планирования.

## Выбор модели под задачу и железо

Не «какая модель лучшая», а «какая модель помещается в мой бюджет VRAM и даёт достаточное качество на моих 50 примерах». Алгоритм:

1. Возьми 50–100 реальных примеров из своей задачи и оцени модель на них вручную.
2. Отсеки всё, что не проходит порог качества.
3. Из оставшихся посчитай объём весов в нужном кванте: `параметры × биты / 8`.
4. Добавь KV-кэш на свой контекст и параллельность, добавь 1,5 ГБ и запас 20 %.
5. Сравни с VRAM своей карты. Если не помещается — либо меньше квант, либо меньше модель, либо вторая карта.

| Модель | Квант | Веса | Минимум VRAM (веса + 4K×4 + запас) | Реалистичная карта | Хороша для |

| Qwen2.5-3B | Q4_K_M | 1,9 ГБ | 4,5 ГБ | любая, даже 6 ГБ | черновики, классификация, дешёвые подзадачи |
| Qwen2.5-7B-Instruct | Q4_K_M | 4,7 ГБ | 8 ГБ | RTX 3060 12 / 4060 Ti 16 | **рабочая лошадка**: RAG, суммаризация, агенты |
| Qwen2.5-7B-Instruct | Q8_0 | 7,6 ГБ | 12 ГБ | RTX 4060 Ti 16 / A2 24 | качество выше, карта та же по классу |

| --- | --- | --- |

> Зеркальная лицензия — половина выбора. Apache 2.0 у Qwen2.5-7B снимает вопросы «можно ли использовать в коммерческом продукте» и «можно ли дообучать». Для Llama 3.1 эти вопросы требуют юридической проверки до начала пилота, а не после.

## Практика: поднимаем и сравниваем

Один и тот же вес в двух движках — единственный честный способ сравнить. Скрипт отправляет N запросов с конкурентностью C и печатает итог.

```bash
#!/usr/bin/env bash
# bench.sh <endpoint> <model> <n> <concurrency>
set -euo pipefail
EP="$1"; MODEL="$2"; N="${3:-20}"; C="${4:-4}"

echo "=== ${EP} | модель ${MODEL} | запросов ${N} | параллельность ${C} ==="

seq 1 "$N" | xargs -P "$C" -I{} curl -s -o /dev/null \
  -w '%{time_starttransfer} %{time_total}\n' \
  "$EP/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL}\",\"max_tokens\":200,\"temperature\":0,
       \"messages\":[{\"role\":\"user\",\"content\":\"Опиши водопад в двух предложениях\"}]}" \
  | python -c "
import sys
lat = sorted(float(l.split()[1]) for l in sys.stdin if l.strip())
ttft = sorted(float(l.split()[0]) for l in sys.stdin if l.strip())
def p(xs, q): return xs[min(len(xs)-1, int(len(xs)*q))]
print(f'  TTFT  p50={p(ttft,.5):.2f}s  p95={p(ttft,.95):.2f}s')
print(f'  TOTAL p50={p(lat,.5):.2f}s  p95={p(lat,.95):.2f}s')
print(f'  RPS ≈ {len(lat)/lat[-1]:.2f}')
"
```

```bash
chmod +x bench.sh
./bench.sh http://localhost:11434 qwen2.5:7b 40 4    # Ollama
./bench.sh http://localhost:8000  Qwen/Qwen2.5-7B-Instruct 40 4  # vLLM
./bench.sh http://localhost:8000  Qwen/Qwen2.5-7B-Instruct 40 32 # vLLM под нагрузкой
```

Смотри не на RPS, а на **p95 латентности при высокой параллельности**. Разница, которую ты увидишь: Ollama при параллельности 4 просядет по TTFT (запросы встают в очередь), vLLM выдержит те же 4 с почти той же латентностью и на 32 запросах выдаст в разы больше суммарной скорости.

Проверка, что стриминг действительно стримит, а не копит ответ и не выдаёт разом:

```bash
# -N отключает буферизацию curl; если таймстемпы идут равномерно — стрим работает
curl -N -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-7B-Instruct","stream":true,
       "messages":[{"role":"user","content":"Посчитай от 1 до 20 через запятую"}]}' \
  | while IFS= read -r line; do printf '%s %s\n' "$(date +%H:%M:%S.%3N)" "$line"; done
```

И диагностический приём, который стоит сделать сразу при первом развёртывании: **проверить, что модель действительно на GPU, а не уехала в CPU.**

```bash
nvidia-smi                                  # есть ли процесс и сколько VRAM занято
watch -n 2 'nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv,noheader'
docker logs vllm 2>&1 | grep -i -E "device|cuda|offload|warn"
```

Если в логах `device=cpu` или падает с `float16` вместо `bfloat16`, значит либо не пробросился `--gpus all`, либо движок не нашёл CUDA, либо формат не поддерживается картой. Это ровно тот класс проблем, который ловится за минуту, если знать, куда смотреть.

## Где это ломается

1. **Оставили `--max-model-len` по спецификации модели.** 128K вместо нужных 8K — и половина VRAM ушла в пустой кэш, параллельность упала вдвое.
2. **Не смонтировали том с весами.** Каждый рестарт контейнера тянет 15 ГБ заново, деплой идёт минутами, а без интернета не идёт вообще.
3. **Забыли `--ipc=host` в Docker.** Путаница в `Bus error (core dumped)` при длинном контексте, ошибки в NCCL при параллелизме.
4. **Слишком высокий `--gpu-memory-utilization`.** Значение 0,99 заканчивается OOM через час работы, когда фрагментация добивает остаток.
5. **`--gpus all` вместо конкретного устройства в контейнере.** Два контейнера делят одну карту, и оба падают в OOM вместо того, чтобы работать по очереди.
6. **Ошиблись с кавычками в docker-compose.** Значение `count: 1` в `deploy.resources` работает, `gpus: all` в строке `command` не работает — формат разный, и ошибка выглядит как «Compose не понимает».
7. **Откатились на GGUF, потому что «квант меньше», и потеряли качество.** Q3 и ниже дают обрывающиеся предложения и циклы генерации — это хуже, чем нехватка VRAM.
8. **Считали, что Ollama — это сервер.** При параллельности 20+ запросов она становится очередью с плохим TTFT, и отладка уводит не туда.
9. **Запустили на коммерческом API с именем репозитория и не задали `HF_HUB_OFFLINE=1`.** В контуре без интернета деплой падает на таймауте с загадочным сообщением.
10. **Модель ехала на CPU, а вы смотрели на логи приложения.** Первые 30 секунд после старта всегда смотри в `nvidia-smi`, а не в ответы клиентов.
11. **Два vLLM на одной карте в Docker Compose.** Каждый забрал `--gpu-memory-utilization 0.9` от своей карты, а карта одна — OOM при старте второго. Дели `0.45` или ставь на разные карты.
12. **Сравнивали Ollama и vLLM на одном запросе и сделали вывод.** На одном запросе разница в скорости незаметна — она проявляется на десятках параллельных.
13. **Взяли Llama без чтения лицензии.** Llama 3.1 — не Apache 2.0, и ограничения на атрибуцию и на имена продукта применяются к вашему продакшн-продукту.
