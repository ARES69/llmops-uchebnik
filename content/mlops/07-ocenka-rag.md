Через две лекции ты собрал систему, которая отвечает. Через месяц кто-то из пользователей напишет, что ответы стали хуже. И ты стоишь перед выбором: откатывать релиз или чинить. Откатывать — потому что «три дня назад точно работало», или чинить — потому что «вроде никто не жаловался». Оба ответа неправильные, если у тебя нет числа. Эта лекция про то, как получить число: разложить качество на измеримые слои, построить судью над золотым набором и встроить проверку в CI. Здесь ты переходишь из инженера «кто лучше, Qdrant или pgvector» в инженера, который может защитить бюджет и не дать качеству упасть.

## «Работает» — не метрика

Главная ошибка в оценке LLM-систем — измерение того, что удобно, вместо того, что важно. Удобно измерить latency. Важно — правильность.

Вторая ошибка — измерять только конечный результат. «Ответ на вопрос верный / неверный» — это одна цифра, которая не говорит, **где** чинить. При этом у RAG-системы четыре независимые точки отказа, и они лечатся совершенно по-разному:

| Слой | Что сломалось | Симптом у пользователя | Кто чинит |
| --- | --- | --- | --- |
| Данные | нет документа или он мусорный | «в базе этого нет» | пайплайн из [лекции 04](mlops/04-dannye-i-pipeliney.md) |
| Чанкинг | нужный документ есть, но разорван | ответ неполный | чанкер |
| Ретривер | документ есть, но не в выдаче | «не нашёл» | эмбеддинги, фильтры, метрика расстояния |
| Рерянкер | документ есть, но на 8-м месте из 20 | «не нашёл», хотя он в выдаче | модель реранкера |
| Генератор | контекст верный, ответ неверен | уверенная неправда | промпт, модель, температура |

Отсюда правило: **оценка идёт по слоям, снизу вверх**. Пока recall ретривера ниже 0.85, трогать промпт бессмысленно — модель не получает правильный контекст, и никакой промпт это не исправит.

## Слой 1: ретривер

Метрики считаются по полю `sources` из золотого набора. Напоминаю из [лекции о данных](mlops/04-dannye-i-pipeliney.md): без этого поля объективной метрики поиска не существует.

```python
# /opt/rag-pipeline/eval/eval_retrieval.py — метрики поиска по слоям
import json
from collections import defaultdict

def evaluate_retrieval(cases: list[dict], search_fn) -> dict:
    """cases: golden set. search_fn(question, k) -> список dict с ключом chunk_id."""
    buckets = defaultdict(list)
    per_case = []
    for c in cases:
        gold = {s["chunk_id"] for s in c["sources"]}
        if not gold:
            continue
        hits = search_fn(c["question"], k=10)
        ids = [h["chunk_id"] for h in hits]
        gold_docs = {s["chunk_id"].split("::")[0] for s in c["sources"]}

        hit10 = next((r for r, i in enumerate(ids, 1) if i in gold), None)
        first_hit_doc = next((r for r, i in enumerate(ids, 1)
                              if i.split("::")[0] in gold_docs), None)

        m = {
            "id": c["id"],
            "recall@5": len(set(ids[:5]) & gold) / len(gold),
            "recall@10": len(set(ids[:10]) & gold) / len(gold),
            "mrr": 1.0 / hit10 if hit10 else 0.0,
            "hit@10": 1.0 if hit10 else 0.0,
            "hit_doc@10": 1.0 if first_hit_doc else 0.0,
        }
        m.update({"rank": hit10 or 0, "doc_rank": first_hit_doc or 0,
                  "tags": c.get("tags", [])})
        per_case.append(m)
        for t in ([c["tags"][0]] if c.get("tags") else []) + ["all"]:
            buckets[t].append(m)

    def agg(rows):
        return {k: sum(r[k] for r in rows) / len(rows)
                for k in ("recall@5", "recall@10", "mrr", "hit@10", "hit_doc@10")}

    return {"overall": agg(per_case),
            "by_tag": {t: agg(rows) for t, rows in buckets.items()},
            "per_case": per_case}
```

Разбивка `by_tag` — самая полезная часть. Средний recall 0.87 может прятать катастрофу: на вопросах про безопасность 0.55, на вопросах про сети 0.95. Среднее по системе выглядит прилично, а продукт для отдела ИБ — нерабочий.

Ещё одна метрика, которую стоит считать всегда: **`rank_in_top1`** — доля случаев, где нужный документ стоит первым. Для RAG это ближе всего к «документ нашёлся сразу», и на этой метке ломается всё остальное.

| Метрика | Что показывает | Целевое значение |
| --- | --- | ---: |
| hit@10 | нашёлся ли вообще | > 0.95 |
| recall@10 | какая доля нужного в выдаче | > 0.90 |
| recall@5 | сколько нужно для контекста из 5 | > 0.85 |
| MRR | насколько высоко нужное | > 0.75 |
| rank@1 | нужный документ первым | > 0.55 |

## Слой 2: реранкер

Ретривер и реранкер оцениваются **одним и тем же золотым набором, но на разном k**. Если MRR ретривера ниже, чем MRR реранкера, — реранкер работает. Если ниже — он не нужен и только тратит latency.

```python
# Сравнение слоёв на одном наборе: берём top-30 от ретривера и top-5 после реранкера
base = evaluate_retrieval(cases, lambda q, k: dense_search(q, n=30)[:k])
after = evaluate_retrieval(cases, lambda q, k: rerank(q, dense_search(q, n=30))[:k])

for name, r in (("до rerank", base), ("после rerank", after)):
    o = r["overall"]
    print(f"{name:>14}: MRR={o['mrr']:.3f}  recall@5={o['recall@5']:.3f}  "
          f"hit@10={o['hit@10']:.3f}")
```

Ожидаемая картина: MRR растёт заметно (0.68 → 0.83), recall@5 растёт умеренно. Если recall@5 после rerank **упал** — перечитывай код: скорее всего, ты фильтруешь кандидатов по `score_threshold` уже после ранжирования и отсекаешь нужное.

## Слой 3: генератор

Здесь метрики становятся субъективными, и появляется главный инструмент оценки LLM-систем.

**Faithfulness / groundedness** — насколько утверждения ответа следуют из контекста. Ключевая метрика против галлюцинаций: ответ может быть написан прекрасно, но если он не опирается на источники, он опасен.

**Answer relevancy** — отвечает ли ответ на заданный вопрос. Ответ «информация о резервном копировании включает расписание и хранение» на вопрос «как настроить расписание?» частично релевантен.

**Context precision** — какая доля переданного контекста реально использована. Низкая — значит, в контекст попало много мусора, и это проблема ретривера, а не генератора.

**Context recall** — покрывает ли переданный контекст золотой ответ. Это мост между ретривером и генератором: если контекст покрывает эталон, а ответ неверен — виновата генерация.

| Метрика | Вопрос, на который отвечает | Как чинить при падении |
| --- | --- | --- |
| Faithfulness | «Ответ выдуман или основан на тексте?» | промпт, модель, температура |
| Answer relevancy | «Это вообще ответ на мой вопрос?» | промпт, переформулировка запроса |
| Context precision | «Сколько мусора я скармлил модели?» | ретривер, rerank, top-k |
| Context recall | «Дал ли я модели всё, что нужно?» | ретривер, чанкинг, корпус |
| Citation accuracy | «Цитаты указывают на реально использованное?» | сборка цитат, промпт |

## LLM-as-a-judge

Прямой вопрос: «Правильный ли ответ?» без эталона субъективен, а с эталоном всё равно субъективен — человек тратит 15–20 минут на 50 кейсов и устаёт на десятом. LLM-as-a-judge — оценка ответов моделью по заранее заданному промпту-критерию. Работает, потому что **проверка на соответствие тексту** (есть ли в контексте то, что утверждает ответ) — это гораздо более простая задача, чем генерация, и модели с ней справляются хорошо.

```python
# /opt/rag-pipeline/eval/judge.py
import json
from openai import OpenAI

JUDGE_MODEL = "qwen2.5:14b-instruct"      # версия судьи фиксируется навсегда, см. ниже
judge_llm = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

FAITHFULNESS_PROMPT = """Ты — строгий судья фактов. Тебе дан ОТВЕТ и КОНТЕКСТ,
на основе которого ответ должен был быть написан.

ЗАДАЧА: найди каждое утверждение ответа, которое НЕ следует из контекста.

КОНТЕКСТ:
{context}

ОТВЕТ:
{answer}

Если каждое утверждение ответа подтверждается контекстом — верни faithfulness = 1.
Если есть неподтверждённые утверждения — верни 0.
Не оценивай стиль, полноту или вежливость. Только обоснованность.

Верни ТОЛЬКО JSON: {{"faithfulness": 0 или 1, "reason": "краткое объяснение"}}"""

RELEVANCY_PROMPT = """Оцени, отвечает ли ОТВЕТ на ВОПРОС по существу.

ВОПРОС: {question}
ОТВЕТ: {answer}

0 — ответ не про вопрос, или уходит в сторону.
1 — ответ по делу, даже если неполный.

Верни ТОЛЬКО JSON: {{"answer_relevancy": 0 или 1, "reason": "..."}}"""

# Хеш промпта — часть версии оценки. Меняешь текст — меняется версия.
import hashlib
JUDGE_VERSION = hashlib.sha256(
    (FAITHFULNESS_PROMPT + RELEVANCY_PROMPT + JUDGE_MODEL).encode()
).hexdigest()[:12]


def judge_faithfulness(answer: str, context: str) -> dict:
    r = judge_llm.chat.completions.create(
        model=JUDGE_MODEL, temperature=0.0, max_tokens=300,
        messages=[{"role": "user",
                   "content": FAITHFULNESS_PROMPT.format(context=context, answer=answer)}])
    try:
        return json.loads(r.choices[0].message.content)
    except json.JSONDecodeError:
        # Судья ответил не-JSON — это тоже результат, который надо считать, а не глотать
        return {"faithfulness": None, "reason": "parse_error", "raw": r.choices[0].message.content}
```

### Плюсы и минусы

| Плюсы | Минусы |
| --- | --- |
| Масштабируется: 150 кейсов за 10 минут вместо 5 часов | смещения: предпочитает длинные, «уверенные» и стилистически гладкие ответы |
| Воспроизводимо при фиксированной версии | зависит от модели судьи — смена версии ломает сравнимость |
| Можно добавлять новые критерии без переразметки | не видит фактической корректности, если контекст сам неверен |
| Дёшево: локальная модель на своём GPU — 0 рублей | требует калибровки на людях, иначе это просто красивые числа |

**Правило калибровки**: возьми 30–50 кейсов, оценённых человеком, и 50 кейсов, оценённых судьёй, и посчитай согласованность (для бинарных — просто долю совпадений, для оценок по шкале — Cohen's kappa). Если согласованность ниже 0,7 — судью нельзя использовать для решений о релизе, только как вспомогательный сигнал. Это 15 минут работы, которые экономят месяцы ложных решений.

> [!IMPORTANT]
> **Судья должна быть не слабее оцениваемой системы.** Если ты оцениваешь ответы qwen2.5:7b судьёй той же qwen2.5:7b, ты измеряешь не качество, а способность модели замечать собственные ошибки. Рабочая конфигурация: оцениваешь модель покомпонтно, судья — на ступень выше. Судья слабее системы гарантированно завышает оценки, потому что не способна отличить тонкую ошибку от уверенного тона.

> [!CAUTION]
> Фиксируй версию. Судья — это код, и он меняется так же, как код: обновил модель судьи, переписал формулировку критерия, добавил пример — и цифры «уплыли» на 5–8 пунктов, а это не регрессия продукта. Сохраняй `JUDGE_VERSION` вместе с результатами каждого прогона и храни оба. Без этого история качества не существует — есть только текущее число.

## Человеческая оценка как источник истины

LLM-судья — это масштабирование, а не замена людям. Разметку делают люди, потому что в какой-то момент встречается вопрос, где «правильный ответ» — это ответ, который сделал бы сотрудник, а не формально вытекающий из текста.

Практическая процедура, которая работает:

1. Возьми 50–100 кейсов из реального лога вопросов.
2. Дай 2 инженерам разметить **независимо**.
3. Посчитай согласованность. Ниже 0,6 — вопрос сформулирован неоднозначно, переформулируйте или удалите.
4. Разногласия разбери лично: они указывают, где в корпусе неоднозначность, и это баг данных, а не кейса.
5. Зафиксируй согласованный результат как golden set и **заморозь**.

Когда человек нужен, а когда хватит судьи:

| Задача | Кто оценивает | Почему |
| --- | --- | --- |
| Ответ опирается на контекст | LLM-судья | проверка соответствия, модели справляются |
| Ответ по делу | LLM-судья | сравнение с вопросом, простая задача |
| Правильность факта | человек + эталон | нужно знать предметную область |
| «Ответ похож на то, как ответил бы наш инженер» | только человек | стиль, тон, полнота, контекст организации |
| «Достаточно ли цитат» | LLM-судья | структурная проверка |

## End-to-end метрики

Итоговые метрики, которые имеет смысл показывать руководству и ставить как SLO качества (по схеме из [наблюдаемости](devops/15-monitoring-concepts.md)).

```python
# /opt/rag-pipeline/eval/eval_e2e.py — метрики, которые видит пользователь
def evaluate_e2e(cases, ask_fn) -> dict:
    rows = []
    for c in cases:
        r = ask_fn(c["question"])
        judge = judge_answer(r["text"], c)
        rows.append({
            "id": c["id"],
            # 1. Точность ответа: человек-эталон или строгий судья + ручная выборочная проверка
            "correct": judge["correct"],
            # 2. Отказ вместо выдумки: главная метрика против галлюцинаций
            "refused_ok": (r["refused"] if c["expected_refusal"]
                           else not r["refused"]),
            # 3. Цитирование: есть ли ссылка И указывает ли она на релевантный источник
            "cited": len(r["citations"]) > 0,
            "citation_relevant": any(
                cit["url"].endswith(s["doc_id"].split("#")[0]) for cit in r["citations"]
            ) if r["citations"] else False,
            "faithfulness": r.get("faithfulness"),
            "answer_relevancy": r.get("answer_relevancy"),
            "latency_ms": r["latency_ms"],
            "tokens": r["usage"]["total_tokens"],
        })
    n = len(rows)
    agg = {k: sum(bool(r[k]) for r in rows) / n for k in
           ("correct", "refused_ok", "cited", "citation_relevant", "faithfulness",
            "answer_relevancy")}
    agg["refusal_rate"] = sum(r["refused_ok"] for r in rows) / n
    return {"aggregate": agg, "per_case": rows}
```

Метрики, которые стоит вывести на дашборд рядом с техническими:

| Метрика | Начальный порог | Что означает провал |
| --- | ---: | --- |
| `rag_correct_rate` | > 0.80 | качество ответов ниже приемлемого |
| `rag_refusal_accuracy` | > 0.90 | либо галлюцинирует, либо отказывается на пустом месте |
| `rag_citation_rate` | > 0.95 | пользователю нечего открыть и проверить |
| `rag_faithfulness` | > 0.90 | ответы содержат неподтверждённые утверждения |
| `rag_context_recall` | > 0.85 | ретривер систематически не дотягивает |

`rag_refusal_accuracy` — метрика, которую почти никто не считает, и именно она определяет, закроют систему или нет. Корпоративный ассистент, который уверенно отвечает на вопросы, ответов на которые нет, опаснее поисковика: на него будут ссылаться в решениях.

## Диагностика по слоям

Главный рабочий инструмент — построчная таблица «симптом → что чинить». Это то, к чему ты возвращаешься, когда метрика упала и надо понять, куда копать.

| Симптом | Что сломалось | Диагностический признак | Что делать |
| --- | --- | --- | --- |
| Частые отказы, «не нашёл ответа» | ретривер | hit@10 низкий, но документ точно есть в корпусе | фильтры слишком жёсткие, embedding-модель, размер чанка |
| Отказы, документа в корпусе нет | данные | нет ни одного совпадения даже по BM25 | корпус неполный: коннектор не забирает этот источник |
| Находит, но отвечает не по тому | реранкер | нужный документ в выдаче на 8–15 месте | включить/заменить reranker |
| Находит, но отвечает поверхностно | чанкинг | нужный документ в выдаче, но релевантный абзац — в другом чанке | структурный чанкинг, увеличить max_tokens |
| Галлюцинации при правильном контексте | генератор | context recall высокий, faithfulness низкий | усилить промпт, temperature=0, сменить модель |
| Галлюцинации при неправильном контексте | ретривер + генератор | context recall низкий | чинить поиск, а не промпт |
| Пропали цитаты | сборка ответа | ответ верный, `cited` = 0 | инструкция про `[N]` в промпте |
| Цитаты неверные | сборка ответа | `[3]` указывает не на использованный источник | маппинг номер→документ строить по факту упоминания |
| Хорошие метрики, плохие отзывы | разметка | метрики зелёные, пользователи недовольны | golden set не отражает реальные вопросы |

> [!TIP]
> Порядок диагностики всегда один: **hit@10 → rank нужного в выдаче → faithfulness ответа**. Три числа, три разных причины. Начинать с конца («может, промпт лучше написать») — это потеря дня работы, потому что в 80% случаев виноват первый или второй показатель.

## Регрессии качества в CI

Золотой набор существует ради одного: чтобы прогонять его **при каждом изменении**. Список того, что обязано запускать eval:

- изменение чанкинга (размер, overlap, стратегия)
- смена модели эмбеддингов или метрики расстояния
- смена или обновление reranker'а
- изменение промпта (системного или user'а)
- смена генеративной модели или её параметров (temperature, top_p)
- изменение правил фильтрации или top-k
- обновление корпуса, если в golden set не проставлен `corpus_snapshot`

```bash

    ok_drop = drop <= max_drop

                  f"порог={thr} падение={drop:+.3f} "
                  f"{'OK' if ok_thr and ok_drop else 'FAIL'}")
    if not (ok_thr and ok_drop):
        failed.append(name)

print("\n".join(checks))
if failed:
    print(f"\nОТКАТ: провалены {', '.join(failed)}. Ухудшился ретривер или генератор — "
          f"смотри слой по метрикам ниже, какая именно упала.")
    print("Top-5 проваленных кейсов:")
    for r in sorted(cur["per_case"], key=lambda r: r.get("recall@5", 0))[:5]:
        print(f"  {r['id']}: recall@5={r.get('recall@5')} тег={r.get('tags')}")
    sys.exit(1)
print("\nВсе пороги пройдены — деплой разрешён.")
```

## Пример расчёта: от 0,87 к 0,79

Разберём конкретный прогон, чтобы цифры перестали быть абстракцией.

Было (после релизa с overlap=120, bge-m3, reranker v2-m3):

```text
recall@5 = 0.870   mrr = 0.812   hit@10 = 0.960
faithfulness = 0.940   correct_rate = 0.840   citation_rate = 0.980
```

Кто-то в рамках «оптимизации индексации» поменял `overlap: 120 -> 0`, чтобы индекс был компактнее. Стало:

```text
recall@5 = 0.790   mrr = 0.744   hit@10 = 0.958
faithfulness = 0.940   correct_rate = 0.760   citation_rate = 0.980
```

Разбор по слоям:

1. **recall@5 упал на 8 пунктов, hit@10 почти не изменился** (0.960 → 0.958). Это ключевая подсказка: нужные документы по-прежнему находятся, но **выпадают из первой пятёрки**. Причина — разрыв фраз на стыке чанков, из-за чего в выдачу попадает хвост без начала.
2. **faithfulness не изменился** (0.940). Значит, генератор работает стабильно и чинить его не нужно.
3. **correct_rate упал сильнее, чем recall@5** (0.840 → 0.760), потому что в контекст попадает неполный чанк и модель отвечает наполовину.

**Вывод**: чинить нужно ровно одно — вернуть `overlap`. Изменение не относится к безопасности и не является улучшением: экономия 15% памяти индекса не стоит 8 пунктов recall.

Это ровно тот случай, где метрики экономят недели: без прогона golden set этот релиз ушёл бы в прод, и падение заметили бы через месяц по жалобам.

## Где это ломается

1. **Золотой набор из 10 вопросов, написанных разработчиком.** На десяти кейсах разница между конфигурациями не отличима от шума. Меньше 50 — это не оценка, это демонстрация.
2. **Золотой набор без поля `expected_refusal`.** Система, которая уверенно отвечает на всё, получает лучшие оценки, чем та, которая честно отказывает. Метрика начинает поощрять галлюцинации.
3. **Судья слабее оцениваемой модели.** Завышенные оценки, и на основании этих оценок принимается решение о выборе модели в проде.
4. **Версия судьи не зафиксирована.** Обновили промпт судьи — цифры уплыли на 6 пунктов, команда месяц разбирается, «что ухудшилось».
5. **Сравнение метрик на разных корпусах.** После пересборки корпуса `recall@5` до и после несопоставимы. Нет `corpus_snapshot` — нет истории.
6. **Только средние метрики, без разбивки по тегам.** recall 0.87 в среднем и 0.55 по вопросам про безопасность.
7. **Eval не в CI.** Гейт качества на словах, который никто не запускает перед релизом.
8. **Порог поставлен «на глаз».** Гейт, который раз в неделю падает на естественном шуме, через месяц отключают — вместе с проверкой.
9. **Оценка только retrieval'а.** Retrieval высокий, ответы плохие — и все уверены, что «поиск-то работает».
10. **Нет метрики отказа.** Самый опасный дефект корпоративного ассистента вообще не измеряется.
